# Adversarial review: one-word `WordText`

## Conclusion

For the reviewed frozen artifact `3d6bbcde4b67b9e99fe35b23db3bf216a79835f8` in `/tmp/gpui-short-text-root`, I found no concrete ownership, lease-count, lifetime, aliasing, or destructor counterexample on the conventional pointer representations exercised by the tests. The implementation makes the right strict-provenance distinction for its inline arm: it creates a no-provenance non-null pointer only as a tagged word, never dereferences that value, and derives the byte-read pointer from `&self.0` instead (`src/lib.rs:4-9, 36-47, 64-83`). The parent reports that all six Miri Stacked/Tree gates now pass for x86_64, i686 and s390x at that exact source version; this is valuable execution evidence, not a language-level guarantee for every pointer representation.

There is one unconditional-portability/soundness gate before broad production use. Construction encodes bytes as a native-endian integer (`src/lib.rs:50-60`), but inline `Deref` later reads the object representation of the `NonNull<()>` field as bytes (`src/lib.rs:64-76`). Rust’s `pointer::addr` documentation says most platforms return the same bytes as the original pointer, but a platform that stores additional pointer information may change representation, with the meaning left to that platform. The Reference guarantees thin pointer size/alignment relative to `usize`, not that a pointer’s bytes are an integer’s bytes. Thus the tested targets establish neither that every byte read from the pointer field is the originally encoded UTF-8 nor that every future target preserves that invariant. If a target’s pointer representation changes or includes non-payload bytes, the unchecked `str` construction can violate its required valid-UTF-8 precondition. I have not demonstrated such a failure on any tested supported target; this is a missing proof/portability gate, not a claimed repro. See the primary [Rust pointer `addr` docs](https://doc.rust-lang.org/std/primitive.pointer.html#method.addr), [Reference pointer layout](https://doc.rust-lang.org/reference/type-layout.html#pointers-and-references-layout), and [`from_utf8_unchecked` safety contract](https://doc.rust-lang.org/std/str/fn.from_utf8_unchecked.html).

I recommend either (a) make the inline encoding conditional on a short, explicit, reviewed target whitelist with `ArcStr` fallback everywhere else, or (b) choose a representation whose bytes are specified as bytes rather than borrowing the pointer object representation. Do not infer a whitelist from pointer width/endian alone: the `addr` contract explicitly leaves extra pointer metadata to the platform. CHERI/capability-style pointers illustrate why the distinction matters, but I found no evidence that the tested Rust target matrix includes such a target; this report does not claim a specific current GPUI target fails.

## What looks internally sound, subject to the target-byte gate

* **Pointer niche and raw tag:** `NonNull<()>` is a suitable one-word niche carrier. Rust guarantees `Option<NonNull<T>>` has the same size/alignment as `NonNull<T>`; `repr(transparent)` delegates `WordText` layout/ABI to that field. `NonNull::without_provenance(NonZeroUsize)` is a strict-provenance constructor and the standard pointer docs explicitly allow non-dereferenceable no-provenance pointers as tags/sentinels. These facts support the one-word and `Option` niche claims, but do not establish pointer-object byte encoding. See [NonNull layout and `without_provenance`](https://doc.rust-lang.org/std/ptr/struct.NonNull.html), [transparent representation](https://doc.rust-lang.org/reference/type-layout.html#the-transparent-representation), and [pointer provenance](https://doc.rust-lang.org/std/ptr/index.html#provenance).
* **Heap alignment discriminator:** ArcStr 1.2.0 promises `into_raw` pointers have at least 8-byte alignment, and its implementation simply forgets the `ArcStr` and returns the existing allocation pointer (`arc_str.rs:391-412`). Therefore low three address bits distinguish the heap arm from inline tags on targets where the address representation is ordinary. The artifact’s `inline_len() == 0` convention also correctly routes the empty `ArcStr` representation through its normal owner/drop path.
* **Lease ownership:** `WordText::from_raw` is called for read-only borrowing inside `ManuallyDrop`, then `as_str()` lends bytes in the ArcStr allocation. That temporary is not dropped and does not decrement a count. `Clone` explicitly invokes `ArcStr::clone` before `into_raw`, creating one new lease; `Drop` reconstructs and drops the one lease held by that `WordText` (`src/lib.rs:41-47, 77-83, 87-105`). ArcStr 1.2.0’s `from_raw` is a thin wrapper around the raw pointer (`arc_str.rs:414-436`), and its safety contract says the pointer must come from `into_raw` and an `ArcStr` instance must not be dropped twice. I found no schedule in this code where a temporary borrow consumes the stored lease or where a clone misses its increment. The proof depends on the wrapper continuing to keep the raw owner private and on its borrow not escaping `&self`; both hold in this artifact.
* **Inline lifetime and mutation:** inline bytes are read from storage within the owning pointer field, bounded to at most `WORD - 1`, and returned through `Deref::deref(&self)`. The safe public API has no mutation/raw-pointer escape; moving or dropping the owner while the borrow is live is prevented. Construction starts from `&str` and copies only its valid UTF-8 bytes. On tested native-endian layouts, payload and length tag do not overlap. These arguments make the unchecked conversion sound provided the pointer-field-byte assumption is true. Its safety precondition is explicit in the [standard library docs](https://doc.rust-lang.org/std/str/fn.from_utf8_unchecked.html).
* **`Send`/`Sync`:** the manual impls are plausible for this closed immutable type: inline state is self-contained and never dereferenced as the stored pointer; heap state owns an immutable ArcStr lease, whose pinned source has `unsafe impl Send + Sync` (`arc_str.rs:126-127`). There is no interior mutation through `WordText`. Thread tests are useful evidence, though they cannot replace the target-byte proof.

Miri’s strict-provenance and symbolic-alignment modes probe specific interpreter models and targets. The [Miri project docs](https://github.com/rust-lang/miri/) describe those checks and supported target setup; passing them does not add a Rust Reference guarantee about pointer byte layout on unmodeled architectures. The supplied README also says the tests do not establish soundness. I did not rerun or mutate the frozen artifact, and did not run the README’s proposed deliberately broken control.

## Equality and adoption costs

The current `PartialEq` is semantically correct (`**self == **other`), but it discards an optimization that the existing long-string owner already provides. In the pinned ArcStr 1.2.0 source, `PartialEq::eq` is `ArcStr::ptr_eq(self, o) || str_eq(...)` (`arc_str.rs:1450-1458`); the public docs likewise say ArcStr equality already checks pointer identity. `WordText::eq` always compares the `str` views (`src/lib.rs:109-113`), so clones of the same long ArcStr no longer take ArcStr’s pointer shortcut. This is a plausible regression for clone-equality workloads, not a measured regression. A safe narrow correction is: when both values are in the heap arm, compare the borrowed ArcStr views using ArcStr’s existing `PartialEq`; otherwise compare their string contents. That preserves static-literal behavior because ArcStr equality falls back to string equality when pointer identity is false. Do not use the encoded `NonNull` address as a universal identity shortcut without the same target audit. No assembly or timing evidence was collected.

The README’s allocation test checks the isolated constructor’s allocation requests and unchanged ArcStr long-string request (tests `ownership.rs:80-107`). It does not measure whole-app retained bytes or latency. The parent-provided profile context (`SharedText` appears in 28 retained allocation requests; text planning/Parley has 83% of requests) is a prioritization hint, not evidence that this helper improves application memory or frame time. Short values under the 64-bit threshold can eliminate their ArcStr allocation and per-clone/drop refcount traffic, but the benefit depends on the actual short-string distribution and lifetime/clone behavior. There is no matched end-to-end allocation comparison or generated-code inspection in this frozen artifact.

The existing GPUI core’s `forbid(unsafe_code)` makes a separate audited helper crate the plausible home for this kind of representation; the artifact README records that boundary. If adopted, keep the helper minimal, document target support and the exact invariant, test every target in that support list, retain the ArcStr long fallback initially, and use Miri/property tests as regression detectors rather than proof. Add the heap-only equality fast path above before claiming behavior-preserving optimization. The artifact reports three normal tests (content/niche/move/clone, thread transfer, allocation requests) and its README reports strict-provenance Miri work; no independent performance claim follows.

## Existing-dependency comparison

The closest existing-dependency comparison is `cold-string` 0.5.0’s `ArcColdString`, reviewed at its exact release tag. Its public API is safe to call, strings up to a word are stored inline, and longer strings are shared through an atomic count. The package declares Rust 1.60 MSRV. Its required manifest dependencies are `portable-atomic` with version requirement `1.15.0` and `require-cas`, `sptr` with version requirement `0.3.2`, and `rustversion` with version requirement `1.0.22`; `serde` and `rkyv` are optional feature dependencies ([tagged manifest](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/Cargo.toml)). Those are Cargo version requirements, not exact lockfile resolutions. `ArcColdStringInner<A>` is `repr(transparent)` over `Encoded<A>`, which is `repr(transparent)` over `NonNull<VintStringInner<A>>` ([arc.rs](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/arc.rs), [encoded.rs](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/encoded.rs)). Rust guarantees the `Option<NonNull<T>>` null niche and transparent layout propagation; the crate’s own layout test additionally asserts that the owner is one `usize`, `Option<owner>` is the same size, and the heap header has the atomic counter’s size/alignment ([test](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/arc.rs#L2101-L2120), [NonNull layout docs](https://doc.rust-lang.org/std/ptr/struct.NonNull.html)).

Its long allocation differs from ArcStr’s two-word header. In v0.5.0, `VintStringInner<H>` has `repr(C)` header plus zero-length trailing payload; `Layout` requests `size_of::<Self>() + vint_len + len`, aligned to `max(align_of::<Self>(), 4)`. `ArcColdString` uses `H = AtomicUsize`, so on 64-bit the raw requested size is `len + 8 + vint_len` ([heap layout and allocator writes](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/heap.rs), [ArcColdString alias](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/arc.rs#L1592-L1627)). The v0.5.0 encoder stores `len - 9` (for 64-bit) using a custom variable-width encoding: one total prefix byte for lengths 9..=256, two for 257..=511, three for 512..=65,791, then wider intervals; the source formula is in [vint.rs](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/vint.rs#L406-L454) and the length bias/allocation in [heap.rs](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/heap.rs#L445-L476). By comparison, the frozen artifact’s ArcStr allocation test records `len + 2 * size_of::<usize>()` requests for nonempty long strings (`tests/ownership.rs:82-98`), matching ArcStr’s `len_flag + count_flag + bytes` allocation layout (`arcstr-1.2.0/src/arc_str.rs:1067-1087, 1205-1217`). Before allocator rounding, those layouts predict cold-string raw-request savings of 7, 6, then 5 bytes across the first three varint intervals on 64-bit. This is a source-derived arithmetic comparison, not a measurement; allocator size classes, usable bytes, and RSS are not included. Cold-string pays a variable-length length read/decode where ArcStr stores length in its first header word. Its reference-count increment uses a saturating compare-exchange retry loop and its last-drop path uses release decrement plus acquire fence before deallocation ([counter operations](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/arc.rs#L1502-L1544), [clone/drop](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/arc.rs#L1763-L1805)); speed and cache effects were not measured here. It preserves one-allocation long strings and sharing, but changes that long path enough that it is not an exact drop-in.

The cold-string source has the same outstanding pointer-byte concern as this prototype: inline construction encodes a native-endian integer into an invalid pointer value, and `inline_bytes` later creates a slice from bytes at the stored `NonNull` field ([v0.5.0 encoded source](https://github.com/tomtomwombat/cold-string/blob/v0.5.0/cold-string/src/encoded.rs#L845-L895)). Its safe public methods and property/Miri tests do not establish that pointer object bytes equal the original integer on every Rust target. It therefore is not a direct safe escape from the portability gate. Its heap equality implementation does include an address shortcut before byte equality, but do not treat this as proof that its inline representation is portable.

The most conservative local formulation still preserves ArcStr’s existing long header, length access, static/literal behavior, and clone/drop implementation while changing only the short-string arm. `ArcColdString` could reduce raw long-allocation requests by 5–7 bytes on the stated 64-bit ranges, but adds a required dependency trio and a different long-path encoding/refcount implementation. The profile context says only 28 retained `SharedText` allocation requests, not how many are long or the impact of their header sizes. That is insufficient to choose between a local short-only helper, adopting cold-string, or retaining ArcStr unchanged; the comparison needs matched retained-memory and workload measurements.

`sinstr` also documents a one-word `Option` niche, but is a poorer `SharedText` fit: its documentation says heap strings allocate like `Box<str>`, and its `NonEmptySinStr::clone` rebuilds heap strings from their bytes rather than sharing an Arc-style allocation. Its `SinStr` also exposes `DerefMut`, while GPUI’s `SharedText` is immutable. The source documents length-tagged `MaybeUninit` inline storage ([repository source](https://github.com/airblast-dev/sinstr/blob/main/src/non_empty.rs)); its one-word size alone does not preserve ArcStr’s long-string clone semantics. Mainstream `SmolStr`, `CompactString`, and `SmartString` representations use roughly three machine words on 64-bit platforms, so they are safe-API alternatives to benchmark if expanding each retained `SharedText` row is acceptable, but they do not preserve this one-word row/niche constraint (see [SmolStr](https://github.com/rust-analyzer/smol_str), [CompactString docs](https://docs.rs/compact_str/latest/compact_str/), [SmartString docs](https://docs.rs/smartstring/latest/smartstring/)).

## Recommended decision

Do not accept `WordText` as universally portable yet. Keep the current frozen experiment as evidence that the size/allocation target is achievable on its tested representations. Before any integration, require a target whitelist or a representation change, preserve long-arm ArcStr equality behavior, and compare full retained/application costs against leaving ArcStr unchanged. `ArcColdString` is a useful benchmark candidate if adopting an external implementation is acceptable, but it does not resolve the same pointer-byte issue and changes long-string access/refcount behavior; benchmark it against a local short-only arm and unchanged ArcStr before choosing.

## Evidence classification

* **Source/API guarantees:** Rust `NonNull` niche, `repr(transparent)`, `without_provenance`, ArcStr raw-pointer alignment/ownership API, and `from_utf8_unchecked` UTF-8 precondition (links above).
* **Artifact facts:** exact source is frozen at commit `3d6bbcde4b67b9e99fe35b23db3bf216a79835f8`; README and tests describe one-word layout, inline threshold, three normal tests, unchanged ArcStr long fallback, and proposed target gates. Parent separately reports all six Miri gates now pass at that exact source version.
* **Reviewer inference:** no concrete ownership/lifetime defect found for the reviewed schedules; unconditional portability is unsupported because the code reads pointer object bytes as encoded text; heap clone equality may regress because ArcStr’s pointer fast path is bypassed.
* **Missing evidence:** an explicit supported-target whitelist/proof, a platform that actually reproduces byte mismatch, broken-control test, generated assembly, end-to-end retained-memory comparison, and any timing result.
