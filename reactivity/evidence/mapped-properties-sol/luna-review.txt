# Mapped-property lifecycle and ownership review

Reviewed read-only in `/tmp/gpui-mapped-properties-sol/reactivity`, HEAD `8c56ff0bbedbcdfde7484a97182b104aadccdbf5`, plus the frozen unstaged mapped-property patch `/tmp/gpui-mapped-properties-sol-evidence/stable-color-review.patch` (SHA-256 `9fde9d83a0be7d5f68db7c0b0fb2323d6c0ee7b010cb4ccec946c10c06a22c7e`). Relevant current-source hashes are listed at the end. No source was edited and I ran no builds or tests.

## Judgment

The three-phase stable-color correction is sound on this frozen snapshot. I found no remaining stale-render, source-replacement, inspector-base, or presentation-acknowledgement hole. The old masked-first shared-color failure is fixed by comparing and advancing every inspector base while all readers still see the old bank, then changing bank slots after the comparisons. It preserves old colors for masked peers, detects visible changes for unmasked peers, and avoids converting source-bound colors into literal history.

The exact-source API already expresses the benchmark shape: one `Signal<Frame>`, one existing `with_inbox_for` route, and `.map/.map_with` projections to transform and per-row colors. The public test at `crates/gpui/tests/mapped_properties.rs:110-147` verifies one exact update across 33 sinks and 1,000 stable rows with zero owner reruns/descriptions, one source read, and 33 destination comparisons. This is evidence that a new action-context API is not required for this case.

## Ownership and lifecycle trace

- Description resolves each borrowed map input against the current `Sources` registry before retaining anything: `runtime.rs:1929-1942`. The retained record owns the inline recipe and a checked destination, while the fanout's BTree key is the resolved true `FieldId` (`runtime.rs:2002-2048`). No signal pointer is retained in the fanout. Exact patch gets the current signal from the current model through that registered field, calls each recipe with that current `Signal<T>`, and admits each output before any destination mutation (`runtime.rs:2527-2551)).
- Replacing a model's `Signal` or changing which field a view projects requires ordinary owner description. That description resolves the borrowed signal again and rebuilds the recipe/fanout. Mapped description marks the candidate dirty unconditionally because equal outputs cannot establish closure identity (`runtime.rs:2046-2048)). Thus an unchanged revision or a reset revision cannot leave an old mapper attached to a replaced source. Exact map patching itself reads the current registered value, not a revision cache or a captured pointer.
- Failure before sink mutation is preserved: all mapped recipes are evaluated and admitted first, then all direct style sinks are admitted, and only then does the destination loop edit bases or values (`runtime.rs:2537-2552)). A rejected mapped output may change scratch entries but cannot mutate styles, inspector bases, or color slots; the next patch reevaluates all recipes before consuming scratch.
- Mapped color outputs get one stable bank source slot per mapped destination. These slots carry the actual resolved `FieldId`, but are deliberately absent from the field-wide `ColorDiscovery.fields` map: `colours.rs:191-205`, `runtime.rs:2002-2044`. This is the right conservative grouping. A closure and its parameters have no equality contract, and equal present outputs do not establish equal future behavior. One output slot per destination preserves recipe identity without a hash, an address/ABA scheme, or forged source IDs. Direct `Color` sinks in the same mapped fanout instead share one slot for the exact direct field (`MappedFanout.direct_color`, `runtime.rs:2021-2044)).
- The patched sink loop first compares old effective styles and updates inspector bases with old bank values still intact (`runtime.rs:2557-2657)). For a color slot it skips `Styles::set`, which would turn that sink into a literal (`runtime.rs:2581-2583)). Only after every sink has compared does the post-pass update the stable mapped/direct slots (`runtime.rs:2659-2675`). For a masked color, `Overrides::update_base` advances the lower declaration while the effective override stays the same (`property.rs:608-625)); a later Inherit rebind uses the declared source slot and its current bank value (`colours.rs:440-469`, `runtime.rs:3658-3687)). For a shared direct slot, delaying the one slot update until after all comparisons prevents a masked first destination from hiding an unmasked peer. The public masked-first test covers both a visible peer change and a later fully masked update/reveal (`mapped_properties.rs:466-513)).
- Full scene preparation resets canvas-slot caches and stages a fresh Canvas palette (`runtime.rs:2993-2999`, `canvas.rs:1049-1057)); the shared paint path therefore seeds a new prepared palette from the updated bank. Mapped color edits that visibly change a sink take the ordinary dirty/presentation path. They do not use the direct-only one-slot `finish_color_slot` fast path, so a mapped color update may require a complete scene preparation. That is a cost limitation, not stale output. A masked-only update need not repaint; the current bank and inspector base are ready when the override is later removed.
- Existing authority boundaries remain in force: `turn.rs:235-265` checks source/owner invalidation before exact patching, and the call to `present()` publishes through ordinary source/presentation epochs. The Reader-gate test verifies a source-dependent question becomes Pending/Updating before exact patching (`mapped_properties.rs:371-417`); the geometry test verifies queries stay on acknowledged state until the candidate token is acknowledged (`mapped_properties.rs:149-218`). The forged-source control rejects before its inbox callback and rebinds to the newly selected field (`mapped_properties.rs:220-281`). I found no map-specific result ticket or foreign completion path.
- The direct-color peer case is internally type-safe: `Color` has a direct style codec, while direct text/scalar outputs have their own closed codec/Value implementations. Mapped outputs still pass through the existing closed `PropertyValue` / `PropertyId` admission path. No generic setter or property catalog extension was introduced.

## Storage and API costs

- The 4-byte mapped color slot code occupies the old trailing padding after `Destination(4)` and `Recipe(24)` in `MappedRecord` (currently 32 bytes); there is no per-record growth. `MappedFanout.direct_color: u32` grows the aligned fanout payload by 8 bytes once per source group, from the pre-fix 80-byte measured layout to 88 bytes by its current field layout. The public `Fanout` enum remains 32 bytes because this payload is boxed. No node header grows.
- A mapped color output retains one `SourceColor` in the style bank. Its fields are `FieldId(8) + Color(16) + PaintColor(16) + Option<PaintSlot>(4) + users(u32)(4) = 48 bytes on this layout. This makes the retained cost linear in the number of mapped color destinations (at most foreground and background per node), rather than linear in the number of distinct historical outputs. The transient color-discovery binding is 8 bytes per color destination and disappears after style construction. The mapped record and scratch `PropertyValue` remain 32 and 28 bytes per mapped destination, respectively.
- Do not use `/tmp/gpui-mapped-properties-sol-evidence/mapped-allocation.log` as a current owner-cost result: it predates the stable-color patch (02:54 vs. 03:12) and reports the old 80-byte MappedFanout and old retained total. It does not account for the new bank slots. No post-fix owner ledger was available in this review. The new in-tree allocation test computes current mapped fanout bytes from `size_of::<MappedFanout>()` at `runtime.rs:4968-5021`, but the frozen test log was run without `--nocapture`, so it does not publish the eprintln measurements. A fresh ledger is required before making a total retained-memory claim.
- The public API is `SignalMap::map/map_with` and `Mapped<U>` (`style_port.rs:70-140`, re-exported in `lib.rs:76,99`). It retains at most 16 bytes of closure/parameter data with alignment <= 8; oversize recipes return a checked mount error rather than heap storage (`style_port.rs:104-140`; public test `mapped_properties.rs:419-464`). `MapValue` is bounded by the crate's existing closed `Value` implementations, preserving the closed PropertyId/validator/impact catalog.
- The mapper purity requirement is a documented semantic law: deterministic, read-only, total work over the current input plus immutable parameters, with no I/O/external mutable reads (`style_port.rs:86-105)). Rust cannot enforce this, as with the existing Source projection law. A mapper is called once per mapped destination on an exact patch. During a full description it is called twice: once when flattening computes the initial style (`element.rs:894-911`), then again to seed mapped scratch in runtime construction (`runtime.rs:1929-1942`). That duplicate initial user computation is safe under the documented purity law, but is avoidable cold work and should be measured or removed before claiming minimum description cost. Runtime patch scratch is evaluated in sorted record order before it is read; the turn-side iterator only inspects destination impacts (`runtime.rs:2053-2067`, `runtime.rs:2537-2544`; `turn.rs:248-254)), so I found no record/value sort mismatch.
- Last-write-wins normalization applies between mapped/direct/literal bindings and drops overwritten recipes; mapped size expands into its existing width/height destinations (`semantic.rs:129-230`, `element.rs:894-911`). Existing tests cover overwrite release and multi-map order (`semantic.rs:381-453`, `mapped_properties.rs:283-369)).

## Remaining evidence gap / bounded next check

Before accepting the mapped-color retention or native path as fully qualified, run only the already-planned fresh post-fix owner ledger and native presentation proof in Sol's isolated tree. The native check should exercise a mapped Color slot across an acknowledged scene, a visible exact update, and an unacknowledged/coalesced candidate; verify current prepared paint values change while the old presented scene remains authoritative until the matching token is acknowledged, and verify a masked update causes no paint pass but becomes visible after Inherit. Do not infer this from the stale allocation log or the recording-backend public test.
