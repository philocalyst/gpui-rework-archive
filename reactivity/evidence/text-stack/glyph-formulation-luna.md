## Existing contract and lower bound

`TextLayout` is an owned, cloneable result. It outlives its temporary `TextShaper`, exposes a value iterator over glyph ID, font slot, UTF-8 cluster, x, and baseline, and is consumed later by canvas paint and `ink_bounds`. Paint walks every placement to resolve a font/glyph/size raster key and then prepares that placement; cache reuse avoids rerasterizing duplicate glyphs, but does not eliminate placement traversal. `TextLayout.width`, `.height`, and `.baseline` are public mutable metrics. Glyph placement therefore needs its own frozen baseline bits; recomputing from the public `baseline` field would change rendered glyphs after a caller mutates metrics. These contracts are visible in the exact [TextLayout source](</tmp/gpui-stack-integration-root/reactivity/crates/canvas/src/text.rs:278>), [glyph owner](</tmp/gpui-stack-integration-root/reactivity/crates/canvas/src/text/glyph_buffer.rs:5>), and [canvas paint path](</tmp/gpui-stack-integration-root/reactivity/crates/canvas/src/canvas.rs:1487>).

For the general case, 12 bytes is the fixed-width cost of this representation: one 32-bit word carries source cluster plus glyph/font code, while x and baseline each retain their exact 32-bit float representation. It is not an information-theoretic lower bound. Shared fields, correlations, narrower bounded domains, dictionaries, or lossy quantization can encode some populations in fewer bits; they add certificates, exceptions, decoding, or altered semantics. The current full metadata word is occupied by the bounded cluster/font/glyph domains; primary-only records may have a spare metadata bit, but that alone does not remove a word. Arbitrary exact x float bit patterns cannot be delta-encoded to a smaller fixed-width residual in general, though particular monotone runs may compress. The common-8 candidate is evidence that a proven shared baseline removes one word for a certified subset.

The common-8 candidate has a real certificate: Parley inline glyphs have zero y offset, and the current Canvas style construction can select one paragraph, one line, and at most one primary LTR raw run. It freezes the first *emitted glyph's actual baseline bits* once, then stores each glyph's 32-bit metadata and x bits. Non-inline marks, wrapping, and mixed fallback stay in full 12-byte form before reserve. Thus the exception does not rely on public mutable metrics or re-summing float advances. At 32,768 glyphs, the logical full payload is 393,216 bytes versus 262,148 bytes for the common encoding, a 131,068-byte payload saving. The existing collected allocation evidence says the 32,768-glyph layout retained bytes fell from 393,256 to 262,188, with no allocation-count change; wrapped and mark cases were unchanged. No throughput gain is evidenced.

## Formulations considered

**Use standard shared ownership for the immutable packed words.** `GlyphBuffer` currently manually steals a `Vec`, stores pointer/capacity/length, rebuilds the vector in `Drop`, and supplies unsafe `Send`/`Sync`. A safe `Arc<Vec<u32>>` (or `Arc<Vec<PackedGlyph>>` for full-only storage) plus the small length/format fields can keep an owner header around 16 bytes while removing `ManuallyDrop`, `NonNull`, `Vec::from_raw_parts`, custom drop, and pointer-range proofs. Cloning then shares immutable glyph storage, just as font and geometry state already share through `Arc`; public metrics remain copied values. Reading through `ChunksExact` on `u32` words or a standard slice iterator keeps access safe. This trades one Arc wrapper allocation when shaping a layout for clone-time removal of the current glyph-vector allocation and copy. It is a concrete, low-risk option if callers clone layouts often; the public API permits cloning, but no clone-frequency evidence was found, so it should not be treated as a net win by default. `Arc<[u32]>` is less attractive as the first cut because converting a capacity-bearing `Vec` to a boxed/arc slice may discard spare capacity and can require resizing. Rust documents `Vec::into_boxed_slice` as dropping excess capacity like `shrink_to_fit` ([Rust Vec docs](https://doc.rust-lang.org/beta/std/vec/struct.Vec.html#method.into_boxed_slice)).

**Factor a shared baseline per line/run for wrapped layouts.** Detailed layouts already retain each run's glyph range and line index, and each line's frozen baseline. A new all-inline certificate could omit per-glyph baseline bits for all glyphs and have an iterator advance through run ranges to select the line baseline. This could expand savings to multi-run/multiline text without recomputing glyph positions. It adds segment state and a run-boundary branch to each traversal, couples glyph iteration to geometry tables, and requires proving bit identity between each emitted `height + run.baseline` and the stored line baseline. The simple case already has a constant-time baseline prefix and no mapping lookup. This is implementable but fails the simplicity bar absent evidence that wrapped/mixed workloads dominate retained bytes; keep it as an experiment only. Parley's public iterator itself computes positioned x and y while walking the stored glyphs, illustrating where the re-computation would move ([Parley 0.12 line source](https://docs.rs/parley/0.12.0/src/parley/layout/line.rs.html)).

**Retain Parley's layout instead of materializing Canvas glyphs.** This would remove the planner's output-copy pass, but it does not remove glyph storage: Parley owns shaped glyphs and retains fonts, coordinates, runs, items, clusters, styles, line data, and line items in its `LayoutData`; its public `Layout` is cloneable and owns that data ([Parley layout source](https://docs.rs/parley/latest/src/parley/layout/layout.rs.html), [Parley layout data](https://docs.rs/parley/latest/src/parley/layout/data.rs.html)). Canvas would also need to retain that larger snapshot and expose a new iterator that resolves Canvas font slots and UTF-8 clusters. The current planner reuses its mutable Parley layout across calls, so an owned independent result requires a deep layout clone or moving/replacing the planner scratch, and a borrowed result would change the current lifetime-independent API. Parley's positioned iterator adds baseline and advances x on each traversal; repeated paint/ink queries would pay that work again. This shifts work and retains more shaping state, so it is not a storage simplification.

## SIMD, indexing, and dispatch

SIMD does not match the paint loop's work. Every glyph has an independent face/glyph/size key, followed by hash lookups, cache/scene resource handling, and rectangle admission. Those data-dependent operations remain scalar even if x/meta/baseline are loaded as lanes. The candidate owner is only 4-byte aligned, so a vector reinterpretation would also need a prefix/alignment path. Official `std::simd` is explicitly nightly-only/experimental ([Rust SIMD module](https://doc.rust-lang.org/std/simd/)); do not conflate that with this repository's already-present `fearless_simd`, which provides stable safe APIs, runtime dispatch and scalar fallbacks ([fearless_simd docs](https://docs.rs/fearless_simd/latest/fearless_simd/)). `fearless_simd` is already used for pixel mask and gamut kernels here, but that does not make arbitrary per-glyph hash/lease/error handling vectorizable. This is a poor fit for an iterator that immediately consumes each decoded glyph in those scalar operations.

Adding a glyph-to-run or glyph-to-line index would duplicate ranges already stored in `TextGeometry.runs`; it could remove a search only if a consumer needs per-glyph geometry. Paint and `ink_bounds` need no caret/selection map. Interaction is already opt-in and its exact byte/affinity stops are separate retained geometry, so tying glyph storage to that cache lifecycle would make common painting retain or maintain data it does not use. Likewise, borrowing the source text/layout cannot satisfy the current result-outlives-shaper contract without changing public lifetimes or preserving an owned shaping snapshot.

## Primary-source cross-checks and what they transfer

The compression literature directly refutes a universal 12-byte information floor, but does not provide a drop-in glyph codec. `simdjson` uses a SIMD first pass to identify structural positions and validate UTF-8, then a second pass to interpret those positions; its streaming API reuses one parser over batches to avoid per-document allocations ([simdjson `parse_many` design](https://github.com/simdjson/simdjson/blob/master/doc/parse_many.md), [paper](https://arxiv.org/abs/1902.08318)). The transferable principle is to find a cheap batch-wide certificate or prepass that simplifies later scalar work. The input here is already shaped and paint keys are data-dependent, so scanning glyph words in SIMD does not skip face lookup, hashing, mask acquisition, bounds checks, or painter-order admission.

Block codecs such as [BitPacker](https://github.com/quickwit-oss/bitpacking) determine a bit width for a fixed integer block and pack all values; SIMD variants require fixed block sizes and distinct wire formats. [StreamVByte](https://arxiv.org/abs/1709.08990) separates small-integer control bytes from packed values and benefits from integer deltas; [FastPFOR](https://boytsov.info/pubs/decoding2013.pdf) similarly compresses integer blocks with per-block widths/exceptions. These methods are useful when values have narrow integer ranges and consumers can pay decode/prefix work. Our positions contain arbitrary exact `f32` bit patterns and the public iterator supports O(1) forward/backward indexing over arbitrary retained layouts; block compression would need a new compressed/uncompressed state, exception storage, and a decoder in paint and `nth`/`nth_back`. A separate block directory also increases owner/header and cold-layout work. So the right lesson is “encode a real shared domain at block scope,” not “apply SIMD bitpacking to raw glyph records.”

[FSST](https://www.vldb.org/pvldb/vol13/p2649-boncz.pdf) compresses byte strings using a static symbol table of frequent substrings (1-byte symbols can represent strings up to 8 bytes), while retaining per-string random access. It is relevant to retaining source strings/corpora, not these already-decoded placements: this `TextLayout` intentionally owns positions and font leases but not source text, and UTF-8 cluster offsets must remain exact for interaction. A symbol table for repeated glyph metadata may work in text-heavy, repetitive labels, but each record still has distinct x and usually distinct baseline; dictionary indices plus palette retention and query overhead are unmotivated without measured repeated records.

Text renderers confirm the cache boundary. `glyphon::TextRenderer::prepare` clears and reconstructs the glyph vertex list from each text area's shaped runs, then derives physical glyph cache keys and resolves glyphs ([glyphon prepare source](https://docs.rs/glyphon/latest/src/glyphon/text_render.rs.html)). `cosmic-text` retains broad `LayoutGlyph` records (source ranges, font/glyph IDs, x/y, bidi, color and editor metadata) and exposes borrowed visible-line `LayoutRun`s from cached lines ([`LayoutGlyph`](https://docs.rs/cosmic-text/latest/cosmic_text/struct.LayoutGlyph.html), [`LayoutRunIter`](https://docs.rs/cosmic-text/latest/src/cosmic_text/buffer.rs.html)). This is sensible for editing and flexible renderer APIs, but not evidence that placements vanish on warm raster-cache hits. Slint's current FemtoVG renderer owns a `TextLayoutCache`, clears it when a component is destroyed or a window adapter changes, and separately clears other graphics caches on scale-factor changes ([Slint FemtoVG renderer](https://github.com/slint-ui/slint/blob/master/internal/renderers/femtovg/lib.rs)). That shows retained shaping/layout caches need explicit lifecycle and scale/owner invalidation; caching our whole `PendingDraw` sequence would also need transform, origin, clip, color, raster scale, damage, mask-generation, and display-list lifetime keys.

## New concrete formulations at the actual paint boundary

**1. Format-specialized safe bulk traversal, preserving the public iterator.** Current 24-byte stride iterator stores data and baseline pointers, a remaining count, and per-record stride fields; its inspected renderer assembly has dynamic pointer increments for the data and baseline streams plus a remaining test in the loop, and still loads baseline each glyph. This is not a timing claim. A private `GlyphBuffer::try_for_each_packed` can match `Full` / certified `Common8` once per batch and loop over safe `chunks_exact(3)` / `chunks_exact(2)` slices. The callback can receive `Glyph` values in the same order; `try_for_each` stops on the same first error, preserving paint's raster/cache/error order. Keep public `glyphs()` as its trait-rich borrowed iterator, and let `ink_bounds` use a fallible fold. This removes raw-pointer stride iterator logic and moves the format dispatch outside the per-glyph loop; it does not remove public iteration or paint work. The `GlyphBuffer` can keep its current 16-byte manual owner initially, which preserves no-allocation transfer and avoids changing `TextLayout` size; a separate safe `Vec<u32>` formulation would remove unsafe owner code at an estimated +16 bytes per layout owner (three-word Vec header and compact lengths/format), with unchanged payload allocation count. Rust explicitly advises iterator implementors to specialize `try_fold` where it improves on the default loop, and `Vec::IntoIter` does implement it as direct pointer traversal ([Iterator implementor note](https://doc.rust-lang.org/stable/core/iter/traits/iterator/trait.Iterator.html), [Vec `IntoIter` source](https://doc.rust-lang.org/src/alloc/vec/into_iter.rs.html)). The implementation is straightforward and safe; whether LLVM emits better code than the current stride loop must be determined by assembly inspection in the authorized next implementation pass. Counterexamples: very short layouts may lose to added closure/dispatch overhead; a safe `Vec<u32>` changes per-layout owner size; users still need O(1) `nth` and reverse traversal from public glyph iteration.

**2. Primary-face paint specialization without storing more data.** `draw_text_working` first validates that the layout's primary face matches the `TextSystem`, then each glyph goes through `layout_key`, which calls `FontSet::face(slot)` to obtain the face ID; it also constructs a full public `Glyph` including the cluster even though paint consumes only id/font slot/x/baseline. `TextLayout` already exposes runs with a font slot and direction. For any all-primary layout (including wrapped/multiline primary layouts), a private paint fold can hoist the primary face ID once and read glyph ID and x/baseline directly from packed data; cluster need not be decoded for paint. The callback still resolves/rasterizes each glyph in its original order and uses exact stored positions; fallback/mixed-font runs keep the existing path. This removes repeated checked face-slot lookup and cluster extraction without a new retained table or allocation. It needs no certificate beyond validating all run slots (or a bit in the already-computed font mask), and does not affect public glyph values, `ink_bounds`, selection, or baseline mutation. Counterexample: a single branch per run may be as costly as current code for short runs; hash/raster/prepare dominate most warm and cold glyph work, so source-level work reduction is not a throughput prediction. The exact fix can be done as an internal `try_fold` helper exposing `(raw id, x, baseline, slot)` and is independently testable against public `.glyphs()` bits.

## Batched key lookup and warm-frame caching

Do not reorder the current loop into a “unique glyphs then place” prepass. `layout_key`, scene mask lookup, possible raster-cache mutation, rectangle construction, and `prepare` currently occur in glyph order; `prepare` can reject invalid geometry or cull an invisible rectangle, and later glyphs must not rasterize before an earlier error. `draw_text_working` publishes nothing until all placements pass and `admit` reserves scene capacity. Pre-rasterizing unique keys changes error visibility and can mutate the `TextSystem` cache for a draw that otherwise fails early. Its `resource_index` also intentionally indexes only newly rasterized masks that become scene resources. A second “seen every glyph” map would add hash work and memory on unique strings; it only helps repeated glyph IDs and still leaves placement geometry.

Warm raster cache is not a warm placement list. The display list's `mask_index` is cleared with the scene; raster masks live in `TextSystem`'s bounded cache, so a newly built scene still resolves per-glyph keys, builds rects, clips/admission checks, and appends ordered placements. `pixels()` has a dirty=false fast return only after a scene is already retained. Persisting placements across frames could avoid that construction only if a scene-level owner retains them and invalidates on layout identity/content, raster scale, transform, origin, clip, color, resource generation, and damage/viewport changes. Canvas's staged replacement scene is built transactionally and may be discarded on error; carrying cached placement records across this boundary would add new lifetime/lease/error semantics. The dirty-scene fast return is real; cross-frame glyph placement reuse is an architectural change, not a codec optimization.

**Scratch-buffer hypothesis (lower confidence than the two folds).** `pending = Vec::with_capacity(glyph_count)` is allocated on each `draw_text_working` call, even when all masks hit or are culled; `resources` is initially empty and `HashMap::new()` is lazy. An exception-safe reusable staging scratch could reduce repeated temporary allocations across multiple text commands in one `CanvasScene`, or across frames if held by the longer-lived `TextSystem`. It must clear pending commands and drop every temporary raster `Arc` on every error, preserve first-error order, and return to a reusable owner after success. Retaining peak capacity can keep up to the max glyph-sized pending vector and resource map alive; moving into a new staged `Canvas` alone does not help next frame because each `stage()` creates a fresh pending Canvas. The proposal is concrete but allocation savings are not established as important relative to command storage, and it should be considered only if allocation traces show the pending vector matters. It is less risky than a whole-layout prepared-record cache because it stores no cross-frame borrowed layout state.

## Storage and proof caveats

The common-8 result is a measured retained-payload reduction for its certified case, not a general `draw_text_working` speedup. The binary report says the stride candidate reduced `.text` versus the prior safe candidate but adds dynamic stride arithmetic and loaded baseline traffic; frame size also moved slightly. No benchmark can be inferred from assembly. Current user-visible proofs of clone/cache behavior should not compare `TextGeometry` Arc identity: layout cloning shares `mapping` while `GlyphBuffer::clone` deep-copies its glyph allocation. The repository already has allocation-counter tests; a non-production-hook proof can measure bytes/count during `TextLayout::clone` or candidate storage cloning and assert bitwise glyph values and zero-allocation borrowed iteration. Collected value equality alone proves decode correctness, not backing-storage identity or cache reuse.

## Recommendation and confidence

Keep the 12-byte fixed record for uncertified glyphs and retain common-8 only where its existing inline/single-line certificate proves baseline sharing. It has the exact, material savings number and does not change paint/cache work. Do not widen it to marks or wrapped/mixed text via exception tables until allocation profiles show those cases dominate. The two next simplifications worth a narrow implementation/assembly review are safe format-specialized `try_for_each` for internal bulk traversal, and the primary-face paint fold; both remove control/decode work instead of adding retained tables. Treat scratch reuse as a third option only after allocation profiling, because peak staging memory and frame staging lifecycle matter.

If the goal is to simplify ownership, prototype `Arc<Vec<u32>>` around the already-produced words and safe slice/chunk iteration as a separate change. That replaces handwritten allocation ownership with ordinary Rust and can eliminate deep clone copies, but adds one allocation and an atomic refcount; first establish that layout clones are common enough. Do not combine that tradeoff with a new SIMD, baseline-index, or Parley-snapshot design.

The existing binary report from the common-8 investigation records a code-size increase versus the 12-byte baseline and a renderer loop with scalar loads; it makes no timing claim. The newer stride-selected iterator removes a mode branch in the inspected hot loop but adds per-glyph stride pointer work, and its owner/iterator implementation is larger. That is evidence about machine code only, not a throughput result. The allocation result is the defensible benefit; paint dispatch, exact geometry, and clone behavior need separate workload evidence before claiming broader savings.
