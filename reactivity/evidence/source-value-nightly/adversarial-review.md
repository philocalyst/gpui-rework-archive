## Result

I found no ordinary safe value shape that lets an actual nested `Signal` pass the new bound while retaining that signal in the value's structural representation. The committed bound addresses the reproduced failure mode: `Source<M, Nested>` is unavailable when `Nested` owns a nested `Signal`, while nested state remains usable through coarse `Win::update`. The candidate's positive tests preserve same-address replacement/refresh, in-place heap-contained refresh, nested Signal construction/default/serde, and the explicitly bounded `Box<dyn Any + SourceValue>` route (`crates/gpui/tests/source_values.rs:45-153`). The baseline capture demonstrates the stale question/text caused by exact outer mutation and by an outer callback mutating a heap-contained inner signal; it is good evidence for the motivating bug, not evidence against this fix.

## Construction and propagation audit

`Source::new` is the only public constructor in the pinned implementation. `Source`'s fields are private and `Copy`/`Clone` only preserve an already-created value (`crates/gpui/src/source.rs:60-90`). `ProjectedSource` is assembled from a `Component` and an existing `SourcePath`; `Path` is crate-private and `SourcePath` has a private supertrait (`crates/gpui/src/source/path.rs:5-20, 53-60, 99-108`). `FieldAction` similarly has private fields and is constructed by `Source::update` or `ProjectedSource::update`; it does not rebuild a `Source`. The `QuestionInputs` implementations consume `Source`/`ProjectedSource`, so they do not bypass the constructor constraint. I found no struct literal, conversion, macro-generated constructor, or alternate safe registration route in the pinned GPUI source that can create a `Source<M,T>` with a failing `T`.

The implementation defines a private custom auto trait `Leaf`, negates it for every `Signal<T>`, and exposes the inaccessible marker as the public trait alias `SourceValue` (`source/value.rs:3-23`). `Source::new` alone adds `T: SourceValue` (`source.rs:74-90`); general `Signal<Nested>` storage is not restricted. That scope is appropriate: it blocks an exact edit of an outer signal value that could structurally mutate an inner registered signal, without banning nested signals from models or coarse owner updates.

Rust's auto-trait rules support the intended structural propagation: aggregate types are auto-implemented only when their fields are, references/raw pointers are conditional on their pointee, and closure auto traits depend on captured types ([Rust Reference: auto traits](https://doc.rust-lang.org/reference/special-types-and-traits.html#auto-traits)). The unstable-book description says custom auto-trait implementations are generated with a bound for each field and negative impls suppress the automatic one ([auto_traits](https://doc.rust-lang.org/beta/unstable-book/language-features/auto-traits.html), [negative_impls](https://doc.rust-lang.org/stable/unstable-book/language-features/negative-impls.html)). Thus ordinary nesting via structs/enums, tuples/arrays, `Option`/`Vec`/`Box`/`Arc`/`RefCell`/`Mutex`, borrowed references, and recursive owned types propagates `!SourceValue`. A wrapper cannot manually implement the private aliased marker. Erased trait objects must carry the bound explicitly; without it their hidden concrete type cannot establish the proof. The candidate test uses `Box<dyn Any + SourceValue>` and its source comment explicitly rejects plain `Box<dyn Any>` (`source/value.rs:18-22`, `source_values.rs:136-152`). This matches Rust's trait-object rules: an object implements its declared base and auto-trait bounds, not arbitrary marker traits inferred from erased concrete storage ([Rust Reference: trait objects](https://doc.rust-lang.org/reference/types/trait-object.html)).

I considered opaque handles, raw-pointer wrappers, `ManuallyDrop`/`MaybeUninit`, recursive containers, `PhantomData`, closures and erased trait objects. A typed reference/pointer/container that actually contains or refers to `Signal` still carries its auto-trait obligation. An untyped integer or a noncapturing function pointer can name a signal only by reaching outside the represented value (for example through global state or an unsafe wrapper); that is not a structural safe-value bypass. No concrete safe callback that mutates a same-owner nested signal while only receiving `&mut T` emerged without an external alias, interior mutability, or a side-effecting accessor.

The feature is explicitly nightly-only in the frozen source (`lib.rs:7` enables `auto_traits`, `negative_impls`, and `trait_alias`). Trait aliases are unstable and currently support a regular trait plus auto traits, including use as bounds and trait-object bounds ([Rust Unstable Book: `trait_alias`](https://doc.rust-lang.org/unstable-book/language-features/trait-alias.html), tracking issue [rust-lang/rust#41517](https://github.com/rust-lang/rust/issues/41517)). Treat this as a nightly prerequisite, not a stable-Rust compatibility result.

## Scope limit: callbacks and projectors

`SourceValue` proves a property of `T`'s type representation. It does not prove that every `Source::update` callback is pure, that a source projector is honest, or that code reached through a callback capture has no effect on the owner or external state. `Source::update` accepts arbitrary `F: Fn(&mut T)` with no `SourceValue` condition on `F` (`source.rs:97-103`). The declaration already says the route's *model argument* is only the selected value; separately, projector documentation calls the purity rule semantic rather than a Rust proof (`source.rs:50-59`), and `modify` notes that arbitrary callbacks cannot be rolled back (`source.rs:105-107`). A captured `Remote`, service, function pointer or global handle can have effects independent of `T`.

That is a real API contract boundary, but not a structural bypass of the reported nested-signal bug. Do not claim the compiler proves edit-closure or projector purity. A stronger general type-level formulation is not practical while retaining arbitrary callbacks and legitimate `Remote`/service captures: Rust closure types expose capture auto traits such as `Send`/`Sync`, not a semantic effect set. Requiring a captureless `fn` would break valid captured operations and still would not prevent global effects. A stronger guarantee would require a different, restricted declarative operation/effect API (or an explicitly unsafe trust boundary), which would reduce application flexibility and is outside this prerequisite.

The public design doc already says arbitrary custom projections are semantic and that opaque aliases, interior mutation, and arbitrary `Deref` reads retain conservative behavior (`REACTIVITY.md:22-35`). It should add one short explicit scope statement near the exact typed operation path: `SourceValue` excludes nested `Signal` in the selected value's represented fields, including ordinary containers; it does not certify callback captures, projector purity, or external/interior effects. Keep the existing owner-grain fallback for opaque aliases and interior mutation. This makes the limit clear without weakening the useful structural guarantee or banning remote/service captures.

## Regression coverage proposal

The current added tests are positive/runtime tests; there is no committed compile-fail fixture asserting that `Source::new` rejects `Signal<Signal<_>>`, a named nested struct, a heap container, `&Signal<_>`, and plain `Box<dyn Any>` while accepting `Box<dyn Any + SourceValue>`. The bound itself is direct and the existing positive test validates its intended extension point, but a compact compile-fail doctest matrix would guard against a future constructor or visibility refactor that accidentally drops the constraint. The candidate does test coarse owner update refresh both inline and heap-contained nested signals (`source_values.rs:45-124`), preserving the supported general model path.
