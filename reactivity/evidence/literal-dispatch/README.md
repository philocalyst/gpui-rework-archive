# Literal style dispatch at the typed input boundary

Source: `582bca7cd0a2836a86c21f82e52cd55515e14d88`, based on `09a9a229f114df7db203e6d12f81947dca923e41`. This is independent of the unmerged counted/batched style palette experiment.

The sealed operand family now distinguishes literal, signal, and explicitly erased input before conversion. Literal builders call a direct setter generated by the existing property schema, with the same validator and conversion. Signal binding and `PropInput` compatibility remain. `.size(...)` preserves the raw input through the typed decision and assigns both dimensions. Radius still stores raw f32 literals and reports invalid values during admission. Existing const generic Flex recipes remain unchanged.

Production changes excluding test bodies: +213/−109 lines, net +104, across six files. No new public const-generic parameter, user macro, retained field, or allocation. The existing private sealed superclass gains an associated constant. Field codes and the size selector are private. Ordinary headers and the source graph are unchanged. This removes literal binding branches; it does not make presentation or mounting sublinear.

## Measurement protocol

`run.py` launches only pinned executables. The same caller bytes are used in the matched baseline and candidate. A third, historical f019 executable provides context for the pre-reactive builder; it is not a controlled runtime attribution baseline. Its binary hash is checked against the earlier frozen campaign. The two matched executables freshly rebuilt their own root GPUI library (`fresh:false`); the supplemental f019 library is historical reuse. `frozen.json` includes exact source, caller, build-log, root rlib/rmeta, and executable hashes. Each process carries compile-time source/variant markers. The three variants rotate over three rounds.

The runner checks zero literal allocation requests, complete independent direct/recipe CPU-pixel equality, and the same recording-owner bounds digest. Builder controls perform 200,000 iterations. Warm recording mounts retain the last owner and report request count, cumulative allocated bytes, net retained bytes, and measured peak. A first recording mount occurs before functional warm-up in each fresh process. It is not cold-disk startup: hash guards and repeated process launches warm files. Allocation-counter totals are neither RSS nor process PSS.

Every timed process pins to CPU 2. Before/after records include processes and CPU/I/O/memory pressure; the runner rejects active compiler processes. Source/binary guards run outside measured operations. A 90-second whole-campaign failure deadline bounds execution. Guard preparation originally refreshed an entire historical worktree index and blocked on filesystem metadata; it was stopped before any capture and replaced by exact-path source checks. No performance row exists from that attempt.

The following results come only from the coordinated guarded capture. All losses remain in the raw data and summary.
