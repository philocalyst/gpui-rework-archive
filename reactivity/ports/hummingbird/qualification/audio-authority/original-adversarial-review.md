## Finding 1 — a failed incompatible natural successor can discard the already-produced predecessor tail

**Severity: real audio truncation on a supported failure path.** The existing “preserve prior tail” logic is conditional on `self.pipeline.is_some()` in `Owner::fail` (`src/audio/service.rs:392–410`). During a natural advance to a different sample rate, `Owner::prepare` first calls `pipeline.finish()` and, once all tail samples have been accepted by the output stream, sets `self.pipeline = None` at lines 472–483. `Pipeline::finish()` means its own pending samples are consumed and its expected output count is reached (`src/audio/pipeline.rs:224–255`); it does **not** mean the output stream queue has drained. The successor's `Pipeline::new` then runs at lines 485–491 and can return `Unsupported("FFT rate-pair resource limit")` for a rate accepted by `Format::checked` but rejected by `fft_geometry` (e.g. 44,101 Hz source to 48,000 Hz output; `src/audio/pipeline.rs:20–53`). The `?` reaches `fail` with `pipeline == None`, so `fail` immediately takes/drops the still-live output stream at lines 393–404. In CPAL, that drops the SPSC queue containing the predecessor tail; in the test sink, `Drop` clears its queue. This contradicts the nearby stated intent to preserve preceding valid resampler/PCM tails and differs from a successor open/decode failure, where the old pipeline remains present and the `FailedDraining` path waits for `output.queued_frames() == 0` (`src/audio/service.rs:569–583`).

**Concrete schedule:** play a short 8 kHz source to a 48 kHz sink; allow its EOF to advance naturally to a valid WAV successor at 44,101 Hz; ensure the sink has accepted but not yet consumed the 8→48 kHz resampler tail; the new 44,101→48,000 admission fails; `fail` closes output and the queue loses the tail. This is not covered by `bad_next_source_keeps_preceding_resampled_tail...` (that successor fails during `File::open`, before the old pipeline is discarded; `tests/audio.rs:484–516`), `hostile_successor...` (decode error, `:954–995`), nor the unsupported-pair test (unsupported pair is first/current track and has no preceding tail, `:997–1016`). The successful differing-rate join test covers only admitted successors (`:841–890`).

**Minimal safe fix options:** before dropping the finished old pipeline, preflight the successor's fallible rate-pair admission with `fft_geometry` and leave the old finished pipeline in place on failure; then the existing `FailedDraining` state can wait for the output queue to empty. This avoids overlapping two full pipelines. More general fix: represent “prior output queue must drain” independently of the new-pipeline slot and make `FailedDraining` handle the no-pipeline case until `queued_frames() == 0`, without closing the stream early. Do not just broaden the `fail` predicate to `queued_frames() > 0`: current `cycle` returns early when `pipeline` is `None` (`src/audio/service.rs:526–527`) and has no state transition to finish that drain.

**Negative fixture:** add a successor with a valid RIFF/WAV header and sample rate 44,101; use a bounded test sink that blocks consumption after EOF (or gates `drain`), then assert that failure does not drop the sink until its queued frame count reaches zero and that the exact preceding-tail samples still arrive. Keep the existing current-track 44,101→48,000 failure test too.

## Finding 2 — stale `Preparation::Failed` survives a direct selection change

`Library::preparation_status` guards `Pending` and `Ready` with `current_selection`, but returns `Failed` unconditionally (`src/app.rs:86–102`). `Preparation::Failed` stores only a string, no `Selection` (`src/app.rs:18–30`), and is installed for worker result errors (`:159–160`), immediate enqueue failures (`:218–220`), request exhaustion (`:197–200`), and status-lane closure (`:114–123`). `Library::SELECTED` is a public typed source and `selected` is public. After a failed prepare for selection A, a public `win.set(Library::SELECTED, selection_b)` changes the current selection but leaves `Preparation::Failed` intact; status remains `Failed` and `preparation_view` shows A's error as if it described B (`:229–241`). The current public-selection regression checks only a still-`Pending` request (`tests/preparation.rs:223–267`), so it does not cover this terminal-state case. This is display/status authority, not a path to queue or playback: the play continuation remains gated by full pending selection and audio revision, and prepared leases are selection-checked.

**Minimal fix/test:** store the selected identity alongside each failed preparation and report `Canceled` (or Empty, by product policy) when it no longer matches `current_selection`; include a failure caused by immediate `StartError` and lane closure. Negative fixture: fail preparation for A, directly set `SELECTED` to B with same generation/new sequence, then assert the UI no longer reports A's failure or offers A's retry semantics.

## Lower-severity CPAL behavior mismatch — pause suppresses the fade-out callback

`Callback::render` contains a 15 ms gain ramp for `playing == false` (`src/audio/cpal.rs:104–161`), and the public `OutputStream::set_playing(false)` calls `StreamTrait::pause()` (`:245–251`). CPAL 0.18.2 says streams are stopped/paused such that the data callback does not fire; `pause` may stop the callback even when hardware continues (`StreamTrait::pause`, pinned docs). Therefore a user Pause normally stops the callback before the 15 ms fade can run; only a callback already in flight could observe the false gate and fade one block. Fade-in still occurs when playback first starts, but pause is effectively abrupt. This is an observable quality mismatch if the ramp is intended to click-suppress pause. Either keep the callback running with gate=false until gain reaches zero (it will emit silence and preserve queued PCM after the ramp), or remove/document the pause ramp as unused. Negative fixture: drive the real `CpalStream::set_playing(false)` seam or a CPAL-independent lifecycle fake and assert the callback is allowed to consume precisely the ramp frames before it is stopped. No hardware run was possible here.

## Bootstrap and close audit

`application::window` and `system_window` correctly share the same wiring and attach the typed audio inbox (`src/application.rs:14–43`); the output device remains lazy until an explicit plan reaches `prepare`. The control thread itself starts asynchronously, then constructs `Media` (which starts the decoder worker) inside its body (`src/audio/service.rs:171–214`). If that second thread spawn fails before empty-queue `attach_audio` (`src/application.rs:33–36`), the control thread marks the gate closed with no token and sends no `Failed` event. Construction can therefore return a `Window` whose audio handle is already closed. This startup rendezvous is explicitly called out as unimplemented in `AUDIO-STOP.md`; record as a known bootstrap limitation, not a newly discovered race. A startup result rendezvous or constructing `Media` before publishing successful service construction would make that failure synchronous.

The revised `Stop` publication ordering is internally sound for output permission: early gate revocation is repeated under the desired mutex after the older publisher releases it. I did not re-report this known-fixed race. The close-race test intentionally proves closed dominates PCM permission even if a control publishes afterward; one nuance is that a concurrent in-flight command can still return `Ok(Receipt)` after `closed` is set, because `change` checks `closed` before acquiring desired and not again under that mutex (`src/audio/service.rs:57–79`, test `terminal_close_dominates...`). The gate prevents output, so this is a result/linearization semantic issue rather than playback revival; close is intended after window close. No stronger finding without an API guarantee that concurrent calls must return `Closed`.

## API contract checks that found no separate bug

- **CPAL 0.18.2:** `ErrorKind::DeviceChanged` means the default route changed but CPAL automatically rerouted and says no stream rebuild is required; `RealtimeDenied` says audio still plays with possible increased latency/glitches; `Xrun` is a potential glitch. Excluding these from `fatal` is consistent with the pinned CPAL contract, while other/unclassifiable errors default to fatal. [CPAL `ErrorKind` 0.18.2](https://docs.rs/cpal/0.18.2/cpal/enum.ErrorKind.html). CPAL documents that streams start stopped and `play()` is required before data callbacks run; the provider does call `set_playing` after creating a stream. [CPAL `StreamTrait` 0.18.2](https://docs.rs/cpal/0.18.2/cpal/traits/trait.StreamTrait.html), [CPAL device stream docs](https://docs.rs/cpal/0.18.2/cpal/traits/trait.DeviceTrait.html).
- **rtrb 0.4.0:** the PCM ring is a fixed-capacity lock-free/wait-free SPSC queue; `push_entire_slice` fails without writing when capacity is insufficient, and `read_chunk` requires an explicit commit. The code computes a whole-frame count from `slots()`, writes that exact prefix, and commits callback reads. Its 100 ms queue is application-owned only, as reported. The separate owned CPAL error ring is not covered by the data callback's no-allocation claim. [rtrb 0.4.0 crate docs](https://docs.rs/rtrb/0.4.0/rtrb/), [`Producer::push_entire_slice`](https://docs.rs/rtrb/0.4.0/rtrb/struct.Producer.html), [`Consumer::read_chunk`](https://docs.rs/rtrb/0.4.0/rtrb/struct.Consumer.html).
- **RealFFT 3.5.0:** `process_with_scratch` accepts the provided scratch to avoid the additional scratch allocation of `process`; this matches the retained plan/scratch design and allocation tests. [RealFFT 3.5.0 `RealToComplex`](https://docs.rs/realfft/3.5.0/realfft/trait.RealToComplex.html).
- **Symphonia 0.6.1:** `FormatReader::seek` invalidates decoder state, and its docs require decoder reset after successful seek; `Decoder::seek` does reset before resuming. Accurate seek goes to a packet at/before the requested point, so the code's post-seek decoded-frame trim is necessary. `next_packet` returning `Ok(None)` is normal EOF; `ResetRequired` requires track/decoder reconstruction, while all other errors are unrecoverable. This implementation maps it to a terminal decoder failure rather than attempting recovery, which is fail-closed. [Symphonia `FormatReader` 0.6.1](https://docs.rs/symphonia-core/0.6.1/symphonia_core/formats/trait.FormatReader.html). The decoder uses `AudioDecoderOptions::default`; in pinned Symphonia 0.6.1, decoder gapless defaults are enabled. [Symphonia `AudioDecoderOptions` source](https://docs.rs/symphonia-core/0.6.1/src/symphonia_core/codecs/audio.rs.html).

## Explicit scope / qualification limits
