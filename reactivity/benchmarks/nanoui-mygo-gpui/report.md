# Native presentation comparison: NanoUI, MyGo, GPUI

This is a Linux/Xvfb comparison harness for the three exact pinned snapshots documented in [`docs/research-core.md`](../../docs/research-core.md). It does not substitute a headless render for a native window. The runner measures process spawn to a visible X-server marker pixel and synthetic button injection to exact marker-pixel state change. It is a proxy for host presentation, not compositor or display latency. The first six archived timing cells are superseded because NanoUI's font was absent and the first normalized fixture clipped MyGo's button title. The corrected 240px-button fixtures passed eager and virtual preflight, and the corrected `cpu-matched` matrix has nine valid cells: eager 0/1,000 and virtual 250,000 for each app. Those cells use GPUI source `78824355bc4ceb1523bdbd21404b8380a50d9e7d`, not current integrated main. Eager 10,000 and native-default remain uncaptured.

Two profiles are separate by design. `cpu-matched` removes GPU rendering from GPUI and MyGo, but the software renderers remain different: GPUI's ReferenceCpu/softbuffer, MyGo's CPU image path and NanoUI's CPU raster/Cairo. `native-default` enables GPUI `x11` + `Auto` and MyGo's own renderer selection with its GTK accessibility bridge; NanoUI remains Linux CPU/Cairo and has no accessibility support. No profile activates an external screen reader, so GPUI's capability and live AT-SPI state must be distinguished from “AT enabled.”

## Measurement protocol

### Corrected fixture definition (preflight passed; timing pending)

All three fixtures request an 800×600 client area, root padding 8, root gap 6, a 48px header row with 8px gap, 16px labels, and a 784×530 body at (8,62). Exact client size is verified in preflight. Row-level geometry and native widget alignment remain API-specific: GPUI/NanoUI place the red marker at the top of the header, while MyGo centers its 40px children in the 48px row; native button bounds and styling differ, and NanoUI's pinned button has intrinsic height with no height option. The synthetic click at (176,24) lands inside all three controls. The shared button title has a 240px width and is visibly complete in each final screenshot. Eager workloads use no scroll container in any framework; every `row N` uses 16px text inside a 784×24 wrapper. This is an overflow/construction workload, not a scrolling test. Virtual-list mode requests the same 784×530 body and 24px rows. Preflight logs source-derived visible intervals/materialization expectations and screenshots show the same text rows 0–21 fully; row 22 intersects the bottom edge but its glyph line is clipped. `build.sh` copies all three sources from `fixtures/` into the app examples before compiling.

One observer process owns one X11 connection over 100 app starts per cell. [XDamage](https://www.x.org/releases/current/doc/damageproto/damageproto.txt) wakes the observer after drawable updates; [XTEST](https://www.x.org/releases/current/doc/xextproto/xtest.pdf) injects pointer events. The XTEST spec uses `rootX/rootY` for `MotionNotify`; button events identify the physical button, so the harness first sends absolute pointer motion and synchronizes before the timed press/release. XGetImage reads one marker pixel before accepting an acknowledgement. Startup records the first exact red RGB pixel after process spawn and window discovery. Click latency includes XTest delivery, framework event handling, frame work, X-server drawable update, damage notification, and exact pixel readback. The observer uses blocking socket-readiness polling with deadlines instead of periodic sleep polling, acknowledges each non-empty damage event before checking state, and retains raw nanoseconds. It does not claim a monitor refresh, compositor, scanout, or photon timestamp. XDamage/XGetImage add observer work; these values are not app-internal frame timings.

At 750 ms after the first pixel, the observer records process RSS, process PSS, and thread count from `/proc` for the first five starts per cell; this is a small idle-memory sample, not host-wide memory. The Xvfb server is kept alive at `:94` and the observer connection remains open across that case's starts. The first fresh-process sample follows compilation, so the filesystem page cache is warm or unknown; later starts are warm restarts. The cache is not dropped and there is no cold-cache measurement.

The direct observer defaults to 20 starts for smoke runs. `run-matrix.sh` uses 100 new-process starts and 10 clicks per start, giving finite-n p50/p95/p99 summaries (p99 is a tail estimate from 100 startup samples or 1,000 clicks, not a universal bound). Framework stage diagnostics are deliberately a separate, low-sample run (`LUNA_STAGES=1`, one start, three clicks) so diagnostic logging cannot inflate the uninstrumented click-to-pixel distributions. GPUI's `PresentedFrame` acknowledgement, MyGo's `MYGO_FRAME_STATS=all`, and NanoUI's view/click markers have different stage boundaries and must remain separately labeled.

## Source-grounded work-removal candidate

The next meaningful text-path experiment is to avoid shaping fully clipped, fixed-metric row text before it approaches the viewport, while keeping its semantic text and row identity. This is safe only when row width/height are fixed independently of text and no parent consumes the row's intrinsic size or text baseline. [GPUI's `TextSite::shape`](../../crates/gpui/src/runtime.rs#L508-L521) caches a shape by width, while its [measure path](../../crates/gpui/src/runtime.rs#L1988-L2015) requests the shape for baseline and intrinsic dimensions; [NanoUI's text cache](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/text_tt.zig#L172-L246) hashes text/style and retains layouts across frames; [MyGo's retained text measurement](https://github.com/egoist/mygo/blob/ea23ad2975a87db9b20efe6690ffedf88f4fe4f3/ui/layoutcache.go#L325-L415) reuses measured text only while text-layout style/constraints stay valid, backed by its [Pango/HarfBuzz layout path](https://github.com/egoist/mygo/blob/ea23ad2975a87db9b20efe6690ffedf88f4fe4f3/internal/text/layout.go#L644-L671). These source paths do not show that any framework currently defers shaping for clipped text.

An implementation experiment should compare a fixed-width/fixed-height row with lazily shaped offscreen content against eager shaping, then reject the optimization if scroll extent, first-visible-row baseline, wrapping, bidi reordering, font fallback/version changes, selection geometry, or accessibility text-range requests differ. The win would be removed initial shaping and glyph-cache work; retained source strings and semantic list metadata remain. Auto-sized rows, content-measured columns, multiline wrapping, and rows whose baselines participate in parent alignment are losing cases. No latency win is claimed until an equivalent virtual-list preflight and paired native capture measure it.

## Input-to-frame scheduling: what source does and does not establish

The three native backends already avoid an always-running loop in their idle path. GPUI's Winit handler applies an input event, then requests redraw only when the commit contains a prepared epoch; `RedrawRequested` does the native draw, and `AboutToWait` selects `Wait` or a retry `WaitUntil` deadline ([pinned Winit 0.30.13 `ControlFlow`](https://docs.rs/winit/0.30.13/winit/event_loop/enum.ControlFlow.html), [GPUI input/redraw path](../../crates/gpui/src/native.rs#L750-L815), [idle policy](../../crates/gpui/src/native.rs#L1010-L1015)). This removes idle polling while preserving redraw after accepted input. It cannot promise same-refresh presentation: the OS/window server and display schedule redraw delivery.

NanoUI's GTK button handlers call `frame()` synchronously on press and release; `frame()` rebuilds, lays out, and paints the full view, then invalidates with `gtk_widget_queue_draw`. GTK's draw signal is the later painting callback. Its `gtk_widget_add_tick_callback` path is retained only for active animation/hot changes in this code ([pinned NanoUI event and frame path](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/linux/surface.zig#L103-L149), [press/release handlers](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/linux/surface.zig#L233-L267)). GTK documents that a tick callback runs before a frame and that `queue_draw` invalidates for drawing after the current event batch ([GTK 3 tick callback](https://docs.gtk.org/gtk3/method.Widget.add_tick_callback.html), [`queue_draw_region`](https://docs.gtk.org/gtk3/vfunc.Widget.queue_draw_region.html)). Therefore the synchronous frame work is not itself a displayed/presented acknowledgement.

MyGo's CPU path requests one GTK tick callback when none is outstanding; that callback sends `SurfaceFrame`, which produces the frame before GTK draws. Its GL path queues a draw directly. Runtime `requestFrame()` clears pending redraw/repaint timers and asks the surface for a frame ([pinned MyGo runtime request](https://github.com/egoist/mygo/blob/ea23ad2975a87db9b20efe6690ffedf88f4fe4f3/ui/runtime.go#L850-L865), [Linux request path](https://github.com/egoist/mygo/blob/ea23ad2975a87db9b20efe6690ffedf88f4fe4f3/internal/linux/surface.go#L320-L330), [tick callback](https://github.com/egoist/mygo/blob/ea23ad2975a87db9b20efe6690ffedf88f4fe4f3/internal/linux/surface.go#L630-L650)). This is a deliberate frame-clock gate for CPU rendering; it may defer work until a frame opportunity, but the source alone does not prove a one-refresh penalty or explain prior diagnostic values.

The concrete shared work-removal candidate is to coalesce repeated updates before one already-pending frame and avoid rebuilding unaffected retained data, while keeping input state, hit-test geometry, and the accessibility projection tied to the same acknowledged presentation. Do not call synchronous `draw` or bypass the GTK frame clock as a general latency fix: it can duplicate work, render during a stale/partial event batch, or move expensive work into the input callback. For text-heavy virtual rows, defer offscreen shaping only under the fixed-metric conditions above; preserve source text and semantic list state, and shape before an item becomes visible or an AT text-range request needs it. The benchmark's observer measures X-server drawable state, not a frame-clock callback, compositor present, or scanout, so only the corrected captures can show whether any policy removes user-visible delay.
