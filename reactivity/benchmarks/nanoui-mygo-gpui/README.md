# Native Linux comparison fixture

This folder contains a reproducible, external-presentation benchmark for the exact source pins already audited in [`docs/research-core.md`](../../docs/research-core.md): GPUI `78824355bc4ceb1523bdbd21404b8380a50d9e7d`, JustRach NanoUI `dfa7f7ab4e890f643703f4ffe4d834ff10defd4f`, and MyGo `ea23ad2975a87db9b20efe6690ffedf88f4fe4f3`. The NanoUI Linux implementation is native GTK3 with its CPU raster path into Cairo; MyGo uses GTK3 with Cairo or GtkGLArea/OpenGL and has ATK; GPUI uses Winit + a softbuffer ReferenceCpu path or its selected Wgpu renderer and can compile AccessKit AT-SPI. NanoUI's pinned README explicitly says accessibility is absent. These are Linux-native windows, not headless/core timings. NanoUI's macOS AppKit/CoreText/Metal cell is unsupported on this Linux host and must remain an explicit blank cell until a macOS runner can execute the identical fixture.

No comparison result is currently valid. The first six timing cells were captured before NanoUI could see the Nix-store DejaVu font, so its text did not render; they also used mismatched fixture geometry and content. Their raw records are retained for audit but are superseded. The current 240px button fixture still requires a rebuilt, reviewed preflight before any new timed run. See [`report.md`](report.md) for exact causes and artifacts.

The corrected fixtures use 16px labels and `row N` text inside 24px row wrappers, with explicit non-wrapping for MyGo and short row strings that fit without wrapping in each API. MyGo selects DejaVu Sans for text; NanoUI selects DejaVu Sans through its theme (the only installed family on this Xvfb host). NanoUI requires that font to be staged into a directory its own font database scans; the build script stages the host-resolved TTF and records its SHA-256. GPUI Canvas is fixed to bundled Noto Sans and its pinned public UI does not expose a font-family setting, so glyph metrics/bytes and shaping engines remain unmatched and must be stated in any result. MyGo/NanoUI scale factors come from GTK; GPUI uses Winit/X11. The Xvfb run reports scale 1 through 800×600 client geometry. Native row/button alignment differs: MyGo vertically centers its header children; GPUI/NanoUI place the marker at the row top; NanoUI has intrinsic button height. The final 240px button title is visible in all three screenshot preflights. The fixtures request root padding 8 and gap 6, a 48px header row, marker target (8,8), click point (176,24), and body at (8,62) with size 784×530. Eager rows have no scroll container in any app and overflow the same body viewport. That is an overflow/construction workload, not a scrolling test. The virtual-list requests use that same body rectangle and 24px rows; geometrically visible IDs are 0–22, while complete glyph lines 0–21 are visible and ID22 is clipped at the viewport edge. Source-derived materialization is 23 for GPUI, 25 for MyGo (two-row overscan), and 28 for NanoUI (one extra row plus four-row overscan); the observer logs these expectations, not an app-internal runtime count. Each fixture takes `LUNA_MODE=eager|virtual` and `LUNA_ROWS=N`. Eager workloads are `0`, `1000`, and `10000`; virtual workloads use `250000`. A new-process startup sample is measured from `Command::spawn` until an exact red-marker pixel is observed in Xvfb. A click sample is measured from XTest button injection until an XDamage event followed by exact pixel readback sees the expected opposite color. A single X11 connection remains open across all app restarts, so no sample tears down the Xvfb server.

The observable is the X server's drawable, not the compositor, vblank, scanout, or photon. The runner blocks on X11 socket readiness with a deadline, then requests a 1×1 XGetImage read; that request/reply and Damage notification define the acknowledgement endpoint. It waits for the exact red startup pixel, and checks exact red/green RGB values on every click. It records raw nanoseconds and summarizes finite-sample p50/p95/p99. The full matrix uses 100 starts and 10 clicks per process; it takes idle memory samples on only the first five starts in each cell, 750ms after first pixel (override `LUNA_IDLE_MS`). RSS/thread count come from `/proc/<pid>/status` and PSS from `smaps_rollup`. This is idle process memory, not host-wide memory. Pointer motion is sent and synchronized before click timing so button coordinates are established; hover damage is drained before the first click.

One X11 observer connection and the Xvfb server stay warm across every process in a cell. The first fresh-process sample follows compilation, so code and data pages are already likely warm; later samples are warm restarts. The kernel page cache is not cleared and there is no true cold-cache sample. Use alternated app orderings to avoid order bias and preserve each raw CSV. XDamage delivery and XGetImage readback add observer/protocol work; the timing is spawn-to-server-pixel and synthetic-click-to-server-pixel, not app-internal compute or display scanout.

Two separate profiles are intended:

- `cpu-matched`: GPUI `x11-minimal` + `ReferenceCpu`; MyGo `MYGO_GPU=0`; NanoUI Linux CPU raster + Cairo. The rasterizers are distinct, so this means software-only native presentation, not renderer equivalence. GPUI has AT compiled out; MyGo's GTK/ATK remains available; NanoUI has no AT implementation.
- `native-default`: GPUI `x11` + `Auto`; MyGo's default Linux renderer selection and ATK; NanoUI Linux CPU/Cairo with no AT. The GPUI binary includes AccessKit's AT-SPI backend and MyGo uses GTK/ATK, but this fixture does not query the session's runtime accessibility status. Record the actual GPUI renderer reported by `LUNA_PRESENT` and MyGo's selected surface/GL driver. This profile does not have a renderer-matched NanoUI cell.

Commands and toolchain hashes are in `build.sh`; Go 1.27.1 was fetched from `https://go.dev/dl/go1.27.1.linux-amd64.tar.gz` (SHA-256 `63d339f0da5ab53635a56f2490a7984dfe12dfcff22ad749f63edaf590168445`). Zig 0.17.0 came from `https://ziglang.org/download/0.17.0/zig-x86_64-linux-0.17.0.tar.xz` (SHA-256 `1cbe9df9f27e6b78d14ccbca43b6703a404ef79ef1c463de901d7f088d4e2026`; verified against Zig's published `download/index.json`). Rust is the environment's pinned 1.97.1 toolchain. Rust observer uses x11rb 0.13.2 and rustix 1.1.5. On this NixOS host, the Go and Zig outputs use the generic `/lib64/ld-linux` path that resolves to the Nix stub; the observer therefore launches each through the matching store glibc loader with the same runtime library path, using `exec` in the measured child PID. GPUI binaries already use the native Nix loader path.

The latency run leaves framework stage logging off to avoid making the measured path pay for diagnostic I/O. For a separate low-sample stage diagnostic, run with `LUNA_STAGES=1 LUNA_STARTS=1 LUNA_CLICKS_PER_START=3`: GPUI prints each acknowledged `PresentedFrame` (native present plus GPUI runtime acknowledgement, not scanout); MyGo's pinned `MYGO_FRAME_STATS=all` prints build/layout/paint/present stages; NanoUI logs first view and click handling. Their stage clocks are not identical and must be reported separately from uninstrumented click-to-pixel latency.
