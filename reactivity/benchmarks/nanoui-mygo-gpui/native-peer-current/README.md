# Native peer preflight for the upcoming current-GPUI comparison

This directory contains source-pinned peer rebuild evidence and six correctness-only Xvfb preflights. It contains **no accepted startup or click timings**. Each preflight used one fresh process, one click, and one screenshot; the observer printed nanosecond values as diagnostics, and those values are excluded from every comparison.

## Correctness-only preflight

All six peer cells passed on a private 1280×800×24 Xvfb at `:109`: eager 0 rows, eager 1,000 rows, and virtual 250,000 rows for both apps. Logs confirm 800×600 client sizes, visible button-title text, first-row ink for populated views, and a red-to-green exact marker-pixel acknowledgement after pointer injection. The click center is at client (176,24), inside each actual button. Virtual cases report the same visible IDs 0–22; each backend's overscan policy is separate: MyGo expects 25 materialized rows; NanoUI expects 28. Font and native button placement/style remain app-specific.

The raw logs and screenshot preflights are under [`preflight-private109/`](preflight-private109/), with their SHA-256 inventory in [`sha256.txt`](sha256.txt). These are gates only. Their single startup/click observations are too few, and are not included as performance data. The server is separate from the shared `:94`/`:97` displays.

The preflight observed MyGo's native GPU probe falling back to its CPU path (`there is none`) on Xvfb. NanoUI's pinned Linux implementation uses its GTK/Cairo CPU path. GPUI's feature/backend state is not represented here; the upcoming current-GPUI build and its runtime renderer result must be recorded independently. Accessibility is also asymmetric: the pinned NanoUI README states that accessibility is absent; MyGo's GTK surface registers ATK/AT-SPI; GPUI's native X11 feature includes AccessKit. The preflight did not run a screen reader or query the session-bus accessibility state.

## Planned native run, still pending

The accepted workload should compare the current integrated GPUI build against these two peers using the same requested 800×600 window, fixture text, marker colors, click point, and Xvfb server. For each app/workload, use 100 fresh starts, 10 marker clicks per process, five idle memory samples at 750 ms, and exact source/binary/fixture checks before every observer launch. Workloads are eager 0, eager 1,000, and virtual 250,000; do not add eager 10,000 unless every app's cost and preflight are reviewed. Rotate app order by workload. Startup endpoint is process spawn to exact initial red drawable pixel. Click endpoint is injected XTEST press/release to exact green/red marker pixel after XDamage and XGetImage readback. This is an X-server drawable acknowledgement under Xvfb, not compositor present, refresh, scanout, or photons.

Native scheduling differences are part of the measured app behavior and must be described, not hidden: NanoUI's GTK press/release callbacks synchronously update its view and call `frame`, then queue GTK draw; MyGo requests a GTK tick for CPU frames and its GL path queues a draw; GPUI processes input in Winit and requests redraw from accepted runtime state. Do not change those policies or inject artificial timer waits to manufacture symmetry. A per-stage diagnostic run can attribute stages but must remain separate from the uninstrumented percentiles. Keep first-pixel/startup and click-to-pixel as end-to-end routes, and label backend selection, accessibility capability/runtime state, font, virtual materialization, and actual window geometry for each app.

The paired runner is not yet ready: the current integrated GPUI source pin and fixture hash have not been supplied in this record. Before capture, add a fail-closed runner that checks exact current GPUI source tree, build manifest, fixture and binary; MyGo's pinned source/fixture/binary; NanoUI's pinned source, exact `build.zig` filter patch, fixture and binary; observer hash; and reviewed screenshot/geometry preflight. Run a guard-only pass over all nine cells before creating output or launching processes. No timing capture is authorized by this preflight record.
