# Identity index second form: adversarial review

Review target: `/root/gpui-validated-sites/reactivity/crates/gpui/src/runtime/nodes.rs`, the uncommitted `Option<Box<Index>>` implementation on top of production commit `4a80f08dd04b105ccbd32cecca2398405d05d62d`. No source, build, or timing changes were made by this review. Existing first-form measurements are in [`evidence/identity-order/README.md`](../crates/gpui/evidence/identity-order/README.md), pinned by its `frozen.json`; they do not measure this second form.

## Correctness and authority

The new index preserves the existing canonical `Vec<Node>` as the sole identity authority. Strictly increasing nodes need no retained index: `locate` tries checked subtraction from the first identity, requires equality at the predicted canonical slot, and otherwise binary-searches the sorted canonical lane. Its extra correction is still only a guess: for a candidate node at `index`, it subtracts `candidate.identity - requested.identity` from `index`, then accepts only if that canonical node has the requested identity. Multiple intervening gaps, overflow, a miss, or a bad prediction all fall through to the ordinary binary search. That makes the acceleration exact; the fallback work is bounded `O(log N)`.

For non-monotone nodes, `Dense` is a current-tree inverse table from `identity - first` to a canonical `u32` position. `u32::MAX` marks a hole. `Sorted` is a `u32` permutation sorted by canonical node identity and binary-searched against those nodes. Because the runtime caps a tree at 100,000 nodes, every valid position is below the sentinel. The span uses checked `last - first + 1`; overflow or a span larger than `2N` chooses `Sorted`. Thus dense storage is at most `8N` payload bytes and sparse storage is `4N`, independent of the lifetime identity high-water mark.

The runtime identity allocation is monotone and checked before admission in `runtime.rs` (`describe_inner`, `next_identity.checked_add(drafts.len())`); each old identity is reused by taking its prior node at most once. `Nodes` exposes only immutable slice access; index data is rebuilt by `replace`, and `take` leaves an empty canonical lane, so a retained index cannot resolve a node while reconciliation has taken the old tree. `Runtime::locate` separately checks target namespace and `logical_valid` before this lookup. These facts support trusting the dense inverse table without rechecking the returned node ID on each hit. If any future mutation path makes `Node.identity` mutable outside `replace`, that proof ceases to hold; the immutable `Deref` boundary is therefore part of the correctness contract.

No correctness blocker was found in the frozen diff. The checked arithmetic covers `u64` extremes, and a dense miss from below `first`, beyond the table, or at a sentinel returns `None`. The sorted fallback indexes only positions built from the current canonical vector. The frozen tests now cover the exact dense threshold (`[6, 1, 3]`, inclusive span 6 for N=3), just above it (`[7, 1, 3]`), and 15,120 permutations across contiguous, gapped, and extreme-ID families, plus missing IDs, replacement, and `take` revocation.

## Cost and workload boundaries

`Option<Box<Index>>` costs one thin pointer in every `Nodes` value. The frozen x86-64 layout is `Nodes=32 B`, `Index=24 B`, and Runtime falls from 2,384 to 2,368 B. `Index` is a cold box, so ordinary ordered trees do not pay its allocation. First dense indexing at the exact N=3/span=6 threshold requests 48 B total: a 24 B descriptor and six `u32` positions. This form also puts the position slice behind a second allocation. The first non-monotone build therefore creates two allocations (the `Box<[u32]>` positions payload and `Box<Index>` descriptor), and adds an extra pointer load on the permuted lookup path. The adjacent `nodes-final.txt` and `layout.txt` evidence report these layouts and requests.

At replacement, `Dense` construction initializes `span` words and writes one position per node, `O(span + N)`; `Sorted` construction sorts positions, `O(N log N)`. Both are description-time work. Reusing `positions` capacity avoids an allocation when the prior payload can serve the new shape, while transitions to a strictly ordered tree drop the index and later permutation may allocate again. `into_boxed_slice` may shrink capacity, so it is not a promise to retain spare capacity across forms. This avoids permanent lifetime-history growth, but repeated permutation/ordered transitions may pay allocator churn.

The frozen second-form capture measures a combined slice against the original BTreeMap baseline, not a change isolated from the first map-free form or validated-position reuse. For 4,096 nodes, paired headless public focus/property operations in gapped/permuted cases improved roughly 54–76%, and four existing large style mounts improved 17–19%. Ordered 4,096 retention fell by 75,184 requested bytes; reordered retention fell by 116,680 bytes after reversal. The complete capture still has losses: warm inspector overrides +2.2% to +11.5%, gapped mount +10.2%, permuted activation +2.2%, and permuted destruction +134.7%. The permuted fixtures are virtual-list cases whose complete public calls include a separate linear presented-row membership check in `Runtime::locate`; these numbers cannot isolate identity lookup. The result remains **held**; do not transfer the first-form numbers or interpret retained-request savings as native RSS/PSS.

`Runtime::locate` first resolves the namespace, then calls `nodes.locate`; for realized-list items it separately scans the prepared/presented nodes to reject unrealized rows. That scan is a semantic admission check and is not removed by a faster canonical identity index. A measured full API operation can therefore remain linear even when the index lookup becomes constant time.

## Assessment and next gate

The current enum is a reasonable minimal representation: it makes the bounded dense-vs-sparse trade explicit without unsafe tagging, key duplication, or per-node flags, and its frozen size ledger is now concrete. I would not add stored gap metadata to optimize ordered gaps. The clamped one-probe correction has no retained cost and an exact binary-search fallback; a gap descriptor would add owner state or another cold allocation to save at most a logarithmic search on selected IDs. I would also keep `Sorted` as the wide-span fallback rather than imposing a lifetime ID cap.

Eytzinger layout is a candidate only for the wide-span sorted-position fallback. Khuong and Morin's primary 2015 study reports sorted binary search as best for small arrays, while Eytzinger often wins for larger RAM-resident repeated searches, with tuned conditional moves/prefetch; this does not predict this code because comparisons dereference canonical nodes at each search step and the actual query distribution includes repeated targets and list-membership work ([paper](https://arxiv.org/abs/1509.05053)). The Linux bcachefs implementation shows a real production use of Eytzinger adjacency/prefetch, but is a different cache/search workload ([pinned kernel source](https://android.googlesource.com/kernel/common/%2B/48d2245586452b8279a854970ce82f43477669d3/fs/bcachefs/eytzinger.h)). Keep the ordinary sorted position slice until a source-pinned experiment beats it in wide-span cases without regressing small or random lookup workloads.

An assembly spot-check used the SHA-pinned `identity_index` baseline/candidate executables in the dense campaign's `frozen.json`. The measured `Win::property<Color>` baseline symbol is 431 bytes and calls `Runtime::resolve`; the candidate symbol is 277 bytes and calls `Runtime::locate`. Candidate `Runtime::locate` includes canonical lookup and list admission; it has no out-of-line `Nodes::locate` call in this monomorphization. The `Runtime::present_inner` measurement closure is 0x4ed bytes in both binaries; `Runtime::present` is 0x3d93 versus 0x3d8c (7 bytes smaller). This does not identify the warm-override loss: a full override operation also runs style/layout/paint, while the linked symbols are from a separate public property lookup and list-oriented fixture. The shared-reference paint edit (`&mut Node` to `&Node`) is therefore neither vindicated nor implicated by these code sizes. No attribution from alias metadata to latency is justified without an isolated paired variant and hot-path evidence.

Before another algorithm variant, measure the existing warm-override path with phase-level boundaries outside loops, separating target lookup, override update, layout, and paint. Preserve the exact app/model and activation paths; direct index lookups alone do not explain a full operation. If a hot paint-only loss remains, an isolated paired compilation can compare the old mutable node reference with the new shared reference while leaving lookup/layout unchanged. Do not weaken the immutable `Nodes` API or infer a no-alias cause from source signatures alone.
