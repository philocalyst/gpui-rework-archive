## What the linked code shows

The concrete stream specialization is `CursorGeometry<()>::try_for_each_pair` at `0x66cc00`, symbol extent `0x1b17` (6,935 bytes) in `nm -S`. `Clusters<()> ::new` is at `0x67ad10`, extent `0x2eb` (747 bytes), and `Clusters<()> as Iterator::next` at `0x67d570`, extent `0x6f5` (1,781 bytes). `Planner::shape` is at `0x6740a0` in stream and `0x67e0f0` in baseline.

At four static sites in the stream helper (`0x66cee1`, `0x66d1fb`, `0x66d645`, `0x66d7bf`), the call to `Clusters::new` is immediately followed by `memcpy` with length `0x110` (272 bytes). At the first site, the constructor's hidden return destination is `rsp+0x698`, then the caller copies those 272 bytes to the iterator at `rsp+0x330`. The temporary ends exactly at the current helper frame's `rsp+0x7a8` boundary. This is a real constructor-result staging copy and 272-byte stack temporary in the linked stream binary; it is not an allocation. Source calls `run.clusters()` in preflight and source emission, and `run.visual_clusters()` for RTL prefix construction, so these static sites represent different traversal paths. They must not be summed as a per-input count without a runtime branch census.

There are also large item transfers. One path copies `0x90` (144) bytes immediately after a `Clusters::next` result at `0x66d6a9`; another copies `0x88` (136) bytes from an `Option<Cluster>` payload at `0x66d826`. The source item is `Option<Cluster>` and `Cluster` contains a `Run`, `Atom`, and `Grapheme`; this pattern is consistent with moving the large by-value iterator item and its payload into consumer locals. The disassembly alone does not establish that both copies execute on every iteration or path, so they are candidate costs to inspect in a follow-up binary, not a per-cluster total.

A separate `0x98` (152-byte) `memcpy` occurs at `0x66d2f9` while `visit_source_pairs` initializes the storage used by its offset lookahead; source at `geometry.rs:368` wraps the supplied iterator in `.peekable()`, and the linked code subsequently calls the ICU segment iterator on the nearby local state. This looks like movement of the large underlying offset iterator into the `Peekable` adapter. Treat it as a one-time call-path copy and verify with the next linked artifact before claiming a saving from a manual lookahead representation.

## Why the current source creates these moves

Pinned Parley source is in `reactivity/vendor/parley/src/layout/run.rs` and `reactivity/vendor/parley_engine/src/shape/atom.rs`.

`Run::clusters()` and `Run::visual_clusters()` return opaque iterators built from `Clusters::new` (`run.rs:199–207, 383–461`). `Clusters` owns a `Run`, an `Atoms`, a `Graphemes`, an `Option<Atom>`, and direction state (`run.rs:386–395`). `Atoms` and `Graphemes` each embed a `ShapedSlice`; `Atom` embeds another slice (`parley_engine/src/shape/atom.rs:18–29, 390–395, 481–491, 583–594`). Those repeated views of the same line slice explain the state size. On this x86-64 linked specialization the emitted object and copy length are 272 bytes.

`Clusters::next` advances the grapheme cursor, updates the active atom at atom edges, then materializes `Cluster { run, atom, grapheme }` (`run.rs:431–460`). This is exactly the recurrence the general cursor API needs, but the bulk caret visitor consumes only a projection of each cluster.

The bulk preflight at `reactivity/vendor/parley/src/editing/geometry.rs:99–167` iterates `run.clusters()` at lines 127–153, although it needs only each source range and a count for the RTL scratch upper bound. `visit_source_pairs` at lines 360–443 uses advances for the RTL visual prefix (388–393), then uses source range, advance, and hard-break state in its logical pass (397–439). The two passes have different projection needs.

The exact source projection rules are available without reproducing geometry math:

- `Cluster::text_range` maps `grapheme.char_range()` through `run.full_slice().text_byte_range(...)` (`layout/cluster.rs:158–163`). `Run::line_slice()` is already the slice used to seed `Clusters` (`layout/run.rs:71–77, 399–415`); its grapheme iterator covers the same line-scoped character range. Its `text_byte_range` maps those absolute shaped-character indexes to the same source bytes (`parley_engine/src/shape/atom.rs:95–130`).
- `Cluster::advance` is **not** always just `Grapheme::advance`: it calls `run.line_spacing().grapheme_advance(&atom, grapheme, is_rtl)` (`layout/cluster.rs:183–191`). The latter includes spacing and justification and direction-sensitive ownership (`layout/spacing.rs:167–210`). Any view must call this exact operation with the same `Atom`, `Grapheme`, and direction.
- Hard-break classification is the first logical character's whitespace being `Newline` (`layout/cluster.rs:222–225`). `Grapheme::whitespace()` exposes the same first-character classification (`parley_engine/src/shape/atom.rs:838–842`).

## Bounded source formulation to test

Keep the public `Run::clusters()` and all random cursor APIs unchanged. For this stream's private bulk path, separate validation from geometry and make the state borrowing explicit:

1. In preflight, hold `let full = run.full_slice()` and walk `run.line_slice().graphemes_start()` directly. For each grapheme, call `full.text_byte_range(grapheme.char_range())`, matching `Cluster::text_range`'s full-slice mapping while using the line-scoped grapheme sequence seeded by `Clusters::new`. Apply the existing empty-layout exception, ordering/range/u32 checks, and increment the same cluster count. This should visit the same grapheme boundaries without constructing `Atoms`, `Atom`, or `Cluster` when the pass does not need them. It retains complete range/font admission before the first callback and preserves `run_count` for `rtl_capacity`.
2. Factor the existing state transition in `Clusters::next` into one `advance_cursor(&mut self) -> Option<Grapheme>` that updates `self.atom` at the current atom boundary. Keep `Iterator::next` as a thin wrapper that constructs the existing `Cluster`, preserving legacy behavior.
3. Add a crate-private synchronous `Run` visitor for the geometry stream. It builds `Clusters` directly in its local state and passes a short-lived borrowed view of `(&Run, &Atom, Grapheme)` to a monomorphized callback. The view exposes only exact source range, exact spacing-aware advance, and hard-break accessors. Preflight does not request it; RTL prefix asks only for advance; the logical pass asks for range/advance/hard break. A higher-ranked callback lifetime prevents retaining the temporary atom/view after the cursor advances. This avoids returning a 136-byte `Cluster` in the stream loop and shares the existing atom/grapheme recurrence rather than implementing another cluster algorithm.

The in-place construction is a distinct part of the experiment. Merely changing `Iterator<Item=Cluster>` into `&mut Iterator` does not remove the 272-byte constructor move. The callback method should initialize the stream-local cursor directly (or make the constructor inline and verify the same result) rather than return the 272-byte `Clusters` value through another opaque iterator wrapper. Legacy iterator construction can continue using `Clusters::new`.

There is one deliberate preflight tradeoff to make explicit: a grapheme-only range pass does not execute `Clusters::next`'s `atom.expect(...)` assertion before the first callback. For a malformed private `Layout` that violates the invariant that the first grapheme/atom edge yields an atom, that particular panic could move into the emission pass after earlier callbacks. The documented stream rejection is about checked font/range admission (`None` before callbacks), while ordinary `Layout` construction owns its internal atom/grapheme invariants. If the implementation intends to preserve panic ordering even for invalid internal Parley state, keep advancing the shared cursor in preflight but avoid materializing `Cluster`; do not silently claim the range-only walk has identical malformed-state panic behavior.

This design adds no persistent field, allocation, index, cache, or per-owner header. It does add private Parley-to-geometry surface and callback monomorphizations; exact source/code size and stack effects remain unknown until linked. Do not inline the whole visitor into `Planner::shape` by default: the helper boundary currently has a 1,960-byte frame and the planner already has a 4,584-byte frame. Keep the same helper boundary unless the release linked evidence supports moving it.

A separate smaller control can replace `.peekable()` in `visit_source_pairs` with a call-local one-element pending state while retaining the original iterator in place. Because the public API accepts arbitrary `IntoIterator`, preserve nested `Option<Option<usize>>` behavior for a non-fused iterator and make decreasing-order fallback replay the currently pending request exactly once. This is only a candidate: the `0x98` copy must first be mapped to the exact move in a new assembly artifact. Do not combine it with the cursor-view control if the goal is to attribute code/frame changes.

## Adversarial correctness and linked acceptance gates

Before adopting the borrowed projection, compare every visitor-emitted range, `advance().to_bits()`, and hard-break classification against the frozen `Cluster` path across the existing real-font matrix. Include graphemes crossing shaped-cluster/ligature boundaries, combining and ZWJ sequences, fallback/font boundaries, RTL visual iteration, explicit newline and U+2028, hard/soft wraps, zero-width/spacing cases, empty text, trailing empty lines, and invalid/overlapping source-range fixtures. Keep the current full-preflight/no-callback-on-invalid-font rule, source-order/decreasing-offset fallback, duplicate request behavior, and direct fallback semantics. Verify the callback can't retain the view and that callback early-break still drops scratch and returns its error. Do not substitute plain grapheme advance for cluster advance.

For the next release-linked artifact, inspect the same symbols and addresses after the source gate: whether all stream `Clusters::new` result-copy sites disappear; whether 144-/136-byte cluster transfers disappear from the bulk path; whether the helper's `0x7a8` frame shrinks and whether the helper itself grows; whether planner frame remains bounded; and `.text`/`.rodata` deltas. A source-level borrowing claim is not evidence of a binary copy disappearing. No cycle or speed conclusion follows from these assembly checks.
