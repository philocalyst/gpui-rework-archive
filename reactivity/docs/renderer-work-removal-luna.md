# Renderer work-removal research

Research snapshot: 2026-10-21. This is a source audit and experiment plan, not a performance result. The GPUI baseline examined is `f0bb6d4b6300793bc2c9d80c0a30ae0c7d3bbf93` (`crates/gpu/src/{renderer.rs,shader.rs}`, `crates/canvas/src/{canvas.rs,image.rs,image/transfer.rs}`, `crates/gpui/src/runtime.rs`). The image-axis follow-up is the isolated source commit `d4d9293f58f6f980d448996faaf254884b6c081e` in `/root/gpui-production-images`; it is not the baseline and has no timing claim here.

## Findings and candidates

### 1. Reuse the existing GPU scene packet across unchanged scene epochs

`gpu::Renderer::render` reconstructs all per-frame GPU input every call. It clears and fills `ranges` and `records`, validates and bins every draw, builds `references`, scans tile ranges for stats, writes globals/draws/tiles/indices/corrections, and creates a bind group (`crates/gpu/src/renderer.rs:405-693`). The image uploader already recognizes an unchanged ordered `ImageKey` list and skips pixel uploads (`renderer/images.rs`, `prepare`), but ordinary draw/tile preparation is still repeated.

**Candidate.** Give each Canvas a non-reused owner identity and an exact visual revision. Advance the revision when a commit changes the scene; `CanvasScene::commit_with_damage` already performs the ordered old/new command comparison in `damage_from` (`crates/canvas/src/canvas.rs:895-925, 1893-1899`), so reuse its result rather than adding another O(draws) comparison. Cache only the most recent GPU packet under `(canvas_id, revision, size, target format, color config)`. Reuse the renderer’s current vectors and buffers; retain the current bind group only while its buffer handles and atlas view remain the same. On cache hit, skip CPU bin/validation passes and redundant queue writes, then still clear/draw/submit the newly acquired target.

This removes repeated scene preparation and upload work, not target rasterization. `Renderer::render` explicitly clears the target and draws a full-screen triangle (`renderer.rs:694-720`); an acquired swap image is not evidence that prior pixels survive. Do not add a second command list, hash every frame, or claim idle zero-render. Keep the ID/revision on the existing Canvas (small fixed header cost); no per-draw metadata is needed.

**Adversarial gate.** Alternate two canvases with equal revisions but different commands; test clear/color changes, size/format changes, changed image keys, atlas growth, empty scenes, `commit()` without damage, and device/surface recreation. Assert a cache hit only for the same non-reused owner/revision tuple; compare full output byte-for-byte (or existing declared HDR tolerance). Count CPU command/tile visits, queue-upload bytes, bind-group creations, GPU submissions and target draws separately. A hit must retain one full target draw. A complete surface loss must rebuild device-owned resources and packet binding state.

### 2. Keep CPU CSR tile bins when both scene and requested tile window are unchanged

`Canvas::render_output` visits every command twice to rebuild the tile CSR each render: count references, prefix-sum, then fill indices (`crates/canvas/src/canvas.rs:1341-1386`). It already retains `offsets`, `indices`, and `cursor` capacity on Canvas; the current code overwrites their contents every time.

**Candidate.** Reuse those same arrays when `(visual_revision, tile_bounds)` is unchanged; add only the cached key, not a second bin table. Changed commands or a changed tile window rebuild by the current correct path. The key must include the actual bounded damage tile rectangle: storing whole-window bins would increase the retained index footprint for callers that commonly render small damaged regions. This saves two command/tile-visitation passes only on exact repeated requests; it does not skip pixel writes and does not help when each frame changes its damage bounds.

**Gate.** Repeat full and identical regional renders with fixed scenes; assert unchanged output, identical painter-order indices, zero `visit_tiles` calls on the hit, and unchanged vector capacities. Then mutate, insert, remove, reorder, resize, and move draws across tile boundaries; require fallback rebuild and compare against a fresh Canvas. Measure full-window and small-moving-region hit rates before retaining the key.

### 3. Test small sample-lane batches to amortize shader draw loads

The GPU fragment shader evaluates a 4×4 sample lattice. Each sample walks the tile’s CSR list, loads a draw record, samples it, and source-over blends in painter order (`crates/gpu/src/shader.rs:350-380`). An inline draw needs six `vec4u` storage words; a compact placement loads its local pair plus shared group words (`shader.rs:37-62`). This is an obvious repeated-read candidate, but the compiler may already hoist invariant reads, so source inspection alone does not establish an opportunity.

**Candidate.** Compare the current sample-major loop with a 2-sample or 4-sample lane batch: move the command cursor outside a small group of independent sample lanes, load the index/draw once, and shade/blend that draw into each lane’s own color. Keep each lane’s draw order unchanged and reduce terminal sample colors in the existing order. Do not batch all sixteen by default: that holds at least sixteen accumulated `vec4` colors plus positions and temporary source colors live, risking register spills and occupancy loss.

**Gate.** First inspect the backend shader IR/assembly and hardware counters to establish whether draw/CSR loads are duplicated. Then compare 2- and 4-lane variants on Apple/Metal, D3D12, Vulkan, and software fallback where available. Require exact equality for the same GPU arithmetic path, or the existing explicit tolerance if shader compiler scheduling changes arithmetic; never relax the CPU-reference pixel contract silently. Include empty/one-draw, deep overlapping translucent stacks, image/glyph-heavy tiles, dense tiles near the reference cap, HDR large-magnitude colors, and sparse edge pixels. Record registers, spills, occupancy, storage transactions, p50/p95 GPU duration, and shader compile size. Reject if savings appear only in isolated draw-fetch microbenchmarks or dense overlap spills.

### 4. Remove repeated sRGB `pow` for the narrow byte-image case

The CPU image path already has an exact 256-entry table of `f32` bit patterns (`crates/canvas/src/image/transfer.rs`, verified exhaustively by `image.rs`); GPU `image_texel` instead normalizes byte channels and calls `pow(x, 2.4)` per encoded texel (`crates/gpu/src/shader.rs:137-169`). Linear filtering fetches four texels for each of sixteen coverage samples (`shader.rs:285-306`). GPU images are packed raw into the existing `WORDS` buffer, and stable image keys already skip image payload uploads (`crates/gpu/src/renderer/images.rs:52-171`).

**Candidate.** Prototype a renderer-owned, active-image-only transfer table using the existing storage binding/buffer, not a new per-node/per-image payload. For straight-alpha 8-bit sRGB (and separately validated Display-P3 transfer channels), use the raw channel byte as the table index, then multiply decoded linear RGB by alpha as today. The table is 256×4 = 1,024 bytes per active renderer; build/upload it only when an encoded straight-alpha image first appears, and omit it for linear float images. Since `Globals.mapping` only consumes `.x` for exposure (`shader.rs:335-348`), an aligned integer bitcast of `.y` could carry its word base without growing the 48-byte uniform; alternatively choose a generated constant table and explicitly measure shader-code/compile cost. Preserve the `pow` path for encoded premultiplied inputs: their required operation is unpremultiply-in-encoded-space then decode, so indexing the original byte is mathematically wrong. Do not build a 65,536-entry channel/alpha table by default; its 256 KiB per renderer is an unjustified floor until measured.

An sRGB hardware texture is a second experiment, not an automatic replacement. It can avoid shader transfer work and may filter in linear light, but correct bilinear semantics require premultiplied-linear interpolation. Straight nonopaque texels must be premultiplied before filtering; encoded-premultiplied bytes must be unpremultiplied before decode. A direct sRGB texture is therefore initially eligible only for proven opaque byte images (all alpha 255), with a per-image texture/allocation and format/binding budget. Existing packed storage path remains the fallback for P3, nonopaque, premultiplied, linear-HDR, unsupported texture limits, and device loss.

**Gate.** Exhaustively compare all 256 table entries with `SRGB_BYTE`; test alpha 0/1/254/255, hidden RGB under zero alpha, all profiles and alpha modes, nearest and bilinear edge clamp, image-key replacement, and source-over overlaps. Compare complete rendered pixels to the Canvas oracle; record image memory, table upload, texture creation, shader work and setup latency for 1 KiB, 64 KiB, and multi-MiB resources. Reject if tiny/one-frame images do not repay setup, or if any format uses the fast path outside its proved domain.

### 5. Treat sparse strips and analytic coverage as a separate, constrained experiment

Vello’s pinned architecture (`645991d1c2860e73c7489fa428a8ae2f72d2622c`, 2026-09-14) describes `vello_cpu` and `vello_gpu` as CPU-preprocessed Sparse Strips renderers: paths are flattened and binned into tiles; sparse horizontal strips retain coverage near boundaries and compact fully covered spans. `vello_gpu` uses vertex/fragment rendering and does not require compute. The experimental compute renderer is a separate family. This corrects older summaries that describe all Vello as compute-only. Its primary source is the [pinned architecture document](https://github.com/linebender/vello/blob/645991d1c2860e73c7489fa428a8ae2f72d2622c/ARCHITECTURE.md), plus the pinned [strip representation](https://github.com/linebender/vello/blob/645991d1c2860e73c7489fa428a8ae2f72d2622c/vello_common/src/strip.rs) and [GPU scheduler](https://github.com/linebender/vello/blob/645991d1c2860e73c7489fa428a8ae2f72d2622c/vello_gpu/src/schedule/mod.rs).

PR [#1759](https://github.com/linebender/vello/pull/1759), merged 2026-07-24 at `c33438626fbd307bdc7b158566c028d16355b1d7`, rewrote Vello Hybrid’s core scheduling/rendering. The release notes call out removal of coarse rasterization, bottom-up/lazy image and filter texture allocation, better filter/layer memory, and clips that can exceed the root viewport. This is useful evidence for delaying optional resources and controlling intermediate lifetimes; it does not show that importing strips removes GPUI’s separate presentation-damage or scene-coherence costs. See the [PR merge commit](https://github.com/linebender/vello/commit/c33438626fbd307bdc7b158566c028d16355b1d7) and [release notes](https://github.com/linebender/vello/releases).

GPUI already applies the optional-resource floor locally: `Renderer::new` starts with a 1×1 glyph-mask atlas and `images: None`, and `prepare_atlas` grows the atlas only when masks are present (`renderer.rs:356,805-835`; image preparation is in `renderer/images.rs`). Thus the Vello lesson here is to preserve this floor when adding new paths; no extra lazy-resource memory win is claimed for this code.

GPUI currently preserves 4×4 per-draw sample membership and blends each sample independently before resolving (`shader.rs:362-380`; CPU `Samples` and `render_band` in `crates/canvas/src/canvas.rs`). A scalar per-shape coverage value cannot generally replace that: two overlapping translucent shapes with complementary subpixel masks have different results from identical scalar coverages with coincident masks. Sparse strips could fit as a tile-local representation derived from the existing command stream—full-coverage runs plus exact 16-bit sample masks at boundaries—without retaining a second scene tree. But a `u16` per boundary pixel per path plus strip descriptors/worklists can cost more than current tile references, and glyph/image inputs are not binary geometric masks. Retain painter order and 16 sample lanes through blending; skip this for v1 unless counters show path-boundary work dominates.

The [Correlation-Aware Semi-Analytic Visibility paper](https://research.nvidia.com/sites/default/files/pubs/2018-08_Correlation-Aware-Semi-Analytic-Visibility/CorrelationAwareVisibility_AuthorsVersion.pdf) is relevant because it explicitly maintains coverage correlation while merging fragments. It targets visibility/depth representations rather than GPUI’s 2D source-over pipeline; adaptation is research, not a drop-in scalar coverage shortcut. The Vello [Sparse Strips tracking issue #670](https://github.com/linebender/vello/issues/670) is a primary design record, but its initial prototype explicitly deferred clipping and blending capability. Use it to bound the design question, not as evidence of compatibility or speed.

Signed/multi-channel distance fields and Loop–Blinn implicit curves also do not replace the present sample model globally. They change edge/coverage approximation and do not by themselves solve arbitrary fill winding, self-intersections, clips, hinted small text, or correlated translucent overlap. They may serve an opt-in icon or large-glyph path with declared tolerance and exact fallback. Relevant primary sources are [Loop & Blinn (2005)](https://www.microsoft.com/en-us/research/wp-content/uploads/2005/01/p1000-loop.pdf) and the [MSDF thesis](https://media.mcfarlaneaviation.com/documents/documents/f8-dp-2015-chlumsky-viktor-thesis.pdf); neither establishes compatibility with this renderer’s color/coverage contract.

## Image-axis follow-up review

The isolated `d4d9293f58` change factors image selection into an `#[inline(never)] render_image_command` helper and leaves the image-only axis-aligned sampler in `crates/canvas/src/canvas/image_axis.rs`. Its sampler precomputes separable X/Y taps per 16×16 tile and reuses two row caches while preserving the 16 sample sources and blend order. The commit message reports a 732-byte smaller linked common render body and restored baseline stack reservation; that is a code-size/stack-layout observation, not a whole-frame timing result. The code retains bounded tile-local tap arrays and a short two-row texel cache, has no retained decoded image, and uses `ImageView` borrows. Non-axis-aligned images continue through the generic path; P3/premultiplied inputs still use exact-index memoization. The source uses the same ratio-first normalization and edge clamp as `ImageView::sample_with`.

The useful general lesson is to isolate rare, high-state paths from the common loop before growing its live ranges. Any follow-up must keep the helper out-of-line only if generated code and call overhead win on actual image workloads; compare aligned and rotated images, nearest/linear modes, 1×1 and large textures, cache-hit and cold decode cases, and the no-image baseline. Preserve the oracle’s byte/alpha/profile/edge/transform matrix; do not infer a memory win from stack reservation alone.

## Priority and acceptance order

1. **Exact unchanged-packet reuse**: highest likely whole-frame work removal with no duplicate command tree. First establish that a stable revision is available without a new O(N) scan; retain full draw/submit for every newly acquired target.
2. **CPU bin reuse for an identical `(revision, tile_bounds)`**: small metadata-only change using current retained arrays; conservative fallback on every mismatch.
3. **Shader two-lane experiment**: only after actual backend code shows duplicated draw loads; stop if register/occupancy metrics regress.
4. **Straight-byte transfer lookup**: 1 KiB active-only shared table; retain the generic path for all channels that require unpremultiplication before decode.
5. **Sparse strips / SDF / analytic paths**: defer until profiling says path-edge work, rather than scene preparation, upload, or image sampling, dominates. Scope first to admitted primitive classes with explicit fallback.

For every candidate, report CPU visits, allocations/capacities, upload bytes, GPU allocations, command/submission counts, shader register/spill metrics, and p50/p95/p99 frame stages independently. Keep the CPU reference and exact 4×4 sample/painter order as the acceptance oracle. Run ordinary and HDR/wide-gamut targets, CPU fallback, WebGL2/Vulkan/Metal/D3D paths where available. A target-specific fast path must fall back cleanly when capability or memory limits are missing; it cannot turn platform-specific support into an application contract.
