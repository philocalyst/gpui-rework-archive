# Graphics work elimination: source audit and next experiment

**Audit date:** 2026-10-22  
**Source:** `/root/gpui-ce3/reactivity`, `codex/reactivity-cleanroom`, `0f0462c62e282c498b457eb8c3e7644ed90954a4`  
**Scope:** read-only adversarial research. No production files changed and no build or timing run was started; existing Sol builds were left undisturbed.

## Finding

The typed-WGSL build step eliminated typed Rust shader-string construction. It did not eliminate WGPU’s runtime shader front end, validator, backend translator, native driver compilation, or per-renderer GPU objects. Those are distinct stages and require different remedies.

The strongest *portable and safe* next implementation is an explicit device-owner `GpuContext` with per-window mutable renderer state borrowed at method calls. It removes duplicate device/module/pipeline/layout construction when several windows can use one compatible device, while retaining the current checked WGSL path. It does **not** reduce the first window’s work. The strongest *first-window* experiment is a target-specific precompiled artifact passed through WGPU’s unsafe passthrough API, initially Vulkan only, with an explicit binding layout and generated-in bounds/loop checks. It can remove WGPU/Naga parsing, validation, and backend translation, but not device creation, resource creation, or device-specific pipeline creation. It is a narrow optional path, not a replacement for WGSL or software fallback.

There is no single portable WGPU artifact that removes all first-window frontend, validation, compiler, driver, and resource work. The only public WGPU path that bypasses shader tooling is deliberately unsafe and backend-specific. A Vulkan driver pipeline cache can reduce later pipeline compilation on a matching driver/device, but it does not solve cold first-window shader work.

## What the current source actually does

The repository builds the same typed source into `ui.wgsl`, validates it at build time, and includes its 15,180-byte artifact at runtime. See [build.rs](/root/gpui-ce3/reactivity/crates/gpu/build.rs:5), [renderer.rs](/root/gpui-ce3/reactivity/crates/gpu/src/renderer.rs:14), and [the typed shader bindings](/root/gpui-ce3/reactivity/crates/gpu/src/shader.rs:28). The build evidence states the artifact is byte-identical to runtime generation and that the existing WGPU path still validates it for the actual backend: [wgsl-buildtime evidence](/root/gpui-ce3/reactivity/evidence/wgsl-buildtime/README.md).

`Renderer::request` requests a device with `DeviceDescriptor::default()` and then constructs the renderer. `Renderer::new` calls safe `create_shader_module(Wgsl(...))`, creates a render pipeline with `layout: None` and `cache: None`, obtains an inferred bind-group layout, and eagerly creates five buffers plus a 1×1 atlas. The raw initial buffer sizes sum to 108 bytes (48+16+8+4+32); that is an arithmetic sum of requested buffer sizes, **not** a claim about driver allocations, alignment, or resident GPU memory. See [renderer creation](/root/gpui-ce3/reactivity/crates/gpu/src/renderer.rs:355).

WGPU 30.0.1’s core source separates the runtime work clearly: WGSL is parsed by Naga, then validated with all validation flags, then reflected into a WGPU `Interface`, then passed to HAL as Naga IR. `ShaderSource::Naga` skips only WGSL parsing; the validator and interface construction still run. The matching pinned source is [`wgpu-core` shader-module creation](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/device/resource.rs#L2363-L2493) and the [`ShaderSource` variants](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/api/shader_module.rs#L173-L215). The public API also warns that normal shader-module creation can consume substantial stack space: [`Device::create_shader_module`](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/api/device.rs#L124-L143).

`create_shader_module_trusted` does **not** skip that parser or validator. It changes `ShaderRuntimeChecks` used by later backend code generation. The default public `create_shader_module` uses `checked()`; the unsafe trusted call allows choices such as omitting bounds guards. This distinction is explicit in the [pinned WGPU API](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/api/device.rs#L165-L187) and [`ShaderRuntimeChecks`](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/shader.rs#L6-L97). It is not a frontend speed switch.

The later backend work is not one uniform stage:

- **Vulkan:** ordinary Naga input is translated to SPIR-V when the HAL shader module is created; pipeline stage creation can also run Naga’s SPIR-V writer for the intermediate path. Raw SPIR-V passthrough avoids those Naga writes but still calls the Vulkan shader-module and pipeline APIs. See the pinned [Vulkan HAL module and stage paths](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/vulkan/device.rs#L699-L803) and local [HAL seams](/root/gpui-ce3/reactivity/vendor/wgpu-hal/src/vulkan/device.rs:1855).
- **Metal:** ordinary Naga IR is kept in the HAL shader module. Pipeline creation writes MSL, then calls `MTLDevice::newLibraryWithSource`; a `metallib` path loads a library object but still must create the render pipeline. See [Metal HAL source](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/metal/device.rs#L169-L310) and the local [module input branch](/root/gpui-ce3/reactivity/vendor/wgpu-hal/src/metal/device.rs:1268).
- **DX12:** ordinary Naga IR is translated to HLSL at pipeline creation and passed to the selected DXC/FXC compiler path. HLSL passthrough still invokes a compiler; DXIL passthrough skips that compiler but not D3D12 pipeline creation. See [DX12 HAL shader translation](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/dx12/device.rs#L279-L427) and the local [DXIL branch](/root/gpui-ce3/reactivity/vendor/wgpu-hal/src/dx12/device.rs:397).
- **GLES:** ordinary Naga input is translated to GLSL, then the GL driver compiles and links it. The public WGPU `PASSTHROUGH_SHADERS` feature documentation does not list GLES, even though the lower HAL has a GLSL source branch; keep GLES on the normal WGSL path. See [GLES HAL compile path](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/gles/device.rs#L292-L360) and [feature support contract](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/features.rs#L1345-L1360).
- **Browser WebGPU:** WGPU’s passthrough wrapper accepts only WGSL for the browser path and forwards it to the browser’s `createShaderModule`, so this does not skip browser compilation. See [WGPU’s WebGPU backend](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/backend/webgpu.rs#L2038-L2076).

A pipeline retains its shader modules in WGPU core, so inferred interface metadata and backend module state can remain reachable for the pipeline lifetime. The source is in [`pipeline.rs`](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/pipeline.rs#L912-L930). A shared pipeline/context can therefore remove repeated retained module and layout objects as well as repeated constructor calls; exact bytes are not measured.

`create_shader_module_passthrough` is the only public WGPU route here that bypasses shader parsing, WGPU/Naga validation, and Naga backend translation. It is explicitly unsafe, warns that malformed data can crash the driver or behave incorrectly, and records entry-point names rather than a reflected resource interface. See the [pinned API](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/api/device.rs#L190-L203), [core passthrough path](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/device/resource.rs#L2499-L2595), and [feature contract](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/features.rs#L1345-L1360). With passthrough, `layout: None` cannot be relied on: pipeline auto-layout needs reflection, but passthrough metadata contains only entry-point names. The renderer must provide an explicit `BindGroupLayout` and `PipelineLayout`; the core’s implicit-layout error path is [here](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/device/resource.rs#L4861-L4894).

## Quantified evidence versus deductions

The existing frozen external-renderer evidence reports that build-time typed WGSL removes **5,680 current-thread Rust allocations and 551,643 requested bytes per renderer construction**. The ordinary external binary shrank by **919,792 bytes**, while its rlib grew by 28,952 bytes because the public generator API remains. The same fixture reports **7,892 allocations / 2.19 MB requested** for an artifact-backed `Renderer::new` call and about **86 ms on llvmpipe**. Its device setup is outside the timing; these are not whole-process startup, physical-GPU, Apple, Windows, or native-application results. The timing deltas are small and noisy, so the evidence itself rejects an end-to-end startup claim. Details and capture controls are in [the evidence README](/root/gpui-ce3/reactivity/evidence/wgsl-buildtime/README.md).

The following are source/algebra deductions, not measured wins:

- `Renderer::request` requests a device for each renderer, but `Renderer::new` already accepts handles cloned from one device. The fair shared-device baseline therefore constructs `N` shader modules, pipelines, inferred layouts and per-window states on the same device. A shared context can remove the repeated module/pipeline/layout construction; each window's mutable buffers, atlas, image state, bind groups, packet and surface remain distinct. Device-request savings belong to a separate native pooling comparison. For one window (`N=1`), this does not remove first-window work.
- An explicit `GpuContext` does not remove `request_device` for the first device. It amortizes it for later compatible windows. The current fixture’s ~86 ms excludes that request, so it cannot tell us how much device sharing would remove.
- A precompiled Vulkan artifact can remove runtime WGSL parse, Naga validation/reflection, runtime SPIR-V writing, and transient source/module construction on its selected path. Driver `vkCreateShaderModule` and render-pipeline creation remain. Without a matching driver cache, the driver still does pipeline compilation.
- A full retained offscreen image costs `width × height × bytes_per_pixel`: 8,294,400 bytes for 1920×1080 RGBA8 and 33,177,600 bytes for 3840×2160 RGBA8, before allocation overhead. These are arithmetic counts, not measured resident GPU memory. A per-swap-image certificate/journal is O(buffer-count) CPU metadata and avoids that full image, but only when the acquired image contents are guaranteed coherent.

## Competing designs and rejection gates

### A. Borrowed, device-scoped `GpuContext` — safest next production slice

**Shape.** Keep the current simple owned entry point as an `OwnedRenderer { context: GpuContext, state: RendererState }` convenience. Split the current state so shared code looks conceptually like:

```rust
struct GpuContext {
    id: ContextId,
    device: wgpu::Device,
    queue: wgpu::Queue,
    layout: wgpu::BindGroupLayout,
    pipelines: FixedFormatSet<wgpu::RenderPipeline>,
}
struct RendererState {
    context_id: ContextId,
    format: wgpu::TextureFormat,
    // per-window buffers, atlas, image state, packet, vectors, counters
}
impl RendererState {
    fn render(&mut self, context: &GpuContext, scene: PreparedScene<'_>, ...);
}
```

The owner passes `&GpuContext` into each mutable window renderer method. `RendererState` stores a private context ID and checks it on entry, so a caller cannot accidentally bind another device’s buffers. The context itself owns one WGSL module and explicit BGL, plus one pipeline per actual output format. The format set is currently three (`Rgba8UnormSrgb`, `Bgra8UnormSrgb`, `Rgba16Float`); native setup currently chooses the first two. Each window keeps its buffers, atlas, image handles, packet/bind groups, and retained CPU vectors because they mutate independently. Pipeline layouts/BGLs can be shared; bind groups cannot.

Use direct `&GpuContext` parameters, not a generic context trait and not a self-referential renderer. The current `Renderer` has 21 direct device/queue/pipeline/layout access sites in the main file; this is a bounded plumbing refactor. A non-generic context parameter adds **no Rust generic monomorphization**. An `OwnedRenderer` wrapper can forward to the same non-generic state methods; avoid a generic `Renderer<C>` used for both owned and borrowed variants, which would duplicate hot method bodies for each concrete `C`. If implementation nevertheless uses a generic, compare linked `.text` and symbol size against the current external consumer; no generic size claim is made here.

**Lifecycle.** Construct lazily when the first GPU window on an adapter needs it; keep no process-global singleton. Reuse only for windows whose surfaces accept that adapter/device. Group separate devices/adapters separately. On device loss, invalidate every `RendererState` using that context generation and rebuild them with the new device; never carry old atlas keys or buffers. On the last window lease, drop the context so pipelines and device state do not stay resident. CPU fallback remains independent and should not construct the GPU context. `native.rs` currently keeps `Instance` and `Graphics` in each `NativeHost`, requests a surface-compatible adapter for each window, and recreates the renderer on recovery; an app-level owner is therefore required before native windows can share. See [native host fields](/root/gpui-ce3/reactivity/crates/gpui/src/native.rs:351), [adapter request and renderer creation](/root/gpui-ce3/reactivity/crates/gpui/src/native.rs:468), and [recovery comment](/root/gpui-ce3/reactivity/crates/gpui/src/native.rs:501).

**What it removes:** repeated `request_device`, shader module, per-format pipeline, implicit layout, and device-specific retained shader metadata for each additional compatible window. It preserves the exact checked WGSL compiler route and every per-window mutable resource. **What it does not remove:** any first-window setup cost or scene/frame work.

**Gate:** an external test creates two state objects against one device and one format. Count one device request, one shader module, one BGL/layout and one pipeline; two independent buffer/atlas/bind-group sets; both output images match the current Vulkan oracle. With two formats, expect one module/layout and exactly two pipelines. Drop either window and verify the other still renders; drop the last and verify all context resources retire; inject device loss/recovery and ensure no cross-generation state survives. If native integration cannot establish same-device surface compatibility for multiple windows, keep this as an explicit reusable library API and do not pool unrelated adapters. No performance claim until a quiet paired capture exists.

### B. Build-time Naga IR — safe, portable, but partial

WGPU’s `ShaderSource::Naga(Cow<'static, naga::Module>)` is behind `naga-ir`; it skips WGSL parsing but WGPU core still validates the module with all flags and builds interface metadata. A no-unsafe path can parse the already-generated WGSL at build time, serialize Naga IR, deserialize it at runtime, then pass `ShaderSource::Naga`. It retains WGPU validation, backend writers, native driver compilation, and pipeline validation.

The artifact format matters. `ShaderSource::Naga` requires an actual Rust `naga::Module`, not bytes. A serialized module adds a runtime deserializer and allocations; a generated Rust literal/builder avoids deserialization but can expand host compile work and linked code. Naga `ModuleInfo` is recomputed by WGPU validation; it is not a public artifact input. Either way, static data generation is nontrivial and no allocation reduction follows from the API alone.

**Gate:** measure WGSL parse and `String` allocation separately from Naga validation and HAL work; compare a generated-IR path that preserves checked validation. Reject if deserialization/IR construction plus retained module memory erases the parse savings, or if first `Renderer::new` allocations/time improve by less than an agreed threshold (suggested initial threshold: 15% requested bytes and 10% median module+pipeline CPU time). This is the safe portability control experiment, not the full-elimination candidate.

### C. Build-time native artifact bundle + explicit layout + passthrough — strongest first-window candidate, narrowest contract

The typed `shader.rs` remains the one source. Build-time generation consumes the exact `ui.wgsl` output and emits per-target artifacts: SPIR-V for Vulkan; DXIL (not merely HLSL) for DX12 if avoiding runtime DXC; MetalLib (not merely MSL) for Metal if avoiding runtime `newLibraryWithSource`; and WGSL always for browser/GLES/unsupported-device fallback. WGPU’s descriptor has these backend-specific artifact fields. `PASSTHROUGH_SHADERS` must be requested only when the selected adapter advertises it; the existing default device descriptor requests no optional feature. Any unsupported backend or missing artifact uses the present checked WGSL route.

This route must explicitly create the six-binding layout from the typed shader’s interface. The source declares group 0 binding 0 uniform Globals; 1, 2, 3, and 5 read-only storage arrays; 4 a 2D float texture. All current resources are fragment-used. Keep a generation/test asserting this manifest against Naga reflection, since WGPU’s passthrough metadata cannot reflect them. Pass the explicit pipeline layout instead of `None`.

**Safety is part of the artifact.** Passthrough sets runtime checks to unchecked. The current fragment shader contains dynamic indexes into `WORDS`, `TILES`, `INDICES`, `CORRECTIONS`, and `MASKS`; a dynamic `range.x..range.y` loop; and vertex `POINTS[vertex_index]` ([shader source](/root/gpui-ce3/reactivity/crates/gpu/src/shader.rs:37), [fragment indexing/loop](/root/gpui-ce3/reactivity/crates/gpu/src/shader.rs:460)). A conservative offline artifact can explicitly use `Restrict` for index/buffer/image-load/binding-array operations, enable loop and integer-division guards, and preserve workgroup initialization. This is **not byte-equivalent to every checked WGPU runtime artifact**: the Vulkan adapter sets index checks to `Restrict`, chooses buffer/image checks from its enabled hardware robustness, and leaves binding-array checks unchecked. See the [actual adapter policy](/root/gpui-ce3/reactivity/vendor/wgpu-hal/src/vulkan/adapter.rs:2838). Additional software guards can therefore add frame work on a robust device. Any less-guarded artifact requires a positive device capability contract and a separate proof that the hardware protection is enabled. Naga’s own bounds-policy defaults are `Unchecked`; see [`BoundsCheckPolicies` and its policy definition](https://github.com/gfx-rs/wgpu/blob/v30.0.1/naga/src/proc/index.rs#L35-L110). Do not call the raw writer with defaults and assume build-time Naga validation inserts runtime guards: validation and guard code generation are separate operations.

In addition, retain host admission limits and prove: CSR ranges are monotone and end within `INDICES`; each index selects a serialized draw; tag/bank word offsets stay inside `WORDS`; correction and atlas coordinates stay within their allocated arrays/texture; the fragment tile formula stays within `TILES` for all in-target fragments; the vertex index is only 0, 1, 2 for the fullscreen draw; and integer arithmetic cannot wrap those addresses. WGPU’s checked route currently provides runtime protection even if a host invariant later regresses. For passthrough, the bounds guard must be in the generated artifact or another explicit proof-enforcing mechanism.

**Backend cost and portability.** SPIR-V is a realistic first target because Naga already emits it and Vulkan is the only backend with WGPU `PipelineCache`. Vulkan driver shader/pipeline compilation remains. DXIL requires a pinned DXC toolchain and a shader model supported by target adapters; HLSL source still runs the runtime DXC/FXC path. A MetalLib requires a Metal compiler toolchain/SDK and an artifact compatible with deployment targets; MSL text still goes through runtime `newLibraryWithSource`. There is no portable GLES binary path in WGPU’s advertised feature contract, and browser WebGPU still consumes WGSL. Thus a complete bundle increases per-target package bytes and build/release matrix cost; no artifact sizes or build-time deltas have been measured. Keeping WGSL fallback means Naga/WGPU fallback code remains linked, so do not expect the 920 KB ordinary-binary shrink from typed source generation to repeat here.

**Gate:** begin as a Vulkan-only spike behind a feature/capability branch, not as default. Require runtime codegen checks reproduced in emitted SPIR-V; explicit interface/layout generation; Naga validation plus SPIR-V validation; exact pixels against the checked WGSL renderer over all existing 40 Vulkan oracle cases and boundary stress for max dimensions/draws/atlas/indices; feature-missing and artifact-error fallback; device-loss and cold-driver tests. Instrument parse, validator, Naga writer, Vulkan module creation, and pipeline creation separately. Suggested production threshold: at least 20% lower requested runtime bytes and 10% lower first renderer construction CPU time on a real supported Vulkan target, with no pixel/limit regressions; llvmpipe-only results can qualify only as a software-driver observation. Reject or keep experimental if driver pipeline creation dominates or if robust checks/layout cannot be held in lockstep with the typed source. No such spike was built in this audit.

### D. Persisted WGPU `PipelineCache` — useful only after a matching first run

WGPU 30.0.1 says pipeline caches accelerate pipeline creation on later executions, but the implementation works only on Vulkan; their useful output must be persisted for the same/similar device, the data is opaque, writing should be atomic, and there is no cache-size reduction API. Creation of a cache from data is unsafe and should be keyed to the WGPU/driver/device identity. See the [versioned `PipelineCache` API](https://docs.rs/wgpu/30.0.1/wgpu/struct.PipelineCache.html), [cache creation contract](https://docs.rs/wgpu/30.0.1/wgpu/struct.Device.html#method.create_pipeline_cache), and current renderer’s [`cache: None`](/root/gpui-ce3/reactivity/crates/gpu/src/renderer.rs:387).

It does not skip WGSL parsing, Naga validation, or Vulkan shader-module creation. A cold install still compiles. A pre-shipped cache cannot be treated as portable across vendors or driver updates; corrupt, stale, or incompatible data must fall back to no cache. This is a warm-start competitor, not first-window work elimination.

**Gate:** compare cold-cache and warm-cache restarts separately on the same Vulkan adapter+driver, test cache invalidation after app shader/pipeline version changes, corrupt/truncated file fallback, atomic replacement, storage growth, and device loss. Reject as a general solution if only warm starts improve or if file/driver identity cannot be managed.

## Secondary frame-work formulation: damage repair only with an acquired-image certificate

The existing GPU packet replay is already a meaningful elimination: it skips command/resource validation, binning, uploads, and bind-group creation. It still full-clears and draws the full target ([redraw contract](/root/gpui-ce3/reactivity/crates/gpu/src/renderer.rs:853), [full-target submission](/root/gpui-ce3/reactivity/crates/gpu/src/renderer.rs:890)). The retained vectors, atlas, image bindings, and packet are per-window; source evidence does not identify a removable “grouped packet reconstruction” in same-token replay, so I do not recommend changing it on speculation.

The runtime already has a compact surface damage journal: three 8-byte rectangles plus a `known` byte, measured as 26 bytes by its test; it tracks successful presentations and refuses stale/unknown buffer ages. See [SurfaceDamage](/root/gpui-ce3/reactivity/crates/gpui/src/runtime.rs:713) and [the size assertion and buffer-age oracle](/root/gpui-ce3/reactivity/crates/gpui/src/runtime.rs:3315). Software surfaces pass buffer age into that journal and repair just the accumulated region. The GPU surface exposes no comparable age/identity: public `wgpu::SurfaceTexture` contains a texture and private presentation detail, while WGPU core surface acquisition returns status plus a logical texture ID only. That logical texture ID is insufficient: Vulkan HAL knows the acquired image index but assigns a **fresh texture identity on every acquire**; DX12 similarly computes an image index internally; neither is exposed as a stable backing-image token.

The contracts are backend-specific:

- **Vulkan is a positive gate.** The Vulkan spec says presentation is read-only and that reacquiring an image and transitioning it from `PRESENT_SRC_KHR` preserves its pre-present contents. It also says contents become undefined if something other than Vulkan modifies the associated platform window. See the [Vulkan reference page](https://registry.khronos.org/vulkan/specs/latest/man/html/vkQueuePresentKHR.html). A WGPU/HAL-issued `{surface_generation, image_index, contents_preserved}` token could support an opt-in Vulkan experiment; any resize/reconfigure/loss/external-window modification invalidates all certificates.
- **DX12 currently disproves unconditional reuse.** The pinned local HAL hardcodes `DXGI_SWAP_EFFECT_FLIP_DISCARD` independently of `PresentMode` ([local source](/root/gpui-ce3/reactivity/vendor/wgpu-hal/src/dx12/mod.rs:1538)). Microsoft says FLIP_DISCARD discards contents and offers no persistence guarantee; FLIP_SEQUENTIAL persists the back buffer across Present calls ([primary enum documentation](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect)). A distinct opt-in flip-sequential surface mode is a plausible future experiment, separate from FIFO/tearing schedule. WGPU currently has no surface-config field for swap effect, so this needs WGPU core → HAL plumbing (or a maintained fork) and an exposed image index/generation. D3D12 only supports flip-sequential or flip-discard; surface creation failure must fall back to current discard+full redraw. Do not change the default or assume a speed gain. No `Present1` dirty-rect path exists in GPUI today.
- **Metal remains Unknown.** HAL holds a `CAMetalDrawable` from `nextDrawable`, but Apple’s drawable-pool/lifetime documentation does not promise preservation or a usable content-age contract. A drawable ID, where available, would identify a drawable but would not by itself prove its pixels are valid. Keep full redraw unless Apple’s contract and platform tests establish retention.
- **GLES/WebGPU remain Unknown/fallback.** Neither WGPU’s public acquisition API nor the audited HAL contract gives GPUI a portable buffer age. Keep full redraw.

A Vulkan-only experiment can reuse the existing 26-byte journal plus a small per-image last-present/generation certificate (fixed-capacity state if swapchain count is exposed), rather than allocating an extra full window image. The current `DamageRegion` is one bounding rectangle, which can overdraw but is conservative. To exploit it, GPU submission must use `LoadOp::Load` and scissor the redraw, or skip the draw entirely for an unchanged image; both require the same acknowledged presentation authority and full fallback on an unknown age. Gate it on byte-exact parity for stale ages/resize/occlusion/device loss, an actual Vulkan `image_index` exposed by HAL, successful-present-only history advancement, and a measured no-change-frame reduction. The Windows flip-sequential option and Vulkan-only token path belong after the main first-window/context experiments.

## Prior art that changes the formulation, not just a tuning knob

- **egui-wgpu 0.36.2** gives its integration a device-owned render state and its custom WGPU example uses `Wgsl(include_str!)`, an explicit bind-group layout, an explicit pipeline layout, and a pipeline stored in callback resources. That is a useful pattern for the `GpuContext` owner and the artifact manifest; it still calls normal `create_shader_module`/`create_render_pipeline` and therefore does not remove shader frontend work. [Pinned source](https://github.com/emilk/egui/blob/0.36.2/crates/egui_demo_app/src/apps/custom3d_wgpu.rs).
- **Bevy 0.17.2** models pipelines as Queued/Creating/Ok/Err and can schedule creation asynchronously on supported builds. That can move work away from the presenting thread; it does not eliminate it. Its optional `ValidateShader::Disabled` path is explicitly unsafe and cites out-of-bounds indexing, so it is not an acceptable frontend speed claim for this renderer. [Pinned pipeline cache source](https://github.com/bevyengine/bevy/blob/v0.17.2/crates/bevy_render/src/render_resource/pipeline_cache.rs).
- **Vello’s sparse-strips family** shares CPU geometry/tiling preprocessing and consumes sparse strip data on CPU or WGPU/WebGL fragment backends; a separate compute renderer remains experimental. This is a serious *recurring frame/representation* direction when scenes are sparse. It does not remove device/shader startup, and replacing this repository’s rounded-rect/glyph-mask path requires visual/per-workload evidence. [Pinned architecture snapshot used by the project research](https://github.com/linebender/vello/blob/7d70631ac848925972c85171dc064a803003f796/ARCHITECTURE.md).
- **Piet** is a drawing API over CoreGraphics, Direct2D, Cairo, and other native systems rather than a portable GPU shader layer. It could eliminate WGPU/Naga from a renderer lane, but would hand output semantics to different system rasterizers and would not make the current linear-light/HDR/glyph behavior equivalent automatically. It is a different product/rendering contract, not a small optimization. [Project README](https://github.com/linebender/piet).
- **Slint** keeps renderer selection and software fallback explicit and has moved its FemtoVG WGPU path to WGPU 30/WebGPU with a WebGL fallback while also adding an experimental Vello renderer. This reinforces that backend variants/fallbacks remain real product paths; it is not evidence that backend artifacts skip device compilation. [WGPU/Vello release note](https://github.com/slint-ui/slint/blob/v1.18.0/CHANGELOG.md) and [backend matrix](https://github.com/slint-ui/slint/blob/v1.18.0/docs/astro/src/content/docs/guide/backends-and-renderers/backend_winit.md).

## Smallest recommended next Sol slice

1. **Implement the safe ownership seam first:** extract `GpuContext` and `RendererState`, keep an owned convenience renderer, pass `&GpuContext` into state methods, make layout/pipelines device-owned and format-indexed, and leave atlas/buffers/packet/images per window. Preserve checked WGSL and the CPU fallback. Add the two-window same-device identity/resource/lifecycle gate above. Do not add a process-global cache or context generic.
2. **Run a separate, bounded Vulkan first-window spike:** at build time generate SPIR-V from the exact typed WGSL via Naga 30.0.1; generate/lock an explicit binding layout; use `PASSTHROUGH_SHADERS` only if the adapter supports it; bake the same Naga bounds and loop guards; otherwise use the existing WGSL code. Instrument WGPU source spans (`naga::front::wgsl::parse`, `naga::validate`, `naga::spv::write_vec`) separately from Vulkan object/pipeline creation. Compare first module/pipeline and total `Renderer::new` allocations/time under fixed controls; keep the artifact path experimental unless it passes the correctness and threshold gates.
3. **Do not fold pipeline cache or damage repair into this slice.** Pipeline cache is warm Vulkan-only. Damage repair needs new public acquisition metadata, positive preservation contracts, and a platform-specific opt-in.

This sequence separates repeat-window amortization from first-window compiler work and gives the highest-work-elimination candidate a proof boundary before it can affect production rendering.

## Implementation disposition, 2026-10-22

The safe ownership spike is in progress after integration of portable presenter
admission. Actual renderers keep one format for their lifetime, so its first
candidate uses a single-format context and no pipeline map. Distinct formats
use distinct contexts; a future multi-format owner requires its own evidence.
The existing owned renderer will forward to the same per-window implementation.
Context generation checks must reject a mismatched state before GPU writes;
arbitrary foreign-device texture views retain the existing checked-WGPU target
precondition unless an independently reviewed identity boundary replaces it.
All header, wrapper, resource and construction costs must be measured against
the existing same-device baseline. No context implementation or performance
result is established by this research report.
