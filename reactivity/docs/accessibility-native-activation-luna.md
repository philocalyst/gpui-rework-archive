# Linux native accessibility activation and worker floor

Source snapshot: cleanroom GPUI `724ece73cb665a1f6d83e97ae7d431eee11a887a`; frozen `empty-x11` binary SHA-256 `b27b609d79e5f0dc9d5fc5fac5c69f25fcd6a510f4ba026eee9046adba4764cb`; `empty.rs` fixture SHA-256 `419d6b422a034f213419cda3f09f794b5ac0d76320cdaa42d5e1f26b42044da8`. This is a source and one-sample runtime attribution note. It is not a competitive timing result and does not recommend disabling accessibility.

## What the pinned adapter starts

GPUI's Linux `x11` feature includes `x11-minimal` plus `accessibility`; the latter enables `accesskit` and `accesskit_winit`. The pinned `accesskit_winit 0.34.1` dependency disables its defaults and selects `accesskit_unix` plus `async-io`. The resolved graph pins `accesskit 0.25.1`, `accesskit_unix 0.24.0`, `zbus 5.19.0`, and `async-io 2.6.0` in the `724ece73` lockfile.

In `accesskit_unix 0.24.0`, `APP_CONTEXT` and `MESSAGES` are process-global `OnceLock`s (`src/context.rs:33-34`), so the D-Bus service and receiver are shared among windows. The first `Adapter::new` invokes `get_or_init_messages` (`src/adapter.rs:129-155`), which starts one unnamed Rust thread and creates one executor (`src/context.rs:47-74`). Each window still owns an adapter and state mutex; it does not create a second process monitor thread. The six-adapter probe already stored in [`luna-accessibility-floor`](../benchmarks/luna-accessibility-floor/README.md) observed the same four tasks after one adapter and six adapters. That probe's synthetic status owner had no AT-SPI bus and no screen reader.

That one thread is not the only helper. AccessKit builds the session connection with `internal_executor(false)` and ticks `session_bus.executor()` from its own event loop (`context.rs:55-61, 169-210`); zbus documents that this suppresses its own executor thread but requires the caller to keep ticking the executor ([zbus 5.19.0 `Connection::executor`](https://docs.rs/zbus/5.19.0/zbus/connection/struct.Connection.html)). The selected `async-io` backend starts a process-wide thread named `async-io` when I/O is first used. Its 2.6.0 docs say that thread is a fallback reactor and explicitly say `reactor_fd()` does not stop it ([async-io 2.6.0](https://docs.rs/async-io/2.6.0/async_io/)). The default profile therefore has an adapter manager and I/O reactor even when no accessibility service is registered.

The event loop observes `org.a11y.Status.IsEnabled` before handling messages. For each property change it reads the current value, creates or drops the separate AT-SPI bus, and activates or deactivates all registered adapters (`context.rs:142-210`). A new adapter is immediately activated if that bus is already active (`context.rs:213-239`). This handles late window creation and true → false → true transitions **while the status service and initialized property cache remain available**. It does not detect `org.a11y.Bus` appearing after the adapter's one-time status proxy/cache initialization, and the current cache implementation makes that failure permanent for the process; see the isolated reproduction and reconnect design below. GNOME's primary AT-SPI bus documentation distinguishes the session bus from the separate, on-demand accessibility bus; the session service `org.a11y.Bus` exposes `GetAddress` and `org.a11y.Status` properties ([at-spi2-core bus README](https://github.com/GNOME/at-spi2-core/blob/main/bus/README.md)).

## Late status-service appearance and reconnect boundary

The isolated probe in [`late-activation`](../benchmarks/luna-accessibility-floor/late-activation/) pins the production dependency versions. Its recorded control shows true → false → true works when `org.a11y.Bus` exists before the AccessKit adapter. In the late case, a session bus is already connected, `NameHasOwner(org.a11y.Bus)` is false before adapter construction, and the service is started two seconds later; the production adapter still makes zero activation callbacks after five more seconds. The original control/late/failed-connect logs and hashes are in [`session-bus-late-activation-20261021`](../benchmarks/luna-accessibility-floor/runs/session-bus-late-activation-20261021/). A second isolated prototype watches `NameOwnerChanged`, queries the current owner after installing the match, and binds each status-property stream to that owner's unique D-Bus name. It passes service-late, initial-true, owner-replacement, and reactivation callback tests; its source and output are under [`session-bus-reconnect-prototype-20261021`](../benchmarks/luna-accessibility-floor/runs/session-bus-reconnect-prototype-20261021/). The original control/late modes construct the real `accesskit_unix::Adapter` against a mock AT-SPI registry/socket. The five `prototype-*` modes test a separate owner/status monitor and emitted status values; they do **not** construct an AccessKit adapter or establish callback activation, GPUI Consumer-tree registration, or screen-reader behavior.

The pinned source explains the stuck late case. `context.rs:184-186` creates one `StatusProxy` and one property stream for the session lifetime; there is no `NameOwnerChanged` subscription. In zbus 5.19.0, `receive_property_changed` documents that an uncached proxy produces no stream events, while its cache initialization (`src/proxy/mod.rs`, `PropertiesCache::new/init`) records a failed `GetAll` as a completed error and exits instead of subscribing for future owner changes. Reconstructing a proxy after owner replacement is necessary; merely retaining this stream cannot repair it. The relevant D-Bus signal reports owner transitions for well-known names ([zbus 5.19.0 `DBusProxy`](https://docs.rs/zbus/5.19.0/zbus/fdo/struct.DBusProxy.html)); zbus can filter it by the first argument as used by the isolated prototype.

The narrow repair is process-level, not per-window: on the already-connected session bus, subscribe to `NameOwnerChanged(org.a11y.Bus)` before querying `GetNameOwner`; for a present owner, create a fresh status proxy pinned to the returned **unique** owner and consume its initial property value; on removal or replacement, deactivate all adapters and retire that stream; on the new owner, create another proxy and apply its initial `IsEnabled` value. Tag queued property updates with the owner identity or monotonically changing local generation and reject updates that do not match the current owner. The prototype demonstrated why: canceling an old watcher does not retract a property update already enqueued. Keeping the well-known-name subscription alive also handles a service that appears after startup without polling or disabling accessibility.

There is a separate session-connection failure boundary. `get_or_init_messages` starts the process worker once and never replaces its `OnceLock` sender (`context.rs:47-74`). If `Builder::session()` or `build()` fails, the worker exits but the sender stays installed; later adapters silently send to a dead receiver (`adapter.rs:129-164`). A bus-restart-capable fix must retain adapter state while reconnecting the session connection with bounded retry, reinstall the owner subscription before its snapshot query, and revoke/deactivate the old AT-SPI bus on disconnect. Do not conflate this with a missing `org.a11y.Bus` name on a healthy session connection: the latter needs only owner monitoring and proxy reconstruction. Zbus 5.19 provides `Connection::closed()` for detecting a lost session connection without polling (`connection/mod.rs:1161-1181`); the reconnect loop can select that future beside messages and owner/property streams.

Reconnect also needs a boundary for already-queued adapter callbacks. `Callback::send_message` feeds one process queue (`adapter.rs:18-50`), and `process_adapter_message` writes queued interface/cache/event messages to whichever `Bus` is current (`context.rs:241-305`). A property or session-owner change can be selected before messages emitted by the old active adapter are drained. The prototype covers status changes, not this queue. An auditable fix tags adapter-generated messages with a process-local active-bus generation captured by the callback installed for each activation; advance it before deactivation on disable, service replacement, and session reconnect, then discard messages from older generations. Keep `AddAdapter` and `RemoveAdapter` as untagged control messages so windows created or closed during reconnection are preserved. Alternatively, drain old adapter messages only after all old adapter state locks have been transitioned inactive, preserving the add/remove controls and proving no callback can enqueue again; this is more dependent on queue ordering. Test old cache/interface/event messages queued immediately before replacement, a window removed while disconnected, and a new window added before status reactivation.

The current isolated prototype proves name appearance, initial-true state, and unique-owner replacement at the callback level. It does not prove session-connection reconnection, queued native-tree update isolation, or real registry delivery; those remain integration gates.

GPUI creates `Bridge` before `window.set_visible(true)` in the Winit `resumed` path (`crates/gpui/src/native.rs:382-401`). Its AccessKit handlers only enqueue owned commands and wake the owner (`crates/gpui/src/native/accessibility.rs:107-195`); the owner later applies actions and projects the acknowledged semantic sheet. `ActivationHandler::request_initial_tree` sets a coalesced initial-tree flag and wakes the owner, then returns `None`; `Bridge::sync` supplies the current full tree on an owner turn, including when no redraw is otherwise pending. This keeps provider callbacks out of a borrowed `Win` and prevents D-Bus reentrancy from mutating UI state. The ignored Linux native test `native_atspi_todo_activation_edit_invoke_and_reactivation` changes `IsEnabled` true → false → true and checks actual AT-SPI tree removal and reappearance (`crates/gpui/src/native/accessibility/linux_tests.rs:76-168, 302-335`). A separate no-session-bus test asserts the application still presents, but does not claim the native tree exists (`:337-365`).

## Observed blank-window processes

The reproducible script [`capture-session-bus-lifecycle.sh`](../benchmarks/luna-accessibility-floor/capture-session-bus-lifecycle.sh) checks the exact source, fixture, and binary hashes, then samples a mapped X11 window on private Xvfb `:97` one second after launch. Raw per-process `/proc` output is retained under [`runs/session-bus-lifecycle-724-20261021`](../benchmarks/luna-accessibility-floor/runs/session-bus-lifecycle-724-20261021). The normal user session bus was reachable (`busctl --user list` returned the user manager and broker), but neither `org.a11y.Bus` nor any AT-SPI name was registered; no Orca, speech-dispatcher, or AT-SPI registry process was observed.

These are one observation per condition, launched in that order; page residency, broker state, and allocator reuse can affect the difference. The 604 KiB PSS difference must not be attributed to AccessKit or treated as a stable saving. The task names and source call graph support the narrower observation that the normal-address case had the AccessKit worker and `async-io` reactor, while the invalid-address case did not. `accesskit_unix::get_or_init_messages` silently exits if session-bus address construction or connection fails, leaving the `OnceLock` sender in place with no receiver; `Adapter::send_message` ignores `try_send` failure (`context.rs:47-74`, `adapter.rs:159-164`). Thus the invalid-address run is a failure-path control where dynamic activation is lost, not a possible product optimization. It still mapped and presented a window.

The selected binary has 24,544,880 bytes on disk. In the live-session-bus sample, its executable mappings accounted for 6,312 KiB RSS/PSS; those are file-backed pages, not a live tree or adapter heap. Remaining mappings include X11, libc, `libxkbcommon`, locale data, and anonymous allocations; do not infer ownership from a VMA name alone. The prior repeated feature-control captures in `runs/frozen724-variant-smaps.txt` and `runs/frozen724-variant-repeats.txt` are stronger evidence for the bundle comparison: they observed about a 3 MiB PSS and three-task increase between `x11-minimal` and `x11` on that older frozen source. They still do not isolate AccessKit's exact heap/code contribution from all feature-linked dependencies.

## Why a zero-worker switch is not an app-only feature toggle

Winit 0.30.13 exposes `EventLoop::as_fd` on X11 and Wayland, but its docs require polling through `pump_app_events` when registering that descriptor in another loop ([Winit 0.30.13 `EventLoop`](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoop.html)). Its `EventLoopExtPumpEvents` API is explicitly nonportable and warns that redraw and lifecycle callbacks must remain synchronous with the OS callback ([Winit pump events](https://docs.rs/winit/0.30.13/winit/platform/pump_events/trait.EventLoopExtPumpEvents.html)). GPUI currently uses `run_app`; moving the application to an outer poll loop would be a Linux event-loop redesign, not a small AccessKit flag.

The async-io reactor descriptor does not remove its own thread. Zbus exposes an executor, but its `Connection` is a private-field type; there is no public session-connection socket descriptor to register in Winit/calloop. `accesskit_unix` owns the connection, executor, property stream, AT-SPI bus, and adapter registry inside its private process worker. So neither adding Winit's fd to an external poller nor calling `executor().tick()` on the UI thread alone is sufficient to eliminate both helpers safely. Blocking the UI while waiting for D-Bus, polling on a timer, or routing platform actions directly into `Win` would also break latency or reentrancy guarantees.

The smallest credible upstream seam is an externally driven Unix adapter service, not a GPUI-only disable switch:

1. Add a supported zbus external-I/O integration that exposes readiness/wake registration for its owned connection and allows the async-io fallback thread to be suppressed safely. `async_io::os::unix::reactor_fd()` alone is not that contract: upstream documents that its thread remains active and that external raw polling can conflict with reactor registration.
2. Add an AccessKit Unix driver/interface that owns one process-wide session status stream and AT-SPI bus lifecycle, but lets an embedder pump its readiness on a compatible Linux event loop. The driver must continue to watch `IsEnabled`, launch/attach the accessibility bus when enabled, and deactivate on disable; it must not require a screen reader to be present at application startup.
3. On the GPUI Linux backend only, integrate that driver into the owner event loop with a wake source. Callbacks stay bounded and owned: activation sets the current session's “needs full tree” flag and wakes the owner; actions enqueue commands and wake; the owner builds or updates the complete published semantic sheet in a turn where it holds `Win`. Keep existing per-window Bridge authority and the current worker fallback for platforms/loop modes that cannot prove the same event semantics. Windows and macOS adapters are unaffected.

Before adoption, test a session with the status service absent at launch and started later, enabled before first adapter creation, enabled after the window is idle, true → false → true, repeated windows sharing one process service, one window closing while another remains, service/bus disconnect and reconnect, and queued action racing deactivation. Measure actual active-session tree availability and action latency against the current worker design; a lower thread count is not enough. The app-level retry gap in the pinned OnceLock failure path should be fixed or explicitly accepted upstream before relying on reconnect tests.
