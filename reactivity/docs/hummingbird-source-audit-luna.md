# Hummingbird source audit against the current GPUI application API

## Pin and scope

I audited source, not the README or screenshots. Both `https://github.com/hummingbird-player/hummingbird` and `https://git.mailliw.org/hummingbird/hummingbird` reported `e15e8ba0ef6ff5445294030d373e3c8ccc7d780c` as `HEAD`. The commit is dated 2026-10-20 (author/commit time 07:15 UTC) and is titled “fix: remember scroll positions in navigation history (#461).” All Hummingbird links below pin that commit. The clone at `/root/hummingbird-reference` is sparse, so I read its exact git objects and extracted `src`, `migrations`, and `queries` to `/tmp/hummingbird-source-audit`; no upstream files were edited.

**Decision:** Hummingbird is a useful real application target, but the current GPUI API is not yet a faithful UI/runtime substrate for it. Its media, scanner, database and most settings logic can stay application-owned. The missing framework seam is a live native app that can drive keyboard/text input, scrollable virtual lists, pointer gestures and images, and safely deliver background completions to one exclusive UI owner. Do not call a button-only or hard-coded-row demo a Hummingbird port.

## What the application actually does

The application entrypoint creates a two-worker Tokio runtime with up to twelve blocking workers; initializes settings, locale, assets/fonts, SQLite, playback session state, scanner, path-availability monitor, power management and actions; then mounts the main window. See [`src/main.rs` lines 40–74](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/main.rs#L40-L74) and [`src/ui/app.rs` lines 347–507](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/app.rs#L347-L507). The window composes playback controls, header, library, search, artist picker, queue/lyrics sidebar, command palette, modals, toasts and window chrome; it handles external path drops to enqueue files in [`src/ui/app.rs`](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/app.rs#L89-L170).

It is not a single static table. The library has album, artist, release, track, playlist and file-tree views, persistent navigation/scroll restoration, sorting and selectable columns, list/grid modes, search, queue operations and context menus. The main table loads an `Arc<Vec<Identifier>>` for the sorted result set, but creates row entities on demand for the viewport range plus a movement-adaptive prefetch margin (at least five rows), then prunes row views outside that range. Row contents/visible columns load asynchronously. See [`table.rs` lines 47–73, 126–162, and 730–790](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/components/table.rs#L47-L73) and [`table.rs` around the visible-range builder](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/components/table.rs#L730-L790). The files view has lazy `Unloaded / Loading / Loaded` child state for directories, flattens only expanded rows, asynchronously loads on expansion and virtualizes the flattened view ([`files_view/tree.rs` lines 14–78](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/library/files_view/tree.rs#L14-L78), [`files_view.rs` lines 480–560](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/library/files_view.rs#L480-L560)). A fake static list would miss both its memory strategy and meaningful interactions.

Async completion is a first-class UI concern: keyed resources abort replaced work, ignore obsolete generations, preserve previous data while loading, and notify the view after background completion ([`async_resource.rs` lines 21–31, 49–76, 102–130](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/components/async_resource.rs#L21-L31)). Search queries SQLite for albums, artists and tracks, builds an in-memory search index, and activates navigation from results ([`search/model.rs` lines 40–113, 115–145](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/search/model.rs#L40-L113)). Library scanning is a background pipeline plus filesystem watcher; its state/events feed UI models. Playback is a dedicated named audio thread with a command channel, event channel, spectrum tap and session watch channel; the UI sends controls and reacts to state/position/metadata/queue updates ([`playback/thread.rs` lines 119–165, 270–320](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/playback/thread.rs#L119-L165)). Preserve this separation; do not move DB, decode or audio work into the UI owner turn.

The project includes real asset/image handling (cover art fetched/decoded off-thread, thumbnail/full-size paths, limited decode concurrency, cache/drop handling), fonts/icons, file drag-and-drop, keyboard maps/command palette, and platform integrations (MPRIS, macOS/Windows media controls, power management). These are app/product requirements for a complete player but are separable from a first visual framework spike. The core UI needs a credible table/list, library navigation, playback controls, search and asynchronous state before these platform extras are called ported.

## GPUI capabilities that are already useful

The current code has a strong starting seam: `Application::demo().open(model)` returns an ordinary owner, and `Win` mutations take `&mut self`, rather than routing model writes through an ambient test dispatcher ([`application.rs` lines 4–19](</root/gpui-ce3/reactivity/crates/gpui/src/application.rs:4>), [`runtime.rs` lines 342–457](</root/gpui-ce3/reactivity/crates/gpui/src/runtime.rs:342>)). The native adapter has a real Winit/wgpu/softbuffer application entry point (`Application::run` / `run_window`) and maps resize, close, mouse and basic keyboard/text events. Its input mapping is currently limited to Backspace, Enter, Space, and plain committed text for the focused target; there is no general key/action, focus navigation, caret/selection/composition, scroll, or list API ([`native.rs` lines 657–755](</root/gpui-ce3/reactivity/crates/gpui/src/native.rs:657>)).

`Win::set`, `update`, `click`, `type_text`, `resize`, and `presented` use exclusive owner turns. Semantic testing is already better than a private test harness: `Win::role(...).text(...).one()`, `count`, borrowed `visit(Part)`, and `bounds` query the acknowledged presentation, and the query tests assert zero allocations in repeated reads ([`runtime.rs` lines 450–457 and 561–627](</root/gpui-ce3/reactivity/crates/gpui/src/runtime.rs:450>), [`runtime/query.rs` lines 6–125](</root/gpui-ce3/reactivity/crates/gpui/src/runtime/query.rs:6>), [`tests/queries.rs` lines 34–79](</root/gpui-ce3/reactivity/crates/gpui/tests/queries.rs:34>)). `Application::demo().open` plus borrowed semantic queries can remain the basis for tests of actual app models and views.

The current retained output and canvas already support styled text, basic boxes, layout, pointer hit targets, typed field changes, software pixels, command recording, a GPU presenter and HDR-capable output config. Keep using one canonical scene path. None of that implies the current view layer provides the product-specific controls below.

## Required gaps versus optional extensions

| Priority | Hummingbird source requirement | Current GPUI gap / practical seam |
|---|---|---|
| P0 for a useful app | Scroll viewport with visible-range realization, prefetch, row recycling/cache limits, stable per-item identity through sort/filter/prepend, selection and activation | `El` owns an eager `Vec<El>`; runtime admits at most 100,000 nodes (`runtime.rs:27`); no scroll container or virtual-list primitive. A 100k result list cannot be represented as 100k elements and Hummingbird deliberately avoids doing that. Add an item-source/list interface that receives `[start..end)` and returns bounded realized rows. Keep total item count and keyed identities separate from realized render nodes. |
| P0 | Native keyboard/keymap, focus, complete text editing (selection, caret, delete, paste, composition), command dispatch | Native maps keyboard events but `Win` currently has no key dispatch; `text_input` can only append and backspace at character boundaries (`runtime.rs:605–615`). Search/command palette and shortcuts need this before the app can be operated. |
| P0 | Async DB query/resource and event delivery on UI thread with cancellation, stale-result rejection, wakeup, and deterministic test pump | Current `Win` is synchronous. Hummingbird's pattern uses keyed async resources and `cx.spawn` to publish results; playback and scanner use independent channels. Keep Tokio/player/scanner external if desired, but add a bounded inbox/wake-to-owner mechanism or equivalent explicit `poll_events(&mut self)` that mutates/presents only under exclusive `&mut Win`. Never block during render or callback. |
| P0 | Rich controls and layout needed for player chrome, navigation, settings and table | The public element kinds are only `Div`, `Text`, `Input`, `Button`; `Style` is compact flex row/column, width/height/gap/padding/font/color/transform. Missing grid/overflow/scroll, borders, alignment distribution, min/max sizing, clipping, icons and image elements. Table column resize, sort headers, horizontal scroll, list/grid mode, playback slider/knob, modal/menu and shortcuts require a control surface. |
| P0 for visual parity | Bundled SVG/icons and asynchronous cover-art images, image fitting and decoded image lifecycle | Current element tree/canvas exposes no image element or icon/path command. Hummingbird loads cover art asynchronously and controls decoded size/cache/drop. Add a borrowed image handle to the canonical scene, deterministic placeholder/ready/error states, and bounded decode/cache policy. SVG/icon pipeline can be later if the first fidelity gate uses rasterized existing assets. |
| P1 for complete product | Context menus, drag/drop reorder, row selection/range selection, column hide/reorder/resize, dynamic grid | Required for faithful library/queue behavior but can follow a basic functional virtual list. Build tests around movement and reorder identity, not just visual paint. |
| P1 platform/product | Open/reveal files, external file drops, OS media buttons/MPRIS, power inhibition, service controllers, reopen/multiwindow/modal focus, packaging | Current native adapter already has Winit close/resize, mouse/key receipt and GPU/CPU presentation, but no app-level file-drop/key action path/media services. Reuse Hummingbird’s platform/domain modules where possible. These are not reasons to put OS calls in the retained scene engine. |

The current identity system issues window-qualified target stamps for retained node identities, but it has no public keyed collection/list contract. Stable item IDs are needed because table sorts, searches and library refreshes rearrange items. A visible row's action must resolve against its current data identity, not silently become the item at the same index after a reorder. Offscreen rows must not receive fresh action targets until realized. This is a framework design requirement inferred from the source's sorting/refetch and row-cache behavior, not a claim that Hummingbird already suffers a bug.

### Explicit no-`Rc`/`Cell`/`RefCell` constraint

Do not mechanically port Hummingbird's closures/entities. Its current first-party UI uses `Rc<dyn Fn>` for table selection and other callbacks, and `Rc<RefCell<_>>` for transient slider/scrollbar/column-resize state; see `src/ui/components/table.rs:10, 68–73`, `src/ui/components/slider.rs:1–40`, and `src/ui/components/scrollbar.rs:1–4, 120–160`. Replace this architecture with ordinary owner fields, typed IDs/actions, immutable snapshots or explicitly owned channels, and direct mutable operations on `Win`.

At the audited revision, `tests/components.rs` used `Rc<Cell<u32>>` to count descriptions (`tests/components.rs:1–15`); this is an actual occurrence of the prohibited types, and the current root work is replacing that test instrumentation. The portable `Signal<T>` itself is an inline value, not `Cell`-backed (`crates/state/src/signal.rs:48–70`). Separately, the framework's `element.rs` uses `Box<dyn Route>` and `Any` downcasts for handler routing (`element.rs:29–35, 87–107`). Type erasure is a dispatch-design choice, not an `Rc`/`Cell`/`RefCell` violation; whether to replace it is a separate architecture decision. If the prohibition applies to framework internals and tests as well as ported application code, keep an explicit source gate so actual occurrences are distinguished from unrelated dynamic dispatch.

## Minimum API/test contract before a larger app port

1. **Real application owner:** one `Application::run`-owned native `Win` with exclusive mutation. Add an owner-thread wake/inbox boundary for typed background messages. Model entrypoints remain concrete and use `&mut M`; no `Rc`, `Cell`, `RefCell`, global mutable registry, or test-only dispatcher.
2. **Input parity:** `Win` must accept the same normalized input record from native and tests: pointer move/down/up/wheel, key down/up + modifiers, text commit/composition, focus/cancel, drag/drop. Event delivery performs hit testing against the last acknowledged scene, so failed/stale presentation cannot activate stale geometry. Keyboard focus and text selection are explicit owner state.
3. **Virtual collection contract:** list takes a stable key and borrowed/indexed item source plus `item_count`, scroll state and a row builder called only for the viewport+bounded prefetch range. Support keyboard selection, pointer activation, wheel/drag scroll and `scroll_to_key`; report visible/realized counts. Row identity follows item key across sort/refetch; a dropped row invalidates its ephemeral target. Preserve data-source ownership outside the presentation tree.
4. **Async resource contract:** keyed generation, cancellation, pending/ready/error while retaining prior good data, explicit delivery on the owner thread, wake, close/drop suppression, and deterministic delivery in headless tests. Media/DB tasks stay background; render only consumes settled immutable values.
5. **Borrowed semantic API:** keep `Application::demo().open(app_model)`, `Win::query/role/visit`, and add keyed virtual-list semantics (visible item key, row role/name, visible bounds; optionally explicit reveal-by-key). Assertions should target what is actually visible/actionable and should distinguish current model from last acknowledged presentation.
6. **Native and rendering parity:** add clip/scroll, images, grids and needed styling to the same retained scene/render packet used by CPU/GPU; do not create a second “Hummingbird-only” renderer. Native integration carries platform events into the same runtime and acknowledges presentation only after OS submission.

Acceptance coverage should start with a deterministic fake library model, not an audio mock UI: test `Application::demo().open` on a few hundred thousand stable IDs while asserting realized element count is bounded by viewport+prefetch; scroll to an item, query/activate it, sort and prepend/refetch while ensuring target identity follows key; test keyboard type/search, selection, shortcuts, wheel/drag scroll, queue reorder, async stale-generation cancellation, worker-thread completion and close-before-completion. A fixture-backed DB test should cover row data and search. The native smoke test should verify first render/input/resize and presentation acknowledgements without relying on photon timing. Hummingbird has extensive separate DB/scanner/playback/media unit tests, but its UI source does not currently provide a broad app-level interaction suite, so these GPUI tests would be essential rather than evidence of port parity.

## Recommended first executable slice (for the implementation manager)

Build one *honest* Library-table vertical-list example against the existing native `Application::run` and the same headless `Win` tests. Use a deterministic indexed source with 250,000 fake `TrackSummary` IDs (not 250,000 `El`s), rows with title/artist and play action, scroll to a stable key, query/click it, then sort and insert before it. Gate: bounded realization (e.g. visible rows + a documented prefetch margin), unchanged stable selected key across sort/refetch, no stale row activation, zero-allocation borrowed inspection, and no `Rc`/`Cell`/`RefCell` in production app code. Add a keyboard search box and synthetic async row-detail completion after the basic range contract works. This will expose the real needed list/event seams before anyone ports every Hummingbird widget or adds a speculative DSL.

Do not make an app-wide win claim from this example. It validates one needed scaling regime and several essential semantics; the full player still needs list/grid/table parity, image/asset lifetimes, file-tree interactions, persistent settings/navigation, playback/scanner event integration, and platform-specific services.
