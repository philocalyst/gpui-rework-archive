# Ready-publication MPSC: source audit and bounded candidate

Status: **research proposal, not implemented**. Read-only inspection only; no builds, tests, queue prototypes, measurements, or speed claims. The pinned repository evidence records rustc `1.97.1`, commit `8bab26f4f68e0e26f0bb7960be334d5b520ea452` (`reactivity/evidence/gpu-packet-reuse/toolchain.txt`).

## Finding: positive-capacity `try_*` can spin behind a paused reservation

In that pinned std, `std::sync::mpsc::sync_channel(bound)` delegates to `mpmc::sync_channel(bound)` (`library/std/src/sync/mpsc.rs:570`); positive capacity selects the preallocated array channel. The public `SyncSender::try_send` and `Receiver::try_recv` are thin calls into the channel (`mpsc.rs:755-757, 813-815`). The receiver documentation says `try_recv` does not block to *wait for data*; that API wording does not mean the implementation is wait-free.

The bounded array channel reserves enqueue positions by advancing a shared tail before writing the value and publishing the slot stamp (`library/std/src/sync/mpmc/array.rs:123-192, 195-212`). Its `try_send` calls `start_send` and only then writes the slot (`:308-316`). If a producer claims the current head slot and is descheduled before writing/publishing it, `start_recv` sees the slot stamp equal to head while tail is ahead and loops with `spin_light`; other stamp mismatches loop with `spin_heavy` (`array.rs:214-284`). The `try_recv` wrapper enters that same loop (`:363-370`). With capacity one this is immediate; with larger capacity it appears after earlier ready slots are consumed and the stalled reservation reaches the head. Thus the GUI owner can spin indefinitely in `try_recv` while the producer is paused. `try_send` also uses a retrying reservation loop with backoff, so its `try` name is not a wait-free progress guarantee.

This is a concrete head-of-line reservation stall, not evidence of an observed user-visible hang in the current build. It matters because accessibility action ingress is a foreign callback and owner drain is on the UI path: [accessibility.rs](</root/gpui-ce3/reactivity/crates/gpui/src/native/accessibility.rs:118>) creates a positive-capacity channel (`CAPACITY = 64`); callbacks `try_send` and signal (`:238-245`), while the owner loops over `try_recv` (`:427-449`). Remote uses the same std bounded channel and receives through the existing bounded staging queue (`remote.rs:92-123, 132-163, 293-305`).

Crossbeam's mature `ArrayQueue` explicitly uses Dmitry Vyukov's bounded MPMC queue and its source likewise loops/backoffs when a reserved slot is not published (`crossbeam-queue 0.3.14 source, lines 1-4, 151-203, 350-397`). Replacing std with a mature bounded MPMC ring is therefore not automatically a cure. `concurrent-queue` has a useful bounded/close/original-value-return API, but its docs state it uses `yield_now` (or `spin_loop` without std) to avoid tight-loop waiting; those docs do not promise wait-free callbacks either ([crate docs](https://docs.rs/concurrent-queue/latest/concurrent_queue/), [queue API](https://docs.rs/concurrent-queue/latest/concurrent_queue/struct.ConcurrentQueue.html)).

## Smaller one-consumer candidate: ready-only intrusive stack + free bitmap

The important change is moving the FIFO linearization point to *ready publication*, rather than a ticket reservation that the consumer must wait behind. A bounded, preallocated MPSC can use one intrusive node per capacity slot:

- Each node is `{ next: AtomicUsize, value: UnsafeCell<MaybeUninit<T>> }`. A producer first claims a free node, moves `T` into it, writes `next = current_ready_head`, then CAS-publishes the node as the new ready head with Release semantics. The successful CAS is the enqueue linearization point. A consumer atomically swaps the ready head to empty with Acquire semantics, reverses that detached LIFO chain, and thereby observes FIFO in the order of successful publication CASes. A single consumer keeps any over-budget remainder locally and drains it before detaching a newer batch.
- Avoid a second Treiber stack for free nodes. For this workload, a free bitmap is simpler and avoids ABA tags: one `AtomicUsize` bitset handles up to `usize::BITS` slots (so the accessibility capacity 64 is one word on 64-bit, two on 32-bit); larger Remote capacities use a preallocated array of bitmap words. Producers claim one bit with a CAS clear; the consumer sets the bit only after saving that node's next link and moving its payload out. If every free bit is clear, `try_send` returns the original value as `Full`, even if one or more nodes are only temporarily claimed by paused producers. This conservative answer is bounded and avoids waiting for those producers.
- Fold close into the ready-head word: reserve the high bit as CLOSED and the low bits as an index/sentinel. `Inbox::close` atomically swaps the word to `CLOSED | EMPTY`, which both prohibits later successful publications and detaches the currently published chain. A producer whose CAS wins first is included in the detached list (send may return `Ok` even though close then cancels it); if close wins first, the producer's expected head no longer matches, it observes CLOSED and returns its original value as `Closed`. This avoids a separate `closed` check/CAS race. Keep accessibility's overflow/session/publication state separate unless a proof shows it can be folded without changing action validation.

**Why the ready head does not need an ABA tag:** producers only prepend; the one consumer removes the entire visible list with one atomic swap and never CAS-pops individual nodes. A producer's successful CAS uses its observed head index only as the `next` link. If that index was detached, freed, reused, and is again the current head, CAS success links to the *current* live node at that index; it does not remove or dereference a stale incarnation. The free bitmap gives each node exclusive free/claimed/ready/consumer ownership and has no reusable tagged-head identity. This argument is specific to push-only producers plus one consumer that detaches whole lists; it does not justify using an untagged Treiber pop stack.

The user-requested alternative—preallocated tagged-index free stack plus tagged ready head—also works in principle, but is larger and has a bounded tag problem. Both free-stack pop and ready-stack publication need a packed index+generation word; generation wrap cannot silently wrap because ABA returns. Checked exhaustion must permanently stop reuse before a generation repeats, with a defined Full/Closed outcome and a way to drain already-published messages. On 32-bit targets, index plus tag compete for only 32 bits. Using a 64-bit pair is conditional on target support; Rust exposes `target_has_atomic` for widths and does not provide every atomic width on every target ([Rust Reference](https://doc.rust-lang.org/reference/conditional-compilation.html#target_has_atomic), [AtomicU64 docs](https://doc.rust-lang.org/stable/core/sync/atomic/type.AtomicU64.html)). For capacity 64, a bitmap is simpler and removes tag exhaustion; for large capacity it costs `ceil(C / usize::BITS)` atomic words and producer scans.

## Footprint and shared work

For capacity `C`, the candidate's pool is `C * size_of::<Node<T>>()`, plus `ceil(C / usize::BITS) * size_of::<AtomicUsize>()` bitmap bytes. With naturally aligned `T` no cacheline padding is needed; node stride is approximately `align_up(size_of::<T>() + size_of::<usize>(), max(align_of::<T>(), align_of::<usize>()))`. Do not pad every node to a cache line by default: that can multiply node storage for small payloads. It may be worth an isolated layout test if producer false sharing is later measured.

The queue header can be small: ready-head `AtomicUsize` (closed bit folded in), one boxed node-slice fat pointer, and one boxed bitmap-slice fat pointer—about five machine words before Arc control-block and accessibility lifecycle/wake fields. Setup normally needs an Arc allocation, node-array allocation, bitmap allocation, and the existing `VecDeque<T>` staging allocation. The current std channel also preallocates bounded slots and Remote separately preallocates staging; therefore this is not an allocation-count reduction by itself. Fold the queue's wake `OnceLock` into the same shared Arc only if doing so removes the current separate notification Arc without changing attach/unbound behavior. Payloads are moved into and out of nodes just as they are moved through std channel slots; this is not a zero-copy win, and it adds one link word per slot plus bitmap bytes.

There is no per-message allocation or per-message refcount. There are still two shared contended points: free-bit CAS and ready-head CAS. A producer can retry/starve under contention; this is **not wait-free**. The progress improvement is narrower and useful: after claiming a node, a paused producer owns only that slot and does not reserve the next FIFO position, so a UI consumer can detach later-published work without spinning behind it. When all nodes are claimed, the queue reports Full rather than making the owner wait.

The detach/reversal is O(k) in the number `k` of visible items. Keep the current per-lane staging/apply budget: reverse one detached chain once, retain the remainder in the unique Inbox, and never invoke application callbacks until all lanes have staged their bounded share. `Remote` currently caps staging at its declared capacity, reports `Stage::Limited` when saturated, and applies only after staging (`remote.rs:144-161, 293-305`); native integration tests assert bounded rows per ready turn and require real wake progress rather than polling (`native/remote_tests.rs:73-99, 153-234`). Accessibility currently examines a fixed `APPLY_BUDGET` array (`accessibility.rs:18, 427-449`). A custom detach path must preserve those budgets and lane fairness rather than draining an arbitrarily large ready list in one GUI turn.

## Ownership, ordering, close, wake, and panic proof obligations

The queue is plausible only with a written ownership-state proof. Each node must be in exactly one state: free (bitmap bit set), producer-claimed (bit clear, not visible), ready (linked from ready head or consumer's detached chain), or consumer-owned while its payload is moved to staging/dropped. No second producer can write a claimed node; no producer may access a ready node; consumer must capture `next` before setting the free bit; only then can a new producer overwrite the link/value. `T: Send` is required. The implementation needs narrowly scoped unsafe for uninitialized storage and the `Send`/`Sync` invariant, with panic-safe reservation and drain guards.

Preserve these contracts from the actual callers:

- **Unbound Remote sends:** the queue exists at `Remote::bounded` and sends before binding remain buffered; zero capacity always returns `Full(value)` (`remote.rs:87-112, 144-160`).
- **Full/Closed returns:** a free-bit miss returns the same owned `T` as `Full`; a close-bit observation returns it as `Closed`. A racing send that published before atomic close is accepted but may be cancelled/dropped, matching Remote's documented revocation race (`remote.rs:50-53`). AccessKit overflow still sets terminal overflow and wakes instead of returning a value to the platform callback (`accessibility.rs:110-113, 238-245`).
- **Exactly-once destruction:** on normal close, drain both queue-visible/detached nodes and staging, moving or dropping each initialized `T` once. If a `T` destructor panics while closing, a guard must retain the remaining detached list for unwind cleanup; never lose a detached list in a local raw index. A producer panic after free-slot claim must release that slot or leave a safely reclaimable state. After final Arc drop, there can be no live safe Rust sender call; the final queue drop must still destroy any initialized but queued values.
- **Status and wake race:** publish node before signaling, as current callers do. Close racing publish is ordered by the combined head CAS/swap. A send that wins just before close may signal after the owner has closed; a spurious late wake is harmless. Keep overflow/session/publication validation before applying queued AccessKit work (`accessibility.rs:423-449`). Make sure close drains messages that were published but not yet signaled, and that a sender which loses to close cannot signal a success wake.
- **FIFO:** consumer reversal preserves the total order of successful ready-head CAS publications. A per-producer sequence of completed `try_send` calls stays ordered because each later call begins after the earlier CAS returns. A send paused before publication has not linearized and need not block the consumer. Tests should pause producers before free claim, after claim/before write, after write/before publish, after publish/before wake, and race each stage with detach/close.

## Literature and library comparison

- **SCQ:** Nikolaev's bounded SCQ is a lock-free, linearizable MPMC queue designed for bounded memory and ABA/reclamation safety; it uses a more involved circular-array protocol and FAA hot spots. It solves a broader MPMC problem than this GUI's MPSC + single consumer, so importing it would carry unused complexity. Lock-free permits one operation to starve and does not establish bounded callback latency ([primary paper](https://arxiv.org/abs/1908.04511)).
- **LCRQ:** a linearizable lock-free FIFO using fetch-and-add ring segments and linked queue nodes; it targets high-concurrency MPMC throughput and x86 performance, not a small fixed-capacity no-allocation callback. Its nonblocking guarantee is not wait-freedom, and its segmented/dynamic design is more machinery than a ready-only single-consumer path ([primary PPoPP paper](https://www.cs.tau.ac.il/~mad/mass/17b/lcrq.pdf)).
- **Jiffy:** the closest literature fit by shape: wait-free MPSC with one consumer. Its proof handles producers that reserve indices and stall by having the consumer scan/fold buffers; it retains buffer lifetime for concurrent enqueuers. That is exactly the difficult reservation hole in a much richer design, not evidence that a simple MPSC ring is stall-free. Its dynamic buffers and reclamation machinery do not drop directly into a fixed preallocated bounded Remote without adaptation ([primary paper](https://arxiv.org/abs/2010.14189)).
- **wCQ:** a bounded-memory wait-free circular queue with cooperative helping, built on SCQ-style fast paths. Its bounded memory includes thread records bounded by the number of threads, and its slow path requires helping/progress protocols. This may be justified for hard per-operation progress guarantees, but it is substantially more code and state than the callback/owner queue needs unless wait-freedom becomes a formal requirement ([primary paper](https://arxiv.org/abs/2201.02179)).
- **Mature Rust queues:** Crossbeam `ArrayQueue` is fixed-capacity and widely used but follows the same sequence-stamped Vyukov-style reservation design and therefore shares the in-flight head-slot waiting caveat. `concurrent-queue` has ready `Full`/`Closed` payload-preserving APIs and a bounded constructor; its default mitigation is yielding in tight loops, not a wait-free promise. These are preferable to custom unsafe code if the goal is only simpler queue API, but not if the exact goal is removing producer-reservation head-of-line waiting ([Crossbeam docs/source](https://docs.rs/crossbeam-queue/0.3.14/src/crossbeam_queue/array_queue.rs.html), [concurrent-queue docs](https://docs.rs/concurrent-queue/latest/concurrent_queue/)).

## Recommendation and falsifiable gate

The ready-only stack + bitmap is the smallest promising *class* of custom queue that removes the identified reservation stall while preserving a fixed payload pool. The tagged-index free pool is more general but is not the minimal formulation for the actual 64-entry Accessibility queue; a bitmap removes its ABA/tag lifetime burden. However, the custom candidate still has CAS retry loops, adds unsafe payload ownership and panic cleanup, two contended atomics, a linked-list reversal, bitmap false sharing, and no per-message allocation savings over current std. `T` remains moved into staging, and baseline std already preallocates.

Reject custom replacement unless a focused adversarial test proves the std receiver can stay in a `try_recv` reservation stall when a producer is paused, and the custom queue's consumer remains bounded in that same schedule while all existing delivery ordering, Full/Closed ownership, close cancellation, panic, wake, and per-lane budget contracts hold. Measure only after correctness: compare owner callback tail latency and producer contention at CAPACITY 64 and representative Remote capacities, and count allocations/storage including the bitmap. Do not call the candidate lock-free/wait-free without the corresponding progress proof; the bitmap and ready-head CAS loops leave a producer vulnerable to starvation under contention.
