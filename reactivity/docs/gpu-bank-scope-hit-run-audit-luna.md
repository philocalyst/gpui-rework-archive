# GPU paint-bank, scope, and hit-run audit

This is a source audit, not a performance result. The implementation reviewed is the in-progress paint-slots tree at `gpui-paint-slots` (Canvas/GPU scope and bank work) and the committed hit-run tree at `gpui-hit-runs` (`966a13ff7d9dc3e04e41aabf9223dd71826951fd`). Those are distinct snapshots. The paint-slots native adapter has not yet connected the GPU bank edit path.

## Paint bank and GPU boundary

Canvas separates per-command translation from a deduplicated `Scope` (inverse linear map plus clip) and working paint values in `crates/canvas/src/canvas/columns.rs`. Scope and paint references are positions in the current complete Canvas scene, not semantic IDs or cross-scene capabilities. They are safe to reuse only while the caller retains authority for that exact scene. `PaintSlot` validates that the current row is shared; `prepare_slots` checks ordered unique writes and preserves alpha bit-for-bit before returning a borrow-held plan. The commit then mutates the already validated rows. Per-slot damage is unioned, so disjoint consumers may conservatively enlarge the repaint rectangle.

The scope lookup is intentionally bounded to the first 32 retained scopes (`DISCOVERY`). It avoids an unbounded quadratic search, but repeated equivalent scopes first discovered after that prefix are not deduplicated. This is a storage tradeoff, not a semantic error: a scene with many distinct early scopes and frequent later repeats can pay one additional 48-byte scope row per later repeat. The production gate should include both repeated-first-32 and repeated-after-32 fixtures, plus all-unique scopes; the current discovery threshold should not be described as universal interning.

The Canvas bank keeps exact working `f32` bits; it does not quantize colors. Alpha changes are rejected by the paint-only edit API because alpha changes can change opaque-tile proofs and material behavior. The GPU renderer spike adds a bank prefix to its packed records and tags a color word with a slot address; its shader has a separate banked fragment path. That path currently uses draw-major order and retains sixteen independent sample colors. It decodes each draw once per pixel rather than once per sample, but carries 16 `vec4` accumulators (64 scalar components) and still evaluates geometry at all 16 sample locations. This trades repeated record/bank loads for live state. Do not claim reduced register pressure or faster shading without target compiler/register and timing evidence.

For comparison, the ordinary fragment path is sample-major: for each sample it walks draws in painter order and source-over composites that sample independently. Coverage must remain correlated with each sample and each draw; averaging a draw's coverage before source-over changes overlapping translucent edges. A bounded 2- or 4-sample chunked kernel is a plausible next experiment: hold S independent accumulators, walk ordered draws, load each draw once per chunk, and update all S samples. It preserves per-sample painter order and limits live colors to S `vec4`s, but increases code and register state over the current sample-major path. Gate it against the current shader with exact RGBA16F/SDR image oracles for overlapping translucent shapes, rounded corners, image masks, HDR, and the Pythagorean coverage fixtures, then measure target GPU time and compiler register/spill data. A draw-major kernel that has only one accumulator is incorrect for overlapping sample coverage.

The present GPUI adapter still does not use the GPU bank edit commit for direct reactive color changes. `Runtime::finish_color_slot` commits the Canvas slot and clears `metadata.paint`; `GpuSurface::render_paint` consequently falls through to `Renderer::render_indices` for the new token. This keeps the result correct but rebuilds renderer records/binning/uploads rather than patching the resident GPU bank. The in-progress `GpuSlotCommit` is not evidence that the application route is wired. The next integration gate is an exact owner/window/token match, banked-packet-only validation, ordered queue writes, and fallback to full render on any mismatch; verify the ordinary unkeyed rendering path stays correct.

There is no zero-copy upload in this design. In the pinned dependency, `wgpu 29.0.4` documents that `Queue::write_buffer` copies data into staging memory and starts the write on the next submission; `write_buffer_with` supplies a mapped temporary staging view, not shared GPU-visible storage. The present slot path writes a changed 16-byte color word and then submits a target redraw. Any benefit is avoided scene reconstruction or reduced command payload, not eliminating host/device transfer. See [Queue::write_buffer, wgpu 29.0.4](https://docs.rs/wgpu/29.0.4/wgpu/struct.Queue.html#method.write_buffer) and [Queue::write_buffer_with, wgpu 29.0.4](https://docs.rs/wgpu/29.0.4/wgpu/struct.Queue.html#method.write_buffer_with).

The renderer's opaque full-tile shortcut is only valid when its proof remains sound. The current rounded rectangle/image sources do not qualify as solid full-tile records. Paint-only edits preserve alpha bits; the GPU indexed patch additionally rejects color changes that would invalidate signed-zero/subnormal opaque proof behavior. Tests should keep zero-alpha/no-draw elision, negative zero, subnormal RGB, source-over order, and changed alpha as separate adversarial cases. Recomputing a geometry bin is harmless; carrying an opaque proof across a changed paint classification is not.

## Hit-run and packed-parent audit

The committed hit-run representation packs hit eligibility in bit 0 and a saturated count of immediately preceding impossible-hit rows in bits 1–7 of the existing byte. “Impossible” means the node was not hit-eligible or its bounds are empty. The reverse hit scan jumps by that count, then performs the original exact geometric/ancestor routing at the remaining candidates. The run is derived while building the new presented cohort, so failed preparation must retain the old cohort's run data and successful publication recomputes it. It is not a logical-node count: virtualized rows omitted from P do not contribute.

The checked implementation has an exhaustive old-scan oracle over a coordinate grid and publication/failure cases, plus long runs around the 127 saturation boundary. Important boundaries for future changes are empty-but-eligible bounds, virtual rows, scroll/list ancestors that are not ordinary hit targets, and hit routing through ancestors without a handler. The skip must never bypass the exact `sheet_hit` transform/clip predicate for a candidate.

A proposed follow-up combines the current 32-bit parent index with a 15-bit saturated impossible-hit run: 17 low bits for parent indices (100,000-node admitted maximum), 15 high bits for the run (32,767 saturation), with low value `0x1ffff` reserved for no parent. This fits in the existing 4-byte parent lane without adding an eligibility byte. The domain proof is conditional on `MAX_NODES < 2^17`; index 131,071 must remain unavailable so it cannot collide with the sentinel. Decode parent only from the low mask, and never expose the packed word as a parent identity. `u32::MAX` is a valid combined encoding for no-parent plus saturated run, so raw-word equality with `u32::MAX` cannot be the no-parent test.

That combined representation needs a focused regression suite before adoption: parent values 0, 99,999 and the sentinel boundary; no-parent at every saturated-run state; run lengths 32,766, 32,767, 32,768 and 100,000; publication after virtual-list omission; scroll/list candidates with empty and nonempty bounds; and AccessKit semantic deltas where only the run changes. Every parent reader (query, list, scroll, hit, accessibility, frozen parent remapping) must go through one checked decoder. The present hit-run commit has not yet made this parent packing; this paragraph records the proposed bit-domain and failure cases, not an implemented feature.

## Evidence boundary

No timing was performed for this note. The sample-major versus banked shader comparison is a formulation-level tradeoff, and the scope discovery limit is directly visible in source. The current GPUI reactive color path's renderer rebuild is also directly visible in the adapter dispatch. Performance or memory adoption requires paired measurements for repeated early/late scopes, unique scopes, sparse and dense color changes, native full rendering, and the exact same image oracle. Keep the Canvas-only and GPU-integrated milestones separate in any report.
