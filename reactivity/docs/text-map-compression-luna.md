## What can be removed exactly

`planner.rs:431-498` stores the Parley cursor rectangle as `(x, y, width, height)`, with `x = r.x0 as f32`, `y = (f64::from(paragraph_height) + r.y0) as f32`, `width = (r.x1-r.x0) as f32`, and `height = (r.y1-r.y0) as f32`. The `Rect` coordinates are finite-checked. For this producer, `cursor.rs:406-433` supplies `r.x0 = line_x as f64`, `r.x1 = (line_x + 1.0_f32) as f64`, and y extrema that are the Parley line's min/max of block and content metrics. The `last_line_cursor_rect` path uses that same last line's metrics and `metrics.offset`; empty and trailing-empty content reach it when there is no adjacent cluster. ICU4X 2.3.0 explicitly yields boundary `[0]` for the empty string at `/root/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/icu_segmenter-2.3.0/src/grapheme.rs:346-350` (the lockfile pins version 2.3.0). Therefore an empty interactive map has one terminal Stop, not zero; the pinned geometry log reports `lines=1, stops=1` for empty text and for the short label reports 14 Stops.

The line row already stores source start/end and `top`/`height` (`layout.rs:90-98`). `freeze_line` computes those from the same f32 min/max metric operands as the cursor path (`planner.rs:394-429`). Rust documents scalar `f32` addition/subtraction and narrowing casts as IEEE round-to-nearest, ties-to-even ([primitive `f32` docs](https://doc.rust-lang.org/std/primitive.f32.html), [cast semantics in the Rust Reference](https://doc.rust-lang.org/reference/expressions/operator-expr.html)). For two finite f32 operands whose top exponents differ by at most 29, the exact sum/difference spans at most 53 significant binary positions and is exactly representable in f64. With a larger exponent gap, the smaller operand is at most 1/32 of a half-ulp at the larger f32 value, too small to alter the correctly rounded f32 result; subnormal and signed-zero cases still need explicit bitwise tests. Widening, computing once in f64, then narrowing should therefore match the producer's f32 operation. This is a mathematical argument to check against the actual toolchain/targets, not a substitute for bitwise producer-oracle tests.

Width is also exactly reconstructible from the stored x bits, but it is not a constant. The producer performs the f32 operation `x + 1.0` before casting endpoints to f64. Reconstruct as `(f64::from(x + 1.0_f32) - f64::from(x)) as f32`. At large x, `x + 1.0 == x` in f32, so width can be zero; other magnitudes can produce a representable width different from one. Preserve this explicit operation order.

A candidate Stop can consequently retain only `{byte:u32, x_bits:u32, affinities:u8, padding[3]}`: 12 bytes when laid out with 4-byte alignment. `x_bits` must use `f32::to_bits`/`from_bits`, so signed zero survives. The y/height come from the source-owned line row, and width uses the formula above. There is a subtle affinity split: if the original Upstream and Downstream `Rect`s compare equal, `append_carets` keeps the Upstream rectangle and sets mask `3`. IEEE `-0.0 == +0.0`, so a Downstream query must reconstruct that coalesced rectangle from the canonical Upstream geometry line even if `caret_line` reports a different line for the requested Downstream affinity. `caret_line` continues to use the requested affinity and source ranges. Do not derive line topology from y: zero-height or repeated-height lines are covered by the A source-owner tests.

This 12-byte reconstruction remains conditional on an independent bitwise oracle for every admitted geometry path. In particular, test both ordinary `cursor_rect` and `last_line_cursor_rect`, empty and trailing empty paragraphs, signed-zero coalescing, x at and above `2^24`, subnormal/cancellation/extreme operands, and line-height 0. The pinned source tests use real Parley paths and heights 0/1/4/22 in `reactivity/crates/canvas/src/text/line_ownership_tests.rs:12-220`; they establish ownership but do not, by themselves, prove every compressed rectangle bit.

## Two costed exact layouts

Let `N` be the emitted Stop count and `S = u64::from(text_len) + 1` the source-byte boundary domain. Keep all products, ceilings, byte offsets and counts checked; do not narrow source bytes or line indices to 16 bits. `N` can exceed `u32` in the theoretical max-source case because a source boundary can have two Stops. Query geometry arrays can still use ordinary `usize` only after checked conversion for the current target.

| Layout | Retained representation | Exact payload formula | Query shape |
|---|---|---:|---|
| A: 12-byte control | contiguous Stop records `{byte, x_bits, mask}` | `12N` for exact boxed payload, or `12C` for a `Vec` with measured capacity `C` | Existing byte `partition_point`; one stored source byte per Stop; line search only when reconstructing y/height |
| B: source-domain rank plane | one flat `u64` buffer: two bitmaps, packed x bits, packed masks, one rank directory and one count header | `16 ceil(S/64) + 8 ceil(N/2) + 8 ceil(N/32) + 8 ceil(S/256) + 8` bytes | Domain bit test plus bounded rank within one 256-byte block; inspect at most two masks in the group |

For B, bitmap A marks source offsets with at least one Stop and bitmap D marks offsets with a second Stop. D must be a subset of A. The source builder already emits byte-ordered groups and at most two records per queried boundary; validate that invariant while encoding and fall back to A if a future producer violates it. A rank-directory entry is the cumulative Stop count before each 256-byte block. For source offset `i`, compute `first = prefix[i/256] + popcount(A bits in the block before i) + popcount(D bits in the block before i)`. The group size is the A bit plus the D bit at i. Since a block is 256 bytes, the within-block work reads at most four `u64` words from each bitmap. The count header is `u64`; the data uses no separate per-array headers or exception allocation. `ceil(S/256)` entries suffice because N is in the header and queries only address `0..S`. Use checked arithmetic for all lengths and byte formulas.

The following are payload math, not measured allocator results. A and B both need the unchanged line/run arrays and the same `TextGeometry`/Arc ownership. Object/enum tags, pointer headers, allocator size-class slack and Arc control-block bytes must be measured on target builds and added; neither candidate creates per-Stop Arcs.

| Pinned A fixture | `N` / `S` | A exact 12N | B flat payload | Choice by payload only |
|---|---:|---:|---:|---|
| Empty interactive | 1 / 1 | 12 B | 48 B | A |
| “a short label” | 14 / 14 | 168 B | 96 B | B, subject to actual type/allocation overhead |
| Wrapped mixed text (936 bytes) | 786 / 937 | 9,432 B | 3,624 B | B, subject to build/query cost |
| 32 KiB repeated ASCII `a` | 33,513 / 32,769 | 402,156 B | 151,688 B | B, subject to build/query cost |
| One 2,049-byte grapheme | 2 / 2,050 | 24 B | 624 B | A |

The ASCII B total is 8,208 B for both bitmaps, 134,056 B for packed x bits, 8,384 B for masks, 1,032 B for the 129 rank entries, and an 8-byte N header. For the wrapped fixture the corresponding terms are 240 + 3,144 + 200 + 32 + 8 B. The one-long-grapheme row shows why choosing on source length alone is wrong. With ceiling effects and headers omitted, B is about `4.25N + 0.28125S + 8`, so its payload crossover with 12N is around `S/N = 27.56`; use the exact checked formula, including actual enum/object headers, not this approximation, to select a representation. If B loses, retain A. A full-width 32 KiB ASCII map has measured line/run capacity 49,152 B and current total geometry-array capacity 1,622,016 B; exact-box A would make the modeled arrays 451,308 B, and B 200,840 B. Those are arithmetic projections from the pinned stop count and unchanged line/run capacity, not observed allocations. A plain 12-byte `Vec` with a 65,536-record capacity would instead use 786,432 B for Stops and 835,584 B for all those arrays; verify its capacity rather than assuming the old Vec growth curve carries over.

A practical A comparison should separate record-width effect from slack removal: first measure the straightforward 12-byte `Vec` control, then exact `Box<[Stop12]>` or a two-pass exact fill. Rust's `Vec::into_boxed_slice` discards spare capacity like `shrink_to_fit`, and the allocator may return more bytes than requested; count any reallocation/copy, requested bytes and construction peak. A two-pass exact count/fill avoids a large temporary but repeats boundary/cursor work. Do not call the `12N` formula “retained allocator bytes” until the allocator ledger confirms it. Rust’s official [Vec docs](https://doc.rust-lang.org/std/vec/struct.Vec.html) specify the capacity and boxed-slice behavior.

B should not allocate its source-domain bitmaps before the exact size comparison selects it. There are two honest construction paths: count Stops then run the source/cursor pass again into the final flat allocation, or materialize the current A Stop vector and flatten it while both buffers coexist. The former charges a second scan/producer query pass; the latter charges the peak of both arrays. Record total allocation requests, requested/retained/peak bytes, and constructor work for both, without a timing forecast. Queries must remain allocation-free. No fallback may retain the original Stops or source string invisibly alongside B.

## A stronger repeated-line factorization, kept as a later control

The pinned 32 KiB case is explicitly `"a".repeat(32_768)` (`geometry_ledger.rs:19-29`). That makes a single verified line-local template worth testing after the 12-byte oracle is sound. The formulation uses the already-required `Line.start/end/top/height` rows as row metadata and one map-owned template containing relative source boundary offsets, exact x bits and exact affinity validity/masks. For byte-stride-one ASCII, relative offsets are implicit; the template need only hold x bits/masks. For a repeated multi-byte line pattern, store the exact relative byte offsets too. Absolute positions are checked `line.start + relative_offset`. Do not add a per-line template ID, HashMap or global cache: this candidate has one shared template only.

A position lookup first uses authoritative `source_line(position)`, never y, then the local relative-offset sequence. At a soft-wrap alias, Upstream resolves to the preceding line's end and Downstream to the following line's start. At a mask-3 coalesced Stop, geometry is the retained Upstream value even when the public query asks Downstream; source line reporting remains affinity-specific. The template must account for first-line start, repeated wrap edges, last-line terminal geometry, empty/trailing-empty paragraphs, and hard separators. A single repeated template is accepted only when every source-relative boundary, affinity pattern and x bit matches the frozen map (including seam ownership); hash may accelerate a candidate check but cannot be the proof. Any mismatch immediately keeps the general A representation. For more than one pattern, dictionary variants and their IDs/headers/build scratch would need a separate, fully charged design.

If a validated pattern has K relative boundary entries, its retained payload is `K * entry_size + exact edge overrides + one template/map header`, in addition to the line array already required by A. An ASCII template can use 8-byte `{x_bits,mask}` entries; a general relative-offset entry is at least 12 bytes before padding. Against the 32 KiB A fixture's `12N = 402,156 B`, an 8-byte template breaks even at `K < 50,269 - overhead/8`; a 12-byte template needs `K < 33,513 - overhead/12`. Since a one-row template's entries are drawn from the map's N line-owned Stop records, `K <= N`: if an exact single template exists, the ASCII encoding's payload is at most 268,104 B before its map/edge header. The report does not claim that the fixture actually matches or has that K: the ledger records N and 745 lines, not the local pattern length or bitwise match coverage. A builder can create the existing raw Stop vector, extract the first candidate template and compare each row, then discard the template on mismatch or raw vector on success; this charges template scratch and overlapping old/new buffers in peak. A two-pass verifier trades that peak for repeated source/cursor work. Either cost must be measured. Repeated text is an opportunity, not proof that a template matches.

Avoid deriving an x coordinate from `x0 + n*advance` or an integer ULP step as a shortcut. The producer advances and rounds f32 repeatedly; an algebraically reassociated multiplication can change bits, and the exponent/ULP transition and tie parity are input-dependent. Exact stored x bits in a verified shared template remove repeated values without changing arithmetic. A block-frame or delta encoding of x bits is another later experiment only if every value decodes bit-exactly and headers/exceptions are included.

## Why not a generic SIMD integer codec first

A and B are naturally cache-conscious for different accesses: A is a directly searchable 12-byte array; B separates source membership, exact x bits and masks into contiguous words. B's small rank directory bounds the lookup to a handful of words. Vigna's primary rank/select paper explains this word-parallel model and Elias–Fano for sparse monotone sequences ([Broadword Implementation of Rank/Select Queries](https://vigna.di.unimi.it/ftp/papers/Broadword.pdf)); Jacobson's foundational static bitvector work is [DOI 10.1109/SFCS.1989.63533](https://doi.org/10.1109/SFCS.1989.63533). A sparse third design can encode the G distinct Stop byte groups (strictly increasing values in `[0,S)`) with Elias–Fano, one exact second-Stop bit per group, and the same packed x/mask streams. Its ideal source-position payload is about `G * (floor(log2(S/G)) + 2)` bits before a practical select/predecessor directory and word padding. That can be smaller than a domain-sized bitmap for sparse maps, but `caret_bounds(byte)` needs predecessor/membership lookup, not just sequential decode; adding select support, directory, group counts and headers makes its actual bytes and query cost a separate design exercise. The one-long-grapheme fixture is too small to justify that overhead; a larger sparse-text fixture would be needed to compare it with A.

Stream VByte separates control and data and SIMD-BP128 packs blocks of integer arrays. Their primary studies target sequential or block decoding of integer lists, not random byte-to-caret lookup ([Stream VByte](https://arxiv.org/abs/1709.08990), [SIMD Compression and the Intersection of Sorted Integers](https://arxiv.org/abs/1401.6399)). Delta-encoding source bytes therefore needs restart/checkpoint metadata and a decode prefix for random caret queries. Frame-of-reference/BP128 has useful contiguous blocks but block width and exceptions must be charged. For exact x compression, first map finite f32 bit patterns into a reversible monotonically ordered u32 domain (invert negative encodings; flip the positive sign bit), then frame-of-reference encode each fixed stop block as `base:u32`, `width:u8` plus exactly packed `ordered_x-base` values. The transform is bijective, so this can preserve signed zero and every x bit without quantization; any 32-bit spread makes a block no smaller than raw x and header/word padding can make it larger. A concrete 128-stop block costs `4 + 1 + ceil(128*width/8)` payload bytes before block alignment/metadata, versus 512 raw x bytes; charge the header and accept per-block raw fallback when it loses. In bidi or mixed-sign/exponent geometry the spread may be wide; no compression ratio is assumed. This is a later orthogonal experiment after A and B because it does not remove the source-offset problem. The simdjson paper and [implementation](https://github.com/simdjson/simdjson) demonstrate SIMD byte-parallel structural scanning followed by indexed consumption in a different workload; they are not evidence that vectorizing a random caret query helps. Rust's portable `std::simd` is still marked nightly-only in the [official module docs](https://doc.rust-lang.org/std/simd/). Keep the first layout target-neutral and safe: ordinary `u64` bit operations/popcount plus bounds-checked indexing. `count_ones` may lower to an ISA instruction or a scalar broadword sequence; inspect release assembly for each supported target and benchmark both paths if CPU feature dispatch is proposed. Do not assume POPCNT or AVX on baseline x86-64, and do not make the common implementation nightly-only.

Unicode source boundaries remain grapheme boundaries from the pinned ICU4X segmenter, not scalar-value or fixed-byte positions. UAX #29 notes that grapheme clusters are relevant to UI interaction and should be atomic relative to word and line boundaries ([Unicode UAX #29](https://unicode.org/reports/tr29/)). A compressed map cannot reconstruct these boundaries from `TextGeometry.len` alone; it must retain exact byte positions in A, a source-domain membership structure in B, or retain and charge the original text. Re-segmenting a hidden source copy would reintroduce ownership/staleness and memory costs that A deliberately avoided.

## Failure, epoch and portability adversaries

- **Empty / terminal / separators:** preserve the one Stop at byte 0 for empty text and terminal Stop for a trailing empty line. CRLF remains an atomic source gap; U+2028 is a hard line break inside the paragraph. Test every endpoint and interior byte against the uncompressed oracle.
- **Wrap/bidi:** two different line-owned Stops can share a byte. Preserve exact sorted order and masks. A pair is not inferred from y or x. Soft-wrap aliases can have equal positions or signed-zero-only equality; mask 3 always decodes the Upstream rectangle.
- **Geometry:** exact x bits, zero/subnormal, signed zero, width at `2^24`, zero/repeated line heights, cancellation and maximum finite operands. Reject/fallback if a decoded extent is not a bitwise match; never quantize.
- **Unicode/font:** nested bidi isolates, Hebrew/Arabic, fallback-font runs, ZWJ emoji, regional indicators, variation selectors, a long combining grapheme, and UTF-8 interior offsets. The A producer's two affinity queries and grapheme boundary validation stay authoritative.
- **Rank arithmetic:** block edges 255/256, 511/512, final partial word, final legal byte `len`, zero/one/two group shapes, malformed D-without-A, count overflow, `len = u32::MAX`, and `S = 2^32`. Use u64 for source domain and counts, checked conversion to target `usize`; reject/fallback on address-space/allocation failure rather than imposing a narrower public text limit.
- **Access patterns:** point `caret_bounds` at both affinities, separate `caret_line`, range validation, directional interval/runs scans, nearest caret, containing grapheme and selection rectangles. Verify query allocation count remains zero and no path silently materializes a Stop vector.
- **Ownership:** `Arc<TextGeometry>` stays immutable and independently retainable; an Arc clone is still the same atomic shared-ownership operation and allocates no new map. `discard_interaction` can trigger explicit COW when shared. A/P/C old epochs keep each old geometry map until leases drop, so measure old-P + new-C and failed-build overlap with the compressed array included. Do not add per-stop Arcs, side caches, or a source-string lease. Rust's [Arc docs](https://doc.rust-lang.org/std/sync/struct.Arc.html) describe shared ownership and its thread-safety boundary.
- **Headers and peak:** measure `size_of` for `TextGeometry`, each storage enum, template/rank metadata and Arc owner on 64-bit and supported 32-bit targets; include allocator metadata, every buffer's requested/capacity/retained bytes, and construction peak. Rank-plane's single `Box<[u64]>` payload includes its count header and all padded words. Template verification's temporary raw vector is included. Box conversion can shrink/reallocate; don't report only retained arrays.

An independent test oracle should freeze each producer Stop as `(byte, mask, x_bits, y_bits, width_bits, height_bits)` before conversion and compare decoded results bitwise, then separately compare public queries to Parley `Cursor` results at every legal byte/affinity and assert invalid UTF-8/grapheme interiors stay `None`. This makes the data-format oracle independent of the decoder. Use the existing A source ownership/line tests as an additional authority, not as a replacement.

## Bounded next Sol slice and evidence required

1. **First:** land only the safe 12-byte Stop control, with exact producer arithmetic for width and line reconstruction. Keep the initial change easy to read and compare against the frozen 24-byte oracle. Retain the established single `Arc<TextGeometry>` ownership model and fallback semantics. Run the complete Unicode, native, ownership, cross-platform compile/test gates already required by A. No performance win is presumed.
2. **Measure capacity as a separate dimension:** compare `Vec<Stop12>` retaining measured capacity with exact `Box<[Stop12]>` or two-pass exact fill. Report exact stop count, map/run/line header sizes, capacities, requested/retained/peak bytes, allocation count, old-epoch overlap, and query allocations. If the box path copies/reallocates, charge it.
3. **Only after the oracle passes:** compare the rank plane against A on empty/short labels, mixed wrapped text, repeated 32 KiB ASCII, large UTF-8/emoji and one-long-grapheme controls. Record memory formulas and actual allocations, source-byte/affinity point-query and full-scan latency distributions under warm/cold cache, startup construction work, and optimized assembly for supported x86-64/ARM64/MSVC targets. Include a portable scalar fallback and measure it. Adopt B only if its retained-memory gain survives full headers and its actual query/build costs satisfy the product target.
4. **Then test one-template factorization** on the repeated `a` control and strict negative fixtures. Record K, exact match coverage, mismatch reason, template+line payload, construction scratch, fallback rate, and old epoch cost. This has the largest chance to remove whole repeated runs of per-stop data, but it has more iterator/API work than A and cannot replace the general compact fallback.

The immediate source change should be the 12-byte control and measured capacity split, not a speculative SIMD codec, global template cache or arena. The rank plane and template are costed research candidates, not a benchmark-backed adoption decision.
