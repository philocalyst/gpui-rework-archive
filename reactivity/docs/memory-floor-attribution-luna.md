# Native memory-floor attribution (frozen GPUI 724)

## Result

The frozen native-default GPUI 724 binary idled on Xvfb at **16,376 KiB RSS and 13,720 KiB PSS**, with four threads in an initial single-process sample. That one sample was not an accessibility cost estimate. I then built an exactly source/fixture-matched `x11-minimal` diagnostic and sampled both builds on two fixtures. The stable direction is a **roughly 3 MiB resident delta** for the full accessibility feature under this Xvfb setup, with three extra process threads; it is not a product proposal to disable accessibility. Full build provenance and exact executable hashes are in [`feature-control manifest`](../benchmarks/luna-accessibility-floor/runs/frozen724-feature-control-manifest.txt); all raw per-process rows and mapping summaries are preserved in [`frozen724-variant-smaps.txt`](../benchmarks/luna-accessibility-floor/runs/frozen724-variant-smaps.txt) and [`frozen724-variant-repeats.txt`](../benchmarks/luna-accessibility-floor/runs/frozen724-variant-repeats.txt). The native-default comparison source, original binary and fixture are pinned in [`native-default build manifest`](../benchmarks/nanoui-mygo-gpui/native-default-724ece73/build-manifest.txt) and [`capture manifest`](../benchmarks/nanoui-mygo-gpui/native-default-724ece73/captures/native-default-20261021/capture-manifest.txt).

The kernel split is more informative than a single PSS number: **1,916 KiB PSS anonymous, 10,866 KiB file-backed, and 938 KiB shared-memory PSS**. The X11 softbuffer mapping alone was 1,876 KiB resident (938 KiB proportional share). The executable contributed about 8.3 MiB resident across its mapped segments. Other large resident mappings were libc (1,220 KiB), libX11 (560 KiB), the glibc locale archive (320 KiB), and libm (308 KiB). This runtime loaded only four dynamic libraries through `DT_NEEDED` (`libgcc_s`, `libm`, `libc`, and the ELF loader); most Rust dependencies, including AccessKit, reside in the executable rather than separate shared-library mappings.

The executable is 24,576,136 bytes; its `.text` is 10.7 MiB and `.rodata` is 5.0 MiB. Those are file sections, not additional resident allocations: the observed mapped residency is the relevant page-floor evidence. No font file was mapped or open at the sample instant. The executable contains Unicode and shaping code/data, but this sample cannot separate those pages from other Rust code or determine whether rendered-font payload remains in heap memory. Four threads were present: main and a second GPUI-named thread, `blocking-1`, and `async-io`. Names alone do not identify the second thread's purpose. The session had no active AT-SPI registry/client and `org.a11y.Bus` was not activatable, but the full accessibility feature remained compiled and its inactive monitor path cannot be assumed allocation-free.

## What the sample does and does not attribute

Linux `smaps_rollup` explicitly sums mapping RSS/PSS and splits proportional residency into anonymous, file and shmem classes ([kernel procfs documentation](https://github.com/torvalds/linux/blob/v6.18/Documentation/filesystems/proc.rst)). This lets us state that most observed PSS is file-backed code/DSO pages, plus the X11 shared buffer. It does **not** say how many Rust allocator bytes are live versus cached, nor which Rust crate caused a clean executable page to be faulted in. `Private_Dirty` and `Pss_Anon` are useful process-private indicators, but neither is equivalent to allocator-live bytes. `/proc` reads are also point-in-time views; even the three-run PSS ranges below move as other processes map the same shared executable/library pages.

Each listed cell is three fresh serial processes, each sampled 750 ms after its first GPUI-present marker. No processes overlapped; Xvfb `:97` remained alive. Both `Auto` apps reported `ReferenceCpu`; no external AT-SPI client/registry was present. The blank fixture draws no text; the zero-row fixture still draws the header/button and invokes font/text services. Values are KiB; the paired deltas are for each serial run, not a causal allocator decomposition.

Paired RSS deltas were 2,988–3,212 KiB (blank) and 2,756–3,268 KiB (zero rows). Paired PSS deltas were 2,988–3,212 KiB (blank) and 2,752–3,328 KiB (zero rows). Median paired PSS deltas were 3,145 KiB and 3,248 KiB respectively. Across the two fixtures, the median paired anonymous-PSS increment was 288 and 280 KiB; file-backed PSS supplied most of the difference. In the zero-row fixture both builds share the same 938 KiB PSS for the X11 shm buffer, so that surface buffer does not explain the feature delta. Executable files shrink by about 5.55 MiB in `x11-minimal` (24.5 MB to 18.7 MB here); this is on-disk size, not resident savings.

The corresponding median clean/dirty categories were: blank `Shared_Clean` 2,052 KiB in both builds, `Shared_Dirty` 0, `Private_Clean` 8,840 vs 5,980, and `Private_Dirty` 1,792 vs 1,504; zero-row `Shared_Clean` 2,060 vs 2,052, `Shared_Dirty` 1,876 in both, `Private_Clean` 11,000 vs 8,192, and `Private_Dirty` 1,916 vs 1,636. These are resident mapping classifications; `Private_Clean` is not allocator-owned/live memory. PSS is lower than RSS because clean shared libraries and other file-backed pages are proportionally charged. The raw files retain each run's full `smaps_rollup`, thread list and top `pmap` entries.

The old minimal CPU-first samples near 8.5 MiB PSS and one thread were built from different source revisions. The exact 724 feature contrast is a much better control, although it measures the total optional accessibility feature bundle, not AccessKit alone: `x11` enables `accessibility`, which includes AccessKit + AccessKit-Winit, AccessKit Unix/AT-SPI, async-io, and its zbus stack. Package examples also compile dev-dependencies; for both build variants the Linux dev graph contains zbus and `accesskit_consumer`, but the normal dependency graph of `x11-minimal` has no AT-SPI/AccessKit/async-io/zbus path. The examples don't invoke those dev-only libraries. Subtracting source-revision-mismatched runs remains invalid.

The preserved AccessKit Unix probe separately showed a process-global worker path: across six adapters its async-io configuration stabilized at four tasks (main, AccessKit worker, `blocking-1`, `async-io`), while its Tokio configuration stabilized at three. The production native sample's thread names were `main`, another `luna_bench`-named thread, `blocking-1`, and `async-io`; only the dependency probe attributes the worker role, so the thread names themselves are not evidence of which crate created a thread. The synthetic probe is not a production binary, and its lower task count was not shown to reduce total memory. See [`probe README`](../benchmarks/luna-accessibility-floor/README.md).

## Next bounded experiment

The same-source feature-control experiment is now complete: the package's `x11` feature equals `x11-minimal` plus `accessibility`; both use the same release profile and `ReferenceCpu`. The zero-row and blank fixtures intentionally split text/font-service cost from window/runtime floor. Three samples are useful for showing a stable ~3 MiB range, but are too few for a high-confidence memory-ranking claim. The feature contrast reports the total optional bundle (adapter, monitor/executor and dependencies), not a per-crate allocator tally. Runtime AT was absent, so the monitor stayed on its inactive path; this does not test live AT behavior or prove no AT-related allocations.

The practical next seam is a focused **process-global Linux executor** experiment that keeps the status monitor continuously active and preserves off-thread action delivery, while measuring whether zbus's `blocking-1` plus async-io helper can be consolidated without adding a larger runtime. The Tokio probe suggests one fewer thread, but it also changes dependencies and its memory result is unknown; it is not an adoption recommendation. Require same-source resident snapshots, actual inactive→active AT-SPI transitions, action delivery, disconnect/reconnect and window-close tests before considering runtime changes. If an actual resident-file budget is the concern, first produce a link map and identify hot/unreferenced sections: GNU ld section GC removes only unreferenced reachable sections when configured (`--gc-sections`); it cannot discard code still referenced by the regular cross-platform target ([GNU ld documentation](https://sourceware.org/binutils/docs/ld/Options.html#index-gc_002dsections)). Any eventual target-profile split must preserve normal Linux `x11` accessibility and explicit GPU behavior.

No global allocator replacement, kernel setting, memory limit, or accessibility disablement is justified by this evidence. The feature-isolated control is a diagnostic, not a product profile recommendation.
