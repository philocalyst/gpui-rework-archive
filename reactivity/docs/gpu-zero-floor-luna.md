# GPUI WGPU zero-initialization floor: read-only audit

**Root-reviewed disposition (research, no implementation):** the most defensible portable cut is to make the Core texture-zero source lazy, keep its current fixed capacity, and make the queue pending-write stream own the “fill is ordered before use” state. Remove the unused default external-texture buffer/upload and empty bind-group layout from device startup as separate, smaller changes. Do not turn this into “all textures are render-pass clearable”: the existing copy fallback is needed for non-renderable and compressed formats and old backend paths.

This audit did not build, benchmark, launch native processes, or edit the checkout. Values below are resource descriptor sizes and recorded operations from source, not VRAM residency or process-RSS measurements.

## Pins and boundaries

The local source is GPUI commit 8c17a763ee7a5f1d2d932d375d2c839759d8a28b. The vendored Core and HAL are version 30.0.1 at upstream WGPU commit 40f4a34ebaf56f9a046231f54125ad046239d3f3; Core's retained archive SHA-256 is 14c018fce9b6270aa203c2fdd56f3cce996713534bd757e4ea58c8560b121f14, HAL's is b6b7fb58561a792bc237628ba0792e332de418fefe145f13b5ed8201e6d52f58. The working tree was only read.

The existing software-first presenter remains the actual blank-window floor: it can show a blank window without constructing WGPU. This report is about a device that has already been requested. A GPU-device allocation reduction must not be reported as blank-window RSS evidence or as a reason to move automatic GPU admission earlier. Keep the CPU presenter, its upgrade policy, accessible UI behavior, and recovery path intact; do not add a backend requirement or make the GPU renderer the only presentation route. See the [portable-presenter boundary](portable-presenter-luna.md).

## What is created today

| Owner | Startup work | Exact source |
| --- | --- | --- |
| WGPU Core | Creates a 512 KiB buffer with COPY_SRC/COPY_DST, plus TOP_LEVEL_ACCELERATION_STRUCTURE_INPUT when ray query is requested | device/mod.rs:34; device/resource.rs:470 |
| WGPU Core Queue | Acquires the pending-write encoder, records transitions, clears the whole 512 KiB Core buffer, then transitions it for COPY_SRC | device/queue.rs:59 |
| WGPU Core | Creates one empty bind-group layout | device/resource.rs:481 |
| WGPU Core | Creates a default external-texture parameters buffer sized as size_of::<ExternalTextureParams>(), stages the identity/default parameters, and queues a copy even when no such binding will be used | device/resource.rs:490, 567 |
| WGPU Core late init | Always constructs/stores a timestamp normalizer wrapper. It returns a no-op state unless the automatic-normalization flag is set, compute is available, and the timestamp period differs from 1.0; only the enabled path creates HAL resources | device/resource.rs:643; timestamp_normalization/mod.rs:86 |
| D3D12 HAL | Creates a separate 256 KiB zero source for generic buffer initialization | dx12/mod.rs:523; dx12/device.rs:72 |
| GLES HAL | Creates a separate 256 KiB zero source and uploads a 256 KiB host zero vector during adapter open | gles/mod.rs:138; gles/adapter.rs:1079 |

Thus the code describes 512 KiB of Core zero-source buffer per device, and an additional 256 KiB source on D3D12 or GLES: 768 KiB of buffer descriptors across those two layers. This is not a statement that drivers commit or residently charge exactly those bytes. Vulkan and Metal do not have the extra HAL source; they implement buffer clear with native fill commands. GLES additionally requests a temporary 256 KiB host Vec in adapter open. Its actual RSS lifetime and GL driver's allocation are unmeasured.

The Core zero source is also not “unused” for WGPU generally. It backs the portable texture COPY fallback and is passed as a dummy geometry/instance buffer to ray-tracing build-size queries. If the ray-query feature is requested, Core adds the ray input usage flag. Until each HAL size-query contract is proven, keep the handle and required usage available for ray-query devices even if texture-zero allocation becomes lazy. The contents appear to be for texture copies, but do not remove or split the ray-query resource based solely on that observation. References: ray_tracing.rs:60 and ray_tracing.rs:242.

The empty BGL is used as a synthetic empty group for holes in pipeline layouts, not as a universal need. Core stores the special RefDeviceEmptyBGL and resolves it through Device.empty_bgl when a group is absent. GPUI's renderer builds one layout with groups in order and binds group 0; its normal pipeline has no holes. A no-hole direct UI device does not need this internal HAL object, but general WGPU callers still can. See binding_model.rs:789, 859, 1076, and GPUI renderer.rs:907.

The default external-texture buffer is used when a normal TextureView is bound to an ExternalTexture slot. A real ExternalTexture already has its own params buffer. GPUI does not use that route. The default resource can therefore be created and staged on first use; keep its default data and binding behavior unchanged. See resource.rs:3397 and resource.rs:3404. This cut saves one HAL buffer creation and the setup staging/copy only for devices that never create that binding; no exact byte count is asserted because the allocation size is the Rust layout expression.

Late init also calls TimestampNormalizer::new for every device. When AUTOMATIC timestamp normalization is not enabled, compute shaders are unavailable, or the queue period is exactly 1.0, the normalizer stores None and creates no HAL resources; the actual feature path can create its own layout, shader, and pipeline. Do not count it as a direct-only resource cut without checking the instance flags and timestamp period. See device/resource.rs:643 and timestamp_normalization/mod.rs:86-109.

## Where the Core zero buffer is required

The full Core source scan found these uses:

- **Queue creation:** the unconditional clear of all 512 KiB in queue.rs:78 is only to establish the source's contents for future texture copies.
- **Texture COPY initialization:** command/clear.rs:303 routes TextureClearMode::BufferCopy through the Core zero buffer. It builds format-block and pitch-aligned row copies and slices them according to ZERO_BUFFER_SIZE / bytes_per_row (clear.rs:385). This covers non-renderable textures and formats that are not attachment-clearable.
- **Memory-init and command paths:** command/memory_init.rs:141 clears discarded surfaces through the texture mode; memory_init.rs:261 calls the same texture clear for deferred initialization. Buffer initialization at memory_init.rs:250 instead calls HAL clear_buffer directly. Explicit texture clear and transfer paths also pass the Core zero buffer: command/clear.rs:279 and command/transfer.rs:672.
- **Queue texture writes:** partial layer/aspect writes pre-clear the untouched part before the write because Core's init tracker is per mip/layer, not texel rectangle. Full coverage can drain that state without a preclear. See device/queue.rs:927 and the exact coverage predicate init_tracker/texture.rs:15. copy_external_image_to_texture has the analogous logic at queue.rs:1189.
- **Ray query:** dummy buffers are passed to BLAS/TLAS build-size queries; retain this case pending backend-contract qualification.

Core uses render-pass clears already when a D2 texture was created with a color-attachment or depth/stencil-write use. For that route, it creates per-subresource views and clears through a LoadOp::Clear pass; otherwise it picks BufferCopy. See device/resource.rs:1733, 1786, and command/clear.rs:481. Renderable surface targets do not need the Core zero buffer for their clear.

The portable copy path cannot be deleted wholesale. Vulkan's vkCmdClearColorImage requires TRANSFER_DST usage and the relevant format feature, and excludes compressed, depth/stencil, and sampler-conversion formats; see the [Khronos reference](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdClearColorImage.html). A texture without render-attachment usage cannot use Core's existing render-pass path. D3D12 RTV/DSV clears require render-target/depth-stencil resource capabilities and a compatible format; Microsoft also notes render-target flags can add memory on some architectures and are unavailable for BC-compressed textures ([D3D12_RESOURCE_FLAGS](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_resource_flags)). GLES and older/downlevel paths cannot be assumed to support one universal texture clear primitive. Keep the Core BufferCopy path as the portability floor.

## Direct-only colored UI has an avoidable texture-side trigger

GPUI's atlas is a private one-mip, one-layer R8Unorm texture with TEXTURE_BINDING|COPY_DST and no RENDER_ATTACHMENT usage. It begins at 1×1. Glyph insertion writes only rectangles, then publishes their tile records; the renderer always binds the atlas at binding 4. Relevant code: crates/gpu/src/renderer.rs:249, 276, 907. The shader samples a single clamped atlas texel for a mask and takes the direct-color branch when draw.atlas.z == 0 (crates/gpu/src/shader.rs:392). Inference: Core's static binding-use tracking can see the sampled atlas even when a frame's branch is color-only, so its uninitialized 1×1 texture can request BufferCopy clearing on that first frame. This should be confirmed by a future init-counter/fault test; source shows binding and usage, not the counter result.

A narrow public-API-safe experiment is to make the no-mask 1×1 atlas perform a full one-texel Queue::write_texture of [0] before it is bound. Core explicitly treats a fully covering write as initialized rather than clearing first; queue writes are ordered ahead of later submitted command buffers. The full-coverage condition is checked by the current per-mip tracker, and Queue::write_texture accepts unaligned bytes-per-row (its call passes “alignment not required”). This retains the exact atlas format, view, shader, and output semantics; it does not change WGPU's initialization guarantee. It adds a 1-byte content write and staging/queue work, so source alone cannot establish a net win. More importantly, it handles only the empty 1×1 atlas. Once glyph tiles are uploaded partially into a larger atlas, Core still needs to zero the uncovered parts under the current coarse subresource tracker.

A private GPUI atlas-coverage proof could eventually avoid that fill only if tied to the atlas object and generation, exact uploaded rectangles, and the same tile coordinates consumed by the current shader; each tile must be published only after its queue write is ordered, and no unrestricted texture view may escape. Current code already inserts the tile only after queue.write_texture and the shader clamps inside that tile. Still, a generic “initialized” certificate would be unsound: uninitialized texels outside the written tile must remain zero to all public WGPU consumers. This route requires a private API that cannot mark arbitrary WGPU textures initialized and a proof that every shader access is inside written coverage. It is not the first implementation cut. No current Core support for that proof was found.

## Candidate comparison

| Candidate | What it buys | Cost and risks | Assessment |
| --- | --- | --- | --- |
| **Lazy fixed 512 KiB Core source** | A device that never needs a texture BufferCopy can avoid the Core 512 KiB object and its initial 512 KiB clear command. It preserves copy batching once used. | Nontrivial one-time publication/ordering and delayed HAL errors. Does not remove D3D12/GLES HAL zero source. | **Best Core cut.** Keep fixed size for first pass. |
| **Bounded dynamically sized source/leases** | Could use less than 512 KiB on first texture clear. The source comment's 16K RGBA32 row is 16,384×16=262,144 bytes (256 KiB), so current capacity is two such rows before pitch alignment. | Smaller capacity can increase copy-region count. Choosing size must use actual format block, device limit and backend copy-pitch alignment. Growing/replacing a buffer requires old handles to stay alive through every pending and in-flight encoder and prevents races. | Defer. It adds complexity with no evidence that the current 512 KiB is costly when used. |
| **Use native texture clears everywhere** | May remove Core's staging source for some backend/format subset. | Vulkan native color clear is restricted; D3D12/GLES portability and format/resource-use constraints remain; compressed or nonrenderable formats need fallback. | Reject as global replacement. Existing renderpass clear already covers the portable renderable subset. |
| **Atlas full coverage or proof** | Can remove the initial 1×1 atlas clear for direct color-only GPUI frames; eventually maybe avoid glyph-atlas whole-subresource clears. | Full atlas upload costs CPU fill/upload; proof requires strict private ownership and exact shader domain. | Small no-mask write is a safe experiment; defer certificates. |
| **Lazy empty BGL and default external params buffer** | Skips one unused HAL BGL for layouts without holes; skips one external params buffer/staging copy for devices without that binding. GPUI's common path needs neither. | First-use error/lifecycle moves into pipeline-layout or bind-group creation; default data and ownership must remain exact. | Good small cuts, independent of zero-buffer work. |
| **Lazy pending-write encoder acquisition** | Queue::new currently acquires a HAL command encoder even before a pending operation exists; with the default external-params upload deferred, that encoder can also be acquired only on first activation. | Activation then needs a fallible encoder-create path; this moves a device-request failure to the first queue operation and must preserve error scopes. | Small follow-on if direct-only startup needs no pending writes. |
| **Lazy HAL zero sources (D3D12/GLES)** | Defers 256 KiB HAL source and on GLES the host zero-vector upload until generic HAL buffer clearing is needed. | WGPU buffer zero-before-read remains required. D3D12 source is owned in shared device state; GLES source is Queue-owned and its element-array fallback still creates a per-range host Vec. Must preserve context/thread and Drop behavior. | Worth separate slice after Core queue path; no guarantee GPUI avoids buffer clears. |

The lazy fixed path retains a small per-device/per-queue state header and pays a state check/lock plus buffer creation/fill at first BufferCopy use; the header's exact Rust size and the first-use CPU cost have not been measured. Dynamic sizing adds capacity/generation ownership and per-submission leases, plus row-size work on first use and possible growth allocations. Lazy HAL sources similarly move open-time cost onto the first generic buffer clear; on GLES the element-array fallback can still allocate/upload a per-range zero Vec. These are costs to instrument, not claimed speedups. The prior lazy-indirect report's Device-size change (1,344 to 1,104 bytes) belongs only to that unrelated change and cannot price these fields.

For dynamic sizing, command/clear.rs requires at least one format-aligned row (max_rows_per_copy > 0) and rounds row count to block height. At 16K×RGBA32 the row is 256 KiB; 512 KiB allows two rows when pitch is that value. A candidate capacity must calculate bytes_per_row = align_to(width / block_width × block_size, lcm(copy_pitch, block_size)) for the actual format/texture, then bound it by the device's legal texture dimension. No smaller exact capacity is recommended without that calculation for all supported backends.

## Initialization policy and backend evidence

WebGPU's specification says resources are conceptually zero-initialized, allows skipping work when an implementation sees developer initialization, and warns that a queue operation's initialization status may only be known when it is enqueued—not when encoded. That is the governing constraint for the Atlas write experiment and for deferred initialization ([WebGPU, Uninitialized data](https://www.w3.org/TR/webgpu/#security-uninitialized); [reviewed source pin](https://github.com/gpuweb/gpuweb/blob/0ba4e22611c995abd3077e422cb82e5ad203974b/spec/sections/privacy-and-security.bs#L38-L57)).

Dawn provides a useful primary-source architecture comparison: its command-buffer code checks subresource initialization, changes an uninitialized render-pass attachment Load into Clear, and calls a texture clear for non-render-pass cases ([Dawn CommandBuffer.cpp at commit 2d4d6e9b3b3ed923d62ccffebdaf52371d47d89d](https://dawn.googlesource.com/dawn/%2B/2d4d6e9b3b3ed923d62ccffebdaf52371d47d89d/src/dawn/native/CommandBuffer.cpp)). At that same verified commit, its D3D12 backend uses attachment clears when the resource carries the depth/stencil or render-target flag, and otherwise clears through an upload-buffer copy ([Dawn D3D12 TextureD3D12.cpp](https://dawn.googlesource.com/dawn/%2B/2d4d6e9b3b3ed923d62ccffebdaf52371d47d89d/src/dawn/native/d3d12/TextureD3D12.cpp)). It sets the color render-target flag from RenderAttachment usage. This is evidence for retaining a copy fallback. The producer's different D3D12 pin returned HTTP 404; its historical claim about adding render-target flags to all uncompressed textures was not verified and is withdrawn.

Backend source confirms different zeroing boundaries:

- D3D12 HAL creates its zero source with D3D12_HEAP_FLAG_NONE; the code comments that it is zeroed by default. HAL clear_buffer copies from it in chunks (dx12/device.rs:102; dx12/command.rs:606). The resource is in shared device state and encoders retain that shared state. A HAL lazy change must preserve that in-flight owner.
- GLES explicitly fills and uploads a host Vec<u8> at open. Queue clear_buffer copies from that source when buffer roles allow, but for element-array buffers it uploads a new zero Vec for each range instead (gles/adapter.rs:1092; gles/queue.rs:334). Adapter::open uses raw GL names for VAO/source/FBOs; errors after earlier acquisitions can return before Queue ownership is assembled, so any refactor at this boundary needs a cleanup guard.
- Vulkan and Metal HAL fill the destination buffer directly (vkCmdFillBuffer, Metal blit fill) rather than maintaining a HAL source (vulkan/command.rs:283; metal/command.rs:594).

Native memory flags do not make a portable shortcut. Vulkan allocation is not baseline-zeroed; the optional VK_EXT_zero_initialize_device_memory defines an explicit opt-in zero flag, while lazily allocated memory is restricted to images with TRANSIENT_ATTACHMENT use. Neither can be assumed by this buffer/texture fallback ([Khronos zero-init extension proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_zero_initialize_device_memory.html), [Vulkan memory allocation](https://docs.vulkan.org/spec/latest/chapters/memory.html#memory-lazily-allocated)). D3D12's CREATE_NOT_ZEROED permits the OS to skip zeroing in some cases but does not guarantee it; the HAL's source uses a CUSTOM L0/L1 heap (dx12/device.rs:88), while Microsoft's flag applies to default-heap committed resources. The current HAL relies on the normal behavior for its own source, which must itself contain zero ([Microsoft D3D12_HEAP_FLAGS](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_heap_flags)). Neither API supports a universal memory/RSS claim.

## Required design shape and lifecycle hazards

A bare OnceLock<Box<dyn DynBuffer>> is not sufficient. It can uniquely publish a handle, but it cannot prove that the initial clear reached the queue before any texture copy that references the handle. Core's queue contract makes this concrete: queue pending writes are inserted ahead of the next user command buffer (device/queue.rs:358); Core currently locks the device texture tracker while it records first-use texture clears, then obtains pending writes later in submit (queue.rs:1457, 1529). It also records partial Queue::write_texture clears directly into the pending encoder while holding its lock. A first-clear implementation must coordinate both lanes.

A viable fixed-buffer shape is a device-owned optional handle plus queue-owned init state. On the first actual BufferCopy need, acquire/create the handle and encode a zero fill and state transitions in the pending-write encoder before the operation that uses it. Do the same before any user command buffer containing an explicit Core buffer-copy clear or deferred texture initialization can be submitted. Publish “ready” only once the fill is in the queue's ordered submission stream; while it is merely recorded, keep it represented as pending in that specific encoder. If submission fails before enqueue, the next operation must still be able to retry or the device must already be invalid. Queue serialization is the ordering boundary; do not expose a source whose fill exists only in one concurrently recorded user encoder. If a scan/preflight is used to detect possible first use, it must cover explicit texture clear commands, memory-init actions, transfer initialization, Queue partial writes, external-image writes, and ray-query dummy use. Avoid an extra whole-command-buffer scan on every ordinary submission: fuse admission with the existing initialization walk or confine discovery work to the unresolved first-use state. A submit-entry check alone cannot see a first need discovered later by deferred memory initialization.

Queue::new also acquires an otherwise empty HAL command encoder before constructing PendingWrites. If both the Core zero fill and default external-params upload are absent, moving this acquisition into a fallible PendingWrites::activate can avoid that one startup acquisition for devices that issue no pending queue writes during device setup. This is independent of the zero-buffer correctness work; it shifts encoder-creation failure and needs to be measured separately.

Preserve all current ownership/error properties while moving the work:

- **No callback under state locks.** Lazy indirect validation already uses the existing cross-target OnceCellOrLock and publishes sticky errors before calling Device::lose. A loss callback can reenter Core. Record the result first, release the init/pending locks, and only then route a Lost/OOM/Unexpected error through the existing handler; Device::lose invokes the callback after it takes/releases its own closure mutex (resource.rs:5506). Do not call it while a OnceCell, queue pending lock, or zero-state mutex is held.
- **Keep API error behavior.** Today Core buffer/layout acquisition failure occurs during request-device; a lazy first-use failure moves to texture write, command submit, or bind-group/pipeline-layout creation. Preserve validation/error scopes, OOM classification, and device-loss callback rules at those new seams. Failures in internal memory-init cannot become panics or silent “initialized” bits. In particular, acquire every fallible prerequisite before draining or marking the affected texture-init tracker, or explicitly restore that tracker on recoverable failure. Publishing a unique HAL handle proves neither zero-before-read nor successful queue submission; that distinction concerns GPU initialization/order, and does not by itself establish Rust undefined behavior.
- **Guard partial HAL acquisitions.** Core Device Drop explicitly destroys zero buffer, empty BGL, default external params buffer, and fence (resource.rs:309). Device::new acquires these sequentially with fallible ? before assembling Self (resource.rs:457). Move fields or change construction only with a stack/RAII guard that releases every earlier raw HAL owner on a later acquisition error and on Rust unwind.
- **Keep lock order explicit.** Texture-view bind-group creation holds the snatch read guard; the rank graph permits its pending-write lock, but a new lazy cell must not introduce an inverse dependency. Audit every caller before putting pending activation inside a shared initializer. A callback cannot run with that outer guard merely because the initializer released its own lock.
- **Retain queue and in-flight owners.** Queue keeps an Arc<Device> because the pending encoder can reference Device.zero_buffer (device/queue.rs:50). The Core device remains the destruction owner and should be dropped after queue/in-flight work. For any future resizeable source, old buffers need strong per-submission leases until all referencing work completes.
- **Imported handles remain caller-owned per existing contract.** Internal source ownership must stay separate from imported buffers/resources; injected failures around first-use init must not call destroy on caller-owned native objects. The [lazy-indirect archive](../evidence/lazy-indirect/README.md) documents imported-resource failure/drop patterns.
- **Trace/replay remains deterministic.** Treat this as Core-internal initialization, not a new public trace action or schema. Replay a direct-only trace with no source initialization and a trace whose first operation needs BufferCopy; verify the replay's first fill precedes the copy. The existing lazy-indirect evidence's narrow buffer-action replay is not evidence for full native trace replay.
- **No public initialization relaxation.** Public textures and buffers keep the WGPU zero-before-read guarantee. A GPUI-only atlas coverage route must be private, tied to a validated texel domain and texture generation, and cannot mark arbitrary textures initialized.

## Minimum decisive gates for a future implementation

1. **Use and byte counters:** prove that queue/device construction performs no Core zero allocation or fill on a device with no BufferCopy, no external-texture binding, and no empty pipeline group. Then trigger the first render-pass-clear texture, full-coverage atlas upload, partial/non-renderable texture, compressed texture, explicit clear, ray-query size request, and generic buffer zeroing separately. Count Core/HAL creations, clears, copy regions, and destroys. Report descriptor bytes separately from driver/RSS.
2. **Ordered concurrency:** concurrently record explicit texture clear, submit a sampled-but-uninitialized texture, Queue::write_texture partial writes, full writes, and submit/map flushes. Force interleavings around pending encoder activation and first initialization. Assert every source read is after a zero fill in queue order, no later operation observes a merely-recorded fill from an abandoned submission, and repeated uses do not reinitialize after a successful enqueue.
3. **Failure and callback reentry:** inject failure at Core buffer create, pending encoder acquisition/begin/end/reacquire, and HAL submit. Cover OOM, Lost, Unexpected, recoverable failure, Rust unwind, and competing first uses. In a loss callback inspect the published sticky state and reenter ordinary buffer creation and registration; it must not deadlock and existing callback/error-scope behavior must hold.
4. **Ownership and teardown:** fail every later Core acquisition after fence/zero/BGL/default-param handles and assert exact destruction; test device/queue drop with a pending encoder and submitted work in flight. Run equivalent imported-buffer failure coverage and verify the imported owner's destroy callback and native ownership rules are unchanged.
5. **Trace and portable backends:** verify direct/replay traces and first-copy replay without adding internal actions. Run Core qualification over noop and actual Vulkan, plus DX12, Metal, GLES/WebGL paths where available, including compressed and non-renderable texture clears. No extension, RENDER_ATTACHMENT usage requirement, or backend-specific policy is acceptable for the baseline.
6. **GPUI visible behavior:** the CPU-first blank window and accessibility behavior stay unchanged; GPU admission remains optional. Exercise direct color-only frames and first text/mask frames on the supported backend matrix, confirm pixels and stable recovery, and separate renderer timing from Core constructor counts.

## Evidence already available, and its limit

The existing lazy-indirect work is useful as a pattern: on its Vulkan/llvmpipe constructor observation, device+queue+late setup had 13 fewer validation HAL acquisitions, 1,608→39 Rust allocation calls, and 474,723→6,026 requested Rust bytes. Its own report excludes driver/libc/GPU allocations, RSS, and elapsed time; it made no timing claim. It also documents the correct sticky-result, callback-reentry, imported-owner, and unwind patterns. These are independent gains from the direct-only GPU zero-buffer question; do not add them together or claim they measured the zero-source savings. See the [lazy-indirect counts and ownership qualification](../evidence/lazy-indirect/README.md).

## Root review and next implementation boundary

The original Luna report and review record are preserved in [the evidence directory](../evidence/gpu-zero-floor/README.md). No shipping source, allocation counter, command-order probe or native measurement was changed for this audit. The first implementation spike isolates the default external-texture parameters owner, then proves ordering/error/drop behavior before considering the larger zero-source change. Empty-layout creation remains separate: `BindGroupLayout::try_raw` currently admits only `InvalidResourceError`, and a lazy acquisition must resolve how HAL errors reach the public getter without an unchecked expectation.
