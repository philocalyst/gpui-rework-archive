# GPUI text geometry: exact pair elimination before worker parallelism

**Integration disposition.** Supplied report SHA-256 `4ce92f14c6cb0c9bcfa5427d94c90515ed5534ec2ab4b17bf4b5b4690e6344e5`. Root reviewed the report and implemented an isolated pair-query candidate at `1a1206f1c5`, based on main `9f9ed16a1a`. The earlier raw-pair oracle at `a03dd04643` passes 80,352 accepted geometry comparisons, 40,032 snapped queries and 10,032 distinct-affinity cases. The successor delays fallback cursor construction and compares packed Stop output against direct producer geometry; 193 parallel Canvas cases/docs pass (four ignored). This is not main adoption or measured acceleration. Branch census, optimized assembly and matched performance/allocation controls remain outstanding. Worker parallelism is not implemented by this report.

**Status:** read-only source audit and design proposal. I ran no builds, tests, measurements, or checkout edits. No latency, memory, or speedup claim is made.

## Source pin and scope

All local paths below refer to the immutable source snapshot `619788822bf4f55818007ac596af0d607b4ebb3b` (tree `4ae6d1c345caa4250e4f66be03e66e33e4df857b`) in `/root/gpui-ce3`. I read it using bounded `git show <commit>:<path>` commands; I did not use the moving checkout files as evidence. The vendored Parley tree identifies upstream Parley 0.12.0 and upstream commit `6e1143dda817360dd3a2a64f9133c6e5dfabd881` in `reactivity/vendor/parley/GPUI-PATCHES.md`; `CursorGeometry` is a local GPUI patch, so that local source, rather than an upstream URL, is authoritative for its new entry/byte tables.

The strongest next slice is to remove redundant affinity work inside that borrowed cursor index. It uses one layout, creates no worker or retained state, and preserves the existing small-text direct-query path. The scoped-parallel alternatives remain possible experiments, but the present ownership and error boundaries make them a worse first change.

## Current owner and actual work

At the pinned `reactivity/crates/gpui/src/runtime.rs:557-563`, each `TextSite` owns its source value, binding, and optional shaped layout. `TextSite::shape_for` at `693-722` normalizes the width, checks the exact width-bit key and whether interactive geometry exists at byte zero, then either returns the cached layout or shapes and replaces it.

One mutable `TextShaper` is created for the whole measurement and final-layout pass (`runtime.rs:2567-2583`). Cephal's measurement closure runs serially at `2648-2690`; it reuses this service and writes results into individual `TextSite`s. Intrinsic min/max probes are noninteractive; known or definite width probes request interactive maps. The `LayoutTree::compute_with` API borrows a `FnMut`, and its private `Engine` borrows `&mut LayoutTree` and the callback (`reactivity/crates/core/src/layout.rs:413-425, 617-620`). The adapter's `batches_help` remains false, so Cephal's default request path is serial. Turning on batching would require changing the adapter's borrowing and measurement contract, not just adding a thread scope around the existing closure.

Final paint calls `shape_for` again with `Some(layout.content_box_width())` and `interactive=true` (`runtime.rs:2863-2887`). It is a true cache hit when the normalized width bits match and byte-zero caret geometry exists; otherwise it is work. A future shape batch should be restricted to those exact misses, since known-width measurements may already have produced the final interactive map. There is an additional sequencing constraint: `refresh_inspector(true)` runs after layout and the paint loop refreshes two caption values at the inspector boundary, invalidating those `TextSite` caches (`runtime.rs:2703-2707, 2737-2751`; `runtime/inspector.rs:519-559`). A prepaint batch cannot include caption slots before that refresh; a batch after it would require splitting/reworking the current interleaved paint loop.

The one planner is deliberately reusable. `TextShaper` owns one optional `Planner` (`reactivity/crates/canvas/src/text.rs:261-315`); that planner owns a private Parley `FontContext`, `LayoutContext`, one reusable `parley::Layout`, `FontSet`, font IDs, and cmap state (`text/planner.rs:43-79`). `shape_inner` lowers the current paragraph into that one layout and streams the output before reusing it for the next paragraph (`planner.rs:163-195` onward). Each additional worker shaper would therefore add its own planner/context/layout/cmap scratch and another font lease. Fallback initialization goes through a process-wide weak registry mutex (`text.rs:71-96`), so parallel cold fallback requests can contend there. Returned `TextLayout`s themselves own an immutable `Arc<FontSet>` lease (`text.rs:208-238`); that is part of the output lifetime and cannot be removed by scheduling.

The optional Canvas `RenderPool` is not a suitable hidden executor. Its constructor starts persistent Rayon threads, and its API is specifically `render(Frame, writer, pixels, offsets, members)` for raster work (`canvas/src/canvas.rs:1913-2014`). It is also behind the `parallel` feature, while `gpui_canvas` defaults to `simd` only and GPUI requests `default-features = false` (`canvas/Cargo.toml:7-24`; `gpui/Cargo.toml:13,28`). Enabling it would add idle workers, feature wiring, and an unsuitable render-specific API. Rust scoped threads can borrow non-`'static` operands and join before returning, but `thread::scope` still creates threads when invoked and propagates an unhandled worker panic; `Builder::spawn_scoped` is needed if thread creation failure must be returned as `io::Error` ([Rust `thread::scope`](https://doc.rust-lang.org/std/thread/fn.scope.html), [Rust `Builder::spawn_scoped`](https://doc.rust-lang.org/std/thread/struct.Builder.html#method.spawn_scoped)).

## A smaller exact work-elimination seam

`append_carets` already avoids building `CursorGeometry` for at most eight grapheme boundaries; longer strings build one transient index (`reactivity/crates/canvas/src/text/planner.rs:436-449`). For each boundary it currently asks the index for both affinities and, if accepted, asks for both geometries (`planner.rs:452-468`). In the indexed route, `CursorGeometry::cursor` resolves the byte's entry (`reactivity/vendor/parley/src/editing/geometry.rs:79-87`); `geometry` then resolves the preceding and current source cluster again (`geometry.rs:89-104`). Thus a valid interior boundary takes six source-path/cluster resolutions in the current source: two `cursor` calls each resolve the next cluster, then two geometry calls each resolve previous and next. This is an operation count from the code, not a timing estimate.

Add one borrowed pair operation to the local Parley `CursorGeometry` API, conceptually `geometries_at(byte, width) -> Option<[BoundingBox; 2]>`. It would:

1. Resolve `next = cluster(byte)` once and build the upstream cursor from that source cluster. If its canonical cursor index is not `byte`, return `None`; the downstream constructor uses the same cluster and therefore has the same canonical index, so the current producer skips both geometries.
2. Resolve `previous = cluster(byte - 1)` once. For byte zero there is no previous cluster. If a source cluster exists there, the cursor constructor forces both requested affinities to downstream; for empty text, the missing cluster instead canonicalizes both requests to the text-end upstream cursor. At text end, a missing next cluster likewise canonicalizes both requests to the same upstream end cursor. Compute that canonical endpoint geometry once and return it twice.
3. For an interior boundary, first try a fast path using the exact cached entry indices. Require: both clusters exist; `previous.text_range().end == byte` and `next.text_range().start == byte`; equal `ClusterPath` line and run indices; equal direction; neither cluster is a hard line break; and actual visual adjacency in the existing `entries` table. The direction-aware adjacency check is `previous_entry + 1 == next_entry` for LTR, and `next_entry + 1 == previous_entry` for RTL. Use checked integer arithmetic and the existing byte/entry slices; no hash, allocation, `unsafe`, or stored field is needed.
4. On that proof, run `geometry_with` once using the upstream cursor and the already-resolved `[previous, next]`, then return the same `BoundingBox` twice. If any test fails, build the downstream cursor from the already-resolved `next` and invoke the existing `geometry_with` twice with the same cached cluster pair. This fallback preserves the old source-affinity rules.

The exact equality proof follows the pinned source operations. `CursorGeometry::new` visits each run's `visual_clusters`, stores the current `offset`, then performs `offset += cluster.advance()` for the next entry (`geometry.rs:43-56`). `Cluster::advance` is a deterministic read of immutable atom/grapheme/run-spacing data (`vendor/parley/src/layout/cluster.rs:183-191`, `layout/spacing.rs:193-210`); it can be zero, negative, or a ligature-split value. For an LTR boundary, upstream geometry places the caret at `previous.offset + previous.advance`; downstream geometry uses `next.offset`. With adjacent entries in the same run, those are the same f32 addition over the same operands in the same order. For RTL, upstream uses `previous.offset`; downstream uses `next.offset + next.advance`. The required reversed entry adjacency means the latter is exactly the prefix assigned to `previous.offset` during index construction. Both queries use the same cluster line metrics and the same cursor width, so their four bounding-box coordinates, then the producer's `(x0 as f32, (height + y0) as f32, (x1 - x0) as f32, (y1 - y0) as f32)` operations, have the same bits. This does not rely on positive advances, monotonic x, font width, or numeric `Rect` equality; signed zero is preserved by reusing one actual result.

The `Cursor` implementation confirms the endpoint and canonicalization facts: a source cluster beginning at byte zero forces downstream, while no source cluster becomes `(text_len, Upstream)` (`vendor/parley/src/editing/cursor.rs:17-43`). Geometry attaches to logical source neighbors, not visual neighbors; upstream uses the previous cluster unless it is a hard break, while downstream uses the next cluster, with a final-line fallback (`cursor.rs:293-317`). That is why the optimization must fall back around bidi/run/line/hard-break boundaries rather than infer from text direction alone.

Do **not** add a blanket `!previous.is_end_of_line()` or `!next.is_start_of_line()` guard. Those cluster predicates are direction-aware (`vendor/parley/src/layout/cluster.rs:270-279`); for RTL, a source-interior cluster can be the visual line edge. Same run and line plus actual adjacent entries is sufficient to rule out an intervening wrap. Hard-break exclusion remains explicit. A soft wrap moves one neighboring source cluster to a different line, so it fails the same-line predicate.

Ligatures do not invalidate the arithmetic: Parley exposes grapheme clusters and divides a shaped ligature's advance over those clusters (`cluster.rs:183-205`). The helper still requires source-contiguous ranges and the actual visual entry relation. Combining sequences, emoji ZWJ graphemes, and any cursor byte that snaps to another canonical cluster remain governed by the existing grapheme segmenter and `cursor.index() == byte` admission (`planner.rs:443-463`; Unicode's normative grapheme-boundary rules are [UAX #29](https://www.unicode.org/reports/tr29/)). A run boundary, bidi boundary, line wrap, hard line break, missing/overlapping source range, or mismatched entry order takes the unchanged two-query fallback.

This should be called only in the existing `CursorGeometry` branch for long maps at first. Keep the direct path for small strings unchanged. It adds no retained field, map, `Arc`, font lease, lock, worker, or scratch allocation. It also shares the two cluster lookups on the fallback path: the valid indexed byte now has two path resolutions rather than six, while only a boundary proved safe omits the second geometry query. The authored line/header delta is not measured; do not state a byte saving until an implementation is reviewed.

## What parallelism would cost and why it is not first

The most contained possible worker partition is after `compute_with`: derive each text node's exact final content width and select only `TextSite`s for which the same `shape_for` predicate is a miss, then shape disjoint sites using worker-private `TextShaper`s and merge successful `Shaped` results back before paint. This avoids concurrent mutation of the layout tree and allows scoped borrowing. It is not a zero-cost splice today: the request list and safe partition/merge need temporary owner/index data; each worker owns a separate reusable planner and font/parser state; output layouts retain font-set leases; fallback lookups may lock; and inspector refresh forces a batch boundary. If the work is not large enough, the setup and duplicated cache scratch are pure overhead. A scheduling threshold must come from target measurements, not a guessed text-length cutoff.

A second candidate is parallel caret extraction from an immutable Parley `Layout`/`CursorGeometry` after line breaking. The current planner does not retain those layouts: it uses one `Layout` as scratch and lowers carets before the next paragraph, then drops the planner after the pass (`planner.rs:46-79, 185-195`). Extracting in parallel therefore either retains multiple full layouts or creates extra staging/merge storage for variable one-or-two-stop results. `CursorGeometry`'s sync traits and the layout's thread-safety should be compile-proven before even trying a borrowed shared-layout split. The pair operation above removes redundant queries at their source without this lifetime/scratch expansion.

If later measurements justify scoped shape workers, enumerate only true final-width misses after layout; keep cache hits on the existing path. Partition mutable text slots with safe disjoint slices and preserve declaration-order paint. Keep one planner per worker for reuse within that batch, but measure the per-worker `FontContext`, `LayoutContext`, Parley layout, cmap/fallback state, output layouts, and font Arc leases; do not retain workers between windows. Use `Builder::spawn_scoped` or an explicit serial fallback for spawn failure, join all started workers before fallback, and route worker `Result` failures through the existing error policy. Unhandled worker panic currently reaches GPUI's present panic boundary, which clears shaped caches; changing that boundary requires separate review. Do not parallelize the raster cache or `TextSystem`, which is mutable (`canvas/src/text.rs:318-355`).

## Independent correctness gates for the pair helper

Use the current two-cursor/two-geometry route as the differential oracle, not expected coordinates computed by the new helper. For every source grapheme boundary, compare the two bounding boxes coordinate-by-coordinate with `f64::to_bits`; then compare the producer's four `f32::to_bits` values and the emitted stop records. Also assert whether the adjacency fast path fired and verify its source ranges, path, direction, and index relation. Existing index-vs-direct bitwise tests are in `planner.rs:728-755` and are a useful baseline, but the new pair helper needs its own old-route oracle.

The adversarial corpus should cover empty and one-boundary text; start/end and snapped-away offsets; LTR and RTL; mixed bidi/run boundaries; wrapped and emergency-wrapped lines; CRLF and U+2028; whitespace/alignment; combining/ZWJ and fallback-font runs; ligature continuations; zero-width and negative advances if admitted by available fixtures; zero-height metrics; signed-zero and large finite coordinates; and rejected nonfinite geometry. For accepted same-run LTR/RTL pairs, directly test entry adjacency and exact bit equality. For every boundary failing any condition, compare the helper's fallback result with the original path and ensure no missing/extra stop or affinity-mask change. Finally compare `TextGeometry` query results and hit/selection behavior against the existing geometry path.

The conclusion is narrow: prove and test this pair API first. It cuts duplicate source/path work without adding retained owners, fonts, worker startup, or a second shaping algorithm. Parallel execution remains an evidence-gated option only if measured cache misses are large enough to justify duplicating planner state and adding a safe merge phase.
