# Accessibility text and virtual-list follow-up

Research pass: 2026-10-21. This supplements [`accessibility-frontier-luna.md`](accessibility-frontier-luna.md) and [`accessibility-incremental-luna.md`](accessibility-incremental-luna.md); it avoids repeating adapter setup, general delta publication, and Linux activation findings. I read the live bridge in `crates/gpui/src/native/accessibility.rs`, the borrowed `Part` query in `crates/gpui/src/runtime/query.rs`, the frozen metadata sheet in `crates/gpui/src/runtime/metadata.rs`, and the list planner in `crates/gpui/src/runtime/list.rs`. ## Findings that change an implementation decision

1. Preserve the current focus scan over acknowledged P. `SemanticState.focus` is live logical state and can name a target not in P after a failed/new description. The current `focus_update` visits P and maps a focused part to its native ID; otherwise it emits the root. Replacing this with `Target` decoding or identity arithmetic would make a logical target appear in a native tree that does not contain it. No duplicate P-to-ID map is justified for a scan that runs only after focus changes. On `presentation_lost`, `Bridge::sync` intentionally retains the last coherent tree; this is a coordinate-authority loss, not a failed preparation. Winit independently processes `Focused(false)`. After the next successful acknowledgement, the epoch/full-tree path carries the live focus again. A useful lifecycle test is: focus P node A, lose the surface, logically focus a newly described B absent from P, assert no tree update while invalid, dispatch window focus false, restore and acknowledge P containing B, then assert the native focus is B. A failed preparation without `presentation_lost` is a different case: old P is still valid, and focus-only updates should be sent against that old tree.

2. A realized-row P record can plausibly lose 8 bytes without adding an index. Current `metadata::Row` is five words/32 bytes: identity, list identity, key, index, count. For the current list builder, a row metadata record is captured on the `ListItem` wrapper immediately parented by the list. The parent's frozen `ListInfo` already contains list identity-derived target and full source count; `Part::parent()` resolves through the same P vector and site namespace. A 24-byte `{identity, key, index}` row therefore supplies all public `ListItemInfo` fields by reading its parent and parent's `ListInfo`, saving 8 bytes for each realized row in the cold P sidecar. Add a structural assertion/test before adopting: every row record must attach to an immediate `List` parent with matching count, and descendants must not accidentally get their own row record. This is not an 8-byte hot `Presented`-node saving; report it as exactly `8 * realized_rows` sidecar bytes, with no speed claim. The loss case is a future list representation where a row wrapper is nested or detached from the list; then parent-derived metadata stops being valid and the row must regain an explicit list reference or use a checked ancestor walk.

3. Do not claim a virtualized list is fully addressable from AccessKit `position_in_set`/`size_of_set`. These fields let a screen reader announce the position and total for exposed rows, but the platform tree still only has realized P rows. WAI-ARIA similarly describes position and set size for a subset, while Windows UIA has separate `ItemContainer` and `VirtualizedItem` patterns with `FindItemByProperty`, `Realize`, and `ScrollIntoView`. The current AccessKit node/action schema has no equivalent arbitrary-index realization request. A credible next layer is a platform-specific UIA provider that exposes a small range/window of placeholder-like items and translates Realize into a stable-key list-scroll request, then returns the realized target only after a new P acknowledgement. Do not create one native node per source item. For AccessKit-only platforms, document navigation as limited to currently exposed rows until a cross-platform virtual-item contract exists. The adversarial test is a million-row list whose target row is not realized: a request must not fabricate a live Target, return row zero, or resurrect an old key after source replacement.

4. The current projected text child is intentionally enough for text/value exposure, not text editing. The bridge emits no `SetTextSelection` or `ReplaceSelectedText` action and `TextInput` advertises neither; that is safer than pretending the scalar editor has selection or IME semantics. AccessKit positions index its `character_lengths` entries, each of which gives UTF-8 byte length for the editor's smallest selectable unit. Its schema explicitly treats CRLF as one unit of two bytes. The bridge now handles CRLF as one entry; retain tests for `"a\r\nb"`, an astral scalar, decomposed combining marks, empty text, and UTF-8 byte sum. The present editor's unit is a Rust scalar, not a grapheme, so decomposed accents are currently two positions; that is a declared editor behavior, not a Unicode grapheme guarantee. If the editor later adopts grapheme caret movement, the AccessKit run boundaries must change with it.

   Text offsets also have platform/API representation differences. AccessKit positions use the run's selectable-unit index; its byte lengths map those indices into UTF-8. GPUI's established native input APIs use UTF-16 ranges for IME/selection. Qt's `QAccessibleTextInterface` uses character offsets and exposes selection, cursor position, per-character rectangle, point-to-offset, and scroll-to-substring. These are related operations, but their offsets must not be passed across APIs unconverted. The low-retention path is to keep the editor's own selection/marked-range state authoritative, convert on the owner barrier when an AT action or native text-input callback requests it, and generate AccessKit text-run boundary bytes only for changed text during active projection. Do not keep a second per-character UTF-8/UTF-16/grapheme mapping in every `Presented` input. For long text, benchmark conversion-on-demand versus retaining an editor-owned offset index already needed for editing.

5. A selection update should be separable from content geometry and tree membership. AccessKit `TreeUpdate` carries the latest focus with each update, and text selection is represented on the input/text node as positions into its TextRun child. Once selection is implemented, a caret move on unchanged text should update only the TextInput node carrying `TextSelection` (plus focus when it changed); it should not rebuild the TextRun value or its `character_lengths`. A text-value change must replace the TextRun boundaries. The same rule applies to selection changed by IME: marked/composition range belongs to the native text-input model; do not encode composition as an AT selection unless the editor's actual selection state changes. Adversarial cases: text changes between request and owner drain; stale run child ID; offset beyond UTF-8 length; CRLF half-boundary; emoji UTF-16 surrogate half; selection direction reversal; cancellation of composition; deletion/reparenting of the focused input.

## A bounded scroll-geometry experiment

**Verified source fact.** Chromium stores accessibility bounds relative to an ancestor offset container, carries sparse scroll offsets, and reconstructs absolute geometry on demand. For text geometry it groups characters into single-line, single-direction, contiguous inline text boxes and stores per-character widths instead of one full rectangle per character. Chromium's performance post explains that repeated scroll updates had been serializing unchanged properties and reports up to 8.25x improvement in its scrolling tests after moving scroll offsets into a bounds fast path. Those figures are Chromium workload results, not a prediction for this runtime. [Chromium Part 3: relative bounds and inline text boxes](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/accessibility/browser/how_a11y_works_3.md), [Chromium accessibility performance post](https://developer.chrome.com/blog/chromium-accessibility-performance?hl=en).

**Proposal/inference.** For GPUI's fixed-height virtual list, prototype one synthetic AccessKit scroll-content node between a list and its visible row wrappers. On an intra-row scroll where realized membership is unchanged, update the scroll-content translation and leave stable row/text child geometry unchanged. That could eliminate per-visible-row `Node` construction and update churn on each scroll tick. The current P only retains a flat node-local-to-window transform; the ordinary traversal has temporary absolute `spaces`, while list viewport offset lives in logical `ListState`. The frozen P list metadata would need to include its scroll offset (one value per list, not per row) or derive the offset from current P geometry. Each child-relative transform must be computed from the accepted absolute transforms and the scroll-content transform; never attach the already-absolute `Part::transform()` directly to each AccessKit node, because node transforms apply to descendants and would double-transform them.

This experiment is valid only if all accepted transforms are invertible and the projection can recover the correct relative mapping without changing full/unclipped bounds, clipping, hit-test authority, or list row positions. Exact f32/f64 rounding matters: test random affine compositions and boundary values against the current absolute-window-rectangle projection, including nested list ancestry, reflections, nonuniform scale, fractional DPI, partially clipped rows, resize, and rows whose transformed bounds cross the window edge. The root's geometry contract keeps hit-test bounds viewport-clipped and exposes unclipped full bounds separately; those two meanings must remain distinct. AccessKit `clips_children` and transforms are inherited in the consumer, so a wrapper with `clips_children` may affect descendants differently from today's flat physical bounds. Require both AccessKit Consumer equality and at least one native AT geometry check before adoption.

The likely win is limited to same-realized-range motion. Crossing an item boundary changes row membership and child lists, requiring structural updates; on small lists or rapid range churn, a full tree projection may beat relative-transform bookkeeping. Gate with: (a) same-range scroll 1000 updates, reporting constructed native node count and allocations/update, (b) boundary-crossing scroll with identical counters, (c) CPU p50/p99 and allocation bytes for 10, 100, and 1000 realized rows, (d) Consumer resolved bounds equal to current full-window bounds within a specified ULP/edge containment rule, and (e) native UIA/AT-SPI hit test plus VoiceOver frame check. Reject if the fast path saves less than the added wrapper/metadata/proof cost or changes any platform-visible bounds by one representable pointer-relevant edge.

There is a useful negative comparison in Chromium's own design: it chooses a general ancestor offset-container graph and sparse offsets, not a blanket per-node absolute transform. AccessKit's transform semantics are more limited than Chromium's full relative-bounds structure, so the idea should stay one list wrapper at first. Servo's 2026 issue asking whether AccessKit transforms can make scroll updates cheaper also records uncertainty about transforms on all children versus an ancestor transform; it is evidence that this needs a consumer test, not proof the proposed wrapper already works. [Servo issue #47161](https://github.com/servo/servo/issues/47161).

## Semantic-tree sparsity and action scope

Jetpack Compose explicitly maintains semantics separately from its composition tree. Nodes without semantic properties need not appear in its semantics tree; clickable/toggleable/list-item subtrees can merge into one accessibility element, while an unmerged tree remains available for services/tests. Qt similarly documents that a plain label exposes text as its accessible name, while larger/selectable/input text should use a full text interface. These are useful constraints for GPUI's author surface: role, name, description, value, actions, and merge/ignore intent need distinct semantics; visual nesting alone should not force a semantic node or a Text API. They are not evidence to auto-merge GPUI controls: merging can hide independently focusable descendants and change keyboard/screen-reader traversal. [Compose semantics tree](https://developer.android.com/develop/ui/compose/accessibility/semantics), [Qt text interface](https://doc.qt.io/qt-6/qaccessibletextinterface.html).

A measured low-risk prototype can avoid constructing AccessKit `GenericContainer` nodes for P parts with no name, description, value, list metadata, actions, role-specific state, or authored relationship, and splice their children into the closest projected ancestor. This is only safe when the elided node contributes no clip, transform, focus boundary, or semantic grouping. It should use the existing preorder/P parent relation and a transient ancestor stack, never a retained second map. Before trying it, count how many `GenericContainer` nodes the current Consumer filters from native exposure and how many native adapter update costs they still incur; if accesskit-consumer already excludes them before its retained tree or tree update cost is negligible, skip this change. A counterexample is an otherwise generic node whose explicit clip or transform constrains descendants; removing its semantic record must not remove geometry/clip behavior. The current projector emits absolute bounds and list clipping on semantic List/ListItem nodes, so a generic container may not itself carry clipping today, but future semantics cannot assume that.

Old P identity and live action authorization are separate. Native actions from a retained old tree should continue to resolve through a non-reused namespace identity and current logical membership, as the current `accessibility_target`/`perform` barrier does; do not require every old-P action to match the latest P epoch, which would cancel stable position-free actions unnecessarily. Conversely, focus publication is a different authority: it must resolve into the P tree by visiting P, and an absent target maps to root until a full P containing it is acknowledged. For text range operations specifically, AccessKit's request has no GPUI text-revision token; do not advertise range actions until the owner can validate run existence and index bounds and define how an old request applies to current text. Exact stale-content rejection would need a revision identity in the synthetic run or a per-input revision map, at a real identity/event/update cost.

## Minimal conformance additions

- **Frozen list metadata:** reorder or change source length after a valid P, before acknowledgement, and assert old row/list reports retain old key/index/count while new P uses the new tuple; query a realized row descendant and verify no duplicated row tuple appears.
- **Unrealized list target:** request a key outside the realized range and after key removal. It must not produce a `Target`; native VirtualizedItem behavior is a separate platform provider contract.
- **Focus authority:** distinguish failed prepare from `presentation_lost`. In the first case focus-only updates may target the old P member; in the second case no geometry/tree publication occurs until a new acknowledgement. In both cases a logical target absent from P must never be used as TreeUpdate.focus.
- **Text positions:** ensure `sum(character_lengths) == value.len()` and every cumulative boundary is valid for the editor unit; specifically test CRLF as one unit, astral characters as one scalar at current editor policy, combining marks as separate scalars, and empty string.
- **Selection cost/correctness:** when implemented, compare TreeUpdate node IDs for caret-only changes against content updates; selection-only changes must not allocate a replacement TextRun boundary vector. Verify malformed/stale offsets fail closed without editing another target.
- **Scroll geometry:** compare current full-projection bounds against the relative-wrapper candidate at every visible row and hit-test boundary; check both one-frame intra-row scroll and multi-frame boundary crossing.
- **Native proof:** AccessKit Consumer tests validate schema, not OS behavior. Track separate UIA/Windows Narrator, macOS VoiceOver, and AT-SPI/Orca provider tests with OS and screen-reader versions. A synthetic application test that only constructs `TreeUpdate` is not proof of native frame, text-selection, or virtual-item behavior.
