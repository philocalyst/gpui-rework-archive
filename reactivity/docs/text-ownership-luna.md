## `FieldId`: namespace proof and follow-up disposition

`FieldId` stores `NonZeroU64(((local as u64) << 32 | scope as u64) + 1)`. Subtracting one before splitting recovers the full 32-bit local ID and 32-bit scope. Local zero maps to raw one, preserving the `Option<FieldId>` niche; the largest accepted pair `(u32::MAX, u32::MAX - 1)` maps to `u64::MAX`, so no addition overflows. Adding one is strictly monotone over all accepted pairs, preserving lexicographic `(local, scope)` ordering. The existing unit test covers local zero, `u32::MAX`, large interior values, scope `u32::MAX - 1`, `Option<FieldId>` size, debug output, and sorted pair ordering.

The namespace allocator is sound at its endpoint. `Sources::next_scope` starts at one (scope zero is owner-local), and each component takes `[start, end)` where `end = next_scope.checked_add(child.next_scope)`. The assigned child-local scopes are strictly below the child’s `next_scope`, so even when `end == u32::MAX`, the highest assigned ordinal is at most `u32::MAX - 1`. `ComponentEntry::contains` checks that half-open interval before the `local()` subtraction. The last-range test constructs a component at `u32::MAX - 1`, resolves its field at that scope, reads revision, writes through it, and confirms a subsequent component fails before registration. Nested schemas repeat this same checked interval construction; no collision or arithmetic hole was found.

`Sources::direct` is the shared admission point for `direct` and `field`; it rejects any `Source` whose ID has nonzero scope with `BindError::NonLocalDeclaration`. `resolve` and `scan` produce qualified IDs, and field reads, writes, revisions, and invalidation route by scope before looking up the owning component. Tests cover duplicate local IDs, source declaration reuse of a resolved ID, independent nested component IDs, equal local IDs across sibling components, and last-range routing.

The initial audit found an API consistency gap: `Sources::register_component` accepted a scoped `FieldId` from public `Component::new`, although component IDs are local to the parent schema. Root fixed this uniformly in `0c3dd8b3e1`; no namespace issue remains in the audited paths.

## Candidate string representation

Current retained strings use `Option<triomphe::Arc<str>>` in both `Node` and `Presented`, plus sparse `Metadata` declarations, resolved-name/description rows, and style overrides. The text is copied from a borrowed `&str` into one shared allocation when changed, then cloned into the immutable presented snapshot. No `Weak`, `make_mut`, or other general-purpose `Arc` features appear in these text paths.

The best fit found is `arcstr::ArcStr` 1.2.0, pinned to release commit [`faa7692b0d6662bb177b3aefa80a6a13f897554d`](https://github.com/thomcc/arcstr/commit/faa7692b0d6662bb177b3aefa80a6a13f897554d) (2024-05-07). Its source defines `ArcStr` as `#[repr(transparent)] NonNull<ThinInner>` and implements `Deref<Target = str>`; a safe `&str` read does not validate UTF-8 repeatedly. Safe construction from `&str` copies already-valid UTF-8. Correction to the initial comparison: GPUI's baseline is `triomphe::Arc<str>` 0.1.16, not `std::sync::Arc<str>`. Triomphe's `ArcInner<T>` has one `AtomicUsize` strong count (no weak count). On x86_64, `Arc<str>::from(&str)` requests one allocation with layout size `round_up_8(8 + len)`, alignment 8; `ArcStr` requests `16 + len`, alignment 8 for nonempty text and uses a static allocation-free empty value. Therefore ArcStr's nonempty allocation request grows by `len mod 8` bytes, except lengths divisible by 8 grow by 8 bytes (1–8 bytes total), not a flat 8 bytes: Triomphe pads its combined header-and-tail layout to alignment, while ArcStr requests the exact length. This was checked with a temporary global-allocator counter against the pinned crates, in addition to source inspection. `ArcStr::from(String)` copies rather than reusing the `String` buffer, but the existing GPUI promotion path also starts from borrowed `&str` and copies.

On 64-bit targets, `Option<triomphe::Arc<str>>` is 16 bytes (fat pointer) while `Option<ArcStr>` is one pointer (8 bytes because `NonNull` has a null niche). Replacing both `Node.text` and `Presented.text` therefore removes 16 bytes from those two fields per retained site, including sites whose option is `None`; verify actual `size_of::<Node>()` and `size_of::<Presented>()` because surrounding padding can affect total struct deltas. For one nonempty string shared between the two fields, net requested-memory reduction is 8–15 bytes per site after ArcStr's 1–8 byte extra payload allocation; for empty text with one existing Triomphe allocation it is 24 bytes (16 bytes of field reduction plus the removed 8-byte allocation). This is a per-distinct-allocation comparison: if a value is shared by k references, count allocation overhead once and field savings for each replaced option. The same one-word saving applies to each `Option<triomphe::Arc<str>>` in sparse semantic metadata: `Declared.name/description`, `Names.name/description`, `TextSlot.value`, and values nested in override contributions. Use `8 * replaced_option_count - sum(nonempty per-allocation growth) + 8 * removed empty allocations` for the break-even; allocation count is distinct promotions, not Arc clones. The total metadata win depends on how many sparse slots are present, while the Node/Presented win is paid across all sites. On 32-bit targets, the analogous field saving is four bytes per option; its allocation layout needs separate measurement.

Empty strings are a special case: `ArcStr::from("")` returns its static empty value and allocates nothing; `triomphe::Arc<str>::from("")` requests an 8-byte, 8-aligned header allocation. Nonempty short and long strings both use the same heap representation in ArcStr; there is no small-string inline branch. A temporary global-allocator counter observed these requested layouts (not allocator size-class/RSS): empty: triomphe 8 B / ArcStr 0 B; 3-byte string: 16 / 19 B; 8-byte: 16 / 24 B; 23-byte: 32 / 39 B; 24-byte: 32 / 40 B; 25-byte: 40 / 41 B; 64-byte: 72 / 80 B. Each nonempty construction performed exactly one allocation in each type. Cloning a shared 6-byte value added no allocation for either type. The `arcstr::literal!` macro can create read-only static storage whose clone/drop avoid refcount atomics, but GPUI's current `Text::literal(&str)` is just `Text::Borrowed` and runtime promotion treats it as dynamic text. Ordinary string literals therefore do not gain the static path automatically. A future opt-in literal API can expose this if its setup cost is useful; it must not silently retain arbitrary short-lived borrowed text.

Clone/drop traffic remains reference counted: publishing a new sheet increments once per cloned value; dropping the prior sheet decrements once. For dynamic values, ArcStr uses one strong-count atomic, the same count as Triomphe Arc, and adds a static-value branch on clone/drop. Thus there is no dynamic refcount-word reduction versus this baseline; the atomic-count claim only distinguished it from std Arc, not GPUI's Triomphe Arc. ArcStr has no weak references or copy-on-write, which matches these fields. Its source contains internal `unsafe`, including the `Send`/`Sync` impl and UTF-8-preserving dereference. That stays encapsulated in the dependency, leaving this crate's `#![forbid(unsafe_code)]` intact, but it is a real trust/dependency cost. The pinned 1.2.0 workflow runs ordinary tests, Loom, Miri, and cross-target builds: [release CI](https://github.com/thomcc/arcstr/blob/v1.2.0/.github/workflows/ci.yml). No `cargo-miri`, `miri`, or `rustup` executable is installed in this environment, so local Miri was not run.

The crate is not tiny: the pinned `arc_str.rs` core is 1,697 lines, the release package is 115.5 kB of source, and it has no mandatory third-party dependencies. If evaluated, specify `arcstr = { version = "=1.2.0", default-features = false, features = ["std"] }`; the default `substr` feature is not needed here. `std` itself is an empty feature; disabling defaults omits the substring implementation from this use. `ArcStr` is explicitly `Send + Sync` in the dependency implementation. `&ArcStr` dereferences to `&str`, keeping shaping, query, and inspector call sites straightforward; convert to owned `String` only at the existing public snapshot boundary.

### Alternatives that lose for this layout

- The workspace already directly depends on `triomphe = 0.1.16`. `triomphe::Arc<str>` still carries a fat pointer, so it does not shrink retained fields. `triomphe::ThinArc<H, u8>` is one pointer and its pinned source stores length in the allocation, but it dereferences to `HeaderSlice<HeaderWithLength<H>, [u8]>`, not `str`. Returning `&str` would require either unsafe conversion (forbidden in this crate) or `str::from_utf8` checks on reads; the latter repeats validation and does not meet the requirement. `triomphe::Arc<String>` would keep a thin field but adds a separate `String` allocation/header and does not fit current one-allocation immutable promotion.
- `SmolStr` 0.3.x is 24 bytes, with up to 23 inline bytes, static-string support, and `Clone::O(1)` (inline copies are bounded; long strings share). The documented layout is the same size as `String`, so replacing both `Option<Arc<str>>` columns costs up to 16 extra bytes per site before counting duplicated inline bytes; it trades the shared payload allocation for denser text bytes only on short strings. `CompactString` also uses 24 bytes with up to 24 inline bytes, but clone is `O(n)` and each `Presented` publication would copy short content. These may win if text allocation rate dominates and working sets are small, but they lose the broad every-node retained-memory goal and require measuring their deeper P clone traffic. Sources: [SmolStr README](https://github.com/rust-analyzer/smol_str/tree/0.3.2) and [CompactString layout/design](https://github.com/ParkMyCar/compact_str#how-it-works).

## Evaluation gate before adopting ArcStr

Use a paired baseline/candidate benchmark built with the same Rust 1.97.1 profile and allocator. Include empty text, 1–8 byte labels, 23/24/25-byte boundaries, multibyte UTF-8, 64-byte text, repeated text from one Signal source, unique labels, metadata name+description, and a 100k-node mostly-`None` tree. Record `size_of` for all relevant structs; allocation count/bytes for first promotion and edit; bytes copied; peak live bytes with old `Presented` retained; acknowledge/present time; and repeated clone/drop cost. Gate on the exact field reduction (16 B/site on x86_64 for Node+Presented options, plus 8 B per metadata Option slot actually present), ArcStr's measured allocation delta `len mod 8` (or 8 for lengths divisible by 8) per nonempty unique promotion and removed 8 B per empty promotion, one allocation per nonempty unique promoted string, zero allocation for empty ArcStr, valid Send/Sync on each supported target, and no regressions outside allocator noise in cold startup or publish/ack. Require the candidate to win a realistic high-node/low-string-density workload as well as a short-label-heavy workload; reject it if extra payload bytes, static branch, or dependency cost outweighs memory reduction in the supported product workload. Assembly inspection is meaningful only after the concrete wrapper is compiled in GPUI: compare current Triomphe Arc and ArcStr clone/drop at `Node.text` promotion and `Presented.text` publication, rather than inferring speed from type width.
