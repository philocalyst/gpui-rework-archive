# GPUI-CE parity and migration-fixture audit

Fresh audit of current `reactivity` HEAD `8a157b3b473b812b5cde81a1ea11230513e42b09`, original GPUI-CE `41a42eb96d6c04e5e71f3577d12934d4de569b20`, and Hummingbird `e15e8ba0ef6ff5445294030d373e3c8ccc7d780c`. Source review only; no builds, benchmarks, tests, or production edits. Original/app links below are pinned source permalinks; current implementation links refer to the local checkout, with the audited commit stated above.

## Finding

Current GPUI-CE has a coherent retained single-owner model with a strong headless/native presentation core, typed update routes, a bounded fixed-height virtual list, constrained text entry, semantics, image painting, and recovery-oriented rendering. It remains far from original GPUI's **full framework feature surface**. A `div`/style rewrite or successful compilation cannot establish feature parity: original app/entity lifecycle, trait and macro ecosystems, element/layout behavior, input routing, platform services, text composition, assets, animation, test tools, and multi-window behavior are separate API/behavior contracts.

The existing `Library` fixture proves list scaling and key stability against fabricated data. It is not an app-migration proof. The smallest useful real Hummingbird gate is a seeded SQLite track-query → searchable ID rows → sorted order → row play action transcript. Keep the 250k fabricated fixture as its separate scale test.

Integration update, 2026-10-22: source-qualified grapheme selection/editing and
native caret/selection paint are now integrated, as are Parley 0.12 and the real
[SQLite/Nucleo Hummingbird Library port](../ports/hummingbird/README.md).

## Fixture audit and concrete recommendation

Current [`catalogue.rs`](../crates/gpui/examples/support/catalogue.rs) fabricates sequential IDs and `Track 000042 — Library recording`; [`library.rs`](../crates/gpui/examples/support/library.rs) checks play selection against its local catalogue. The row UI is useful, but it does not touch SQLite, Hummingbird's actual search model, query ordering or domain IDs. Its `tests/library.rs` 250k count remains a good bounded-realization stress case only.

Use Hummingbird's existing query/test domain for a small deterministic fixture. Upstream already has an `insert_track` helper writing true track records ([`db/tests.rs`](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/tests.rs#L49-L75)) and a three-track seeded fixture with IDs 1, 2, 3 and album/artist links ([same test module](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/tests.rs#L598-L635)). `TrackQuery` supports sorting and fetching stable IDs ([query builder](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L257-L280), [ID fetch](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L330-L339)); Hummingbird search maps fetched rows into `(id, title, artist, album_id)` then constructs its real search items ([`search/model.rs`](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/search/model.rs#L91-L112)). Search is partly in app matcher logic, so use that existing item/matcher path or state clearly that text filtering is the test driver's filter; `for_search` alone is a projection, not a query-string predicate ([`track.rs`](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L289-L299), [fetch rows](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L528-L535)).

Smallest meaningful transcript: (1) seed those actual rows into in-memory SQLite; (2) fetch search results and filter by a title/artist term, asserting exact IDs; (3) sort by title through `TrackQuery`, asserting order while IDs stay stable; (4) render IDs/labels through current `ItemSource`, play a visible row, then resort or prepend and assert the selected/played ID remains the same identity. Include one stale async search completion if the fixture is intended to prove `Questions`; otherwise keep it a separate framework protocol test. This proves the real data seam and identity behavior, but still does not claim Hummingbird UI port parity.

## AST migration: conservative automation boundary

The strongest justified source rewrite is narrowly local: original `px` takes `f32` and wraps `Pixels` ([original `geometry.rs`](https://github.com/philocalyst/gpui-ce/blob/41a42eb96d6c04e5e71f3577d12934d4de569b20/crates/gpui/src/geometry.rs#L4052-L4060)); current `.w/.h/.size/.gap/.p/.font_size` accept `f64` property values ([current `element.rs`](../crates/gpui/src/element.rs)), while current `.rounded` takes `f32` ([same file](../crates/gpui/src/element.rs)). I found no same-named general `.rounded(px(...))` API in the pinned original source, so that is not a rewrite candidate. A plain `px(12.3)` → `12.3_f64` changes the original f32 rounding. For a direct literal-only argument in one of the known f64 property slots, emit `12.3_f32`, which the current sealed `IntoLength` conversion widens to f64 before property admission (an explicit f64 cast is unnecessary). Preserve literal value/suffix correctness; allow only a Rust numeric literal representable as the original `f32` argument. No arithmetic, constants, variables, `Length`/percentage/rem conversion, method chaining on `px`, or macro-token rewriting.

Without rustc name/type resolution, source AST alone cannot prove an unqualified helper or trait method resolves to GPUI: `px`, `div`, `rgb`, imports, aliases, re-exports, local shadowing and extension traits can collide. Even a fully qualified `gpui::div()` only proves a constructor token path; old and current `div` return different APIs and defaults. The current layout defaults to column and current `flex()` explicitly selects row; original `flex()` selects display flex and its docs default flex to row. Therefore do not automate bare `div()` or `.flex()` as parity mappings. Avoid `use` rewrites unless the whole module's import/binding environment is understood.

A workable AST-only tool may emit the `px` candidate as a **diff** only for an unambiguous source chain rooted at literal `gpui::div()` and a whitelist of target property method calls with direct one-literal `px(...)` arguments, with a closed supported chain and no macro/token-muncher boundary. This syntactic condition is still not proof of behavioral layout parity; attach a diagnostic/proof note that callers must review the chain. Better default is to print a candidate diff and diagnostics, never silently apply it. A literal `px(...)` with an unknown consumer must remain a diagnostic: its surrounding type/use is required to know whether widening to `f64` is valid.

Do not rewrite colors automatically. Original `rgb(u32)` returns palette `Rgba` and divides each channel through `f32`; original `rgba(u32)` reads `RRGGBBAA` ([original `color.rs`](https://github.com/philocalyst/gpui-ce/blob/41a42eb96d6c04e5e71f3577d12934d4de569b20/crates/gpui/src/color.rs#L21-L41)). Current `rgb(u32)` returns tagged `Color`; `Color::rgba` takes four `u8`s ([current `color.rs`](../crates/canvas/src/color.rs), [helper](../crates/canvas/src/color.rs)). Same hex spelling alone does not establish equivalent consumers/color-space conversion. Preserve old symbol calls as diagnostics for manual adaptation; never rewrite shadowed/local color helpers.

Classify as manual/unsupported when AST encounters macro invocations/definitions, `cx`/`Entity`/`Render`/context use, extensions or `apply` closures, unknown method chains, imported aliases, unqualified helper names, color APIs, relative lengths, dynamic style values, or any operation where source identity/invalidation matters. This avoids pretending AST shape provides rustc's method, trait, macro-expansion or type semantics.

## Parity bar

A **full original GPUI feature parity** claim still requires substantial work beyond the list/search fixture: original entity/context/subscription and executor lifecycles; general input/actions/keymaps/focus/IME/clipboard/gestures; rich element/layout/style/length semantics; text/editor/rich runs; asset/cache/SVG/path/font services; animation; multiwindow and original platform breadth; accessibility action parity; and app/event/visual test infrastructure. A real Hummingbird data fixture is necessary migration evidence, not a substitute for those missing contracts.


## Implementation and release policy

The target remains full functional replacement of the original framework. This
audit does not authorize reducing the 1.0 feature scope. Old API spelling is not
itself the objective: a typed source/component formulation may replace an entity
or context API when it preserves the required ownership, observation, lifetime,
composition and platform behavior with less complexity. Each replacement needs
a representative app scenario and an explicit failure/lifecycle transcript.

Before adding another subsystem, identify the canonical data it can borrow,
which existing admission/publication barrier owns its effects, and which duplicate
state or traversals the formulation removes. Review all non-test shipping code,
not just the new module. If a design needs a parallel tree, a second event model,
or a distinct testing API, first try to express it through the existing canonical
scene/source/semantic mechanisms. Simplicity is established by readable code and
actual usage, not a promised final line count.

Keep three kinds of fixture evidence distinct: upstream app-domain behavior
(real SQLite schema/queries, IDs and matcher), large adversarial scaling inputs,
and framework lifecycle/failure counterexamples. A fixture can serve several
purposes, but fabricated titles do not prove an application port and compilation
does not prove visual/input parity. The editor and dependency worktrees named in
this snapshot are pending; future integration evidence must identify its own
source rather than retroactively relabeling this audit.
