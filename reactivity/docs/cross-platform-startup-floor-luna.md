# Cross-platform native startup and blank-window floor

**Scope and evidence labels.** This is a read-only review of the current native presenter, pinned local dependency implementations, platform-primary API docs, and the fresh-process results provided by root. Local implementation facts cite checked-in files/source. “Measured” means the supplied/checked application run; “documented” means primary API/protocol facts; “risk to test” is deliberately not promoted to a confirmed defect. No production changes were made.

## Decisions in order of value

1. **Preserve CPU-first native admission and measure both submit and visible content.** The current `Auto` path creates a hidden window in Winit `resumed`, records the root, creates a CPU surface, then shows and requests redraw. In `redraw`, it paints directly into softbuffer's borrowed buffer, calls Winit `pre_present_notify`, calls `Buffer::present`, and only then acknowledges the exact prepared frame. It starts hardware initialization after this completed software present; GPU work runs on an owned worker, while surface creation/capability negotiation is polled on the event-loop thread. Keep that division: do not initialize wgpu/driver before the first software present, don't acknowledge the source epoch before the native presenter accepts it, and don't let the worker own Winit handles, view state, or the token. Winit specifically recommends creating windows/graphics only after first `resumed`, and says redundant suspend/resume callbacks must be tolerated. [Current `native.rs`](/root/gpui-ce3/reactivity/crates/gpui/src/native.rs), [current upgrade worker](/root/gpui-ce3/reactivity/crates/gpui/src/native/upgrade.rs), [Winit `ApplicationHandler` 0.30.13](https://docs.rs/winit/0.30.13/winit/application/trait.ApplicationHandler.html).

   The `PresentedFrame` callback is correctly documented as a **host submission + acknowledgement boundary**, not proof of compositor latch, monitor scanout, or photons. Keep one benchmark for process-start-to-that-callback and a separate OS-specific measure for first actually visible content. Use fresh processes, fixed display scale/window size, at least 15 runs, median/p95/max, and report first blank-window visibility separately from first nonblank content. For a cross-platform user-facing “first visible frame <50 ms” claim, don't silently use only the Rust callback. The app's current opening order maps the window visible before its first software buffer submission, so explicitly record whether an empty/old background flash is observable.

2. **Fix and test presenter promotion/recovery per OS before declaring Auto cross-platform.** The existing X11/llvmpipe tests validate a real native CPU→GPU handoff and cancellation, but they do not cover Win32 or AppKit surface stacking and they should not stand in for physical hardware tests.

   * **Windows: a material fallback incompatibility is documented.** Softbuffer 0.4.8's Win32 backend builds a GDI DIB section and presents it with GDI blits (pinned source `softbuffer-0.4.8/src/backends/win32.rs`). wgpu 29's DX12 path associates a DXGI swapchain with the same HWND. Microsoft says flip-model HWNDs should not also be targeted by GDI, and after the first successful flip-model `Present`, GDI no longer works on that HWND even if the swapchain is later destroyed. [DXGI swap-effect docs](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect), [flip-model guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model). This means “drop GPU, recreate softbuffer, continue CPU” is not a safe recovery contract after a successful GPU present on Windows. Exact wgpu DX12 swap effect must be confirmed from the pinned backend source/build and reproduced on Win32, but likely flip-model restriction makes CPU fallback after promotion unavailable. Choices to spike: retain GPU as the only presenter after promotion and recover/recreate DXGI on device loss; add a non-GDI Windows CPU presenter (e.g. a D3D/DXGI upload path, which still needs the device) that keeps the same epoch barrier; or use a separate native presentation surface/window if UX permits. Don't claim Auto can recover to CPU on Win32 until one is demonstrated.

   * **macOS: current two-layer construction appears structurally compatible, but top-layer behavior is untested.** Softbuffer creates a CALayer sublayer under the AppKit view's root layer. The pinned `raw-window-metal` 1.1.0 used by wgpu creates a CAMetalLayer sublayer when the view root is not already a CAMetalLayer; this is intentionally preferred to replacing NSView's root layer. [raw-window-metal 1.1.0 docs/source](https://docs.rs/raw-window-metal/1.1.0/raw_window_metal/struct.Layer.html), [softbuffer 0.4.8 source](https://docs.rs/crate/softbuffer/0.4.8/source/src/backends/cg.rs), [wgpu-hal 29.0.4 Metal source](https://docs.rs/crate/wgpu-hal/29.0.4/source/src/metal/mod.rs). However, a Metal layer is installed before the device/render pipeline is ready; confirm it doesn't visually cover the software CALayer while `try_upgrade()` returns pending, and confirm dropping a failed/new generation leaves the software layer visible. Test actual AppKit, not just layer API shape.

   * **Wayland: CPU and Vulkan attach different buffer types to the same Winit `wl_surface`.** Softbuffer imports the existing raw `wl_surface`, creates XRGB shared-memory buffers, and commits them. Vulkan WSI surface creation also associates with that same native `wl_surface`. Protocol commits replace current content, and the compositor may read an attached buffer until its release event; storage cannot be mutated/reused before release. [Softbuffer Wayland backend source](https://docs.rs/crate/softbuffer/0.4.8/source/src/backends/wayland/mod.rs), [Khronos Wayland surface creation](https://registry.khronos.org/vulkan/specs/latest/man/html/vkCreateWaylandSurfaceKHR.html), [Wayland `wl_surface`/`wl_buffer.release` protocol](https://wayland.freedesktop.org/docs/html/apa.html). The protocol model is compatible with sequential buffer commits but does not prove this handoff's surface roles, event-queue integration or teardown are correct. Test cancellation after surface creation but before renderer readiness; test GPU present followed by device loss/CPU re-presentation; verify an old shm buffer stays alive until released.

   At minimum add native acceptance cases on Win32, AppKit, X11 and Wayland for: software first submit visible; adapter ready while model changes; adapter created but renderer delayed; first GPU present; injected loss before and after GPU promotion; suspension/resume; resize/DPI change; close while worker is pending. Assert the displayed epoch and `owner.presented(token)` always match, and assert no transient blank/covered software redraw during a delayed upgrade. For each platform capture a window screenshot at every forced handoff stage.

3. **Cull backend code that the actual automatic path can never select, but treat this as a measured build experiment.** `gpui_gpu/Cargo.toml` currently enables wgpu's `vulkan`, `gles`, `metal`, and `dx12`, while production `upgrade::BACKENDS` is only Vulkan|Metal|DX12 and the test explicitly asserts GL is excluded. The explicit `Gpu` policy currently constructs a different environment-configured instance and may intentionally expect GL. A *CPU-first Auto-only* build can remove unused GLES to reduce code size/page-in/linker work, but removing GLES from the common library would silently remove a backend from explicit mode. Best next test: split features (`native-auto` without GL vs `native-gpu-all` with it), build release binaries, compare bytes + cold page faults/first-start wall time/working set on Linux, macOS, Windows, and run explicit-GPU compatibility. `wgpu::Instance::enabled_backends` describes compile-time-enabled backends; merely enabling a backend at compile time doesn't mean it has been initialized at runtime. In the pinned wgpu-hal, Vulkan uses `ash::Entry::load()` from `Instance::init`, and DX12 loads `d3d12.dll` through `libloading`; both are only reached when an instance for those backends is created, which Auto defers until after the CPU present. This corroborates why early wgpu-instance construction is a meaningful startup boundary. [workspace GPU features](/root/gpui-ce3/reactivity/crates/gpu/Cargo.toml), [current runtime backend mask](/root/gpui-ce3/reactivity/crates/gpui/src/native/upgrade.rs), [wgpu-hal Vulkan instance source](https://docs.rs/crate/wgpu-hal/29.0.4/source/src/vulkan/instance.rs), [wgpu-hal DX12 instance source](https://docs.rs/crate/wgpu-hal/29.0.4/source/src/dx12/instance.rs), [wgpu `Instance` API 29.0.4](https://docs.rs/wgpu/29.0.4/wgpu/struct.Instance.html). Don't describe dropping `gles` as a proven RSS win without measuring page residency.

4. **Use the existing same-buffer renderer seam; optimize transfer only with platform-specific proof.** Native software `render_bgrx(&mut softbuffer_buffer)` already writes into the target buffer rather than allocating a second whole-window CPU image. Softbuffer's documented buffer is 0xRRGGBB in integer bit order (little-endian bytes B,G,R,0); a copy isn't inherently needed to satisfy its public buffer contract. Softbuffer states `Buffer::present` is no-copy for Wayland, X with XShm, and Win32; it performs a blocking copy on AppKit. Its `present_with_damage` is supported on Wayland, XShm, Win32 and Web, and otherwise equals regular present. [Current CPU direct-buffer seam](/root/gpui-ce3/reactivity/crates/gpui/src/native.rs), [softbuffer `Buffer` 0.4.8 docs](https://docs.rs/softbuffer/0.4.8/softbuffer/struct.Buffer.html). Thus don't add a global staging/copy layer. A platform-native AppKit display layer/texture upload may reduce the documented copy only if a measured profile shows it matters; it brings separate pixel format, layer lifetime, ordering and color handling risks. Damage updates can reduce traffic on some platforms but require buffer-age tracking and correct restoration of prior pixels; the runtime's frame token must still correspond to a fully composited frame. Benchmark unchanged vs tiny edit vs full-window invalidation, and report per-platform copy/CPU time before implementing.

5. **Treat memory floor by the OS's metric, not one portable RSS number.** Latest checked Linux X11 CPU-first Auto runs (llvmpipe refused before renderer initialization) record empty at PSS 8,716 KiB / anonymous 1,588 KiB / one thread, and workbench at PSS 10,764 KiB / anonymous 1,828 KiB / one thread. The post-Swash Todo-empty delta is therefore about **240 KiB anonymous** in these samples, a big change from the pre-Swash CSV's ~12.9 MiB delta (workbench 14,376 minus empty 1,492 KiB, and six threads). Startup CSV has 15 fresh runs: spawn-to-submit median 31.568 ms empty, 40.792 ms workbench (max 44.792 ms), and 56.845 ms graphics; graphics misses 50 ms in this before-scoped-shaper run. Empty's PSS is about 8.5 MiB, not 7 MiB; it remains far below the separate llvmpipe process initialization. [post-Swash native memory CSV](/root/gpui-ce3/reactivity/crates/gpui/evidence-native-memory-auto-swash.csv), [15-run startup CSV](/root/gpui-ce3/reactivity/crates/gpui/evidence-startup-swash.csv), [pre-Swash native CSV](/root/gpui-ce3/reactivity/crates/gpui/evidence-native-memory-cpu.csv).

   Linux `smaps_rollup` reports RSS and PSS; PSS divides shared pages among their mappers, while `Private_Dirty`/`Anonymous` more closely tracks this process's dirty heap but is not equal to user allocator live bytes. [Linux kernel procfs `smaps`/`smaps_rollup`](https://www.kernel.org/doc/html/latest/filesystems/proc.html). Windows `WorkingSetSize` includes resident shared and private pages; `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage` is process commit/pagefile charge, not private resident memory. Capture both plus private working set when available; don't label commit as RSS. [Microsoft `PROCESS_MEMORY_COUNTERS_EX`](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex), [memory counters glossary](https://learn.microsoft.com/en-us/windows/win32/memory/memory-performance-information). Apple tools report footprint/dirty pages and clean file/framework mappings separately; clean mapped code can increase resident pages without behaving like dirty heap, and allocation bytes are not the same as footprint. Use Xcode Memory/VM Tracker or XCTest `XCTMemoryMetric` against native app launches, record clean/dirty and physical footprint at the same post-present point. [Apple: reducing app memory use](https://developer.apple.com/documentation/xcode/reducing-your-app-s-memory-use), [Apple VM Tracker and footprint](https://developer.apple.com/documentation/xcode/analyzing-the-memory-usage-of-your-metal-app).

   Cross-platform row schema should include binary size, cold start to window creation, `PresentedFrame`, first verified nonblank pixels; warm steady idle CPU; page faults; thread count; one platform-native resident/committed/footprint measure; private/anonymous/dirty where exposed; loaded graphics modules/drivers before and after first software present and after GPU promotion. Report OS version, window system/display server, hardware/software adapter type and driver, CPU, display scale, and whether debug/validation layers are on. Separate CPU-reference from GPU hardware and software adapters. Never compare an llvmpipe process with a CPU-reference process as though the driver were an app-owned allocation.

## Highest-value next experiments

1. **Windows GPU promotion recovery proof** (before calling Auto complete): use instrumented actual Win32, delay renderer after DXGI surface creation, then test CPU redraw; after one successful GPU present inject device loss and test re-presentation. Current GDI backend may be irreversibly unusable after flip Present, so expect to need permanent GPU promotion/recreation or a different fallback.
2. **macOS delayed-layer proof:** pause at “surface exists, renderer pending”; capture output while CPU submits; then first GPU frame; destroy GPU surface and force CPU fallback. Ensure the Metal sublayer never masks the software sublayer when empty and z-order after failure is correct.
3. **OS-by-OS startup+floor matrix:** compare identical small empty/Todo/Gallery builds with CPU-first software only vs Auto (do not force GPU before first present). Capture 15 cold launches per build and post-first-frame snapshots; use the correct platform-specific memory metric above. Re-run Gallery after scoped-shaper change. If the 50 ms bound still misses, profile model declaration/tree build/layout/raster sections independently; avoid spending time on no-copy paths softbuffer already provides.
4. **Backend-code-size experiment:** remove GLES only in an Auto-specific feature configuration, compare release binary size and cold page-in/load time on each OS, plus explicit-Gpu backend acceptance. Roll back if users need GL or no measurable cold benefit.
5. **Presentation partial damage:** only after an edit benchmark shows present/copy dominates. Include surface age and repaint correctness; AppKit will use full-copy fallback per softbuffer docs.

## Implementation decision addendum: durable Windows and AppKit handoff

**Windows architecture.** The current DX12 backend's pinned source does use `DXGI_SWAP_EFFECT_FLIP_DISCARD`; the uncertainty about effect is closed. Since Microsoft specifies GDI is permanently unavailable on an HWND after its first successful flip-model `Present`, the existing single-HWND design cannot guarantee return to softbuffer CPU output after later GPU/device loss. There are three choices:

1. **Keep DXGI as the presenter after GPU promotion.** On device loss, recreate device + swapchain and continue presenting the latest canonical scene. If needed, rasterize the scene on CPU and upload pixels through the recreated device. This is the smallest design and retains one window/epoch path; it still requires a working adapter. WARP is not a universal guarantee: Microsoft's D3D12 WARP route uses `IDXGIFactory4::EnumWarpAdapter`, and the D3D12 WARP device is only available when the Windows Graphics Tools optional feature is enabled on supported systems. [WARP D3D12 availability](https://learn.microsoft.com/en-us/windows/win32/direct3d12/porting-from-direct3d-11-to-direct3d-12).
2. **Keep the current top-level Winit HWND GDI-only and present DXGI from a child HWND.** Show the child only after its first complete GPU frame; hide it on loss and return to GDI on the parent. Child windows are clipped to their parent client area and `CreateSwapChainForHwnd` binds to the specific target HWND, so this preserves a separate GDI parent. The OS routes child input to the child by default; a disabled child forwards messages to its parent, but this must be tested with Winit mouse/keyboard/capture behavior. Child must be positioned/resized for DPI, minimize, and client-size changes; its native handle must outlive `wgpu::Surface`; focus/accessibility and close ordering become application concerns. This is a structurally clean CPU fallback but materially larger scope. [Win32 child-window behavior](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features), [CreateSwapChainForHwnd](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi-idxgifactory2-createswapchainforhwnd).
3. **Declare GPU promotion permanent** and return an explicit device fault if GPU reconstruction fails. This is a minimal code change but narrows recovery behavior after promotion.

Prove option 1 with an actual Win32 device-removal test first; choose child HWND only if a hardware-independent CPU fallback remains a required contract. Do not add a child-window stack before tests demonstrate a benefit that justifies new HWND routing and accessibility risks.

**AppKit raw layer drop is not detachment.** Verified in the pinned source: `raw-window-metal`'s `ObserverLayer::Drop` removes KVO observers only. It does not call `removeFromSuperlayer`; Core Animation's root layer retains its inserted CAMetalLayer after the Wgpu surface releases its own retain. Its test explicitly calls `layer.removeFromSuperlayer()` before dropping it. This matters in two states: while an Upgrade has created the Metal surface and the renderer is pending, the original CPU CALayer is lower; after a failed *initial* `try_upgrade`, current code drops GPU but reuses that old CPU surface, so future software submissions may remain beneath the attached Metal sibling. By contrast, a device-loss path that constructs a new CPU surface appends a fresh softbuffer layer and should place it above the stale Metal sibling. Recommended bounded fix/test: after a failed initial GPU frame, recreate the CPU softbuffer surface after dropping GPU; prove layer order and visible output with AppKit screenshots at “surface created / renderer pending”, “GPU initial present failure”, and “post-promotion device loss”. Verify that the newly added CPU layer is indeed composed above stale Metal layer. [raw-window-metal ObserverLayer implementation and explicit detach test](https://docs.rs/crate/raw-window-metal/1.1.0/source/src/observer.rs), [wgpu-hal Metal surface](https://docs.rs/crate/wgpu-hal/29.0.4/source/src/metal/surface.rs).
