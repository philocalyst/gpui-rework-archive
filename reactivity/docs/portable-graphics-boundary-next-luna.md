## Finding

The production rendering boundary is already largely portable. The first-party GPUI renderer does not create Vulkan, DXGI, EGL, or Metal objects, and it does not branch on a native handle in its production path. Winit owns event/window integration; WGPU/HAL own target binding, API selection, presentation leases, and backend workarounds. Remaining first-party native code is mostly application policy: CPU-first operation, renderer choice, frame authority and acknowledgement, resource limits, resize/occlusion behavior, recovery, and Winit callbacks. Those choices determine product behavior and should remain outside HAL.

The smallest concrete structural elimination I found is to remove one redundant retained value from each admitted GPU surface: GpuSurface.config, a full wgpu::SurfaceConfiguration. GPUI can reconstruct this descriptor from the existing surface_config(size, format) helper, window dimensions, and Renderer::format() at the two existing configure call sites. The public WGPU Surface already retains its most recent configuration after configure because acquisition uses it; WGPU Core also retains presentation configuration. The GPUI copy is not needed to remember mutable policy.

This is a bounded owner reduction across Vulkan, Metal, DX12, and GLES. It removes a copy from each live GPU surface while leaving surface creation, configure calls, selected format, and all backend leases unchanged. It does not remove a driver object, avoid a driver call, improve frame time, or reduce WGPU's required internal configuration state.

## First-party inventory and what should stay there

The pinned first-party native.rs builds the fixed app configuration at lines 249–261, owns GpuSurface at 263–269, creates the explicit-GPU surface and renderer at 481–527, updates dimensions and configures on nonzero resize at 562–602, and configures the automatic handoff at 783–835. It chooses sRGB formats and opaque alpha, FIFO, and latency 1; enforces texture/pixel limits; keeps CPU as the initial and Windows recovery path; retries or recreates lost surfaces; and acknowledges a frame only after successful presentation. These are rendering policy and state-machine obligations, not raw platform binding.

The production path delegates automatic eligibility and target admission to WGPU/HAL. WGPU's automatic_surface_admission uses the window handle, filters the plan through compiled backend features, and performs no instance, adapter, surface, or device creation. The target-bound adapter operation owns the WGPU surface, requests an adapter with that exact surface as compatible_surface, then validates format, color space, alpha mode, and present mode before device creation. HAL classifies Win32, Apple, Xlib/Xcb, and Wayland targets and marks when a surface may safely be prepared. X11/Vulkan can prove the target before device work; Metal and Wayland defer target creation until renderer readiness. Win32 same-HWND GDI recovery is excluded from Auto, while explicit GPU remains separate. Pinned local paths:

- /root/gpui-acknowledged-text-geometry/reactivity/vendor/wgpu/src/presentation.rs:1-29,31-69,117-139
- /root/gpui-acknowledged-text-geometry/reactivity/vendor/wgpu-hal/src/presentation.rs:1-111
- /root/gpui-acknowledged-text-geometry/reactivity/crates/gpui/src/native/upgrade.rs:1-5,195-305,347-405

The target plan is not a durable capability promise. It is paired with a live surface and adapter, does not configure a swapchain or acquire a texture, and expires with target/device recreation. The application still decides whether a candidate may become authoritative, after it has rendered and presented a complete frame. Keep CPU authority, commit tokens, cancellation, bounded retry, close, resume, and recovery in GPUI: WGPU cannot decide when the application considers a frame delivered or whether to fall back to the reference CPU presenter.

There is no production raw-window-handle/backend selection in the audited first-party GPU/native modules at this pin. The only direct RawWindowHandle reference found under GPUI source is in Linux X11 integration-test setup at crates/gpui/src/native/upgrade_tests.rs; Linux target_os conditionals around native graphics are test gates and staged worker details. This finding is limited to those audited crates, not every platform conditional elsewhere in the workspace. The portable gpui_gpu manifest opts into WGPU 30.0.1 with vulkan, gles, metal, and dx12, with WGPU defaults disabled; it adds no native graphics crate itself.

The gpui_reactivity_host::native::Driver is a generic Winit ApplicationHandler that passes borrowed window/device events synchronously to the host (crates/host/src/native.rs:1-125). GPUI owns the Winit event loop, window visibility, redraw requests, resize and close behavior, and calls Window::pre_present_notify immediately before present. Winit says this call belongs between drawing and submitting/committing the buffer and uses it to schedule/throttle redraws; its documented platform-specific effect is Wayland. This is window-system coordination, not a HAL swap operation, so keep it in the host. Keep window creation, event loop, user-facing fallback, and frame acknowledgement in the app layer.

The graphics scope here does not include unrelated first-party platform code such as text, input, clipboard, or accessibility. Softbuffer's CPU surface is selected and driven through its portable API; native CPU-window presentation internals belong in Softbuffer, not GPUI.

## Proposed smallest slice: reconstruct config at configure time

The existing helper at native.rs:249-261 contains the entire configuration policy and returns the descriptor by value. Renderer::format() at crates/gpu/src/renderer/owned.rs:33-35 returns the immutable format from its owned context. Replace the cached field with the local value at each existing configure call:

    let config = surface_config(size, gpu.renderer.format());
    gpu.handle.configure(gpu.renderer.device(), &config);

On normal resize, retain the existing early return for either zero dimension, device and 16 Mi-pixel limits, owner resize, and configure ordering. Reconstruct using the actual nonzero size. On Auto handoff, continue configuring with [width.max(1), height.max(1)], including a minimized zero-size window; that behavior differs from normal resize's zero-size early return. Keep configure inside the existing error/limit closure. Remove the config field and its two constructor assignments in native.rs and native/upgrade.rs, plus the four width/height mutations. The helper stays first-party because sRGB/FIFO/opaque choices are application policy.

Do not call Surface::get_configuration here. WGPU returns a clone; reconstructing from immutable renderer format and current dimensions avoids that extra API clone and prevents a second mutable format/dimensions cache in GPUI. No vendor API or per-target config type is needed.

### Owner and cost model

- **Retained host state removed:** one SurfaceConfiguration value in each admitted GpuSurface. Its concrete size is target/compiler dependent; this audit did not build or report numeric bytes. The descriptor includes an empty view_formats vector from the existing helper, so there is no populated view-format buffer to count. No new allocation, refcount, lock, enum/header, global state, or persistent config copy is introduced.
- **Required WGPU state remains:** public Surface stores its last configuration, clones it after configure, and uses it to construct surface-texture descriptors. Published WGPU Core 30.0.1 also keeps presentation configuration in its live presentation object. HAL/backend state retains the format/extent or swapchain resources it needs. None of these are GPUI copies to remove.
- **Call/allocation behavior:** the same two Surface::configure sites remain. The same values reach WGPU; configure and its internal clones still happen as before. The helper constructs a short-lived descriptor at configure time. On resize this replaces mutating the cached descriptor with rebuilding it; in Auto it moves that fixed descriptor construction from the Ready packet to the event-thread configure point. It adds no driver work, and no elapsed-time improvement is claimed. No shader, device, or surface startup path changes. If resize or event-thread CPU is a gate, measure that path on each backend rather than infer it.
- **Source/API cost:** delete one field, two constructor initializers, and four dimension writes; use the existing helper at two configure sites. No vendor lines or public method are required. A future per-target header check can reuse the existing test ledger at native.rs:1346-1356, which reports size_of::<GpuSurface>(). Do not infer a cross-platform byte value from one target.
- **Like-for-like gate if implemented:** compile and measure the same GpuSurface header and retained application allocation cohort on every supported target/backend selected by the product matrix. Verify selected format and all fields exactly match the prior descriptor for explicit GPU, initial setup, nonzero resize, normal resume, resize after device loss, and Auto handoff at zero size. No frame-time or RSS claim follows from removing one Rust field; such claims need separate actual platform measurements.

This changes only the source of a value at configure time. It does not shift platform policy to WGPU or justify adding a vendor configuration builder: that would hide the same application policy while leaving dimensions/format work and WGPU's internal descriptor owners in place.

## Lifecycle and backend adversaries

The descriptor change must leave configure timing and texture ownership exactly intact. WGPU's public API panics if a SurfaceTexture referencing the surface is alive during Surface::configure; HAL's safety contract additionally requires all GPU work, acquired surface textures, and derived views to be finished, and forbids configuring a surface on a different device. Acquisition permits at most one outstanding texture and requires it to be presented or discarded. GPUI's Suboptimal path drops the acquired frame before resize/reconfigure; the Auto render-failure path drops both view and frame before discarding the GPU cohort; ordinary success presents before acknowledgement. Preserve those orderings and the target/renderer format invariant. WGPU API: [Surface::configure/get_configuration/get_current_texture](https://docs.rs/wgpu/30.0.1/wgpu/struct.Surface.html). Exact local contracts at f9fe: vendor/wgpu/src/api/surface.rs:34-48,119-145; vendor/wgpu/src/api/surface_texture.rs:29-40; vendor/wgpu-hal/src/lib.rs:674-749.

| Backend | Existing WGPU/HAL lease or constraint | Consequence for this slice |
| --- | --- | --- |
| Vulkan | HAL owns acquired image index and semaphore metadata. Every successful acquire gets a new WGPU texture identity even when the native swapchain image is reused; present sends the native image index and wait semaphores. Native Vulkan maps timeout, out-of-date, and surface-lost results, plus an Intel out-of-range image workaround. Local path: vendor/wgpu-hal/src/vulkan/swapchain/native.rs:480-561,563-620. | Reuse the existing config values; never cache image identity in GPUI or bypass acquire/discard/present. |
| DX12 | HAL creates the swapchain during configure with DXGI_SWAP_EFFECT_FLIP_DISCARD, owns backbuffer resources, tracks acquisitions, and waits for present queue idle on reconfigure/unconfigure. It presents through the swapchain. Local path: vendor/wgpu-hal/src/dx12/mod.rs:1472-1707,1710-1769,1823-1845. Microsoft documents that D3D12 supports flip-sequential/flip-discard only and that GDI no longer works on the same HWND after the first successful flip-model Present1, even after swapchain destruction. | Do not make same-HWND GDI restoration an Auto guarantee. Keep the Win32 admission rule and explicit-GPU choice unchanged. |
| Metal | HAL turns an AppKit/UIKit view into a Metal layer, records whether raw-window-metal injected it, and detaches/releases only its injected layer on the main queue during Surface drop. Acquire retains both drawable and texture, skips occluded macOS windows before nextDrawable(), and maps no drawable to timeout. Local path: vendor/wgpu-hal/src/metal/mod.rs:160-192; metal/surface.rs:210-237,378-439. Apple documents drawable-pool exhaustion if references are retained, plus an optional one-second timeout or indefinite wait depending on allowsNextDrawableTimeout. | Keep late layer attachment in the existing Auto path. Never move CAMetalLayer setup/cleanup to GPUI or retain acquired frames across configure. |
| GLES | EGL selects display/window mechanisms from raw handles inside HAL, creates its EGL window surface and a renderbuffer/FBO, then returns that renderbuffer as the acquired texture; it does not expose a stable present-image-age contract to GPUI. Local path: vendor/wgpu-hal/src/gles/egl.rs:921-987,1300-1420,1424-1469. | Reconstruct the same generic configuration. Do not infer backing-buffer identity or preserve pixels from the Rust config. |

These lines are local fork implementation evidence, not guarantees of every driver's behavior. For example, Apple's [CAMetalLayer documentation](https://developer.apple.com/documentation/QuartzCore/CAMetalLayer) says the layer owns a finite drawable pool and clients must release strong drawable references after commit; [allowsNextDrawableTimeout](https://developer.apple.com/documentation/quartzcore/cametallayer/allowsnextdrawabletimeout) documents the one-second timeout when enabled and an indefinite wait when disabled. Microsoft documents flip effects and the GDI restriction in [DXGI_SWAP_EFFECT](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect), and D3D12's supported swap effects in [Swap Chains](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains). The official Vulkan [vkQueuePresentKHR reference](https://registry.khronos.org/vulkan/specs/latest/man/html/vkQueuePresentKHR.html) is its API contract; acquired-image identity and semaphore details above come from the pinned HAL implementation.

## Shader portability and legacy reach

The f9fe production renderer compiles WGPU 30.0.1 features Vulkan, GLES, Metal, and DX12. The official [WGPU v30.0.1 feature manifest](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/Cargo.toml#L842-L855) explicitly maps dx12, metal, vulkan, and GLES; it exposes no DX11 backend. The f9fe GPU crate feature list is reactivity/crates/gpu/Cargo.toml:22-26. This slice keeps that feature set and the CPU presenter unchanged.

The a871 snapshot's offline artifact is deliberately a static SPIR-V/Vulkan path. In reactivity/crates/gpu/src/renderer/artifact.rs:1-60, generated words and explicit layout/interface are selected from the device profile; the feature is optional in crates/gpu/Cargo.toml:9-31. At that same pin, HAL's DX12, Metal, and GLES shader-module branches reject StaticSpirV with “Static SPIR-V requires the Vulkan backend” (vendor/wgpu-hal/src/dx12/device.rs, metal/device.rs, and gles/device.rs). This is evidence against claiming the static path provides equal compiler-work or memory gates on all backends. It is not part of f9fe, is not the proposal here, and does not remove checked WGSL fallback or all driver/pipeline work.

If “preserve legacy backend reach” means original GPUI Windows Direct3D 11, this WGPU 30.0.1 cleanroom tree already has a reach gap: it compiles DX12, Vulkan, and GLES for Windows, not DX11. The current upstream Zed Windows implementation is a separate source tree and uses the Windows Direct3D 11 API (official project source imports D3D11CreateDevice and D3D feature levels 10.1/11.0/11.1 in [gpui_windows/directx_devices.rs](https://github.com/zed-industries/zed/blob/main/crates/gpui_windows/src/directx_devices.rs)); do not represent WGPU DX12 as equivalent D3D11 support. A true D3D11 route would require a distinct backend or retained original renderer and its own rendering/lifecycle proof, outside this owner cleanup.

This audit establishes no blanket support guarantee for older Windows, OpenGL drivers, or GPUs. Microsoft's [D3D11 deployment documentation](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/direct3d11-deployment) describes D3D11.1 on Windows 8 and partial support on Windows 7 with the platform update; the WGPU v30 manifest only states backend compile targets. DX12 has separate OS and hardware requirements; Microsoft describes Windows 10 and a Direct3D 12-compatible GPU/WDDM 2.0 driver in [Understanding Direct3D 12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/directx-12-getting-started). WGPU's compiled GLES route may cover systems with a usable implementation, but the tree does not certify every older system. Keep the existing CPU fallback; explicit GPU attempts still need a runtime-compatible adapter and target and can fail normally. The config-field removal does not narrow currently compiled routes, but cannot close the existing DX11 gap.
