## Recommendation

The next bounded Sol change should add **one typed, static SPIR-V source path** through generic WGPU and implement only its Vulkan 1.0 fallback: store `&'static [u32]` in the HAL shader wrapper, then create a short-lived `VkShaderModule` for each pipeline stage under the already-integrated `CompiledStage` cleanup guard. Keep ordinary `Raw(vk::ShaderModule)` ownership exactly as it is. Keep checked WGSL as the fallback and propagate all passthrough errors. Do not start with a six-language/backend source enum: each backend has different native lifetimes and compile semantics, and the current qualified artifact is SPIR-V for Vulkan.

This preserves Vulkan 1.0 support, reuses the `ffb4b8f58035330f4034a6891ec87de6574195c0` RAII fix, adds no extension or global cache, and does not add platform-specific branches in GPUI. It removes a long-lived `VkShaderModule` handle from the Core shader-module owner's HAL representation while leaving the reusable-raw-module contract intact. Whether the driver reclaims/caches native memory is an implementation result to measure, not a guarantee from the Rust ownership change. It does **not** remove pipeline compilation. For one pipeline using two stages, it moves the two module-create calls from shader-module creation into pipeline creation; for a shader used by multiple pipelines, the temporary route recreates a module per pipeline use. There is no timing evidence that this is faster.

Treat inline `VkShaderModuleCreateInfo` chaining as a second, separate experiment. When the `maintenance5` feature is actually supported and enabled, it can avoid the native module object. The root HAL currently does not query, enable, or remember that feature. Driver pipeline parsing/validation/compilation still happens, and a self-referential pNext representation is an easy use-after-move bug. I would not make the first static-artifact patch depend on this extension.

The broader research principle is **static immutable code at rest; backend-native intermediates only for the shortest interval allowed by that backend's API; retain every object the backend or WGPU contract still requires**. This is a later comparison, not a six-backend API proposal: Vulkan has a standard temporary-module path, D3D12 can consume a bytecode view during PSO creation, Metal uses a library/function before pipeline creation and the current HAL retains library references in pipeline-stage metadata, and GLES compiles shader objects into a retained linked program. The first change should leave those backends' current behavior untouched.

## Current owner trace and the lifetime seam

In the root HAL, `ShaderInput<'a>` carries borrowed `SpirV(&'a [u32])` at `reactivity/vendor/wgpu-hal/src/lib.rs:2526–2547`. HAL shader objects have no input lifetime. Vulkan maps Naga output and ordinary SPIR-V to `ShaderModule::Raw` at `vulkan/device.rs:1883–1913`, and destroys that raw handle only when HAL `destroy_shader_module` runs at lines 1926–1935. `create_shader_module_impl` makes the native object at lines 680–707.

Core’s passthrough path selects `hal::ShaderInput::SpirV(&[u32])` at registry `wgpu-core-30.0.1/src/device/resource.rs:2499–2597`; it does not retain the descriptor bytes. Core `ShaderModule` owns a boxed HAL module with no source lifetime (`src/pipeline.rs:68–85`). A compute pipeline holds an `Arc<ShaderModule>` in `ComputePipelineState::_shader_module` (line 307), and a render pipeline holds stage module Arcs in `RenderPipeline::_shader_modules` (line 921). Those Arcs are deliberate reusable leases: an application can use one module to build more than one pipeline, and the pipeline may also keep the module alive.

At the public facade, `wgpu/src/dispatch.rs:752` shows `DispatchDevice::as_core_opt()` returns `Some` only for Core dispatch and `None` for WebGPU/custom dispatch. `CoreDevice` owns its `ContextWgpuCore`, device ID, and error sink (`wgpu/src/backend/wgpu_core.rs:466–474`). Its existing passthrough method routes through `Global::device_create_shader_module_passthrough` and reports a returned error through `context.handle_error` (`backend/wgpu_core.rs:1103–1138`). The narrow static method should preserve that route, not call HAL or Core `Device` directly from the facade. Thus `None` means only “this dispatch is not Core”; lost device, missing `PASSTHROUGH_SHADERS`, non-Vulkan Core backend, and native errors should produce the ordinary invalid module/error-scope behavior. That distinction prevents an availability fallback from swallowing real shader errors. The static Global entry point can build the normal passthrough descriptor from the static slice and entry-point metadata, then use the same Core resource helper and error sink. Because that descriptor still carries `spirv: Some(Cow::Borrowed(words))`, the existing active trace branch records the same SPIR-V bytes and replay uses the ordinary dynamic Raw route.

Adversarially, the API descriptor clone path does not itself defeat a static borrow. `CreateShaderModuleDescriptorPassthrough` derives `Clone` and uses `Cow`; cloning a `Cow::Borrowed` source preserves the borrowed view. Core's `Device::create_shader_module_passthrough` consumes the selected input synchronously in the HAL call, then creates a HAL trait object, and stores only `PassthroughInterface` entry-point names, a label, and device ownership in its Core `ShaderModule` (`wgpu-core-30.0.1/src/device/resource.rs:2499–2597`). `Global::device_create_shader_module_passthrough` does not capture the descriptor in the live resource. With the optional `trace` feature and active trace, however, it intentionally copies shader bytes to trace binary data (`src/device/global.rs:1026–1092`); that is a trace artifact, not a hidden live Core owner, and must be included in trace-mode memory accounting.

The ordinary pipeline descriptor similarly contains handles, not source data. Public `RenderPipelineDescriptor<'a>` derives `Clone` and refers to `ShaderModule` handles (`wgpu-30.0.1/src/api/render_pipeline.rs:199–259`). The wgpu-core backend translates those handles to IDs (`wgpu-30.0.1/src/backend/wgpu_core.rs:1337–1408`), then Core resolves each ID to an `Arc<ShaderModule>` in `device/global.rs`; `create_render_pipeline` clones the resolved descriptor for error/result handling and, on success, moves its shader-module Arcs into `RenderPipeline::_shader_modules` (`wgpu-core-30.0.1/src/device/resource.rs:4184–4205, 5010–5080`). Compute uses the corresponding `_shader_module` Arc (`resource.rs:4010–4124`). Thus a new HAL static slice can remain zero-copy through descriptor clones and Core resolution, but Core intentionally continues retaining the *module lease* for repeat pipeline use. Dropping the user handle while a pipeline or another descriptor Arc exists cannot invalidate the static slice; dropping the last module Arc calls `destroy_shader_module`, which must treat the `StaticSpirV` arm as a no-op for native-handle destruction.

The Vulkan destroy rule permits deleting a module after a pipeline has been created from it, even while that pipeline is used: [`vkDestroyShaderModule`](https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroyShaderModule.html). It does not permit the HAL to take an ordinary reusable `Raw` module away after the first pipeline if another pipeline creation may follow. Root’s stage-local `CompiledStage<'a>` at `vulkan/device.rs:252–265` already carries the temporary module’s ownership as `Option<&ash::Device>`; its Drop destroys only stage-local modules. `compile_stage` selects Raw without an owner and Intermediate with the guard at lines 709–820. That commit also validates the entry-point CString before creating a module and covers success, early exits, unwind, and non-ownership of Raw in a fake dispatch test. The evidence is `reactivity/evidence/vulkan-stage-ownership/README.md`.

The candidate already passes static arrays as `Cow::Borrowed(words)` at `reactivity/crates/gpu/src/renderer/artifact.rs:46–53`. The general passthrough descriptor is `Cow<'a, [u32]>` (`wgpu-types-30.0.1/src/shader.rs:124–144`), and the HAL `ShaderModule` has no input lifetime, so it cannot store an arbitrary call borrow. Extending that borrow to `'static` with a cast is unsound. The narrow seam is a separate, internal static-SPIR-V creation entry point whose source parameter is explicitly `&'static [u32]`, plus a `ShaderInput::StaticSpirV(&'static [u32])` HAL variant. Its descriptor metadata should be limited to the existing label/entry-point fields. Do not reuse the `Cow` field, infer `'static` from a borrowed descriptor, or add a cross-backend language enum.

Conceptually the facade should add just one `unsafe` method taking the existing label and entry-point metadata plus `words: &'static [u32]` (for example, `create_shader_module_static_spirv(label, entry_points, words)`). Source ownership is explicit in the input type; metadata borrows only for the call. Make Core select the Vulkan static source only when the active backend is Vulkan; retain existing dynamic `Cow<'a, …>` mapping and checked WGSL behavior elsewhere. Other HAL backends need an explicit unsupported arm for this Vulkan-only input, rather than conversion to another language or an unreachable assumption at a public boundary. Keep the API source path limited to this typed unsafe entry point and keep application-side artifact/profile admission sealed. Since the GPU crate calls across a crate boundary, prefer a narrowly scoped doc-hidden unsafe vendor method unless this is intentionally supported as public experimental API; do not add a new public safe shader-ingestion API. GPUI itself still has no OS, raw-HAL, or platform API branch. Static lifetime proves only storage validity, not shader correctness or safety: preserve the existing unsafe boundary, artifact generator's exact-interface checks, strict SPIR-V validation, sealed per-device/profile admission, and error-scope behavior. The Vulkan `VkShaderModuleCreateInfo` contract also requires valid SPIR-V, a 4-byte-multiple code size, supported capabilities and declared extensions; its official [reference](https://docs.vulkan.org/refpages/latest/refpages/source/VkShaderModuleCreateInfo.html) makes clear that `'static` alone satisfies none of those conditions.

For the first Vulkan implementation, the HAL representation can be as narrow as:

```rust
enum ShaderModule {
    Raw(vk::ShaderModule),                   // existing reusable contract
    StaticSpirV(&'static [u32]),              // new, immutable source recipe
    Intermediate { /* existing Naga module/checks */ },
}
```

A static-input route creates the Core Arc as usual, but HAL stores only the static slice for this arm. During every Vulkan pipeline-stage build, `compile_stage` creates a fresh temporary module from that slice and returns the existing `CompiledStage` with `temporary_owner: Some(&self.shared.raw)`. Its destructor handles normal return, later-stage failure, render-pass/driver failure, and unwind. HAL destroy of `StaticSpirV` has no native handle to free. The static words outlive Context, Core Arcs, pipeline creation, and concurrent stage calls. Do not route normal dynamic SPIR-V through this arm and do not consume or recycle Raw handles.

There is no extra HAL Arc, runtime hash, mutable registry, or global cache in this formulation. The Core Arc lease remains because Core needs module identity/interface data and because the general contract retains modules; it now points to a small borrowed recipe rather than a native module. The SPIR-V array remains linked in the binary, so runtime heap reduction is not binary-size reduction.

## Static module creation versus inline pNext

### Vulkan 1.0 temporary-module route

This is the compatibility baseline. Vulkan 1.0’s standard path is `vkCreateShaderModule`, then `VkPipelineShaderStageCreateInfo::module` points to the handle; the [Vulkan Guide](https://docs.vulkan.org/guide/latest/ways_to_provide_spirv.html) describes that as the original path. For the new static source, defer creation until pipeline construction, use the stage guard, and destroy the object once `vkCreateGraphicsPipelines` / compute / ray-pipeline creation returns. All Vulkan 1.0 devices retain this path; it does not touch device creation or extension gates.

The HAL no longer retains a persistent VkShaderModule handle after the pipeline call; the stage guard destroys the temporary handle after success or failure, as Vulkan permits after pipeline creation. That lifecycle does not guarantee when or how the driver reclaims/caches native storage. The route shifts module creation to the pipeline boundary and repeats it for every pipeline stage use. The driver still sees SPIR-V at module creation and still creates/compiles the pipeline. A cache hit, a module reused many times, or an implementation's internal module cache can change costs; no speed claim follows from ownership alone.

### Inline stage pNext

The [Vulkan Guide](https://docs.vulkan.org/guide/latest/ways_to_provide_spirv.html#inlining-inside-vkpipelineshaderstagecreateinfo) documents a stronger option: if `VK_KHR_maintenance5` or `VK_EXT_graphics_pipeline_library` is supported/enabled, put a `VkShaderModuleCreateInfo` in `VkPipelineShaderStageCreateInfo::pNext` and set `module = VK_NULL_HANDLE`. The [Vulkan refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineShaderStageCreateInfo.html) specifies that null module means the shader code comes from the chained module-create info; VUID stage-06845 requires a real module or a valid create-info chain unless the relevant feature/identifier alternative is active. The maintenance5 feature description states directly that the structure may be chained to pipeline creation and that its feature must be queried and set true in `VkDeviceCreateInfo.pNext` before use ([feature refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceMaintenance5Features.html)). Vulkan 1.4 promotion does not remove the feature-query/enablement requirement; `VK_KHR_maintenance5` was promoted to 1.4 and its extension dependencies are documented [here](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_maintenance5.html).

The alternative GPL route also requires actual `VK_EXT_graphics_pipeline_library` device enablement, its `VK_KHR_pipeline_library` and API/props2 dependency, and `graphicsPipelineLibrary=true` queried and enabled ([extension refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_graphics_pipeline_library.html), [feature refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceGraphicsPipelineLibraryFeaturesEXT.html)). GPL’s stated purpose is to compile four pipeline parts separately and link them; using it just to inline code adds more device/pipeline surface than maintenance5. Prefer maintenance5 when already available; keep the temporary Vulkan 1.0 route otherwise.

**The current root HAL enables neither option.** I found no `maintenance5` or `graphics_pipeline_library` references in the root Vulkan HAL. Device creation at `vulkan/adapter.rs:2995–3065` starts from `required_device_extensions`, builds `PhysicalDeviceFeatures`, enables only those feature structures and extension names, and records the actual enabled extension list in DeviceShared (`device.rs:848–850`, adapter line 2913). The feature structure currently has maintenance4 but no maintenance5 at adapter lines 124–125. Support advertised by the physical device, or an API version at least 1.4, is not equivalent to an enabled logical-device feature. For promoted maintenance5, the feature bool is the decisive state even if the KHR extension name is not in the enabled-extension list. If inline chaining is later implemented, add support query, feature enablement, and an actual enabled-feature bit to the device state. Only enter the inline path on that recorded bit; otherwise use the temporary module path. Do not opt into GPL or maintenance5 just because the extension is present.

The added pointer graph deserves its own safety boundary. Today `compile_stage` writes `create_info.p_name = entry_point.as_ptr()` and keeps the CString alongside the Vulkan struct (`device.rs:805–820`). The pointer targets CString's separately allocated buffer; moving the CString handle does not relocate that buffer. A new `p_next` pointing at a `VkShaderModuleCreateInfo` embedded in `CompiledStage` would point into the stage struct. Moving that stage into an `Option`, `Vec`, or `ArrayVec` after setting pNext invalidates the self-pointer. Do not make a self-referential stage and assume an ordinary Rust move is harmless.

For a separate inline experiment, allocate/fix every module-create record at its final address before writing any stage `p_next`, retain that storage, the static code, and CString buffers through the synchronous Vulkan call, and do not mutate/reallocate the module-record storage afterward. A `Vec`'s heap allocation survives moving the `Vec` handle, but pushing after taking pointers can reallocate its elements; an inline `ArrayVec` can itself move. A pinned fixed-capacity bundle or a heap allocation populated to final capacity and then frozen are candidates, each with explicit unsafe invariants and nontrivial lifetime tests. This must be measured for stack/heap/code impact rather than described as allocation-free. Test pointer validity inside the fake dispatch and with Vulkan validation layers. The existing `CompiledStage::temporary_owner` is specifically a VkShaderModule destruction guard; an inline stage has `module = VK_NULL_HANDLE`, so do not route it through that owner flag or assume the guard keeps its pNext target alive. Inline avoids the module handle and its create/destroy calls; it does not guarantee less shader parsing or pipeline work.

## Failure, reuse, and concurrency checks

For the Vulkan temporary route, exercise: module-create failure before a handle exists; a failure on the second stage after the first temporary exists; render-pass/pipeline failure after stage assembly; unwind while stages are owned; successful creation; repeat construction of multiple pipelines from one Raw module; and Raw module destruction only after its normal Core last-owner drop. Add the new static variant to the existing stage ownership dispatch test. On success the guard destroys stage-local handles after pipeline creation, which Vulkan explicitly permits; on every error the same guard closes them. A failed create must never destroy the Raw reusable module.

The pinned HAL's ray-tracing pipeline call passes `vk::DeferredOperationKHR::null()` (`reactivity/vendor/wgpu-hal/src/vulkan/device.rs:2368`), so its stage guards currently outlive the pipeline-create call and can drop on return. Preserve that fact in review: Vulkan permits non-null deferred ray-tracing operations, whose create parameters, shader modules and inline SPIR-V may be accessed until the operation completes ([Vulkan Guide](https://docs.vulkan.org/guide/latest/ways_to_provide_spirv.html#deferredoperationkhr)). If a future HAL path starts a deferred operation, a local `CompiledStage` drop at the API return boundary would be too early; ownership must extend to completion before destroying the module or ending the pNext/code storage lifetime.

For static arrays, drop the application’s shader wrapper while a Core pipeline still retains its Arc, then drop pipeline and Device in order. The bytes are process-static either way, so there is no dangling borrow. Create two pipelines concurrently from the same static module: each call owns independent temporary modules and stage arrays, with no shared mutable cache state. The calls introduce no source-side lock; each still follows the host-synchronization rules of the Vulkan commands and objects it uses, as detailed below.

The temporary-module route must preserve the `Arc` lease semantics, not turn a reusable module into a single-use resource. A pipeline-create call makes its own temporary module for each static stage and never modifies the stored slice or `ShaderModule`; concurrent calls therefore read immutable `u32` storage and own separate handles. A second and later pipeline from the same Core module must also work after the first temporary module has been destroyed. When `vkCreateShaderModule` succeeds, make the temporary-handle guard its first owner before any operation that can return or unwind. `create_shader_module_impl` optionally applies an object name after native creation when passed a label (`vulkan/device.rs:680–707`); both the Intermediate path and the reviewed static path pass `None`, so there is currently no labeling step between module creation and guard construction. Keep that `None` call and construct the guard immediately; if a later change adds labeling or another fallible/unwinding operation, move guard ownership ahead of it. A failed `vkCreateShaderModule` has no handle to destroy. A failed later stage or pipeline call drops every already-guarded temporary; test a panic/unwind at each ownership transition too.

There is an intentional error-phase change: on the current raw path `vkCreateShaderModule` reports SPIR-V/module errors during shader-module creation; with deferred static SPIR-V, the first Vulkan parse/validation error may surface from pipeline creation. The candidate's `GpuContext::new` keeps shader-module and pipeline creation inside the same nested WGPU error scopes (`crates/gpu/src/renderer.rs:414–490`), so this specific call site can observe either phase. A generic vendor API must document the deferred validation point and callers must keep errors intact; it must not report a module as validated just because a static slice has `'static` lifetime. No module/pipeline error may trigger a checked-WGSL success retry.

The new code does not change host synchronization rules or add a lock. Immutable static data removes source mutation races; it does not synchronize any Vulkan handles or extend their lifetimes. Avoid the overbroad claim that every concurrent operation on one `VkDevice` needs an external lock: Vulkan specifies host synchronization per command/object. For example, pipeline creation internally synchronizes ordinary use of a shared pipeline cache, but requires external synchronization if the cache was created with `VK_PIPELINE_CACHE_CREATE_EXTERNALLY_SYNCHRONIZED_BIT`; the destination of `vkMergePipelineCaches` has its separate synchronization rule ([pipeline chapter](https://docs.vulkan.org/spec/latest/chapters/pipelines.html), [graphics-pipeline refpage](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateGraphicsPipelines.html), [merge refpage](https://docs.vulkan.org/refpages/latest/refpages/source/vkMergePipelineCaches.html)). `vkDestroyDevice` itself requires external synchronization on the device and queues, and freeable child objects must be released first ([device destroy refpage](https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroyDevice.html)). Preserve the existing caller/HAL obligations for each object/command and concurrent destruction; do not add a global device mutex or imply that a borrowed SPIR-V API replaces required synchronization. The current candidate sets `cache: None`, but that only selects `VK_NULL_HANDLE` for the explicit cache; Vulkan notes implementations/layers may still use an implicit cache.

For the inline route, also test that a device with support merely advertised but feature not enabled takes the temporary fallback; a device where support is queried and the feature is truly enabled takes the null-module/pNext branch; all stage pNext and code pointers remain valid through the driver call; and a failure/unwind leaves no leaked native module because none was created. Leave Raw module creation on the normal route. Keep a successful static shader path eligible only after artifact/profile validation; do not convert module creation or pipeline errors into a WGSL retry.

## Other backend lifecycles

### Metal

HAL’s `ShaderInput::MetalLib` calls `new_library_from_metallib_bytes` and immediately stores a retained `MTLLibrary` in `PassthroughShader` (`metal/device.rs:1268–1297`; `metal/mod.rs:1109–1127`). The byte helper constructs DispatchData over the input bytes and passes it to `newLibraryWithData` (`metal/library_from_metallib.rs:34–47`). MSL source instead calls `newLibraryWithSource` at module creation (`device.rs:1299–1316`). Pipeline compilation obtains a `MTLFunction`; Core retains the shader module Arc, and HAL’s pipeline-stage data also stores a retained library (`metal/mod.rs:1132–1155`, render/compute construction at `metal/device.rs:1471–1483, 1637–1649, 1844–1852`).

Apple documents that `MTLFunction` instances can use significant memory and recommends dropping strong references after pipeline creation ([MTLFunction](https://developer.apple.com/documentation/metal/mtlfunction)); its best-practices guide says `MTLLibrary` and `MTLFunction` can be released after their dependent pipelines are built ([Persistent Objects](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/PersistentObjects.html)). The pinned HAL stores the passthrough `MTLLibrary` in the shader module and also retains it in pipeline-stage metadata (`metal/mod.rs:1109–1155`; `metal/device.rs:1271–1316, 1471–1483, 1637–1649, 1844–1852`). A future static `.metallib` route would need to audit both owners; merely borrowing library bytes does not remove the retained library, and dropping the stage metadata reference is justified only if every later pipeline operation is proved not to need it. Creating a library/function per pipeline can move work or duplicate loads when a module is reused. Apple's binary-archive mechanism is another, device/OS-sensitive pipeline cache and not a portable static-library substitute ([binary archives](https://developer.apple.com/documentation/metal/creating-binary-archives-from-device-built-pipeline-state-objects)). Keep existing Metal behavior untouched in the first Vulkan slice.

A prebuilt `.metallib` is Metal IR, not necessarily a GPU-specific executable: Apple says runtime converts Metal IR to device-GPU binary, whereas source MSL first compiles to Metal IR and then to GPU code ([Metal libraries](https://developer.apple.com/documentation/metal/metal-libraries)). Metal binary archives can carry GPU-targeted pipeline binaries and avoid runtime shader compilation, but are device/OS-sensitive and fall back to IR compilation on archive miss; Apple specifically documents possible invalidation after an OS update ([archive guide](https://developer.apple.com/documentation/metal/creating-binary-archives-from-device-built-pipeline-state-objects)). That is a separate pipeline-cache artifact system, not a free portable substitute for static metallib bytes.

### Direct3D 12 and the existing Direct3D 11 renderer

WGPU's DX12 input type has `ShaderInput::Dxil` or `Hlsl`, no D3D9 backend, and no DXBC input (`wgpu-hal/src/lib.rs:2537–2545`, `dx12/device.rs:1866–1902`). DXIL passthrough is copied to `Vec<u8>` at module creation and cloned into `CompiledShader::Precompiled` in `prepare_shader` (`dx12/device.rs:403–406, 1882–1887`; `dx12/mod.rs:1348–1370, 1870–1884`). A later static DXIL arm could hold `&'static [u8]` and point the PSO bytecode view at it for the synchronous PSO call, eliminating those two Rust-side copies if the exact downstream code path also stays borrowed. No per-shader native module handle is created; the retained native object is the final PSO. Microsoft defines `D3D12_SHADER_BYTECODE` as a data pointer and length, passed in the graphics/compute PSO descriptor ([bytecode refpage](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_shader_bytecode), [CreateGraphicsPipelineState](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-creategraphicspipelinestate)). HLSL still goes through compiler paths; offline DXIL generation would need separately qualified artifacts.

Do not conflate this with original GPUI's Windows D3D11 renderer. The earlier comparison refers to the full original GPUI source tree's `crates/gpui_render/src/artifacts.rs:33–46` and `crates/gpui_windows/src/directx_renderer.rs:2386–2405`, which generate static SM5 bytecode and create D3D11 shader objects. Those files are absent from both audited cleanroom trees (`/root/gpui-ce3/reactivity` and `/tmp/gpui-offline-shader-sol/reactivity`); this is a source comparison only, an **unimplemented cleanroom backend**, and not a cleanroom runtime or measurement result. WGPU's D3D12 backend is a separate API. Microsoft documents D3D12 feature levels starting at 11_0 ([feature-level page](https://learn.microsoft.com/en-us/windows/win32/direct3d12/hardware-feature-levels)); do not describe this path as DirectX 9 support.

### GLES / GL

WGPU GLES currently stores passthrough GLSL as an owned `String` (`gles/device.rs:1476–1500`) and builds a pipeline by creating/compiling stage shaders, linking them into a program, and deleting the stage shader objects (`gles/device.rs:245–290, 461–535`). A static GLSL arm can borrow the source and avoid that Rust String while keeping identical runtime GLSL compiler/link behavior and the linked program. WGPU HAL currently marks GLSL passthrough as a backend path and rejects SPIR-V, MetalLib, MSL, DXIL and HLSL here.

GL program binaries are an optional, implementation-specific pipeline-artifact option, not cross-vendor shader binaries. Khronos’s `GL_OES_get_program_binary` describes a pre-linked program reload path to avoid runtime compile, but says a loaded binary can fail after hardware/software/compiler changes and the app should fall back to original GLSL ([official extension spec](https://registry.khronos.org/OpenGL/extensions/OES/OES_get_program_binary.txt)). The desktop `GL_ARB_gl_spirv` spec explicitly says it is not written for OpenGL ES ([official spec](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_gl_spirv.txt)). Any GL binary path belongs in a later per-driver program-cache design, with source fallback, not in the Vulkan static artifact change.

## Pipeline-cache interpretation and provenance

Three costs must stay separate:

1. Offline artifact generation removes the admitted compositor’s runtime Naga front-end/reflection/SPIR-V write work. It does not remove driver compilation or device creation, and WGPU/Naga remain in the build and in checked WGSL fallback.
2. Static Vulkan plus a temporary module removes the retained `VkShaderModule` object while preserving standard Vulkan module-create and pipeline work. It can repeat module creation when the same artifact creates more than one pipeline.
3. Inline pNext removes the module object and calls; the API still supplies SPIR-V to pipeline creation, so driver validation/parsing/compile may move into that pipeline call. A Vulkan shader-module identifier is a more aggressive cache-hit path, not a simpler static module: it is an opaque driver-generated identifier, requires the feature and `FAIL_ON_PIPELINE_COMPILE_REQUIRED`, and pipeline creation may report compile-required if a compatible pipeline is absent ([stage identifier refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineShaderStageModuleIdentifierCreateInfoEXT.html), [identifier extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_shader_module_identifier.html)). Retain SPIR-V for misses/fallback.

GPUI's candidate sets `cache: None` in `reactivity/crates/gpu/src/renderer.rs:469`, so HAL uses `vk::PipelineCache::null()` in Vulkan render/compute/ray creation (`vulkan/device.rs:2177, 2231, 2359`). Its final DHAT record disables Mesa's disk shader cache with `MESA_SHADER_CACHE_DISABLE=true`; that does not mean every in-process or implementation-provided implicit cache is disabled. Khronos describes pipeline-cache reuse as part of pipeline creation ([Guide](https://docs.vulkan.org/guide/latest/pipeline_cache.html)); the Vulkan cache header identifies vendor ID, device ID, and pipeline-cache UUID ([header refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheHeaderVersionOne.html)). Apple's archive and Khronos's GL binary sources show similar implementation/OS sensitivity. Record exact source commit, generated artifact SHA-256, shader/pipeline route, API version, device/vendor/driver, enabled extension/feature list, pipeline-cache state/UUID, Mesa-cache setting, process state, and OS for each comparison. If testing module identifiers, record `shaderModuleIdentifierAlgorithmUUID` too.

The offline-artifact README is the evidence source for the current measurements: matched first-owner Context is WGSL `7,833 / 2,188,947 requested / 365,318 retained bytes` versus artifact `68 / 9,572 / 7,906`; Renderer is `7,891 / 2,194,752 / 370,323` versus `126 / 15,377 / 12,911`. The raw artifact route holds two Vulkan modules. Cache-disabled DHAT attributes `34,380 retained host bytes in two vk_common_CreateShaderModule blocks` to those native modules. The final live-owner comparison is a `323,032-byte` host-retained reduction after subtracting the native payload; it is not GPU memory, RSS, device memory, or a timing result. The frozen `bea848dbe4` evidence README charges `616` authored shipping lines (`+551` GPU `src`/`build.rs` code lines plus 65 vendor lines). That is not the final source count: the host-only `db73d4f1cca7f173f98ab835176de2908c464156` interface-proof refinement adds 33 comment/test-free host lines, taking GPU `src`/`build.rs` to `+584` and authored shipping code to **649 lines total** (`584 + 65`). The refinement ledger confirms identical SPIR-V bytes and linked fixture binary; allocation and DHAT results remain attributed to the earlier frozen source, not freshly remeasured at db73. The five unique static word arrays remain 139,064 bytes, the optional fixture binary remains +202,304 bytes, and the feature is off by default. No future result should be forecast from these numbers.

## Bounded Sol evidence gate

Implement only the explicit static SPIR-V route plus the already-integrated Vulkan 1.0 stage guard. Keep WGSL fallback, Raw passthrough, extension configuration, app window/device APIs, and non-Vulkan runtime behavior untouched. Use the existing sealed profile and private static artifact family; don’t add runtime hash/copy scans or global caches. The branch is optional/off by default until qualified.

Rank the work this way: **(1)** static-SPIR-V recipe + temporary Vulkan 1.0 module, preserving Core `Arc` leases and the checked fallback; **(2)** only after that is correct and measured, an optional maintenance5 inline-stage prototype with explicit queried/enabled feature state and separately audited stable pNext storage; **(3)** defer Metal, DX12, and GLES borrow changes to backend-specific proposals, with no broad source enum in the current API. The first slice has no predicted speedup; its concrete target is the long-lived HAL module handle, and the evidence must record whether the implementation actually removes live host-retained bytes after pipeline construction.

Required evidence before making claims:

- Re-run the same Context and Renderer owner scopes, same real Vulkan adapter and optional feature request, same `cache: None`, same DHAT live-owner point, same Mesa cache setting, and same owner drop/poll controls. Report Rust allocation requests/requested/retained/peak bytes separately from DHAT-attributed native host heap and whole-process retained bytes.
- Recount the final source delta and linked artifact/binary costs on the implementation commit, rather than reusing the db73 candidate's 649-line total as the cost of a future change. Compare WGPU tracing disabled/enabled separately if that feature is part of the supported build matrix, because trace mode intentionally captures source bytes.
- Count actual shader-module and pipeline calls: first construction, repeated pipeline creation from one module, failures, and concurrency. Confirm static modules do not retain Vk handles after their guards drop, while Raw modules survive all later pipeline creations and destroy exactly once.
- Add success, second-stage failure, pipeline failure, and unwind cases for static-module guards; extend the fake dispatch check for Raw non-ownership. Run actual Vulkan validation/rendering on qualified hardware/software separately; fake dispatch ownership tests are not driver conformance.
- For inline maintenance5, require a separate patch with exact feature query + create enable + persisted actual-enabled bit; exercise supported/enabled, supported/disabled, and unsupported devices, and test pNext pointers under fake dispatch and validation layers. Compare against temporary-module path with cache settings held fixed. Do not assume that extension advertisement or Vulkan 1.4 alone means active.
- If a startup/performance claim is later wanted, measure wall/CPU time on a named cold and warm setup with repetitions and report driver/pipeline-cache provenance. This research contains no timing or hardware-memory estimate. If no such result is collected, keep claims strictly about observed host allocation and object lifetime.
