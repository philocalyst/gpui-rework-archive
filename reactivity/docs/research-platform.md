# Platform and footprint research

**Decision snapshot (research checked 2026-10-20).** Vendor the pinned selected Winit 0.30.13 source behind a small host boundary; keep the framework's portable window/event types independent of Winit. Replace Taffy with the exact `zortax/cephal` 0.1.1 source at commit `3c1747d2722f18f1f72811882e4cdede17b52362`, behind our own layout-tree adapter. Cephal's low-level traits fit a framework-owned retained slab better than its convenient owning `Tree`, but it is a brand-new 0.1 crate, so ship only after differential and candidate/cache recovery validation. Start with one main/event/UI/presentation owner thread and no worker pool. Add workers only for measured independent work; Cephal's parallel mode owns a persistent pool and is slower on several common workloads. Count application heap, mapped/resident process memory, shared pages, CPU presentation buffers, and GPU/compositor resources separately. “Zero” means zero app allocations and no unnecessary work on warm idle paths; it cannot mean zero OS, compositor, driver, mapped pages, or GPU allocations.

This note follows the contract in [`final/00-model.md`](inputs/final/00-model.md), [`final/07-platform.md`](inputs/final/07-platform.md), and [`final/08-runtime.md`](inputs/final/08-runtime.md), including the two-epoch presentation model, bounded pools, allocation ledger, persistent layout state, and generation-checked leases. It corrects the existing runtime/memory and fast-path references to Taffy where the layout engine changes.

## 1. Exact upstreams and boundary

### Winit

The selected upstream is [`rust-windowing/winit`](https://github.com/rust-windowing/winit), version 0.30.13, pinned here to commit [`e9809ef54b18499bb4f2cac945719ecc2a61061b`](https://github.com/rust-windowing/winit/tree/e9809ef54b18499bb4f2cac945719ecc2a61061b). It is Apache-2.0. Do not follow 0.31.0-beta.3 for the initial vendor: that prerelease splits the package into core/backend crates and changes important event-loop APIs, so it adds migration risk before there is a stable release. 0.30.13 uses `ApplicationHandler` / `run_app`; `EventLoop` is intentionally `!Send + !Sync`, must be created once on the main thread for portable behavior, and event-loop creation opens the platform display connection. Its proxy is the cross-thread wake mechanism. These are architectural constraints, not costs solved by wrapping the loop in a worker thread. Sources: [0.30.13 version metadata](https://docs.rs/crate/winit/0.30.13), [event-loop API](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoop.html), [upstream event-loop source](https://github.com/rust-windowing/winit/blob/e9809ef54b18499bb4f2cac945719ecc2a61061b/src/event_loop.rs), [release notes](https://github.com/rust-windowing/winit/releases/tag/v0.30.13).

Winit is intentionally low-level: it creates windows and translates platform events; it does not draw. On Linux, its default features include both X11 and Wayland, Wayland client-side decorations, and dynamic Wayland loading. Keeping both display backends is required for one Linux binary that supports both; disabling only unused extras such as default Adwaita CSD can reduce dependency and binary surface if the design supplies its own/native frame policy. The package source is about 2.7 MB, but that is source archive size, not executable or resident memory. Pin features and target triples in the vendor manifest; do not infer runtime cost from crate count. Sources: [Winit 0.30.13 feature list](https://docs.rs/crate/winit/0.30.13/features), [manifest at pinned commit](https://github.com/rust-windowing/winit/blob/e9809ef54b18499bb4f2cac945719ecc2a61061b/Cargo.toml), [Winit's scope](https://docs.rs/winit/0.30.13/winit/).

Vendor this exact package and retain its upstream license and copyright files. Patch only the internal host integration and carry each patch as a small, reviewable commit; preserve a machine-readable upstream commit and a reproducible rebase path. The public framework boundary should expose `WindowKey { index, generation }`, portable attributes, normalized input/lifecycle/resize/scale/redraw events, explicit wake/timer requests, and checked window commands. A single `WinitHost` owns `EventLoop` and native windows. Winit IDs and raw window/display handles stay in the host crate; GPU surface creation gets a short-lived typed adapter there. Keep an internal raw-event escape hatch for integrations, but do not make raw Winit types the core protocol. Normalize IME, pointer, keyboard, and scale semantics once at the boundary; retain source timestamps and platform-specific data only when the portable event would otherwise lose required meaning.

### Cephal

The exact crate is [`cephal`](https://github.com/zortax/cephal), version 0.1.1 published 2026-10-16, at upstream commit [`3c1747d2722f18f1f72811882e4cdede17b52362`](https://github.com/zortax/cephal/tree/3c1747d2722f18f1f72811882e4cdede17b52362). It is dual-licensed MIT OR Apache-2.0. Pin and vendor the commit, retain both license files, and keep an easy fallback switch until the differential corpus and workload gates pass. The project states that its tests include 6,084 Chrome-generated fixtures from Taffy and compare random/incremental/parallel results to cold layout. Its own performance numbers are author-published and hardware-specific, not independent validation. Sources: [upstream repository and README](https://github.com/zortax/cephal), [0.1.1 docs/API](https://docs.rs/cephal/0.1.1/cephal/), [0.1.1 crate metadata](https://docs.rs/crate/cephal/0.1.1).

API checked in the pinned source: `Tree` is a ready-made columnar owner with interned styles, caches, contexts, and a `Scheduler`; its methods cover node construction, style patch, `compute_layout`, measurement, changed-node reporting, and optional parallel layout. A framework that already owns the retained tree can instead implement `tree::LayoutTree`, `tree::CacheAccess`, and `schedule::Incremental`, then call `compute` / `Scheduler` directly. `LayoutTree` supplies child access, style, measurement, leaf/child compute, and unrounded output; `CacheAccess` owns the `NodeCache` and generation/speculation state; `Incremental` adds parent, depth, and scheduler flags. This is the adapter seam. The original statute proposed an inverse journal; revision 2 instead uses private memo state with immutable published outputs and cache invalidation/poisoning on failure. It is feasible, but it is not a drop-in `TaffyTree` rename: audit every operation and cache lifecycle in our adapter, including style interning, removed/reused node generations, measurements, hidden nodes, absolute repositioning, rounding, detailed grid metadata, and discard/replay of presentation drafts. Cephal's default `Tree` uses `std::sync::Arc` in its parallel support; do not use that convenience path if it violates our runtime's pointer policy. Sources: [traits](https://github.com/zortax/cephal/blob/3c1747d2722f18f1f72811882e4cdede17b52362/src/tree/traits.rs), [scheduler](https://github.com/zortax/cephal/blob/3c1747d2722f18f1f72811882e4cdede17b52362/src/schedule/mod.rs), [owned tree](https://github.com/zortax/cephal/blob/3c1747d2722f18f1f72811882e4cdede17b52362/src/owned/mod.rs).

The upstream README's serial/parallel/Taffy comparison on an i9-13900K (24 threads) shows why the default must remain serial: parallel loses on a 100k-node contained edit (2.5 µs vs 2 µs), 100k random leaf-width edit (10 vs 8.4 ms), 10k flex row (1.9 vs 1.7 ms), 100×100 grid (8.6 vs 8.4 ms), and 10k resize (2.1 vs 2.0 ms). It wins on 100k nested-flex cold layout (12 vs 34 ms) and 10k random-tree cold layout (12 vs 25 ms). The proposed runtime should use its inline/serial adapter at launch; only experiment with bounded parallelism for large cold roots with enough independent children. The pool's startup, thread stacks, idle wakeups, Arc-sharing, and scratch buffers are paid costs and must be included in the comparison, not hidden by reporting layout kernel time alone. Source and workload details: [Cephal README benchmark table](https://github.com/zortax/cephal/tree/3c1747d2722f18f1f72811882e4cdede17b52362#performance), [parallel executor source](https://github.com/zortax/cephal/blob/3c1747d2722f18f1f72811882e4cdede17b52362/src/owned/parallel/mod.rs).

## 2. Threads and ownership

**Baseline: one owner thread.** Run Winit's event loop, event normalization, input dispatch, reactive graph, presentation draft, layout, hit/accessibility publication, and initial renderer submission on the event-loop/main thread. Use `ControlFlow::Wait` when there is no deadline or input; use `WaitUntil` for real animation/media/timer deadlines, and request redraw only after a committed presentation change. This matches the `!Send` graph and Winit's platform requirements and avoids idle CPU polling and eagerly-created thread stacks. The existing “input/compositor thread” language in `runtime/fastpath.md` must be corrected: Winit callbacks arrive at its owner event loop, while the OS compositor is a separate process. A presentation-resident fast path can be O(1) and allocation-free inside input dispatch; it does not imply an extra app thread.

**Demand workers, bounded and lazy.** Keep a process-wide small worker service unstarted until the first actual async action, expensive decode, or measured CPU task. Configure an explicit maximum, bounded queues, priority, cancellation/generation checks, and sleep when empty. Do not create one pool per window or one per layout invocation. Keep OS, GPU, font, and blocking filesystem calls away from the UI owner when APIs allow it, with owned immutable snapshots and completion messages sent through bounded ingress. Cephal's pool is a possible later experiment; its default is one worker per available core including caller, which is inappropriate as a first-window default for this runtime.

**Separate presentation owner only after evidence.** A render/presentation thread can remove GPU waits from UI input, but adds a thread, queue, epoch pinning, frame copies or shared packet ownership, synchronization, and shutdown/device-loss complexity. Prototype only if traced frame submission or driver waits violate latency budgets. Then give it ownership of the GPU device/swapchain and immutable `PresentationPacket`s; UI remains the sole owner of graph, layout, and native windows unless the chosen backend explicitly permits surface lifecycle calls elsewhere. Use bounded two-epoch leases, a small fixed packet ring, stale-packet dropping/coalescing, and device-generation fences. Do not share the mutable graph or retained layout tree across threads.

## 3. Memory: report separate quantities

The minimal executable, warm-start cost, and retained process memory are different measurements. ELF `PT_LOAD` segments describe file bytes and memory bytes separately (`p_filesz`/`p_memsz`); the kernel maps segments and pages become resident on demand. A stripped small file can still map many shared libraries and allocate large private heaps; a larger file-backed text segment can remain mostly nonresident and share clean pages between processes. On Linux report at least: on-disk executable bytes; ELF load-segment sizes (`readelf -lW`); virtual size; RSS; PSS; private clean/dirty; shared clean/dirty; app allocator live/reserved bytes; thread count/stacks; and GPU allocation/heap counters where available. Use `/proc/$pid/smaps_rollup` and `/proc/$pid/smaps` rather than equating RSS with owned bytes. Track p50/p95 cold launch to first usable frame and warm relaunch separately. The kernel documentation explicitly defines RSS, PSS, and private/shared page counts per mapping; ELF's `PT_LOAD` explicitly separates file and memory sizes. Sources: [Linux proc maps/smaps docs](https://docs.kernel.org/7.0/filesystems/proc.html), [ELF program headers](https://man7.org/linux/man-pages/man5/elf.5.html).

Build-size candidates worth testing: release `opt-level="s"` vs `"z"` vs `3`, `lto="thin"` vs `"fat"`, `codegen-units=1`, `strip="symbols"`, linker section GC, and only necessary Winit/GPU/font features. Report final file size, clean and warm start, first frame, runtime RSS/PSS, and frame/CPU cost for each profile. Do not assume size optimization improves startup or RAM; LTO can increase link time and sometimes code size, compression adds startup decompression and changes page locality, and static linking duplicates library pages across processes. Avoid UPX and blanket static linking as defaults. Avoid `panic=abort` unless it remains compatible with the runtime's explicit panic isolation and diagnostics. The success metric is a smaller relevant mapped/resident working set and faster cold first frame, not only `ls -l`.

“Near zero” must have four ledgers:

| Ledger | Count | Policy |
|---|---|---|
| App heap | live, committed/reserved, allocation count by phase | zero steady-state app allocations after warm-up, as `runtime/memory.md` requires; novelty/cache fills attributed and budgeted |
| Process mappings | RSS/PSS, private/shared, clean/dirty, page faults, thread stacks | measure OS-owned libraries and mappings, with page-cache sharing shown separately |
| CPU-side presentation | packet ring, persistent upload staging, Wayland/X11 buffers, font/IME | account each buffer's dimensions, format, generations, outstanding lease, and reuse point |
| GPU/compositor | VRAM/device-local and host-visible allocations, swapchain images, compositor imported/copy resources | report per backend and window; these are not proven by the app allocator hook |

Demand paging and shared mappings reduce eager loads and allow code/data pages to be shared; they do not make those pages free, guarantee residency, or erase RSS/PSS. Wayland `wl_shm` explicitly maps one shared backing region in client and server and permits reusing the mapped pool, while buffer release says when the compositor no longer uses a buffer. Reuse only after release. Linux DMA-BUF/native GPU paths may avoid a CPU copy on some format/modifier/device combinations, but “zero-copy” is not a protocol guarantee that every compositor/driver path has no hidden import, conversion, staging, or synchronization cost. Sources: [Wayland protocol spec: `wl_shm_pool`, `wl_buffer.release`](https://wayland.freedesktop.org/docs/html/apa.html), [Khronos Vulkan specification](https://registry.khronos.org/vulkan/specs/latest/html/vkspec.html).

Native windows, event queues, display connections, compositor surfaces, GPU contexts/devices, swapchains, shaders/pipelines, font/IME caches, and kernel thread stacks all carry OS/driver costs. Window creation alone may connect to a display; a shown Wayland window needs a presented frame before it appears. A headless/windowless runtime can avoid a display connection only if it truly does not construct a platform event loop/window. Don't promise a zero-footprint native window or zero-driver first frame.

## 4. Shared ownership, zero-copy, and buffers

The current design correctly prefers borrowed reads. `triomphe::Arc` is not a universal replacement for references or local ownership: it removes `Weak` support and the weak-count word/operations, and adds `ArcBorrow`, `UniqueArc`, `ThinArc`, and header-plus-slice options. It remains atomically reference counted and each clone/drop still performs count traffic. Use a local direct borrow for reads, plain in-owner storage or window-lifetime slabs for retained records, and cross-thread `triomphe::Arc` only for immutable snapshots/leases that genuinely outlive the producer frame. This is consistent with the runtime's measured ~4.6× Arc-clone read overhead versus borrowing and its `Snapshot<T>` rule. Do not use Arc per signal, node, event, child, or render property. Do not add a `Weak`-based lifecycle: use generation-checked slot keys and explicit owner revocation. A `triomphe::Arc` cannot be converted transparently to `std::sync::Arc`; choose one type at each crate boundary. Sources: [triomphe 0.1.17 docs, released 2026-10-10](https://docs.rs/triomphe/0.1.17/triomphe/), [triomphe source](https://github.com/Manishearth/triomphe/tree/v0.1.17), local runtime's [borrow-vs-read result](inputs/final/08-runtime.md#41-the-measured-laws).

Zero-copy is a lifetime and synchronization contract, not a promise that bytes never move. A leased buffer is immutable while an OS compositor or GPU may still read it. Return it to its pool only after the protocol release/fence for that exact generation; resizing, device loss, hidden surfaces, and window destruction must retire generations without freeing in-flight storage. For Wayland shared memory, wait for `wl_buffer.release`; for GPU resources, wait for the backend's completion fence/ownership handoff. A stale callback after reuse must fail its generation check. If the system cannot signal external consumers, copy into owned bounded storage rather than risking use-after-free or mutating shared content.

Persistent mapped upload rings save map/unmap churn but require aligned ranges, explicit flushes on non-coherent memory, and fences before reusing bytes still read by the device. Partial writes need dirty-range coalescing; persistent mapping does not make host writes automatically visible or allocation-free in the driver. Double buffering bounds memory/latency and enables the current logical/presentation epoch split; a third buffer can reduce producer stalls under GPU latency but retains another full packet/resource set and can increase input-to-photon lag. Swapchain image count and queue depth are backend/compositor negotiated. Vulkan specifies FIFO, mailbox, and immediate presentation modes; mailbox replaces a pending image (freshness), FIFO retains a queue (ordering but can add latency), and immediate may tear. Pick policy from measured UI latency and power, not a blanket “triple buffer is faster.” Source: [Khronos Vulkan WSI/presentation specification](https://registry.khronos.org/vulkan/specs/latest/html/vkspec.html#VkPresentModeKHR).

## 5. Low-risk experiments, rejection list, and gates

**Do first:** baseline slim/normal release profiles and Winit feature sets; compare cold launch, first usable frame, warm idle, first-window open, close/reopen, and visible-window idle. Add a reproducible Linux capture script for `readelf -lW`, file bytes, `/proc/$pid/smaps_rollup`, page faults, thread count, app allocator counts, CPU buffers, and Vulkan/device memory counters. Test both Wayland and X11 separately. Use `/usr/bin/time -v` only as a coarse complement, not as the shared/private split. Keep host startup phases timestamped (process entry, event loop created, first window, first committed CPU presentation, first GPU submission, first compositor-visible frame).

**Cephal adoption gates:** run upstream fixture suite at the pinned commit; replay the framework's Taffy fixtures and randomized style/structure traces against cold Cephal; compare every layout coordinate/size and rounding decision under deterministic text/image measurement. Test style edits, text measure cache invalidation, insertion/removal/reparent, absolute moves, scroll/overflow, RTL, scale changes, speculative draft rollback, and stale node generations. Compare retained-node bytes, cold layout time, contained-edit time, resize time, and changed-node counts at 1k/10k/100k, using identical release profile and machine. Adopt `LayoutTree`/`CacheAccess`/`Incremental` only if the adapter is sound and no common workload regresses beyond budget; retain a serial implementation and feature flag for one release. Check style completeness against our platform API: “CSS-like” is not equivalent to all existing layout semantics.

**Parallel layout gate:** benchmark serial first and report pool construction separately from steady layout. Enable only above an empirically derived node/work threshold when p95 cold-layout improvement exceeds thread/pool cost and input p99, memory, and idle wakeups stay within budget. Cephal itself reports losses on small/contained updates and common grid/flex rows. A pool that sits idle all day is a startup, stack-reservation, and lifecycle liability, even if its warm kernel benchmark wins on a large tree.

Reject these proposed “optimizations” absent evidence: busy polling the Winit loop (`Poll`) while idle; an eagerly-started full-core pool; one Arc clone per read or per node; increasing in-flight frames without a latency and memory budget; mutating/recycling shared compositor/GPU buffers before release/fence; pretending shared mappings eliminate residency; judging success from stripped ELF bytes alone; static linking/compression/abort-on-panic as unconditional defaults; unbounded queues or epoch pins; and direct input-thread mutation of the graph/layout tree. Each either defeats idle, ownership, bounded-memory, panic, or presentation correctness contracts already stated by the design.

**Acceptance report:** publish the build profile and exact upstream commits; file bytes and ELF segment table; cold/warm startup-to-visible-frame distributions; idle CPU and wake rate; app allocation count after warm-up; app live/committed bytes; RSS/PSS/private/shared mappings; thread count; per-window CPU/GPU buffer bytes and max in-flight epochs; and p50/p95/p99 input-to-present latency. State machine, distro, display server, driver/GPU, display scale, and test scene with each result. A passing app-allocator gate does not claim zero total system memory.
