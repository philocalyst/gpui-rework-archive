# GPUI async ergonomics: read-only design audit

Implementation disposition, 2026-10-22: the final **clear-the-pinned-future**
refinement controls the proposed implementation. The earlier stored-result and
prompt-executor-drop sketch is a rejected control, retained for the review
record. `spawn` takes `&mut self`. Preserve the current owner-lease release before
user destructors: a FutureStarter RAII destructor can cancel its exact task while
QuestionLane's generic Drop remains unchanged. No per-ordinary-question task,
Waker or new cancellation Arc is approved. The Sol implementation is isolated;
this report is not an integrated API or performance claim. GPUI commit links
identify local unpublished source snapshots and may not resolve on GitHub.

**Verdict.** The bounded first convenience should be an opt-in typed `Future` adapter layered on `Questions`, driven by an injected executor with a statically typed per-task cancellation handle. Do not retrofit a Waker or task slot into ordinary `Controller`/`Completion`. The adapter can keep the existing owned-input, request-stamp, last-value, one-slot mailbox and owner-barrier rules while removing the repetitive “freeze, enqueue closure, finish Completion” glue. Its essential new contract is cancellation that wakes or stops that exact task, with the existing physical credit held until the old future has actually been dropped and its terminal admitted. A poll-only `Cancellation` wrapper does not meet that contract.

## What is already there

I audited source commit [`6d77c71c1227bd2609518cc5f3a49e37fc176f82`](https://github.com/gpui-ce/gpui-ce/tree/6d77c71c1227bd2609518cc5f3a49e37fc176f82); current root HEAD `55822d62c4e636b1a6d2f4adcb197ef55f78ee36` has later plan/evidence edits, with no changes to the audited GPUI source, contract, tests, or port files. `Reader<T>` is an inert typed key with no dereference, block, or hidden start; `Questions::question` takes a borrowed-family freezer and an explicit prompt `start` closure, crossing the worker boundary only with `I: Send + 'static`. It allows one physical completion and retains only the newest frozen input until that credit returns. The lane retains its last value through Pending and Fault ([`reader.rs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader.rs#L33-L78), [`question.rs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/question.rs#L45-L89), [state storage](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/question.rs#L156-L174)).

Cancellation today is intentionally a borrowed hint: `Cancellation<'a>` only reads `Controller.current != ticket`; `Completion::run_cancellable` can check during synchronous work, and catches that closure’s panic. Neither it nor `Completion::is_cancelled` owns a task Waker or causes another poll ([`reader.rs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader.rs#L289-L300), [sync helper and terminal Drop](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader.rs#L319-L405)). On a relevant input change, the lane advances its stamp/current hint and keeps only the new latest work; the active cap continues to occupy the mailbox. Only after a terminal reaches the owner, its payload is taken, and the owner retires the mailbox does `start_pending` launch the next request ([refresh](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/question.rs#L426-L507), [terminal admission/retirement](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/question.rs#L564-L603), [`Mailbox`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/linear_mailbox.rs#L20-L90)). The `RequestGate` separately invalidates prior stamps, including A→B→A; cancellation is not acceptance authority ([`request.rs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/state/src/request.rs#L143-L205)).

That distinction is what an adapter must preserve. Rust’s `Future` contract says `Pending` registers the current task’s Waker and a task is polled again after the Waker fires; futures are inert unless polled, and `poll` should return promptly ([`Future`](https://doc.rust-lang.org/std/future/trait.Future.html#runtime-characteristics), [`Waker`](https://doc.rust-lang.org/std/task/struct.Waker.html)). If a wrapper merely checks the existing cancellation hint when polled, this trace strands the lane: A polls `Pending` forever; inputs change to B; `current` changes, but A receives no wake; A is never polled again; its `Completion` never drops; B cannot receive the single physical credit. The API needs an executor/task-level cancel path that wakes or stops A itself.

`Remote::bounded` is useful but solves a different seam: it queues owned values on a bounded FIFO and its send path does not invoke application code; it is not a task executor or a cancellation handle ([`remote.rs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/remote.rs#L50-L123)). The Future adapter should use the existing response mailbox rather than invent another result queue.

## Proposed public surface and internal seam

Keep the current `.question(inputs, freeze, |input, completion| ...)` call unchanged. Add a separately named future method with closure inference intact:

```rust
pub trait QuestionTask {
    /// Idempotently cancel this exact spawned task, including stopping it after `Pending`.
    /// It must not be a bare wake: it must make the executor stop polling and
    /// drop the task, and must wake/schedule cancellation even when the task
    /// is currently Pending.
    fn cancel(&mut self);
}

pub trait QuestionExecutor {
    type Task: QuestionTask;

    /// Ok means one task was accepted and a handle for that task is returned.
    /// Err means the future was rejected and dropped before return.
    fn spawn<F>(&self, future: F) -> Result<Self::Task, StartError>
    where
        F: Future<Output = ()> + Send + 'static;
}

// Sketch: generic method/result types are inferred from `make` and its async block.
questions.question_future(inputs, freeze, executor, |owned| async move {
    service.lookup(owned).await.map_err(SearchError::from)
})
```

The actual method constraints should mirror existing `question`: `I: Send + 'static`, `T: Send + 'static`, `E: Error + Send + 'static`, `make: FnMut(I) -> Fut`, and `Fut: Future<Output = Result<T, E>> + Send + 'static`. That keeps input freezing owner-side and permits no borrowed `Source` input or model/source/reader borrow to survive into the future. The factory may capture owned services; document that it must return promptly and must not access the owner. The task body runs on the injected executor. This is a typed `Future` convenience, not a hidden executor singleton.

Internally, introduce a private `QuestionStarter<I,T,E>` lifecycle (`start`, `cancel`, `retire`) behind the existing start slot. Wrap current closures in a one-field `SyncStarter<S>` with no-op cancellation/retirement; use a `FutureStarter<X,Make,Task>` only for `.question_future`, holding the injected executor, typed factory, and `Option<X::Task>`. Preserve the public closure bound `S: FnMut(I, Completion<T,E>) -> Result<(), StartError>` on `.question` so closure argument inference does not depend on downstream trait-solver inference. A doc-hidden transparent one-field wrapper may change the hidden inferred lane type, but need not add a task field to an ordinary lane. Do not use `dyn Future`, `Box<dyn Future>`, or trait-object task dispatch.

The adapter’s future wrapper needs one subtle lifecycle detail. Its `Completion` must not publish success from inside the `poll` call: an owner could otherwise retire the mailbox while the old future/task still has user code or a destructor left to run. Use a statically generic wrapper with a pinned inner future as its first field and a finalization guard as its last field. On `Poll::Ready`, store the owned `Result<T,E>` in the guard and return `Ready(())`; on a caught poll panic, mark the guard as panicked and return `Ready(())`. When the executor drops the completed wrapper, Rust drops fields in declaration order, so the inner user future is dropped first and the last guard then calls `Completion::complete`, reports `WorkerPanicked`, or lets `Completion` drop as `Abandoned` on cancellation ([Rust field drop order](https://doc.rust-lang.org/reference/destructors.html#destructors)). The mailbox then remains leased until this terminal is applied and retired by the owner. Use safe structural pin projection (for example, a small direct [`pin-project-lite` dependency](https://docs.rs/pin-project-lite/latest/pin_project_lite/macro.pin_project.html)) for the wrapper; `Pin` exists precisely because a future may be address-sensitive and projection has safety obligations ([`std::pin`](https://doc.rust-lang.org/std/pin/)).

Concrete internal shape:

```rust
#[pin_project]
struct RunFuture<F, T, E> {
    #[pin]
    future: F,                // declared first, dropped first
    finish: Finish<T, E>,     // declared last, publishes only during drop
}

struct Finish<T, E> {
    completion: Option<Completion<T, E>>,
    outcome: Option<Result<T, E>>,
    worker_panicked: bool,
}
```

`RunFuture::poll` catches unwind around the pinned `future.poll(cx)`. `Pending` stays pending; `Ready(result)` puts the owned result in `finish.outcome`; panic sets `worker_panicked`; both terminal cases return `Ready(())`. `Finish::drop` consumes the completion to publish the stored result or the worker-panic terminal. With no stored terminal, it leaves the completion to its existing `Drop` implementation, which publishes Abandoned. This sends no result before `F` has been physically dropped and avoids a task box. The executor must promptly drop a completed wrapper, as required above.

Catch panic around each inner `poll`, not merely the factory call. Map a future poll panic to the existing `WorkerPanicked` path; map domain `Err(E)` to a normal domain Fault retaining the prior value; map factory/executor startup panic consistently with the existing `ExecutorPanicked` start path. The user future’s `Drop` must be non-panicking, as with ordinary cancellation-safe Rust tasks; a panic in a destructor is outside the clean result/panic distinction. Never treat `Task::cancel()` returning as credit return. It requests cancellation; the task must actually drop and its finalizer must publish terminal before owner retirement.

On source/dependency supersede, first publish the new ticket/current value, then cancel the stored old task handle. Cancel on transition to unavailable input, lane fault, explicit close, and natural owner Drop. When the owner applies a task terminal, it must drop/retire the old handle before recycling the mailbox and starting the latest pending input. This preserves one physical task, not merely one valid result. Task-handle cancellation after task completion must be harmless.

## Executor contract and alternatives

The task trait’s semantic contract is load-bearing:

- `spawn` must enqueue promptly and must not poll the future inline on the owner stack or re-enter GPUI. A worker may race to finish before `spawn` returns; its completion only queues the existing host wake and is admitted at the ordinary barrier. The local host wake is an event-loop proxy, not direct owner callback ([native wake](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/host/src/native.rs#L44-L55)).
- `Ok(handle)` transfers the exact future to that task; `Err` must drop it before return. An executor that accepts the future and then returns `Err` without a cancellation handle can leak the credit. An executor that accepts then panics before returning its handle can also leak it. Require spawn panic to occur before acceptance (or to drop the accepted task before unwind); the existing catch maps a startup panic but cannot recover a handle the executor never returned.
- `cancel` is idempotent, prompt, nonblocking and non-panicking; it must request abort/drop of the exact task and wake/schedule that abort, including cancel-before-first-poll and cancel-between-Pending-and-Waker-registration races. A bare task wake is insufficient unless a cancellation-aware wrapper observes a flag and then stops polling the inner future. If a task is in `poll`, cancellation cannot preempt it; it takes effect after that poll returns. Tokio’s `AbortHandle::abort` explicitly does not imply completion, and `is_finished` may remain false after abort; `spawn_blocking` cannot be aborted ([Tokio `AbortHandle`](https://docs.rs/tokio/latest/tokio/task/struct.AbortHandle.html)). These are exactly the reasons the GPUI mailbox, rather than `abort()` return, remains the retirement authority.
- A completed executor task must promptly drop its task future. Otherwise the guard intentionally withholds the terminal/credit even if the task returned `Ready`.

This maps naturally to a native executor handle. Upstream GPUI’s published `Task<T>` is an ergonomic precedent: it is a future and dropping it cancels, while `detach` continues without a returned value ([GPUI `Task`](https://docs.rs/gpui/latest/gpui/struct.Task.html)). That is evidence for a familiar user shape, not evidence that cleanroom GPUI already has such an executor; it does not. By contrast, `iced_futures::Executor::spawn` accepts a future but returns `()` and has no per-task cancel handle ([Iced executor trait](https://docs.rs/iced_futures/latest/iced_futures/executor/trait.Executor.html)). An adapter for a fire-and-forget executor can wrap the task in `futures_util::Abortable`; its implementation stores an `AtomicWaker`, checks abortion, registers, then rechecks to close the lost-wake race, and `abort()` wakes the task ([pinned-version source](https://docs.rs/futures-util/0.3.34/src/futures_util/abortable.rs.html#L8-L26), [poll/abort logic](https://docs.rs/futures-util/0.3.34/src/futures_util/abortable.rs.html#L139-L202)). That fallback allocates one `Arc<AbortInner>` per abort pair (the source calls `Arc::new` in `new_pair`); keep that cost inside the opt-in adapter, not every ordinary controller. The GPUI crate does not currently depend directly on `futures-util`; it is present in the lockfile transitively ([pinned manifest](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/Cargo.toml)).

A second alternative is adding `AtomicWaker` to each Controller and making `current` changes wake it. That works mechanically if the future registers before checking the cancellation flag, but adds cancellation storage to every ordinary question, which pays for async in the wrong place. An opt-in per-future Arc/Waker avoids that global cost but repeats the `Abortable` allocation and cancellation protocol. Prefer an executor-native associated handle as the primary API; offer the Abortable adapter only where the backend has no native handle and its per-request allocation is accepted. The existing borrowed `Cancellation` remains useful for synchronous workers such as Hummingbird’s DB search loop ([worker use](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/ports/hummingbird/src/worker.rs#L87-L123)); it is complementary, not the Future cancellation mechanism.

## What it costs and what stays the same

The ordinary path keeps the existing `Controller` fields (single `Mailbox`, `AtomicU64 current`, and feature-gated native wake) and `Completion` fields (controller Arc plus request stamp); do not add a `Waker`, task box, or cancellation Arc to those common types ([`Controller`/`Completion`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader.rs#L242-L300)). Its current `start` closure is only wrapped in a transparent generic starter and it gets no task handle. The Future-only lane stores its executor, future factory, and one `Option<Exec::Task>` slot; its future and wrapper remain generic, with no GPUI-owned `Arc` allocation or `dyn Future`. The executor may allocate or box internally, and its associated handle’s size varies by backend; do not claim a byte count or speedup until measured. `Completion` still carries its existing Arc clone per active response. If a backend lacks task abort support, the explicit Abortable fallback adds one shared cancellation allocation per active future question/task, not per ordinary question.

The API removes repeated completion wiring and centralizes Future polling/panic/lifecycle. It does not remove the caller’s service/executor choice, owned-input freezer, domain error type, existing Reader projection, or view presentation policy. [`QuestionInputs`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader/inputs.rs#L21-L52) already freezes Source, prior Reader, or pair inputs with typed versions; the example’s custom worker is explicit today ([library example](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/examples/library.rs#L30-L46)). The bounded Hummingbird port and tests already establish cooperative cancellation, latest-value coalescing, stale-result rejection, worker-panic recovery, owner close, A→B→A invalidation, and a crucial adversary: a start function may return `Err` while retaining its Completion, so start rejection does not fabricate a free physical credit ([question tests](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/tests/questions.rs#L113-L164), [retained-cap rejection](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/tests/questions.rs#L498-L531), [A→B→A](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/tests/questions.rs#L365-L388)). The future adapter should inherit those outcomes rather than inventing a new status model.

## Review traces the implementation must pass

1. **Never-waking old future:** A returns `Pending` forever. Source changes to B. The lane updates the current ticket then cancels A. The exact task is woken/aborted; before its future drops, the mailbox remains leased and B has not started. When A’s wrapper drops, its `Completion` publishes `Abandoned`; owner admission ignores A’s stale ticket, retires the physical mailbox, and starts only B.
2. **Abort racing a ready result:** A completes as B supersedes it. `cancel` may be a no-op because A already finished. A’s result remains stamped A; the owner rejects it as stale, retires the terminal, and starts B. A→B→A must reject the first A even though values compare equal; ticket identity, not input equality, decides.
3. **Fast completion before `spawn` returns:** a worker can poll and drop the task before the `spawn` call returns its handle. The terminal is staged but not applied inline; after return, the lane stores the handle. Normal owner admission then takes/validates/retire. No completion callback can re-enter an active owner turn.
4. **Spawn reject and half-accept:** `Err(Busy)` is legal only if the future is dropped before return (terminal from its Completion follows); owner reports `StartRejected` and never calls B until the actual terminal is retired. A deliberately broken executor that enqueues then returns Err or accepts then panics demonstrates why the trait contract is required; if such backends must be tolerated, the API needs a pre-installed shared abort cell/guard, which costs the Abortable-style allocation.
5. **Poll panic and retry:** a panic inside `poll` becomes `WorkerPanicked`, task teardown publishes the terminal, the owner is not poisoned, and a retry can start. A domain `Err(E)` remains a domain Fault and retains prior value. Cancellation after an already completed task is harmless.
6. **Owner close:** close first invalidates current authority and requests task cancellation before closing ingress, and never applies the late outcome. Do not join/wait on the task from the owner close path.
7. **Lost wake window:** cancel immediately before first poll and cancel between the Future’s pending check and Waker registration. The task handle must guarantee runtime abort, or a cancellation-aware wrapper must use a flag plus a register-then-recheck wake protocol like `AtomicWaker`.

## Bound the first slice; do not imply Solid parity

The accessible [Solid v2 RC discussion #2995](https://github.com/solidjs/solid/discussions/2995) describes a much broader graph model: computations may return Promise or Async Iterator values, downstream reads derive pending/error/stale/optimistic behavior, and old content remains visible while refresh is pending. The official blog index lists Ryan Carniato’s three async articles—“Fetch High, Block Low,” “Write Sync, Run Async,” and “One Graph, Two Machines”—but their bodies still returned no readable content in the audited session; the index/title is not technical evidence ([official index](https://www.solidjs.com/blog)). I do not infer implementation detail from those three articles.

At pinned Ripple TS commit `fed124465d162ce17ce009936ef50061719d9882`, `trackAsync` accepts a PromiseLike or a PromiseLike plus `AbortController`, increments a version, aborts the previous run, marks pending before starting, accepts only the current version, and aborts on teardown ([types](https://github.com/Ripple-TS/ripple/blob/fed124465d162ce17ce009936ef50061719d9882/packages/ripple/types/index.d.ts#L287-L291), [runtime](https://github.com/Ripple-TS/ripple/blob/fed124465d162ce17ce009936ef50061719d9882/packages/ripple/src/runtime/internal/client/track-async.js#L220-L352)). Its compiler active-block and pending-boundary requirements are material; this is not a portable `Future` recipe. Together these sources support testing the more modest GPUI slice—one typed async question with stale-while-revalidate and error projection—without calling it feature parity or making speed claims.

Streams are a separate API decision. A Future produces one terminal answer and fits the current one-slot completion; a Stream emits many values and needs explicit policy: bounded ordered backpressure versus latest-snapshot coalescing, terminal/fault behavior, and buffer ownership. Do not smuggle repeated emissions through `Completion`.

Optimistic mutation/rollback is also separate. `CONTRACT.md` says successful owner operations commit before pure derivation; derivation may produce Pending/Fault but cannot generically roll back arbitrary committed `&mut` writes ([failure table](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/CONTRACT.md#L109-L128)). The answered Solid composition discussion #3085 reports that component-library ephemera belongs in a keyed sidecar joined to user-owned rows at read time; mirroring membership loses in-flight optimistic additions and creates synchronization problems. The accepted report says the pattern handled optimistic add/rejection, commands during an open action, and refresh reconciliation ([discussion answer/report](https://github.com/solidjs/solid/discussions/3085)). GPUI inference: preserve the application’s source membership/writer authority; keep tool-owned selection, drag, measurement and inspector ephemera owner-local and keyed by stable row ID. Do not mirror the app collection. Preserve optimistic membership separately. A GPUI optimistic API would require an explicit staged action/overlay with its own base-version, commit, rollback and conflict rules; a future adapter cannot supply those semantics.

## Adversarial refinement: clear the pinned future before publishing

This refinement supersedes the earlier `Option<Result<T,E>>`-in-finalizer sketch and its prompt-drop-after-`Ready` executor requirement; the public API, owned-input boundary, cancellation, stale admission and Solid/stream/optimistic conclusions above are unchanged.


Use a `#[pin_project]` wrapper with `#[pin] future: Option<Fut>` first and a `Finish<T,E>` containing the `Completion` last. Scope the projected `Pin<&mut Fut>` borrow around `poll`; after it ends, `Pin<&mut Option<Fut>>::set(None)` is safe for `!Unpin` futures: the standard-library contract says it runs the old value's destructor before overwriting the pinned location ([`Pin::set`](https://doc.rust-lang.org/std/pin/struct.Pin.html#method.set)). Rust drops struct fields in declaration order, so ordinary cancellation drops `future` before `Finish` ([drop scopes](https://doc.rust-lang.org/reference/destructors.html#destructors)). This retains safe projection and avoids unsafe extraction.

For `Ready(result)`, keep `result` only in the poll stack, mark `Finish`'s unwind fallback as `WorkerPanicked`, clear/drop `future`, then consume `Completion` to publish `result`. For a caught `poll` panic, mark that same fallback **before** dropping its panic payload, then clear/drop `future` and publish `WorkerPanicked`. A panic payload can itself have a panicking destructor. If either payload or future destruction panics, no result has been published; unwinding eventually drops `Finish`, which emits exactly one `WorkerPanicked` terminal. For cancellation before a terminal poll, field order drops the future first and `Finish` then emits `Abandoned`; have `Finish::drop` classify an active unwind as `WorkerPanicked` as well, so a destructor panic cannot be mislabeled as a clean early credit return. As usual in Rust, a second panic from another destructor while unwinding can abort the process; the adapter cannot promise recovery from arbitrary panicking destructors.

This satisfies this code's **one-physical-`Completion` lease**: terminal publication follows destruction of the actual user future, its captures and local async state. After successful publication, the executor may retain the now-trivial wrapper or finish returning from `poll`; it owns only `future: None` and an empty finish, with no `Completion`, result, or user future state. That is the meaningful lease boundary here: existing [`run_cancellable`](https://github.com/gpui-ce/gpui-ce/blob/6d77c71c1227bd2609518cc5f3a49e37fc176f82/reactivity/crates/gpui/src/reader.rs#L372-L400) also publishes `Completion` before the worker call itself returns. It does not promise reclamation of the executor's task node/stack. Therefore it removes both the stored `Option<Result<T,E>>` task growth and the need to demand prompt executor destruction on `Ready`. **Cancellation still needs actual task teardown** (or an abort wrapper that clears this inner option): a bare abort request/wake returning is not credit return. Serial, non-reentrant polling and the existing queued owner wake remain executor/event-loop obligations; a future may wake itself just before `Ready`, so a duplicate queued poll must not publish twice.

One API correction for the injected seam: define `QuestionExecutor::spawn(&mut self, future)` rather than `&self`. The private starter already owns mutable executor state, so this lets deterministic/custom test executors keep a plain queue and counters without `RefCell`/`Cell`; pool handles that need sharing can hold their own shared state. This is opt-in and does not add state to ordinary question controllers.

A concurrency caveat belongs with that boundary: the owner may admit the staged terminal on another thread after `Completion` signals but before the executor observes `Poll::Ready`. Dropping/canceling the associated handle in that interval must not reclaim or move the task allocation while its `poll` stack still borrows it; executor teardown has to serialize with the active poll and finish when that poll returns. This is compatible with the lease rule, but it is an explicit executor-handle requirement, not something `Pin::set` supplies.
