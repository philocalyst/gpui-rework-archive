# Core research for the GPUI reactivity rewrite

Research snapshot: 2026-10-20. This is evidence for a design review, not a claim that the proposed runtime has been implemented or benchmarked. “Verified” below means supported by the cited primary source; it does not mean independently reproduced in this workspace.

## Read first: what the current design commits to

The root model describes a generative frame lifetime (`El<'f>`) over a per-turn bump arena, a retained diff that takes ownership of changes, and a progressive storage ladder (`T` → `Signal<T>` → `List<T>` → `Entity<T>`). It also commits to typed ports, one optional `#[reactive]` macro, and says retention is “zero-tax” for simple authoring. The root model itself says a component's `view(&self)` is pure and effects live in `changed(&mut self, ...)` ([00-model.md](inputs/final/00-model.md), §§2–4).

The runtime notes recommend inline signal values, a typed 64-bit generational slot, a contiguous `List<T>` plus identity directory, paint-order SoA display storage, SIMD-assisted hashing with equality confirmation, and a frozen chunk arena. Round 2 measurements are explicitly from an M3 Pro/macOS and mark unsafe experiments Miri-pending ([datastructures.md](inputs/runtime/datastructures.md), [datastructures-2.md](inputs/runtime/datastructures-2.md), [memory.md](inputs/runtime/memory.md)). These numbers are useful hypotheses for local comparisons, not portable cost constants.

The surrounding implementation concern is real: GPUI has explicit entity contexts and a mature native event/render stack. A rewrite must preserve its host integration path or make a clean boundary for it. The source-backed embedded GPUI spike below offers a more concrete model for a nested surface than the current frame-borrowed tree alone.

## Findings by evidence status

### Verified facts

**Bevy’s change detection is a useful mechanism, not a drop-in reactive graph.** Bevy ECS 0.20.0 documents `ComponentTicks` as storing when a component was added and last mutably dereferenced; `Mut<T>`/`ResMut<T>` provide unique mutable access, while `Ref<T>` allows shared access and change detection. Its `Tick` values are relative to system runs, with periodic clamping to prevent overflow of age comparisons ([Bevy change detection docs, 0.20.0](https://docs.rs/bevy/0.20.0/bevy/ecs/change_detection/); [tick source](https://docs.rs/bevy_ecs/latest/src/bevy_ecs/change_detection/tick.rs.html)). Bevy 0.5’s release notes explain the reason for ticks: a boolean dirty flag lost changes depending on stage/run ordering; ticks allow systems to observe writes since their last run ([Bevy 0.5 release notes, 2021-03-12](https://bevy.org/news/bevy-0-5/)).

**What transfers:** timestamp/epoch comparison can make “changed since this consumer last ran” robust to delayed scheduling and avoid clearing every subscriber bit. Preserve Bevy’s “write access marks changed” simplicity only if equality filtering happens at the destination or if mutation guards can distinguish actual edits. The current design’s `DerefMut`-publishes-on-drop policy matches Bevy’s conservative behavior but can cause false-positive scheduling; the destination compare is needed to bound consequences.

**What does not transfer:** Bevy systems declare access sets, so the scheduler can detect conflicts and parallelize compatible systems; Bevy documents that system access is managed automatically and conflicting accesses prevent simultaneous execution ([Bevy ECS system docs, 0.20.0](https://docs.rs/bevy_ecs/0.20.0/bevy_ecs/system/)). A UI read graph discovered by executing a component/view is data-dependent: it is not automatically a static access declaration. A dynamic graph needs explicit read instrumentation, a generated dependency plan, or a conservative invalidation fallback. Do not present a tick as if it discovers a dependency.

**Rust generational arenas solve a specific ABA failure, with a finite counter.** `generational-arena` 0.2.9 describes storing `(index, generation)` and rejecting stale IDs when the generation no longer matches; after remove/reuse, old handles fail even if the same physical index is occupied ([crate docs, 0.2.9](https://docs.rs/generational-arena/0.2.9/generational_arena/)). `slotmap` 1.1.1 similarly versions keys and documents that its 31-bit version can wrap after 2³¹ delete/reinsert cycles on one slot ([slotmap crate docs, 1.1.1](https://docs.rs/slotmap/1.1.1/slotmap/)).

**Implication:** a `u32` generation is practically large, not mathematically never-reused. The design statement that a stale `Slot` can “never” become live again is false unless the implementation retires exhausted slots, widens the generation, or constrains handle lifetime so old IDs cannot survive a full wrap. Diagnostics do not establish that invariant. Identity also needs an owner/container namespace if slots may cross containers, windows, saved snapshots, or process boundaries; a generation/index pair alone only identifies a slot within its owning arena.

**Rust arenas trade individual reclamation for cheap allocation and bounded lifetimes.** The Rust compiler’s `rustc_arena` docs describe bump allocation and all-at-once destruction; no per-object free is available while the arena lives ([rustc_arena docs](https://doc.rust-lang.org/stable/nightly-rustc/rustc_arena/index.html)). The Rust Reference says a `Box` allocation remains at a stable heap address even when its `Box` pointer value moves ([Rust Reference, memory allocation and lifetime](https://doc.rust-lang.org/reference/memory-allocation-and-lifetime.html)). A chunked arena can therefore keep earlier addresses stable as its chunk directory grows, but only by not moving/deallocating chunks while references are live. Rust's safe `&mut` API must also prevent references from coexisting with mutation that reallocates or reclaims backing storage.

**The frame-lifetime proposal can be sound, but its API must expose the lifetime boundary in Rust's type system.** A generative scope can be modeled as a closure universally quantified over a fresh lifetime and return only a value whose type does not carry that lifetime. Covariance permits shortening a long-lived borrow into a frame; it does not prove that a frame arena or mutable retained store may be changed while an `El<'f>` borrow is live. Lowering must end all borrows into the frame before resetting/reusing the arena and before mutating any aliased retained allocations. The current prose's “generative” word is not itself a proof; the actual signature, variance, drop order, and reentrancy behavior need compile-fail tests and Miri coverage.

**Bevy Reflect is typed runtime metadata with explicit participation and boundaries.** Bevy 0.20’s `Reflect` derive generates `Reflect`, `Typed`, registration, and `FromReflect`; reflected types generally require `'static + Send + Sync` and reflected fields. Fields can opt out to preserve invariants or allow non-Reflect members. Dynamic values are represented by explicit `DynamicStruct`, `DynamicEnum`, etc.; reflection is not automatic for arbitrary Rust values ([Bevy Reflect docs, 0.20.0](https://docs.rs/bevy/0.20.0/bevy/reflect/); [derive docs](https://docs.rs/bevy/0.20.0/bevy/reflect/derive.Reflect.html)).

**Implication:** typed reflection can reduce boilerplate for inspector, serialization, and style/property metadata, but it cannot conjure stable field names or legal mutable access for every type. The model’s “near-zero macro boilerplate” target is achievable only with deliberate derives/attributes or a closed library-owned schema. Keep reflection opt-in, use generated typed field descriptors where possible, and make editor/style overrides patch into validated fields rather than use stringly-typed mutation in the hot renderer.

**SIMD APIs are target-sensitive and unsafe at the hardware boundary.** Stable `std::arch` intrinsics are architecture-specific; calling an intrinsic requires the relevant CPU feature to be guaranteed or runtime-detected. Rust’s docs explicitly recommend higher-level portable abstractions when possible. `std::simd` is documented as portable but remains nightly-only as of the current docs ([Rust `std::arch` docs](https://doc.rust-lang.org/std/arch/); [`core::simd` docs](https://doc.rust-lang.org/core/simd/)).

**Implication:** retain scalar/reference implementations; let LLVM vectorize simple byte loops first; use stable `std::arch` only behind runtime feature dispatch and one audited unsafe module. Hashing or comparing retained descriptions must be collision-safe: a hash can select candidates, never prove structural equality. The local DS notes already recommend a mandatory equality confirmation, which is the sound direction.

**Parallel ownership is easiest over disjoint slices, not a shared mutable tree.** Rayon 1.12 documents `par_chunks_mut` as producing non-overlapping mutable slices (`T: Send`) and parallel iterators generally require `Send + Sync` closures/data ([Rayon 1.12 parallel iterators](https://docs.rs/rayon/1.12.0/rayon/iter/); [parallel slices](https://docs.rs/rayon/1.12.0/rayon/slice/trait.ParallelSlice.html)). This favors phase-separated work over immutable snapshots or disjoint SoA ranges. A local `!Send + !Sync` graph is a legitimate baseline for main-thread UI; it does not imply that arbitrary callbacks, layout, text shaping, or platform surface APIs can be parallelized safely.

**Nested GPUI is already an explicit experimental project, and it uses a surface/protocol seam.** At retrieval, `zed-industries/embedded_gpui` main was [`28bc6d3d559b62040626403040b680ad96ef696b`](https://github.com/zed-industries/embedded_gpui/commit/28bc6d3d559b62040626403040b680ad96ef696b), authored 2026-09-05. Its design document describes a GPUI guest compiled to `wasm32-wasip2` and embedded in a native GPUI host. It uses host-owned `SurfaceApi` and guest-owned `ViewApi` objects, routes input/geometry as typed calls, and returns retained display lists/scenes to the host. The host never calls into wasm synchronously on its frame path; one worker owns the Wasmtime store, with ordered requests/effects. The document explicitly calls this an experimental spike and says it depends on a GPUI branch hook ([design document at pinned SHA](https://github.com/zed-industries/embedded_gpui/blob/28bc6d3d559b62040626403040b680ad96ef696b/DESIGN.md), lines 189–230).

**Implication:** “GPUI in GPUI” should mean a well-defined embedded surface/guest capability, not recursively mounting a second framework runtime as ordinary borrowed `El<'f>` nodes. A nested surface needs ownership/lifetime, input routing, resize/scale, accessibility/focus, text shaping, damage transfer, and scheduling contracts. It may be synchronous in-process for same-runtime surfaces and asynchronous across wasm/process boundaries, but those are different port forms.

**What NanoUI actually does, from pinned source:**

- Native UI uses a function pointer `View { ptr, build }` that receives mutable app state and `*Context`; the view executes again for each event/frame ([`ui.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/ui.zig#L95-L112)). `Context.begin` resets its frame arena with capacity retained, clears frame nodes/stack/hits, and starts a fresh tree; persistent per-ID maps separately hold old rectangles, hits, animation, widget memory, scroll, and text editing state ([`context.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/context.zig#L118-L183), [begin/rebuild](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/context.zig#L250-L277)). Thus it is immediate authoring plus retained interaction/cache state, not a retained component tree with automatic field-level invalidation.
- A frame runs the builder until interaction changes stop, with a hard ceiling of three build passes, then measures bottom-up, arranges top-down, caches old rectangles, paints a full instance list, and commits hit targets ([`frame.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/frame.zig#L21-L82)). This buys a correct same-frame response without a reactive scheduler. A pathological view that keeps mutating state across build passes is truncated at the ceiling; the new core should prefer queued/settled state transitions and a diagnostic when it fails to converge.
- Node identity is a 64-bit Wyhash of parent identity plus explicit string key, explicit integer key, or child ordinal ([`childId`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/context.zig#L311-L324)). This is compact and convenient, but differs from the local core's arena/generation/index identity: hash collisions are not checked, and ordinal fallback transfers state when earlier siblings appear/disappear. The row helper sets integer key to the row index, so inserts/reorders before a row likewise move state to a different item unless callers key by durable item identity ([`list.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/list.zig#L30-L53)). The proposed `Slot<T>` should preserve identity through reordering and validate owner+generation.
- Virtualization is a high-value, very simple pattern: with fixed row height it computes the visible interval from prior-frame viewport size and scroll offset, builds only that range plus configurable overscan (default 4), and inserts before/after spacer boxes ([`list.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/list.zig#L17-L83)). It supports the 100,000-row hillclimb scene. Its scope is explicitly uniform-height rows; variable-height rows need a prefix-sum/Fenwick/order-statistics index and invalidation of measurements.
- The small-state convention is a useful authoring compromise: `Context.state(T, key)` stores at most 48 bytes, alignment ≤16, in an inline fixed buffer keyed by the current box id plus a compile-time type and key; stale widget/motion records are swept in fixed batches ([`context.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/context.zig#L444-L465), [`motion/store.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/motion/store.zig#L31-L59)). It avoids a heap object per widget. Caveats: a type may not fit or exceed alignment; pointer provenance/lifetime must remain valid; allocator failure returns a static fallback object and can alias same-type widget states; cleanup removes only up to 64 stale records per sweep, so high churn can create a backlog. Port the bounded inline fast path only with a safe typed spill path and observable overflow/fallback behavior.
- Typed compile-time reflection minimizes repetitive setters: `Div.set` uses a compile-time field name and `@field` for assignment ([`div.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/div.zig#L16-L27)); `motion.Target.overlay` enumerates `Target` fields using Zig `@typeInfo` and applies non-null fields, making override precedence explicit ([`motion.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/motion/motion.zig#L32-L52)). But `Target.get` maps fields to numeric channels via a separate hand-written switch ([same file, lines 54–70](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/motion/motion.zig#L54-L70)); adding a style field can update overlay but leave animation extraction stale. The lesson for Rust is derive field descriptors and channel/property IDs from one schema, or generate compile-time exhaustiveness checks. Don’t provide arbitrary unvalidated field mutation as “reflection.”
- Rendering remains full-frame: paint recursively walks the fresh tree to create all GPU instances, records hit rectangles, clips/culls content, and sorts elevated layers ([`paint.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/paint.zig#L13-L32), [node traversal](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/paint.zig#L42-L145)). The Metal renderer uses a two-buffer in-flight ring and copies instance bytes into reusable GPU buffers; it retains image atlas uploads by dirty row, not a persistent damaged-pixel target ([`metal.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/metal.zig#L20-L40), [buffer upload](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/metal.zig#L175-L190), [atlas dirty rows](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/metal.zig#L98-L113)). This validates reusable frame buffers and resource-specific dirtiness, not whole-frame-zero-work claims.
- Native UI and WebView are alternatives in a window's `Content` tagged union, not mixed native/webview subtrees ([`window_types.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/window_types.zig)). The README explicitly lists accessibility as absent at this snapshot. Native/webview sibling composition therefore still needs a surface/ownership seam and cannot be inferred from NanoUI's support for both modes ([limitations](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/README.md#L398-L408)).
- The offscreen `Tester` shares the exact `frame.run` path, injects pointer/key/text/scroll input, advances time deterministically, renders to PNG, and captures clipboard locally ([`tester.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/tester.zig#L39-L94), [input helpers](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/tester.zig#L109-L189)). Widget tests exercise visible text, simulated interactions and pixels through this path ([`tests.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/tests.zig#L17-L27)). This is an excellent validation interface for the rewrite: one deterministic driver for input, time, view updates, rendering, and damage assertions.
- Adversarially, NanoUI's measure, arrange, and paint use recursion ([`layout.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/layout.zig#L27-L101), [arrange](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/layout.zig#L103-L238), [`paint.zig`](https://github.com/justrach/nanoui/blob/dfa7f7ab4e890f643703f4ffe4d834ff10defd4f/src/ui/paint.zig#L42-L50)). A deeply nested or attacker-supplied tree can exhaust stack; the local core's iterative subtree/preorder/remove loops are safer. Conversely, the local core's exact hit-test scans every node and walks ancestors per candidate; in a depth-N tree where every node has geometry, work reaches Θ(N²). A compact core needs an adversarial depth benchmark plus a broad-overlap hit test and should use iterative traversal and a retained spatial index before promising large trees.

**Measurement limitations in NanoUI's comparison:** `hillclimb/README.md` says 30 warm-up and 300 measured frames, repeated 3 times, then it keeps the run with the lowest median. That is an optimistic best-run selector; report per-run distribution, not only the minimum median. It compares a full nanoui renderer to MyGo's own renderer and Clay's layout-only path, with Clay text measured by nanoui and no Clay GPU/encode/process metrics. Its 100k uniform-list comparison is valuable, but not apples-to-apples for retained-vs-reactive invalidation. The dated MyGo window note has p50-like medians of three, but no p95/p99 input-to-present latency and a different workload definition from zgui's benchmark. Treat all results as hypothesis-generating and recreate the source fixture/version.

**PanGui’s line-count claim is explicit, dated, and limited in scope.** PanGui’s own 2026-01-27 post says a layout rewrite reduced its layout implementation from about 11,000 to 4,800 lines of C#. It explicitly counts data structures, enum declarations, and user API method definitions, and attributes much of the change to sharing axis logic, integrating blending, sharing hypothetical/commit computation, and simplifying an expand solver. Its benchmarks exclude tree creation, allocation, and destruction; were run on Ryzen 7 7800X3D; and compare against pinned Clay `76ec363`, Yoga `8ba025e`, and Taffy `175442d` ([PanGui post](https://www.pangui.io/blog/05-layout-rework-and-benchmarks/)).

**Use:** this is evidence that carefully unifying two mirrored dimension paths and sharing computation can materially reduce a mature subsystem. It is not evidence that a complete reactive framework needs 4,800 lines, that lower LOC caused the speed result, or that C# line counts compare to Rust. Record the claimed before/after, change list, commit hashes, compiler, machine, and omitted costs when citing it.

### Hypotheses requiring local measurements

1. The paint-order SoA plus chunked retained tree will improve frame cost over GPUI's current element/cache path for sparse updates. The local datastructure experiment is suggestive, but its M3 Pro, synthetic trees, and microbenchmarks do not establish end-to-end UI behavior or cross-platform wins.
2. Bevy-style ticks/epochs will make invalidation cheaper than clearing per-subscriber flags for this runtime. Measure both sparse and broad writes; include reader-set churn, overflow maintenance, and subscription removal.
3. SIMD hashing will be useful after layout/representation costs are measured. The local lab says its 128-bit hash beats a scalar hash, but no independent source was found that validates that exact byte format, hash, or target. Benchmark optimized stable scalar, auto-vectorized, and dispatched intrinsic versions on x86-64, Apple ARM, and wasm before selecting.
4. Parallel sibling/layout work may pay only for large independent batches. The critical product path includes UI-thread synchronization and dispatch; benchmark thresholds, task creation, cache contention, deterministic ordering, and serialization before adding worker support.
5. Tile damage compression should reduce bookkeeping and renderer submissions when many rectangles overlap. It may increase overdraw and miss small sparse wins. Measure damage generation, compositing, GPU bandwidth, and input-to-present p50/p99 together; conservatively overdraw but never under-invalidate.

## Design contradictions and unsafe pitfalls to resolve before freezing APIs

**Borrow checker and `view(&self)`:** the model wants `view` to return frame-borrowed nodes and also allows outputs to borrow state owned by components. A normal `&self` view can borrow component fields; that is sound only while that component remains immutably borrowed. In the same turn, the runtime cannot call `changed(&mut self)`, mutate a `Signal` inline, destroy child state, or reuse any storage behind those borrows until the description has been consumed and all borrows end. Specify a strict describe → lower/finish frame borrows → commit → mutate/effects sequence. If a child stores a borrowed closure/value beyond its frame, it must be rejected by type or converted to owned data at that boundary.

**Dynamic dependency tracking vs “no ambient context”:** automatic tracking usually needs a current observer during reads. `Deref` alone cannot both return `&T` and safely record arbitrary dependencies without hidden thread-local/task-local state or generated instrumentation. If tracked deref is a macro rewrite, define how it handles nested derefs, methods, operator overloads, control flow, early returns, borrows, and third-party types. If it uses a dynamic scope, explicitly mark that scope and its thread/reentrancy rules. Offer explicit `read()`/`map()` APIs as a predictable fallback. Avoid promising automatic tracking on arbitrary `&T` access.

**“Freeze” and stable references:** appending to a chunked arena can preserve addresses, but freezing does not by itself solve concurrent mutation or removal. State whether arena entries are immutable after publish, whether old generations live until all readers leave, and whether references cross turns/threads. Use epoch reclamation or owned `Arc` only if cross-turn sharing requires it; local frame references should remain scoped. Never return an `&T` from an arena and then allow slot reuse/destruction while that borrow can survive.

**Slot reuse and ABA:** generational IDs must include container/owner identity wherever an ID can be stored outside its originating list; `Slot<T>`'s type brand distinguishes `T`, not two `List<T>` instances. On 32-bit generation wrap, retire the slot or prove no stale ID can remain. Serialized IDs need an explicit namespace/epoch; do not trust process-local slot keys as persistent database IDs. Add tests that force a tiny generation type to wrap and that move stale IDs between two same-typed lists.

**Zero-copy vs retained ownership:** a frame arena is reset each turn; retained state must outlive it. If a changed value is borrowed from the frame and the retained store keeps it, some ownership operation is required: copy, clone/refcount, intern/shared backing, or a separate longer-lived arena. “No copy” is plausible for unchanged operands and borrowed reads, not for every changed transient payload. Define cost per port type and test drop behavior; especially avoid silently retaining captures whose lifetimes point into a reset frame.

**Typed reflection vs style/behavior overrides:** reflection metadata does not establish that a field is safe to mutate, serializable, or semantically meaningful as an override. Use explicit override metadata: allowed property, merge rule, reset semantics, precedence, invalidation impact, and behavior hook capability. Keep behavior overrides as typed capabilities/traits or registered functions with owner lifetime; do not let a string key bypass type checking in the core. Reserve open-ended reflection for inspector/plugin seams.

**Damage compression and visual correctness:** union/tile compression is a conservative superset of changed pixels, never a replacement for tracking old and new bounds. Movement, clipping, opacity, transforms, scroll, text metrics, and nested surfaces need old/new invalidation. If damage records are dropped or capped, fallback to a full target redraw. A retained GPU target also requires explicit invalidation on resize, scale/format change, context loss, and surface exposure.

## Algorithm candidates for the compact core

These papers solve adjacent problems; none is evidence that adopting the data structure will improve UI latency. Keep the current direct-index topology and tile damage as the baseline, and only branch into a more complex structure when traces show its target cost dominates.

- **Adaptive Radix Tree (ART)** — Leis, Kemper, Neumann, ICDE 2013, DOI `10.1109/ICDE.2013.6544812`. ART adapts internal-node representations to fanout, maintains sorted keys, and supports prefix/range as well as point queries ([IEEE primary record and abstract](https://ieeexplore.ieee.org/document/6544812/)). This is a candidate for a style selector/index keyed by names or prefixes, if the runtime needs ordered string-prefix queries. Reject it for node topology, slot-to-record mapping, or numeric signal IDs: the current arena index gives direct addressing and O(1) sibling edits; ART adds key traversal, allocations, and update machinery without a matching query need.
- **Roaring bitmap** — Chambi, Lemire, Kaser, Godin, “Better bitmap performance with Roaring bitmaps,” *Software: Practice and Experience* 46(5), 2016, DOI `10.1002/SPE.2325`. It partitions integer space into containers and selects packed-array/bitmap representations so sparse and dense regions can be handled differently ([paper](https://arxiv.org/abs/1402.6407); DOI metadata in [Wiley](https://onlinelibrary.wiley.com/doi/10.1002/SPE.2325)). The local 64-pixel damage map is already a bounded viewport bitset with touched-word clearing; keep that for predictable dense screen coordinates. Benchmark Roaring only for sparse dirty-node/dependency sets over a large ID space or for set algebra across subscriptions. It is a representation alternative, not a replacement for geometric damage bounds, and must handle node-ID reuse by operating on validated current IDs/epochs.
- **Fully functional succinct trees** — Navarro and Sadakane, *ACM Transactions on Algorithms* 10(3), 2014, DOI `10.1145/2601073`; the primary preprint states the static `2n + o(n)`-bit tree representation context and develops static/dynamic fully functional succinct operations ([arXiv paper](https://arxiv.org/abs/0905.0768); [ACM DOI page](https://dl.acm.org/doi/10.1145/2601073)). Consider balanced-parentheses/LOUDS-like encodings for frozen snapshots, compact serialization, or read-mostly traversal after mount. Reject as the initial mutable tree: preserving stable generational handles, O(1) local edits, and cheap mutation while supporting succinct navigation is a separate, complex implementation. The current topology's links are easier to audit and optimize; measure bytes/node and traversal cache misses first.
- **RRB vectors** — Stucki, Rompf, Ureche, Bagwell, ICFP 2015, DOI `10.1145/2784731.2784739`. The paper describes immutable sequences with efficient structural reorganization, concatenation, insertion-at and split while retaining indexed lookup/update/iteration properties ([author-hosted paper](https://www.cs.purdue.edu/homes/rompf/papers/stucki-icfp15.pdf)). This may help immutable child-list snapshots for undo, cross-thread publication, or large sequence splice workloads. Reject it as core mutable topology: path-copying persistent updates are unnecessary for a main-thread edit model and do not provide node identity, parent links, or direct stable handles by themselves. A narrow persistent snapshot API can be added later if undo/worker ownership requires it.
- **Order maintenance** — Dietz and Sleator, STOC 1987, DOI `10.1145/28395.28434`; the authors' report formalizes insert/delete/order queries and gives algorithms with amortized or worst-case O(1) operation bounds ([CMU author page and report](https://www.cs.cmu.edu/~sleator/papers/maintaining-order.html), report dated 1988). Use this family only if the runtime frequently compares order of two arbitrary nodes without traversing siblings, or needs stable labels for merging independently edited streams. Current traversal order is already represented by linked siblings; do not label every node just in case. Re-labeling and label exhaustion/rebalancing become correctness concerns if this is introduced.
- **Differential dataflow** — McSherry, Murray, Isaacs, Isard, CIDR 2013, DOI-less proceedings paper; it tracks changes with partially ordered logical versions and indexed differences to reuse work in nested iterative data-parallel computations ([CIDR primary paper](https://www.cidrdb.org/cidr2013/Papers/CIDR13_Paper111.pdf)). Its domain is continuously updated relational/graph computation, not the common UI case of a small dependency graph and a few dirty passes. Reject in the compact UI core; consider as an isolated data-query or virtual-table engine if nested iterative queries become a real requirement. Its multi-dimensional times and retained differences are unjustified complexity for ordinary view invalidation.
- **Self-adjusting / incremental computation** — Acar, Blelloch, Blume, Tangwongsan, PLDI 2006, DOI `10.1145/1133255.1133993`. The implementation combines dynamic dependence graphs and memoization; its experiments cover selected applications and report wins over recomputation for those workloads ([CMU author-hosted paper](https://www.cs.cmu.edu/~blelloch/papers/ABBHT09.pdf); [PLDI 2006 paper copy](https://www.philinelabs.net/~ktangwon/papers/pldi06.pdf); DOI metadata [CMU department page](https://csd.cmu.edu/academics/doctoral/degrees-conferred/umut-a-acar)). Adopt the principle of recording actual read dependencies and recomputing affected pure descriptions. Do not infer that arbitrary Rust view functions are safely memoizable: mutation, I/O, nondeterminism, interior mutability, and borrow-sensitive references need explicit effect boundaries. Dynamic dependency capture and memoization must be measured against a full rebuild baseline and have a conservative invalidation fallback.

## Adversarial evaluation of the local compact core and model

This is a source audit of [`tree.rs`](/root/gpui-reactivity-tree/reactivity/crates/core/src/tree.rs), [`spatial.rs`](/root/gpui-reactivity-tree/reactivity/crates/core/src/spatial.rs), and [`damage.rs`](/root/gpui-reactivity-tree/reactivity/crates/core/src/damage.rs), not a claim that a benchmark or property test has passed. Pin the workspace commit before treating these observations as reproducible facts.

- **The topology/geometry split is sound and worth preserving.** `Tree::Entry` holds generation plus parent/first/last/prev/next indices and `NodeKind`; links are `u32` offsets into one flat vector, so mutation does not invalidate a borrowed node reference because the API exposes IDs, not internal references. `NodeId` includes arena namespace, generation, and index; cross-tree IDs are rejected. Removal increments generation and returns the slot to the freelist only when increment succeeds, so exhausted slots retire instead of wrapping. This is stronger than index-only or wrapping generation designs. At source-layout level the entry is about 28 bytes with normal Rust layout; assert this with `size_of` in a benchmark build and measure cache behavior before compressing it. `NodeId` itself is 16 bytes, and that cost is the price of its 64-bit owner + 32-bit generation + 32-bit slot identity unless the owner is supplied by an API context. The `NodeKind::{Native, WebView, NestedGpui}` variants are tags only; this core has no host API, renderer, focus/input router, accessibility tree, or cross-surface compositor implementation.
- **Tree edits are deliberately local, but insertion order is append-only.** Attach/detach and moving to end of sibling list are O(1); reparent cycle validation walks ancestors O(depth); removal walks the subtree iteratively O(subtree size). This is a good compact mutable base. If authoring needs insert-before/move-before or arbitrary paint-order comparison, expose that as a separate operation and measure it before adding order labels.
- **Spatial hit testing is the clearest adversarial algorithmic risk.** It scans preorder and, for every geometrically hit candidate, walks every ancestor to verify invertibility and clips. A depth-N chain where every node covers the point costs Θ(N²), even before accounting for the full scan; a broad set of overlapping siblings is Θ(N) and must preserve last/topmost paint order. First improve to a single iterative traversal carrying accumulated clip/validity (linear in visited nodes), then add a retained broad-phase index only if large flat scenes need it. Any index must return candidates in paint order and run the exact inverse/local-clip test before declaring a hit.
- **Subtree geometry refresh and damage are correctly scoped but need a size policy.** Moving/reparenting a root updates every descendant world transform, so O(subtree size) work is semantically expected if world matrices are cached. Damage records both old and new subtree bounds, preventing trails. However, an enormous subtree can set most of the viewport bitset; when nearly full, `Damage::add` still loops covered tiles. Add a threshold to switch to `full()` once measured tile coverage crosses a fraction of viewport, and define a full-redraw fallback for damage allocation/capacity failure. `Damage::new` currently errors above `MAX_TILES` rather than falling back, so huge surfaces are rejected even when full-redraw would be safe.
- **Mutation failures should be transactional.** `SpatialTree::set_geometry` validates input and its record cap before damage changes, which is good; its subsequent erase/push/refresh sequence has no recoverable failure path. Preserve that prevalidation rule for any future fallible index allocation. Damage and geometry should not partially mutate when capacity/allocation fails.
- **Numerical validation must include composed transforms.** Local geometry validates finite transforms, but repeated affine composition can overflow to non-finite world values. Current bounds/hit operations reject invalid derived geometry, but mutation still succeeds. Consider returning a diagnosed transform-overflow error, promoting world math to f64 with finite checks, or forcing a full redraw and excluding invalid hit regions. Adversarial input should include near-maximum finite scale/translation across deep chains and singular transforms.
- **Hit-test and transform adversaries should be explicit review gates:** (a) a million-deep or practical stack-limit chain; (b) a flat broad-overlap scene; (c) one huge subtree moved every frame; (d) clip on every ancestor; (e) singular and near-singular transforms; (f) remove/reuse slots while stale `NodeId`s are retained; (g) independent trees with equal slot/generation; and (h) viewport dimensions at, below, and above the tile cap. Compare correctness against a slow scalar reference and report allocations, visited nodes, and p50/p95/p99.
- **Typed reflection cannot erase Rust's ownership rules.** A derive can generate a single property schema (`field id`, type, parse/clone/apply function, styleability, merge/precedence, invalidation `Impact`, behavior capability) from explicitly annotated fields; an editor or CSS-like layer can then validate and store typed overrides without string dispatch in the hot path. It cannot soundly mutate `&self`, a borrowed child frame, or arbitrary private fields. In particular, current `view(&self)` purity conflicts with style/behavior override mechanisms that mutate app state from render; resolve overrides into an owned immutable presentation snapshot or typed sinks before `view`, and keep behavior replacement behind explicit capability traits/function registration.
- **“Near-zero macro boilerplate” has a concrete ceiling.** Zig's compile-time field enumeration shows how one schema can remove duplicated overlay logic, but even NanoUI's separate `Target.get` switch can drift from the reflected field list. In Rust, procedural derives need annotations for opt-in and compiler-visible trait bounds; they cannot infer semantic merge rules, safety, or whether a field may be overridden. Minimize boilerplate with one `#[derive(Style)]` or `#[derive(Reflect)]` plus field attributes and generated exhaustive IDs/getters, while keeping built-in layout/style property types closed. A true zero-annotation promise for arbitrary user structs is incompatible with privacy, orphan rules, trait bounds, and semantic policy.
- **The model's describe→commit borrow boundary is the largest soundness gate.** While `view(&self)` returns `El<'_>` borrowing component state, the runtime cannot then call `changed(&mut self)`, mutate inline `Signal<T>`, move/drop children, or reuse arena storage that aliases those borrows until the description is lowered and every frame borrow ends. Rust NLL helps only if the API shape makes the final use explicit. Freeze cannot make mutable aliases safe; it only says which backing allocations remain alive/stationary. Require a higher-ranked frame scope, owned lowered records, no references retained across turns, compile-fail lifetime tests, and Miri for any unsafe arena/reflection implementation.
- **Zero-copy should be promised per value path, not globally.** Borrowing unchanged data into the frame can be zero-copy. A publication that survives frame reset needs owned data, `Arc`/interned backing, or a longer-lived arena. A `Vec` changed transiently and retained by a list cannot safely borrow frame memory. State the copy/clone/refcount cost in each `IntoProp` plug implementation and test drop/reuse behavior.
- **Freeze, storage reuse, and ABA are separate concerns.** A frozen tree can still have mutable app state, can still be removed, and can still receive stale async completions. Arena owner + generation + slot protects synchronous handles; request stamp/epoch protects async presentation; the two identities should not be conflated. If snapshots cross threads, publish immutable owned chunks and retain them through reader completion (`Arc`/epoch scheme), rather than share mutable references and call the arena frozen.

## Concrete recommendations

1. Keep the typed retained tree and frame-borrowed describe path, but make its compile-time boundary real: a higher-ranked `describe` closure, no stored frame references, a mandatory end-of-borrow before commit/mutation, and separate owned/shared port forms for values that cross turns.
2. Split runtime into a simple single-threaded local core and an optional parallel lane that only accepts immutable snapshots or statically disjoint slices. Default UI scheduling to its owning thread. Add parallelism after end-to-end measurements, not as a premise of the data model.
3. Use Bevy ticks/epochs as an invalidation primitive, paired with explicit/dynamic dependency registration. Maintain a conservative full-owner fallback when dependency tracking is disabled or stale. Do not conflate component change ticks with signal graph subscriptions.
4. Adopt generational slots with an owner namespace and retirement-on-wrap. Keep the generation width decision tied to a documented lifetime and reuse bound, not intuition. Keep process IDs separate from serialized identities.
5. Make equality the final truth after hash/cache lookup. Prefer scalar Rust plus optimizer-generated vectorization first; add per-target SIMD dispatch only where application-level traces show it matters.
6. Define nested native/webview/guest UI as a typed surface port. Reuse host renderer/text/accessibility systems where possible; cross-runtime guests communicate through ordered events and retained scene deltas. Document which calls are synchronous and which cross an async boundary.
7. Make typed reflection opt-in and derive-driven. Use it to generate metadata for inspection and validated overrides; preserve hand-written typed builders/traits for normal app authoring. One focused derive is realistic; a promise of no annotations for arbitrary Rust types is not.
8. Treat local performance figures as provisional. Re-run the DS lab on x86-64 and current ARM, then compare full realistic UI workloads with zortax/zgui pinned to an explicit SHA and report environment, warmup, p50/p99, allocations, frame-stage counters, and first-mount costs.
