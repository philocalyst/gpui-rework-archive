# Default accessibility floor and exact GPU redraw reuse

Research snapshot: 2026-10-21. Source audit only; no implementation, rebuild, or timing was done for this note. The current GPUI source examined is `e10c2226d5d85cf5b0c5a77ae638c5bcca8da968` in `/root/gpui-ce3/reactivity` (the audited renderer/native paths are unchanged from reviewed `71ce05bb92c7fd2f40cd99a564de3627b68ff4df`). The prior same-source Linux feature control is frozen at GPUI `724ece73cb` and is preserved in [`memory-floor-attribution-luna.md`](memory-floor-attribution-luna.md) and `benchmarks/luna-accessibility-floor/`.

## Finding: no safe current switch can make the default AT bridge cold

The ordinary Linux `x11` feature is `x11-minimal + accessibility`; `accessibility` brings `accesskit 0.25.1` and `accesskit_winit 0.34.1`, pinned in `crates/gpui/Cargo.toml` and `Cargo.lock`. `Bridge::new` constructs `Adapter::with_direct_handlers` while the native window is created, before the host makes it visible. This is required by the pinned Winit adapter: its constructor panics for an already-visible window and documents that it must be installed before first show. GPUI therefore cannot move the existing adapter construction to a later redraw or presentation callback without breaking the adapter's lifecycle contract. See GPUI `crates/gpui/src/native/accessibility.rs::Bridge::new`, AccessKit Winit 0.34.1 [`src/lib.rs`](https://docs.rs/crate/accesskit_winit/0.34.1/source/src/lib.rs), and the [0.34.1 release](https://github.com/AccessKit/accesskit/releases/tag/accesskit_winit-v0.34.1).

On Unix, AccessKit 0.24.0 starts one process-global worker the first time `accesskit_unix::Adapter::new` calls `get_or_init_messages`. `APP_CONTEXT` and `MESSAGES` are `OnceLock`s; the worker builds an executor and session-bus connection, subscribes to `org.a11y.Status.IsEnabled`, and retains a vector of per-window adapter entries. A status change activates or deactivates all registered adapters. Each window adds/removes a handler entry, but does not start its own global monitor worker. The source also documents that Unix activation/action/deactivation callbacks run on another thread. Exact pinned source: [`context.rs`](https://docs.rs/crate/accesskit_unix/0.24.0/source/src/context.rs) lines 33–74, 169–210 and [`adapter.rs`](https://docs.rs/crate/accesskit_unix/0.24.0/source/src/adapter.rs) lines 122–164. The crate's [0.24.0 API/release page](https://docs.rs/crate/accesskit_unix/0.24.0) confirms the AT-SPI backend and its internally spawned executor.

This means “initialize the full native bridge only when an AT client appears” is not an application-level optimization available today. It requires a backend/API redesign that still observes late `IsEnabled` transitions and attaches the platform provider before the OS can query the window. A monitor-only AccessKit API plus late Unix provider registration is a plausible upstream seam, but the existing generic Winit constructor does not expose it; Windows/macOS provider lifetimes also have different host-message requirements. Keep the bridge enabled by default. Do not substitute a nullable adapter, environment-variable probe, or user accessibility toggle for system activation notifications.

The activation-to-tree latency is a distinct path from this resident-page measurement. GPUI's `request_initial_tree` handler sets its active/initial atomics and wakes the owner, then returns `None`; the adapter supplies a placeholder while GPUI's next owner turn drains activation and `sync()` publishes the full acknowledged sheet. The current floor captures had no AT-SPI client, so they contain no measurement of status-signal-to-first-tree or action-to-owner latency. Any lazy-provider experiment must report that interval independently and preserve the initial-tree ordering contract.

### What the measurements do and do not say

The source-matched `x11` versus `x11-minimal` controls measured about **3.15 MiB median paired PSS delta on the blank window** and **3.25 MiB on the zero-row text window**, with three additional process threads. Most of the PSS increment was `Pss_File`; the zero-row control's 938 KiB X11 shared-memory PSS was equal in both variants. The runnable binary shrank about 5.55 MiB on disk in the minimal control. This is the total optional accessibility feature graph, not a per-crate or allocator-live measurement. Runtime AT-SPI was absent; the experiment does not measure active-provider latency. Full distributions, hashes, process mappings, and the probe are in the prior report's linked artifacts.

PSS is proportional mapping residency, not private allocated bytes. File-backed pages can be shared by processes and their proportional charge changes with co-resident mappings; it does not identify which Rust crate caused a code page to be faulted in. The observed thread count is likewise not a memory attribution. The Linux kernel describes the `smaps_rollup` fields and mapping accounting in its [procfs documentation](https://github.com/torvalds/linux/blob/v6.18/Documentation/filesystems/proc.rst).

### Realistic next steps, in order

1. **Attribute the binary before changing code.** Build the ordinary `x11` application with a linker map and symbol/section size report; capture `readelf -SW`, `readelf -lW`, and per-VMA `smaps` before/after the native adapter is constructed and after the worker's first bus/status cycle. Match executable, feature set, Rust toolchain, target, fixture and active-AT state. Compare cold-start resident pages, not just `.text` bytes. The previous probe did not collect a map or page-fault attribution, so it cannot tell whether the 5.55 MiB linked-binary difference is live monitor code, generic dependency code, or dead section retention.
2. **Test release whole-program optimization as a build-profile experiment.** The workspace has no custom `[profile.release]` override, so Cargo's documented release defaults apply: `opt-level=3`, `lto=false`, `strip=none`, and 16 codegen units. Cargo/rustc document ThinLTO as whole-program cross-crate optimization with longer linking, and GNU `--gc-sections` as reachability-based removal of unreferenced input sections. This justifies a *measurement*, not an expected win: GPUI's Linux monitor and provider are reachable and therefore cannot be discarded as dead code. ThinLTO may fold or eliminate cross-crate wrappers, but it can also grow hot functions. Keep optimization only if paired release artifacts show a repeatable reduction in resident PSS-file/pages without a material increase in cold startup or action-to-tree response. Sources: [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html), [rustc LTO and dead-code options](https://doc.rust-lang.org/rustc/codegen-options/index.html), [GNU ld section GC](https://sourceware.org/binutils/docs/ld/Options.html#index-gc_002dsections).
3. **For a measured runtime page-floor reduction, first upstream the lifecycle boundary.** A future AccessKit Unix design could keep the small status subscriber active, but defer loading/constructing the heavy AT-SPI provider side until the first enabled notification; it must handle enable-before-first-window, enable while idle, disable/re-enable, bus disconnect/reconnect, a window added while already enabled, and provider activation racing close. The active transition must publish a complete initial tree before a client can query it. Test actual AT-SPI discovery and action round-trips, not merely an environment probe. If deferring code pages requires a dynamic module, include module ABI, packaging, signing, platform fallback and load-latency costs; do not assume `dlopen` is a free or portable boundary.

Avoid linker stripping as a claimed resident-memory win without mapping evidence. Cargo release defaults already disable debug info, while symbol/file metadata outside loadable segments is not in the process PSS. Likewise, changing to Tokio based on “one fewer thread” is unsupported by the feature control: the separate adapter probe changed task count but did not demonstrate an RSS/PSS benefit.

## Renderer note review: narrow exact-token packet reuse is the next safe GPU work cut

The earlier [`renderer-work-removal-luna.md`](renderer-work-removal-luna.md) correctly identified repeated GPU packet preparation, but its proposed stable visual revision was not yet present in the examined GPUI source. Current `Canvas::damage_from` does an ordered equality walk during `CanvasScene::commit_with_damage`; runtime stores that damage on `Prepared`. The CPU native backend uses damage plus `SurfaceDamage` buffer-age history to repair the existing softbuffer image. The GPU native branch does not: it obtains the current surface texture, calls `renderer.render(scene, &view)`, and presents. The current GPU renderer always validates/traverses groups, rebuilds draw records and tile CSR ranges/references, recomputes statistics, writes the retained GPU buffers, creates a bind group, and clears/draws a full-screen triangle (`crates/gpu/src/renderer.rs::Renderer::render`, approximately lines 405–740). The native surface is configured for `RENDER_ATTACHMENT` only (`crates/gpui/src/native.rs::surface_config`).

### Candidate: cache only a renderer's exact already-prepared presentation token

`Win::with_scene` returns both the borrowed `PreparedScene` and the opaque current `PresentationToken`; the token contains a non-reused window namespace and a sequence. It stays the same for an OS exposure redraw of the already prepared scene, and changes for a newly prepared scene. Each `GpuSurface` owns exactly one `Renderer`. Add an internal native-facing render entry point that supplies the token sequence as a reuse key; keep the general public GPU `render` entry point uncached unless its caller supplies an explicit per-renderer unique key. Retain the **current packet in the storage already owned by Renderer**: records, ranges, references, corrections, image/atlas state, and the bind group. On an exact-key hit with matching dimensions/color config/format, skip validation/bin reconstruction, queue writes, resource preparation and bind-group creation; still encode the clear/full-screen draw into the newly acquired target and submit/present normally.

This is narrower than a visual-scene revision cache but has a clean proof boundary and no duplicate draw tree, per-draw IDs, scene hash, or retained pixel texture. It pays only a small key and one retained bind-group handle. Equal visuals under a *new* token conservatively miss. The actual source-token can be read in the same owner callback as the scene; no repeated source scan is needed. Target size/config checks remain mandatory on every call. A new Renderer on device recreation naturally begins cold. Surface reconfiguration on the same Renderer can reuse the scene packet only after current-target dimensions and format pass validation.

The hit cannot skip drawing into the acquired surface image. Wgpu describes `SurfaceTexture` as the frame returned by `get_current_texture`; its public API does not promise preservation of the previously presented pixels. GPUI's current configuration requests only `RENDER_ATTACHMENT`. This candidate therefore must not treat same-token redraw as permission to present an untouched swap image. A later GPU retained-image/partial-damage design would need explicit owned texture storage, format/copy capability checks, and present-buffer history; that is a separate memory/correctness trade.

**Correctness gate.** Compare full rendered target bytes/declared HDR tolerance for (a) first render/cache fill, (b) same-token redraw after exposure, and (c) full miss. Require exact same-token hit with no source/tree walk, queue scene-buffer writes, image upload, atlas mutation, or new bind group. Assert a new token misses even where its pixels happen to match; size/format/color-config change misses; renderer/device replacement starts cold. Exercise image-only and glyph-mask scenes, atlas growth, zero-draw scene, HDR target, failed render admission followed by retry, and WGPU error/recovery. Retain full target clear/draw/submission counters so the report can distinguish *preparation* work removed from raster/submit work retained. Benchmark actual same-token OS expose/redraw traces and report hit rate; do not promote a synthetic all-hit loop as a general frame win.

### Deferred directions

* The CPU tile-bin key from the earlier note is subsumed for this native path if the exact packet cache hits; independently it can still help callers that reuse Canvas region renders, but it must include exact tile bounds and cannot assume every regional request repeats.
* GPU damage rendering across distinct tokens is not an immediate follow-up. `wgpu::SurfaceTexture` carries no public buffer-age/preservation contract. A retained intermediate texture costs a full extra render target (for example, 8 MiB at 1280×800 RGBA16F) before accounting for swapchain or backing leases. Only investigate after current output damage statistics show enough stable untouched area to repay the storage and final present/blit bandwidth, and only with a fully defined recreation/age protocol.
* Lane-batched shader traversal and sparse-strip/path alternatives remain profile-gated. Current code preserves per-sample coverage and painter order; reducing this to scalar coverage breaks correlated translucent edges. The Vello pinned-source, shader register-pressure and image-path caveats in the earlier renderer note remain valid; this pass adds no SDF or SIMD speed claim.
