# Async graph research and GPUI fit

## What the primary sources do and do not establish

The official Solid blog index lists Ryan Carniato’s three recent posts, “Fetch High, Block Low” (Aug 19, 2026), “Write Sync, Run Async” (Aug 24), and “One Graph, Two Machines” (Aug 26). Direct requests to those article pages were blocked by Cloudflare, so I could not read or verify their details. I do not treat the titles as technical evidence. The accessible official author post is the [Solid v2 RC overview](https://github.com/solidjs/solid/discussions/2995), which says async is represented in the reactive graph: computations may produce promises (and, in the prose, async iterators); downstream consumers derive pending, error, transition, stale-value, and optimistic state instead of application code maintaining separate flags. It also characterizes resources/manual batch and transition APIs as workarounds being removed or replaced. This is an author overview, not a substitute for the inaccessible three-post series.

I pinned the corresponding official Solid source at `solidjs/solid` RC tag commit [`ff4d3c4479163fbdd3327f5b22d0c3ea7bd1a2c5`](https://github.com/solidjs/solid/tree/ff4d3c4479163fbdd3327f5b22d0c3ea7bd1a2c5). Ripple TS was pinned to official repo HEAD [`fed124465d162ce17ce009936ef50061719d9882`](https://github.com/Ripple-TS/ripple/tree/fed124465d162ce17ce009936ef50061719d9882). Ripple’s type contract is narrower than Solid’s prose: [`trackAsync` accepts a PromiseLike or a PromiseLike plus AbortController](https://github.com/Ripple-TS/ripple/blob/fed124465d162ce17ce009936ef50061719d9882/packages/ripple/types/index.d.ts#L287-L291). Its implementation shows concrete mechanics: each effect run increments a version, aborts the previous controller, marks pending before invoking the callback, and only applies resolution/rejection when that run remains current; teardown aborts; errors route to the catch boundary ([implementation, lines 220–352](https://github.com/Ripple-TS/ripple/blob/fed124465d162ce17ce009936ef50061719d9882/packages/ripple/src/runtime/internal/client/track-async.js#L220-L352)). It requires an active compiler block and upstream pending boundary ([lines 134–195](https://github.com/Ripple-TS/ripple/blob/fed124465d162ce17ce009936ef50061719d9882/packages/ripple/src/runtime/internal/client/track-async.js#L134-L195)); this is coupled to Ripple’s compiler/DOM/SSR runtime, not a portable API recipe.

## GPUI’s current point in that design space

The pinned local GPUI tree audited here is `reactivity` HEAD `36921e2c42efe8569889d16a27295d8ee7b790a2`. It already has several semantics an async parity audit should credit. `Reader<T>` is an inert copyable key without deref, blocking read, producer ownership, or hidden work start ([reader.rs](https://github.com/gpui-ce/gpui-ce/blob/36921e2c42efe8569889d16a27295d8ee7b790a2/reactivity/crates/gpui/src/reader.rs#L27-L42)). `Questions::question` makes the caller explicitly define an input freezer and a prompt start function whose contract forbids running UI code; only owned `I: Send + 'static` crosses into the worker lane ([question.rs](https://github.com/gpui-ce/gpui-ce/blob/36921e2c42efe8569889d16a27295d8ee7b790a2/reactivity/crates/gpui/src/reader/question.rs#L45-L89)). It allows only one physical completion outstanding, stores only the latest frozen input while waiting, and carries a request stamp. Its state retains the previous value through Pending and Fault ([question.rs lines 45–52, 161–174](https://github.com/gpui-ce/gpui-ce/blob/36921e2c42efe8569889d16a27295d8ee7b790a2/reactivity/crates/gpui/src/reader/question.rs#L45-L52)). Thus stale-result rejection, stale display, typed error/status and back-pressure are architectural guarantees, not features to redo with a “resource” boolean.

The real UX cost is the application boundary around them: callers must declare/freeze inputs, supply executor/service enqueue behavior, convert domain errors, and manually project Reader states into view elements. `Remote::bounded` is likewise explicit infrastructure (owned bounded sender/inbox; any-thread sends never invoke user code), which is valuable for isolation but visible scaffolding ([remote.rs](https://github.com/gpui-ce/gpui-ce/blob/36921e2c42efe8569889d16a27295d8ee7b790a2/reactivity/crates/gpui/src/remote.rs#L27-L53)). A production-level improvement should remove repeated orchestration, not weaken those boundaries: provide an opt-in typed adapter around a `Future<Output=Result<T,E>>`/request factory that freezes owned inputs on the owner, schedules via an injected executor, assigns a cancellation/version token, ignores stale completion, retains the prior owned result, and reports a typed status to a standard projection. Cancellation must be cooperative (`CancellationToken`/AbortHandle owned by the task); do not lend `&mut Model` or a reader borrow into a future across `.await`. Keep explicit policy knobs for stale-while-revalidate, clear-on-refresh, retry, and stream snapshotting rather than making one loading policy ambient.

GPUI differs from Solid/Ripple in lifetime and runtime target: it has no compiler-generated graph/DOM boundary, and its view description has strict borrowing/owner rules. Promise-shaped values alone cannot safely provide Solid’s transparent “all derived reads suspend/stale/error” semantics. The best parity path is a high-level safe adapter over current lanes with explicit ownership and presentation policies. It must preserve current cancellation and delivery authority. Reconnect behavior needs its own explicit contract: it is not an existing general guarantee. Its tests must exercise dropped owners, superseding inputs, cancellation, repeated failure/retry and any proposed reconnect behavior, not just a happy future.

## Actual Hummingbird proof fixture

Hummingbird is Apache-2.0 (`Cargo.toml`), pinned at [`e15e8ba0ef6ff5445294030d373e3c8ccc7d780c`](https://github.com/hummingbird-player/hummingbird/tree/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c). A smallest meaningful production-shaped fixture is a query-backed **search result palette over seeded SQLite rows**, not a synthetic 250K generator. Reuse these exact production seams:

- `src/library/db/query/track.rs`: `TrackQuery::for_search` and `TrackQueryForSearch::fetch_rows` execute the production projection against `SqlitePool` (pinned [lines 297–299 and 528–535](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L297-L299)). Its ordering builder uses SQL ordering plus deterministic tie breakers ([lines 474–478](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/library/db/query/track.rs#L474-L478)).
- Seed only a few artist/album/track rows using the real SQLite schema migrations, especially `migrations/20240730163128_create_artist_table.sql`, `...163151_create_album_table.sql`, and `...163200_create_track_table.sql` (track has stable integer `id`, title/sortable title, optional album, duration and unique location; pinned [track schema](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/migrations/20240730163200_create_track_table.sql#L1-L14)). Prefer the repository’s in-memory DB/test support rather than duplicating production SQL.
- Preserve source identity with stable DB IDs and selection/accepted result IDs, not randomized display labels. The actual `SearchModel` loads album/artist/track rows from those queries, creates match strings, and maps accepted album/artist/track results to a navigation event ([model.rs lines 33–112, 120–151](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/search/model.rs#L33-L112)). Its generation counter drops stale loads when closed or superseded ([lines 162–229](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/search/model.rs#L162-L229)).
- Have the tiny fixture prove seeded SQLite search/order, query replacement while an earlier result is outstanding, stale suppression, close/reopen/reconnect behavior, selecting a stable id, and keyboard/accessibility actions against the real palette control. To cover playback without audio/device setup, exercise the production `SearchPaletteItem::Track::on_middle_click` or its narrow event seam with an ID-backed lookup and assert the queued track ID; the production method loads `tracks().by_id(id)` then calls `play_track_next` ([search_item.rs lines 153–163](https://github.com/hummingbird-player/hummingbird/blob/e15e8ba0ef6ff5445294030d373e3c8ccc7d780c/src/ui/search/search_item.rs#L153-L163)). A real query + minimal data is a more credible adapter test than a large synthetic data pass because it keeps SQL semantics and selection identity in the evidence.

The standalone main GPUI checkout did not contain source for the new migration utility yet at audit time; I read the separate tool branch only on request from its author. The bounded rule treats `px(f32)` as removable only for finite decimal float literals and rewrites to a suffixed f32. This matches the original pinned GPUI implementation: [`Pixels` is `#[repr(transparent)]` over f32 and `px` simply constructs `Pixels(pixels)`](https://github.com/gpui-ce/gpui-ce/blob/41a42eb96d6c04e5e71f3577d12934d4de569b20/crates/gpui/src/geometry.rs#L2815-L2816), [`px` documents logical pixels and returns the same f32 argument](https://github.com/gpui-ce/gpui-ce/blob/41a42eb96d6c04e5e71f3577d12934d4de569b20/crates/gpui/src/geometry.rs#L4050-L4059). Suffixing the same decimal literal with `f32` preserves its f32 rounding. Do not extend this to integers, computed expressions, constants, or negative values other than literal negative zero without compiler-backed evidence.

## Composition follow-up, 2026-10-22

The three official article pages still return no readable body. A separate
[answered Solid composition discussion](https://github.com/solidjs/solid/discussions/3085)
is accessible. Carniato recommends rendering membership directly from the
user-owned collection while joining library-owned interaction state by stable
row ID. Mirroring the collection introduces synchronization and can hide
optimistic membership until settlement. The discussion also reports an engine
bug involving reads through derived stores; the proposed pattern needs actual
transaction tests, not just API similarity. This is the discussion's evidence,
not a claim to have read the linked blog article.

For GPUI, use that outcome as a composability gate: component selection, drag,
measurement and inspector state must remain owner-local, joined to application
rows by typed stable identity. A contained-owner adapter must preserve the
application's source registry and writer admission rather than copying its
collection into a tooling model. Optimistic application membership and local
interaction state need distinct lifetimes. This is a design inference; a general
optimistic adapter is still unimplemented.

A Future convenience wrapper that checks `Completion::is_cancelled()` only when
polled is insufficient: an obsolete, indefinitely Pending future may never wake,
so it can hold the single physical completion credit forever. An executor
adapter must have a cancellation path that wakes or drops that exact task, and
reclaim credit only after physical task retirement. Preserve typed owned input,
stale-result admission, previous-value projection, panic/failure distinction and
ordinary-question header costs. No model or reader borrow may cross await.
