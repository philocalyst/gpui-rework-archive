# Luna 03: elements and rendering review

This is a first-pass implementation review for the element, view, and rendering documentation. The current crate docs are useful orientation, but they are not a complete guide to the public element APIs. Treat this report as review notes, not as a source of truth: implementation in this checkout wins when it differs from upstream or existing prose.

## Documentation model

Jiff’s crate docs are a good structural reference: begin with a short promise and one compiling example, name the central types and the relationships between them, then link into task-oriented examples and deeper API documentation. See [Jiff’s crate overview](https://docs.rs/jiff/latest/jiff/). For GPUI, the opening should orient a reader from a `View` to an `Element` tree, explain the frame lifecycle and identity, and then give task paths such as “make a reusable component,” “paint custom content,” “render a large list,” and “load an image.” The public method docs should explain constraints and state lifetime, not repeat a list of builder names.

The best examples in the pinned consumer sources show choices in context. Zed uses `RenderOnce` for prop-driven component examples and `Render` for entity-backed screens; it uses `uniform_list` with stable IDs and a tracked scroll handle for registry and file rows. Hummingbird uses `uniform_list` for fixed-height file rows and table/queue entries, and `canvas` for a window resize hitbox and cursor behavior. Those use cases map well to short cookbook sections.

## Verified behavior and factual corrections

- **The frame phases are a handoff, not a retained element lifecycle.** `Drawable` enforces `request_layout → prepaint → paint` for a particular element value. The associated state types carry data only across those phases. `LayoutId`, bounds, and phase state are frame-local; retained element state goes through `Window::with_element_state` and a stable ID, or through an entity/view. See `element.rs` around `Element`, `Drawable`, and `AnyElement`.
- **Bounds do not clip by themselves.** The `Div` style/overflow path establishes a clip for scrolling content; custom drawing must use the current mask or explicitly call `Window::with_content_mask`. `Canvas` invokes prepaint after layout and passes its result into paint, inside the refined style’s paint operation. See `div.rs` element phase methods, `canvas.rs`, and `rendering.md`.
- **`RenderOnce` and `Render` represent different ownership.** `RenderOnce::render(self, ..)` consumes a value and does not give it an entity identity or independent invalidation. `Render::render(&mut self, ..)` runs on an entity; notifying that entity invalidates its rendered view. A one-shot component can still hold entity handles or use retained state under stable element IDs. Neither trait’s call count is a lifecycle contract. See `element.rs` and `view.rs`.
- **View caching is opt-in and has a concrete layout contract.** `Entity::cached(style)` / `AnyView::cached(style)` provide the root style because content is not rendered to measure it on a cache hit; callers need definite dimensions appropriate to the use. Cache reuse also depends on the resolved bounds, content mask, text style, direction, and bidi mode. Dirty notifications and `Window::refresh` force work; inspector picking disables this cache. The implementation also records entities accessed while rendering so reactive dependencies can be restored on reuse. Avoid describing cached views as unconditional memoization. See `view.rs`, `ViewElementCacheKey`, `ViewElement::request_layout`, `prepaint`, and `paint`.
- **Identity is a path, and identity kinds are different.** An `ElementId` contributes to a `GlobalElementId` path; the path scopes retained element state. A `LayoutId` is a layout-engine node for this frame and is not a persistent key. A `View` backed by an entity uses that entity ID as its view element ID. Rendering the same entity at repeated sibling positions can collide in its descendant state namespace; give repeated logical rows distinct view entities or use unique stable child IDs. See `element.rs` ID stack in `Drawable::request_layout` and `view.rs` `View::entity_id` / `ViewElement::id`.
- **`AvailableSpace` carries meaning.** `Definite(px)` is a constraint; `MinContent` and `MaxContent` are intrinsic sizing queries. A measure callback receives both known dimensions and available space and returns the measured size. Do not tell users that every requested style size is a guaranteed final size. `LayoutId` is frame-local. See `taffy.rs` layout requests and measure closure, and the `AvailableSpace` definition.
- **Variable-height and uniform lists have distinct costs and update protocols.** `List` virtualizes items with measured heights in a sum tree; `ListState` must live in the owning view. Use `splice`/`reset` when item identity or count changes and `remeasure`/`remeasure_items` when existing items’ heights may change. `measure_all` can make initial scrollbar geometry accurate but costs work up front; uniform height hints offer a cheaper estimate. Remeasurement preserves either a pixel offset (`remeasure_items`) or a proportional in-item position (`remeasure`). `uniform_list` measures one item and derives the others from that height, so each rendered item must share its block-axis size; it renders only the requested range plus overdraw. See `list.rs` and `uniform_list.rs`.
- **Uniform list offset/nearest wording should follow this checkout.** `Top` applies the offset as an inset above the target; `Center` centers in the remaining viewport; `Bottom` ignores the offset. `Nearest` uses the inset when deciding whether the item is above the visible region. The strict offset method still leaves an already-visible item in place for `Nearest`. The current edited docs in `uniform_list.rs` say this accurately; preserve those details when expanding the guide.
- **Images have more than one loading path.** `ImageSource::Resource` uses GPUI’s asset loader and can be resolved by an explicit cache, nearest ancestor `ImageCacheElement`, or global fallback. `Render` and CPU `Image` sources are already decoded; `Custom` lets callers return pending/finished results, and callers must notify the owning view when their custom loader becomes ready. The built-in retain-all cache polls a shared background task and schedules notification after completion. Optional loading UI is delayed (the source constant is 200 ms); fallback content handles terminal errors. Animated frames require retained state on a stable element ID and request repaint only for an active window when reduced motion is off.
- **Accessibility nodes require identity.** The element prepaint wrapper inserts a node only for an element with an ID and either an accessibility role or `is_a11y_hidden() == true`; a hidden role-less element receives an internal generic container so the subtree can be hidden. Synthetic children are added after prepaint and require the same ID plus role/hidden contract. See `element.rs` accessibility hooks and `Drawable::prepaint`.
- **Special-purpose elements have important phase timing.** `container_query` runs after its own bounds are known; its child cannot affect the query element’s size. `Deferred` keeps its child layout but queues painting after ancestors; recursion is depth-limited. `Anchored` fits its subtree against the window viewport and switches anchor sides or snaps to edges. `Svg` transforms rendering without changing layout bounds or hitbox. `Surface` composites an available platform/GPU source using `ObjectFit`. See their respective element modules.

## Public API areas to cover and cross-link

1. **Component choice and identity:** `IntoElement`, `Element`, `RenderOnce`, `Render`, `View`, `AnyView`, `ViewElement`, and `AnyElement`. Link to entity/context docs for notification and retained state; link `ElementId` to the identity section and `LayoutId` to layout constraints.
2. **Custom element walkthrough:** concrete state types from request-layout and prepaint; child layout composition; reading resolved bounds; registering hitboxes/focus/accessibility in prepaint; painting inside style/clip state. Contrast `canvas` as the supported small custom-paint route. Link to interaction and accessibility guides.
3. **Containers and interaction:** `Div`, `Styled`, `ParentElement`, `InteractiveElement`, `StatefulInteractiveElement`, `Interactivity`, `Stateful`, `ScrollHandle`, and `ScrollAnchor`. Explain capture/bubble, filtered button/payload listeners, outside listeners, focus vs focus request, and stable IDs. Cross-link styled property docs rather than duplicating the generated builder inventory.
4. **Large collections:** compare `list` and `uniform_list`; explain `ListState` mutation, visible range/overdraw, uniform-height invariant, stable ID, `track_scroll`, scroll anchors, follow-tail, and `ListOffset`. Include one variable-height example and one fixed-row example. Link to `ListSizingBehavior` and horizontal sizing details.
5. **Text and inline flow:** cover `Text`, `StyledText`, `TextLayout`, `InteractiveText`, truncation and position/index mapping, inline fragments, and paragraph direction. Explain that the layout object is measured text geometry, not persistent widget state. Link text style and shaping docs.
6. **Images and visual elements:** `img`, `ImageSource`, `StyledImage`, `ImageCache`, `ImageCacheProvider`, `RetainAllImageCache`, `svg`/`Transformation`, and `surface`/`SurfaceSource`. Clearly distinguish resource loading, predecoded values, and caller-owned loaders; document fit, placeholders, errors, animation, platform availability, and cache lifetime.
7. **Layout helpers:** `container_query`, `anchored`, `deferred`, and animation helpers. State timing and coordinate space first; make feature-specific examples link from the overview.
