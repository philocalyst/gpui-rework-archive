# X11 XIM deferral: behavior and floor evidence

**Source pin:** the clean-room worktree is based on committed GPUI HEAD `36dabab5c07f9dfa7633161794242e935777fe34`; its lockfile pins vendored Winit `0.30.13`. This report changes no production source and runs no display benchmark. The local source links below are the implementation evidence; external links are primary Xlib/POSIX/platform references.

## Decision

An opt-in lazy **XIM open** is structurally feasible without disabling international input, provided Xlib locale setup and xkbcommon compose initialization remain eager. Defer the first `XOpenIM`/`XCreateIC` work until the event loop processes the first `set_ime_allowed(true)` request. Do not defer the current LC_CTYPE/XSupportsLocale block as part of the first experiment: Xlib binds the locale and modifiers to an input method when `XOpenIM` runs, POSIX locale state is process-wide, and Winit's keyboard compose table is initialized during the same event-loop construction. Keeping the locale decision at the existing point avoids changing ordinary compose/dead-key behavior or making another thread mutate process locale. [Xlib locale and input-method specification](https://www.x.org/releases/X11R7.6/doc/libX11/specs/libX11/libX11.html), [POSIX locale state](https://pubs.opengroup.org/onlinepubs/009695399/functions/setlocale.html).

This is a startup-work hypothesis only. No fresh-process before/after XIM-deferred timing or memory result is available. The existing mapping captures show the locale archive and xkbcommon mappings are already resident on a blank X11 sample; therefore this change cannot be credited with removing those pages. Any win may be limited to XIM probing, context creation, native state, and X server/IM round trips, and may be zero when the local fallback is cheap. Do not claim RSS/PSS savings until measured against matched binaries and sessions.

## End-to-end current path

1. `EventLoop::new` creates two `std::sync::mpsc` channels at `vendor/winit/src/platform_impl/linux/x11/mod.rs:185-186`: window-to-loop IME requests and loop-to-handler IME events. It calls `setlocale(LC_CTYPE, "")`, checks `XSupportsLocale`, and restores the previous locale if Xlib rejects it (`:187-209`). It then constructs `Ime` (`:211-218`).
2. `Ime::new` snapshots `XMODIFIERS`, queries the root `XIM_SERVERS` property, and tries the configured modifier first, then `@im=local`, then `@im=` (`ime/input_method.rs:265-307`). The `@im=local` path exists to retain compose input even if no external IM server is available. If the configured modifier fails, Winit registers `XRegisterIMInstantiateCallback`; if the active IM dies, its destroy callback installs that watcher and replaces it with the fallback. A later instantiate callback rebuilds the IM and all live contexts (`ime/callbacks.rs:24-65,91-205`). Keep these semantics.
3. Each new X11 window receives an XIC with IME disabled (`window.rs:531-535`). `set_ime_allowed` arrives through the request channel and destroys/recreates that window's XIC with the requested style (`ime/mod.rs:197-213`). Focus/unfocus call XSetICFocus/XUnsetICFocus on the XIC (`event_processor.rs:1269,1332`); destroy removes the XIC (`:846`). Cursor placement reaches the XIC through `set_ime_cursor_area` (`window.rs:1737-1744`).
4. `XFilterEvent` is used for key press/release only when the focused window has an allowed XIC (`event_processor.rs:132-174`). XIM can consume composition/preedit keystrokes and key releases, with special modifier replay preserving modifier state (`:201,950-1003`). Otherwise Winit uses its independent xkbcommon key processor; the xkbcommon compose table and two mutable compose states are already initialized with the event-loop keyboard context (`linux/common/xkb/mod.rs:54-92`, `compose.rs:17-57`). This is the ordinary key translation and dead-key/Compose path that must stay warm.
5. For XIM-accepted input, Winit calls Xutf8LookupString through `lookup_utf8` and emits committed text; XIM preedit callbacks deliver start/update/end and cursor positions. Xlib says XFilterEvent is the filter step for IM event flow, while lookup is made through the associated XIC. [XIM protocol](https://www.x.org/releases/X11R7.7/doc/libX11/XIM/xim.pdf), [Xlib input-method API](https://www.x.org/releases/X11R7.6/doc/libX11/specs/libX11/libX11.html).

The locale block cannot be moved wholesale to first editable focus without a keyboard behavior change risk: Winit's `XkbComposeTable::new` selects its locale from `LC_ALL`, `LC_CTYPE`, or `LANG` and is constructed during event-loop creation. POSIX states that locale state is common to all process threads. A worker-thread XIM/locale initializer would therefore violate both the explicit local comment that all XIM calls must happen on one thread (`ime/mod.rs:1`) and the process-global locale contract.

## Minimal deferral shape

Retain `ime_sender` and the disabled IME event behavior. Replace the eager `Option<RefCell<Ime>>` initialization with an event-loop-owned lazy state that can retain the event sender and the `Ime` instance after first use. When an `Allow(window, true)` request is processed, open the IM and create the target window's allowed XIC before returning to the X event pump. `Allow(window, false)` before initialization is already the default and should not initialize XIM. Keep XIM creation, callback registration, replacement, lookup, and destruction on the existing event-loop thread.

The subtle part is live windows: today every window gets a disabled XIC at creation. A lazy implementation must either (a) create the same disabled XIC for every currently-live window when the first IM is opened, then apply the requested window's enabled style, or (b) prove that only creating contexts as windows become editable preserves focus/activation and `Ime::Enabled`/`Disabled` event order. Option (a) is the lowest-risk first version. The registered windows are tracked in `ActiveEventLoop.windows`; use that owner-thread registry or add a small XID ledger. Do not create one context per window from an XIM callback while a mutable `RefCell<Ime>` borrow is active.

The existing two MPSC channels still allocate and remain present in this minimal version. A separate, more exotic source-only follow-up could remove the IM-to-event-loop channel by storing callback output in a queue owned by `ImeInner` and draining it after `process_xevent`. This is only safe if every XIM callback and drain stays on the XIM-owning event thread and callback-generated events remain deferred until the current IME mutable borrow ends. Directly calling the Winit application callback from an XIM FFI callback is unsafe for reentrancy and event ordering. Replacing the request channel requires cross-thread `Window` API delivery and a wake path, so it should not be folded into lazy init without a separately measured need.

Expected source cost for a behavior-preserving spike (estimate, not a patch): about 40-80 changed Rust lines across `x11/mod.rs`, `event_processor.rs`, and `ime/mod.rs`, plus 100-200 lines of X11 IME integration tests/fixtures for active and unavailable IM servers. A callback-output queue experiment adds roughly 30-60 lines and is a distinct change. The surrounding IME module is 1,234 Rust lines across `mod.rs`, `input_method.rs`, `callbacks.rs`, `inner.rs`, and `context.rs`; the full relevant keyboard/event processor is 1,891 lines. These counts describe the existing audit surface, not code to rewrite.

## Failure cases and acceptance checks

The deferral must pass these before adoption:

- Start with no editable field, then enable editing in an existing window and immediately type; the first key must not be dropped while XIM starts. Repeat with enabling in the same callback as focus acquisition.
- Type ordinary Latin, a modifier shortcut, dead-key accents, and multi-key Compose sequences before and after the first XIM request. Verify identical key events, text commits, and modifier state. Exercise key release during preedit and modifier keys consumed/replayed by XFilterEvent.
- With a real XIM (at least ibus or fcitx), test preedit updates, cursor/spot movement, commit, cancel, and focus transfer across two windows. Test each fallback path: valid XMODIFIERS, empty XMODIFIERS, missing/unopenable server, local fallback, and no usable XIM.
- Start with unavailable configured XIM, then make it available; verify instantiate callback replaces the fallback and recreates existing contexts. Destroy the active XIM and verify fallback reconnect, preedit cleanup, and no stale XIC use.
- Close one of several windows while another remains active; close while an Allow request is queued; toggle true/false rapidly; destroy the event loop; check all XIC/XIM resources close on their owning thread.
- Test invalid/unsupported LC_CTYPE. Confirm fallback locale selection and xkbcommon compose behavior are byte-for-byte equivalent to eager behavior. Never move `setlocale` onto a background worker.
- Use an X server/IME that delays or fails `XOpenIM` to test that first editable activation reports/handles failure without hanging the UI or dropping the key. Because lazy XIM moves possible wait time to activation, measure first-editable-input latency separately from first-window startup.

Winit's repository has no existing X11 IME integration test covering this matrix (source search in the pinned tree found no `XIM`/`XMODIFIERS` tests). Add these as integration tests using an isolated Xvfb/Xorg and a controllable test XIM or a small XIM test server; the root's reserved `:94` display is not for this probe.

## Other platform lifecycle comparison

- **Windows / Winit 0.30.13:** no analogous process-global XIM object. Winit obtains/releases an `HIMC` per operation (`windows/ime.rs:24-26,158-160`) and toggles the default IM context association with `ImmAssociateContextEx` when allowed (`:141-151`). Windows documents that a default input context is associated with each window at creation; custom contexts have explicit attach/detach lifetime. [Microsoft input-context lifecycle](https://learn.microsoft.com/en-us/windows/win32/intl/input-context), [ImmAssociateContext](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontext). Deferring XIM logic to Windows would add no matching per-event-loop resource and risks changing platform behavior.
- **macOS / Winit 0.30.13:** Winit's `WinitView` always implements `NSTextInputClient` and stores marked text and IME state (`macos/view.rs:243+`). AppKit's `NSTextInputContext` is the bridge for the activated client; AppKit owns activation and marked-text interaction, and Winit retrieves the context when it must discard marked text. [Apple `NSTextInputContext`](https://developer.apple.com/documentation/appkit/nstextinputcontext), [Apple custom text-view lifecycle](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/TextEditing/Tasks/TextViewTask.html). There is no Winit event-loop `XOpenIM` equivalent to defer.
- **Wayland / Winit 0.30.13:** `WindowState` stores `ime_allowed=false` and a list of text-input protocol objects. `set_ime_allowed` enables/disables and commits protocol state only for objects that have entered the surface (`linux/wayland/window/state.rs:1019-1047,1129-1139`). Protocol state must be updated when text focus moves, and enter/disable invalidates state. [Pinned text-input-v3 protocol](https://github.com/wayland-mirror/wayland-protocols/blob/main/experimental/xx-text-input/xx-text-input-v3.xml). The compositor/service owns the IME work; protocol object binding and enable semantics differ from an eager Xlib XIM open. Do not infer that laziness is free or portable across backends.

## Existing memory/startup attribution and limit

The frozen 2026-10-21 X11 mapping snapshots in `benchmarks/luna-accessibility-floor/runs/frozen724-variant-smaps.txt` show a blank application with `locale-archive` at 320 KiB PSS, libX11 resident mappings, and libxkbcommon mappings. The matched `x11-minimal` snapshot still has the same 320 KiB locale archive mapping; that feature comparison is not a control for XIM and cannot attribute the mapping to Xlib versus compose. A separate modern CPU-first sample records no Vulkan/Mesa mapping before first CPU present, and its CSV records 8,716 KiB PSS / 1,588 KiB anonymous at 1 second, but does not contain per-file mappings. Thus current evidence confirms CPU-first avoided early graphics drivers; it does **not** tell us how many resident bytes or milliseconds eager XIM adds.

The reproducible read-only probes used for this audit are:

```sh
rg -n 'Ime::new|XOpenIM|XCreateIC|XFilterEvent|lookup_utf8|xkb_compose_table_new_from_locale|set_ime_allowed' vendor/winit/src/platform_impl/linux/x11 vendor/winit/src/platform_impl/linux/common/xkb
nl -ba vendor/winit/src/platform_impl/linux/x11/mod.rs | sed -n '180,220p'
nl -ba vendor/winit/src/platform_impl/linux/x11/event_processor.rs | sed -n '132,215p;940,1015p;1255,1340p'
```

These source probes are reproducible in the pinned worktree and use no display. No assembly or allocation probe was run: the relevant cost crosses into Xlib and the X server, and source inspection cannot turn `mpsc::channel`, XIM/XIC handles, or locale-page residency into a measured startup or memory saving.
