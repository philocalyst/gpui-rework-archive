== Subscriber lists — intrusive slab vs Vec-per-cell vs CSR (1000-subscriber publish)
========================================================================
  size_of<SubNode {prev,next,target} (intrusive, 12B)> =  12  align = 4
  · Intrusive node is 12 bytes/subscriber; a Vec<u32> is 4 bytes/subscriber + 24B cell header.
  · Per-cell memory: Vec cell = 24B + 4B/sub; intrusive cell = 4B (head) + 12B/sub in shared slab.

  publish 1000 subs (FRESH, in-order allocation):
    Vec-per-cell : min    250ns  median    292ns  (0.29ns/sub)
    intrusive    : min    375ns  median   2250ns  (2.25ns/sub)
    CSR contig   : min    208ns  median    292ns  (0.29ns/sub)

  publish ~1000 subs (intrusive AFTER churn — scattered node allocation):
    intrusive    : min   2042ns  median   2208ns  (2.21ns/sub)
  · Churn scatters the next-chain across the slab -> cache misses on the walk. This is the real
  · intrusive cost: publish locality degrades with subscription churn.
    CSR rebuilt  : min    500ns  median    542ns  (0.54ns/sub)

  unsubscribe+resubscribe pair (intrusive O(1) pointer surgery):
    intrusive    : min 2.2ns  median 2.2ns per pair
  · Intrusive unsubscribe is a handful of array writes, no scan, no realloc — the design's claim holds.
  · Vec-per-cell unsubscribe needs a back-index (swap_remove moves the tail sub, invalidating ITS pos).
  >>> VERDICT: KEEP intrusive doubly-linked in a dense slab as the DEFAULT (memory.md is right): O(1) zero-alloc
  >>> VERDICT: subscribe/unsubscribe is the property that matters for mount/unmount churn, and 12B/sub is fine.
  >>> VERDICT: REFINEMENT: for high-fanout *stable* cells (theme, a palette read by 10k rows), publish walks
  >>> VERDICT: dominate and intrusive locality degrades under churn. Rebuild those into a CSR run at epoch
  >>> VERDICT: boundary (contiguous targets) — the publish becomes a linear scan. Pick per-cell by fanout×churn.

== The tape — span records, 128-bit hash, dedup intern, memcmp confirm
========================================================================
  size_of<SpanRecord (call_site,key,hash128,off,len)> =  32  align = 8
  · 32 bytes/span. call_site is an interned Location*; key packs an optional .key() discriminant.

  hash128 over   64B span:  scalar   63.5ns (1.01 GB/s)  |  wide(8B)    3.6ns (17.86 GB/s)  17.7x
  confirm memcmp   64B:     std==   2.5ns (25.82 GB/s)  |  chunked   5.5ns (11.59 GB/s)

  hash128 over  256B span:  scalar  329.7ns (0.78 GB/s)  |  wide(8B)   21.8ns (11.77 GB/s)  15.2x
  confirm memcmp  256B:     std==   5.7ns (45.18 GB/s)  |  chunked  13.0ns (19.72 GB/s)

  hash128 over 1024B span:  scalar 1403.2ns (0.73 GB/s)  |  wide(8B)  143.5ns (7.13 GB/s)  9.8x
  confirm memcmp 1024B:     std==  19.8ns (51.85 GB/s)  |  chunked  45.7ns (22.39 GB/s)

  Dedup intern over 10k spans:
    hash+intern+confirm 10k spans: 522708ns total (52.3ns/span); spans_lowered = 1 of 10000
  · The dedup collapses 10k describe->lower operations to ONE. The per-span cost is a 128-bit hash
  · (~0.1-0.3ns/byte) + a table probe + a single memcmp on the representative. Hash-equal WITHOUT
  · memcmp confirm is a correctness bug (collision) — the confirm is mandatory and cheap.
  · Even under a forced hash collision, the memcmp confirm rejects false reuse -> renders correctly.
  >>> VERDICT: Span record = 32B: {call_site:u32, key:u32, hash:u128, off:u32, len:u32}. Adopt the WIDE
  >>> VERDICT: (8-byte-at-a-time) 128-bit hash: measured ~3-8x the scalar byte loop and multi-GB/s, so hashing
  >>> VERDICT: a described frame is bandwidth-bound not compute-bound. std `==` autovectorizes to parity with a
  >>> VERDICT: hand-chunked compare — use `a == b` for the mandatory confirm (simpler, equally fast).
  >>> VERDICT: Dedup intern (hash->rep + confirm) collapses 10k identical rows to 1 lowering at ~ns/span.

== Describe-frame read-sets — sorted-smallvec vs bitset vs epoch-stamped
========================================================================
  size_of<Small read-set (inline 8 x u32)> =  40  align = 8
  · Inline capacity 8 covers the common view (reads a handful of cells) with ZERO alloc.

  (A) sorted merge-diff (8-cell set, 1 in/1 out): 16.1ns  (added 1, removed 1)
  (B) bitset XOR diff (2048 slots / 256B bitmap):        27.7ns  (scans whole bitmap)
  (C) epoch-stamped mark (O(reads)=8 writes):         5.1ns
  · (A) sorted diff is O(|old|+|new|) with tiny constants; on an 8-cell set it is a handful of ns
  ·     and allocation-free (added/removed reuse scratch). It gives EXACT added/removed sets.
  · (B) bitset XOR scans the WHOLE slot space every diff regardless of read-set size -> loses when
  ·     slots >> reads (the usual case: thousands of slots, ~8 reads). Wins only for dense huge sets.
  · (C) epoch-stamp marks in O(reads) but does NOT by itself yield the 'removed' set (needs the
  ·     prior list too) — it is the READ-RECORDING primitive (dedup a cell read twice this frame),
  ·     not the diff. Best combined with (A): epoch-stamp to dedup during describe, sorted-diff after.
  >>> VERDICT: Read-set = inline-8 SmallVec<u32> of interned slots kept SORTED (insert keeps order, or sort
  >>> VERDICT: the tiny set once at frame end). Diff via sorted merge -> exact added/removed, ~ns, zero-alloc.
  >>> VERDICT: Use an epoch-stamp array as the intra-frame DEDUP (a cell read twice records once). Reject the
  >>> VERDICT: bitset except for pathologically dense read-sets: it pays O(total slots), not O(reads).

== SoA patch queue — sort/dedup + scatter + upload-range coalescing
========================================================================

  10000 patches -> 3697 distinct slots:
    (A) std stable sort + keep-last :  101000ns  (10.1ns/patch)
    (B) dense-scatter dedup (no sort):   31042ns  (3.1ns/patch)
    (C) LSD radix (4x8) + keep-last  :   82041ns  (8.2ns/patch)
    coalesce 3697 slots -> 276 upload runs: 1416ns

  10000 patches -> 6341 distinct slots:
    (A) std stable sort + keep-last :  106042ns  (10.6ns/patch)
    (B) dense-scatter dedup (no sort):   51333ns  (5.1ns/patch)
    (C) LSD radix (4x8) + keep-last  :   82250ns  (8.2ns/patch)
    coalesce 6341 slots -> 2310 upload runs: 3791ns

  1000 patches -> 628 distinct slots:
    (A) std stable sort + keep-last :    8791ns  (8.8ns/patch)
    (B) dense-scatter dedup (no sort):    4333ns  (4.3ns/patch)
    (C) LSD radix (4x8) + keep-last  :    9500ns  (9.5ns/patch)
    coalesce 628 slots -> 236 upload runs: 333ns
  · Dense-scatter dedup avoids sorting entirely: winner[slot]=last index in O(n), enumerate via a
  · first-touch list, sort only the DISTINCT slots for coalescing. When distinct << patches (palette
  · swap: many writes, few slots) it dominates. When distinct==patches it degenerates to 'sort the
  · distinct slots' and radix wins on the key sort. All are allocation-free with reused scratch.
  >>> VERDICT: Adopt DENSE-SCATTER dedup (winner[slot] + first-touch list) as the default drain: O(patches)
  >>> VERDICT: with keep-last for free, then sort only the distinct touched slots (radix LSD when distinct is
  >>> VERDICT: large) and coalesce ascending runs into upload ranges. This beats sorting all patches whenever
  >>> VERDICT: there is write amplification (the exact case SoA queues target). Reused scratch => zero alloc.

== Closure SSO — 3-word inline storage viability
========================================================================
  size_of<fn(&mut u64)> (fn pointer)      = 8
  size_of<[|| 42]> (capture-free closure)  = 0
  size_of<[move || x]> (one u64 capture)   = 8
  size_of<[move || a+b+c]> (3 u64 capture)  = 24
  3-word inline storage capacity           = 24 bytes
  · A capture-free closure / fn item is size_of==0 or one pointer -> stored inline, no box, no alloc.

  · box and increments a `closure_spill` counter (memory.md §4). The common region producer (reads a
  · field, returns an element) is capture-free -> inline, zero-alloc.
  >>> VERDICT: Route by TypeId with an FxHash/identity-hash map (NOT std SipHash — it re-hashes an already-
  >>> VERDICT: avalanched id). For a small fixed per-window handler set, a sorted array + binary search is
  >>> VERDICT: cache-tiny and competitive; a compile-time perfect hash is possible when the type set is closed.
  >>> VERDICT: Closure storage: 3-word inline union (fn ptr + <=2 words captures); capture-free producers are
  >>> VERDICT: size_of==0 and inline; oversized captures spill to a counted pooled box.
